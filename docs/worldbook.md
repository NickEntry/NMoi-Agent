## 写世界书的配方

这一节不是设计稿，是**怎么用**。前面几节讲我们为什么这么实现，这一节讲你手上那一条该怎么填。

### 12.1 一条条目由什么决定

| 字段 | 它决定什么 | 拿不准时 |
|---|---|---|
| 名字 | 只在列表里显示；**唯一例外**是 `tool_call_` 开头（见 12.3） | 随便写，能认出来就行 |
| 关键词 | 什么时候激活。命中最近 `scan_depth` 条消息里的任意一个 | 写 2–5 个同义说法，别写整句 |
| 常驻 | 勾上就不看关键词，永远在 | 人设、格式约定这类"每一轮都要"的 |
| 位置 | 插到哪：系统提示前后 / 历史里第 N 条之前 | 设定走系统前，示范走历史里 |
| 角色 | 注入成 user 还是 system | 规范用 system，示例对话用 user |
| 优先级 | 同位置内的先后，小的在前 | 默认 0，要压过别人就写 -1 |
| 粘性 / 冷却 / 延迟 | 命中后多带几条 / 多久内不再触发 / 会话多长才启用 | 先不填 |
| 整词 / 大小写 / 正则 | 匹配方式 | 中文别开整词（没有词边界） |

### 12.2 三条最容易踩的

1. **关键词写成了句子**。`今天天气怎么样` 只有原句才会命中；换个人问法就失效。写 `天气`、`下雨`、`气温`。
2. **一条里塞了三件事**。一条只讲一件事，关键词才对得准；否则一命中就把三段不相干的设定一起塞进去。
3. **指望它"按顺序读"**。注入是按位置 + 优先级排的，不是按你在列表里看到的顺序。要固定先后，用优先级。

### 12.3 `tool_call_<工具名>`：改工具说明

名字以 `tool_call_` 开头的条目**不进上下文**，它改的是请求体里 `tools` 那一条定义。

- **只对存在的工具有效**：`tool_call_read_file` 在没声明 `read_file` 的那一轮什么也不做。
  MCP 工具同样适用（名字照抄 `mcp__服务器__工具`）。
- **正文是纯文本** → 只换 `description`。这是最常用的一种：

  ```text
  名字：tool_call_get_time_info
  正文：先看手机时间再回答"几点"，不要凭上下文猜。
  ```

- **正文是 JSON** → 可以连 schema 一起换（少写哪个就不换哪个）：

  ```json
  {
    "description": "按指定时区查时间",
    "parameters": {
      "type": "object",
      "properties": { "tz": { "type": "string", "description": "例如 Asia/Shanghai" } },
      "required": ["tz"]
    }
  }
  ```

  `parameters` 必须是对象。写坏了整条不生效（不会把坏 schema 发出去），工具按默认那份继续用。
- **正文留空 = 用应用自带的那一份**。所以"恢复默认"就是把正文清掉，不需要记住原文。
- **同一个工具写了多条，只有第一条生效**。别用几条拼一段——拼不了，后面几条会被忽略。
- **写完怎么确认**：问模型"你现在这个工具是怎么描述的"。它读到的是覆写后的那一句；
  读不到就是你名字拼错了（大小写、下划线都要对上）。

### 12.4 一个能抄的骨架

```text
角色设定（system，常驻，优先级 0）
  └ 你叫 Neko，说话简短，先给结论。

格式约定（system，常驻，优先级 -1）       ← 排在角色设定之前
  └ 回答里的路径一律写成 `a/b.md`。

领域知识（关键词 3–5 个，scan_depth 4）
  └ 关键词：天气 / 气温 / 下雨
  └ 正文：查天气要用 get_time_info 先确认日期，再查预报。

工具说明（名字 tool_call_get_time_info）
  └ 正文：先看手机时间再回答，不要猜。
```
