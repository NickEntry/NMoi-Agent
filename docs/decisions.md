## D10 依赖版本锁死 + 提交 Cargo.lock

**理由**：本机工具链是 rustc 1.75（无 rustup，无法换版本），CI 上是 stable。
若用 caret 版本，本地与 CI 会解析出不同版本，出现"本地能过 CI 不能过"。
所以所有第三方依赖写 `=X.Y.Z`，workspace 的 `rust-version = 1.75`，并提交 `Cargo.lock`。

**代价**：升级要手改版本号；换来的是可复现。

## D11 三种"保护"标记是正交的

| 标记 | 谁设置 | 挡住什么 | 不挡什么 |
|---|---|---|---|
| `protected` | 系统（失败 / 错误 / 异常 / 用户说"记住"） | 一切压缩 | — |
| `pinned` | 用户或策略 | 重排 | 编辑、压缩 |
| `locked` | **用户** | **内容编辑、重排**（正文 / 思考 / 工具块；位置） | **压缩、丢弃、回灌** |

**为什么这么切**：用户原话是"锁定后无法通过编辑工具去编辑，但依旧可以被压缩工具压缩"。
三者混成一个布尔会立刻产生矛盾：`protected` 必须禁止压缩，而 `locked` 必须允许压缩。

**Q7 已拍板（2026-10-21）：`locked` 也锁位置。** 用户手动锁一条消息，意思就是"这段别动"——
既别改字，也别挪位置。`pinned` 留给模型/策略自动标（它不挡编辑），两个标记的差别落在
"谁设的、挡不挡编辑"，而不是"挡不挡重排"。实现上：任何重排逻辑先问 `pinned || locked`。

## D12 上下文分界线 = 窗口切分，压缩 = 归档 + 画线

- 线是 `dividers` 表里的一行，用 `after_seq` 定位，`kind ∈ {user, compression}`。
- **线只能落在原子单元边界**：切开 tool_call / tool_result 会产生非法消息序列（设计文档 §4.2）。
- 线之下才是当前窗口；线之上仍然保留在库里，可回灌（追加到尾部）、可删线还原。
- 压缩工具的默认动作从"就地改写消息"变成"归档线上内容 + 画一条线 + 把压缩结果作为新消息放线下"。
  **理由**：就地改写的收益是省 token，代价是缓存从变更点全破；画线同样是"变更点靠后"，但语义清晰得多，且删线即还原。

**一个反直觉点**：删线会让窗口变长、缓存全冷——这是用户主动操作的确定代价，不做优化。

## D13 块级编辑要留审计，不能只改字符串

每次编辑写一条 `edits` 记录：`unit_id / message_id / block / before_hash / after_hash / tokens_before / tokens_after / revision`。

**理由**：undo、同步冲突判断、"当时为什么变了"的诊断都依赖它。只改行不留痕，事后无法判定是用户改的还是模型改的。

## D14 工作区读取：三级截断 + `force_full` 最高优先级

| 限制 | 默认值 | 超限行为 |
|---|---|---|
| 行数 | 2000 行 | 截断并返回剩余行数 + `start_line` 提示 |
| 单行字节 | 4 KiB | 该行保留头部 + 标注原始字节数，记入 `long_lines` |
| 总字节 | 256 KiB | 截断并返回剩余字节 |
| 文件总大小 | 64 MiB | 拒绝（非 `force_full` 时） |

**超长单行的处理理由**：压缩过的 JS / 单行 JSON 常见几十万字节。
静默丢弃会让人以为"文件就这么短"；整行塞进去会把上下文一次打爆。
所以取"保留头部 + 明确标注 + 结构化上报"，调用方可以选择跳读或全量读。

**`force_full` 压过一切**（含二进制与大小上限），这是用户明确要的逃生口；
代价由调用方承担，所以 UI 上要二次确认并显示字节数（Q10）。

## D15 许可策略：GPL-3.0-only

| 对象 | 许可 | 说明 |
|---|---|---|
| 本项目 | **GPL-3.0-only** | 原为 MIT；因要捆绑 GPL 组件，整体切到 GPL-3.0 |
| 运行时依赖 | MIT / Apache-2.0 | rusqlite、regex、serde、uuid、sha2、thiserror、tempfile，均为宽松许可 |
| 容器方案 | PRoot `GPL-2.0-or-later`、proot-distro `GPL-3.0-only` | 在 APK 里分发这些二进制 → 分发包必须满足 GPL |
| 参考 kelivo | **AGPL-3.0-only** | 只参考 UI 与交互设计，不复制代码；AGPL 代码不能并入 GPL 项目 |

**为什么切**：容器是可选项，但它要分发 PRoot（GPL-2.0-or-later）。GPLv2-or-later 可以升到 GPLv3，
所以整体取 GPL-3.0-only 是最省事、也最不容易出错的选择——不必逐文件论证"这是聚合还是衍生"。
本项目不计划商用，GPL 不构成现实限制。

**红线不变**：kelivo 是 AGPL-3.0，**任何代码片段都不能抄**（AGPL 与 GPL 不兼容）。
只能读它的公开文档与行为，自己实现。

## D16 测试策略

- 本地做 `cargo check --workspace --all-targets`（语法 / 类型），**加上短测试**（口径见 D16.1）。
- 测试在 CI 跑（Codeberg runner 或 GitHub Actions，取决于可用性）。
- Provider 集成测试 **opt-in**：只有显式设置 `NMOI_LLM_BASE` 时才跑，默认 skip（CI 上 127.0.0.1 不存在）。
- **`test*` 前缀的模型别名不得自动使用**，需要用户单独授权。

### D16.1 什么算"短"（2026-10-20 修订，按实测数字）

用户口径：**本地不跑完整测试，但可以跑用时短的小测试**（设备性能堪忧）。
设备是手机上的 PRoot（aarch64），实测下来贵的是**编译**，不是运行：

| 动作 | wall |
|---|---|
| 首次编译 core 的测试二进制（一次性） | 15s |
| 改一个 core 源文件 → 增量重建 → 跑一个模块 | **21s** |
| core 单模块（10–24 项） | 2–3s |
| 整个 `-p nmoi-core --lib`（238 项） | **3s**（测试本体 0.58s） |
| `-p nmoi-storage` 首次（bundled SQLite 要编 C） | 62s；之后 1s 级 |

由此定下的做法：

- **本地可以跑**：本次改动那个 crate 的 `--lib` 过滤测试，单次（含增量编译）控制在 **≤ 60s**。
  写新测试的轮次，跑自己那几个模块就够（`cargo test -q -p nmoi-core --lib -- runtime::`）。
- **本地该跑**：新测试**推之前先在本机跑一次**。这一条是拿真金白银换来的——
  2026-10-20 那轮 45 项新测试一次没跑就推了，CI 首轮暴露两个真 bug
  （IPv6 的 Host 头漏方括号、请求头校验排在建连接之后），多烧一轮 CI。
- **留给 CI**：`--workspace --all-targets`（跨 crate + 集成测试）、首次 bundled SQLite 编译、
  任何需要外网的。这些不是"更重要"，是"更贵"，放在 CI 上跑一次就够。
- 拿不准就先跑，**超过约 60s 就停手**改成 CI 见。别为了省 3 分钟烧 10 分钟。

## D17 五类模型角色统一抽象

`ModelRole { TitleSummary, Compression, Translation, Vision, ChatSuggestion }`，
每个角色独立配 provider+model、思考开关、思考强度、提示词 / 世界书、禁用开关、"使用当前聊天模型"。

**关键约束**：这些请求单独计量与计费，不进会话上下文预算；失败静默降级，不影响主对话。
**理由**：否则一次"标题总结"失败会把正常对话带崩，或者悄悄吃掉窗口预算。

## D18 思考字段类型 + body 合并优先级

思考字段族：`openai_effort` / `responses_reasoning` / `anthropic_thinking` / `gemini_thinking_config` / `none` / `custom`。
新增模型时按 **provider 类型**给出默认字段类型，用户可覆盖。

body 合并顺序（后者覆盖前者）：

```text
软件默认值 → provider 自定义 → model 自定义 → body 屏蔽（删除指定 key/value）
```

**理由**：屏蔽必须最后执行，否则前面刚设的值又会被"屏蔽"逻辑漏掉。

## D19 模型名用正则匹配 + 家族最新版本兜底

归一化：`.` 与 `-` 视为等价分隔符，剥离 `[分组x]` 前缀，大小写不敏感。
例：`claude-opus-5.5`、`Claude-Opus-5-5`、`opus5.5`、`[分组A]opus5-5` 都归一到同一家族；
命中家族但版本缺失时按该家族**最新版本**处理（需要一张家族版本序列表，不能靠字符串比较）。

**必须**在 UI 上显示"这些参数来自规则 X，可手动覆盖"——正则填的默认值不能装作是事实。

## D20 推理回放三态，默认按 provider

`auto` / `always` / `never`。判断依据是 provider 的协议要求，不是偏好。

- 本项目的本地端点实测：思考内容可丢弃 / 原样回传 / 篡改，三种都 200 且答案一致，**无签名约束** → 回放是客户端策略。
- 该端点因此默认 `never`：省 token，并且切断"退化传染"（设计文档 §3.4.1.1）。
- 若某 provider 要求回传（带签名才能续接工具调用），则该 provider 下思考内容**不允许删除**，压缩只能归档。

## D21 强制续接 = 能力位 + 降级路径

- `supports_assistant_prefill = true`：以 assistant 消息结尾，让模型续写（真 prefill）。
- 不支持：追加一条最简续接指令，不重复已输出内容。
- 两种都是**追加**，不破坏前缀缓存。
- 被中断的 assistant 消息标 `incomplete`，UI 的"继续"与"重试"是两个不同动作。

## D22 视觉替换：图片不进聊天模型

开启后，图片先送视觉模型，结果（文字描述）作为 `SourceTag::VisionBridge` 追加进上下文，原图进归档并保留 ref。

**代价要写在 UI 上**：描述会丢细节，聊天模型看不到原图；这是用户显式选择的降级。

## D23 世界书格式对齐 kelivo

`{version:1, type:"lorebook", data:{..., entries:[...]}}`，条目字段：
`id / name / enabled / priority / position / injectDepth / role / content / keywords / useRegex / caseSensitive / scanDepth / constantActive`。
`position ∈ {BEFORE_SYSTEM_PROMPT, AFTER_SYSTEM_PROMPT, TOP_OF_CHAT, BOTTOM_OF_CHAT, AT_DEPTH}`。
对齐格式的原因是用户已有现成世界书文件要能直接导入（工作区有示例）。

## D24 FFI 先手写 C ABI

stage 0 只用 `extern "C"` + `catch_unwind`，把"panic 不跨 FFI"这条硬约束锁死在第一天。
UniFFI（Kotlin / C#）留到 stage 2 接口稳定后再加；手写 C ABI 同时也是 R1 的永久退路。

## D25 工作区不依赖容器

文件读写 / 查找 / 搜索 / 编辑独立实现，Android 上先跑通这些；
容器（PRoot / chroot）是**可选增强**，只影响 bash 与沙箱内工具是否可用。
选型、许可影响与实现步骤见 `docs/sandbox.md`。

## D26 bundled SQLite 默认开启外键

`rusqlite` 的 `bundled` 功能在编译 libsqlite3 时给了 `SQLITE_DEFAULT_FOREIGN_KEYS=1`，
所以 `ON DELETE CASCADE` 是**默认生效**的（这一点在 CI 上被一条测试抓到：用"删会话留下消息"造孤儿，
结果消息被级联删掉了）。

`storage::configure()` 仍然显式 `PRAGMA foreign_keys = ON`：系统 SQLite（Android 自带）不一定开，
不能依赖编译期默认值。同时新增测试把"默认开启"这个前提钉住，夹具改用"关外键后插孤儿"来还原真实损坏形态。

## D27 引擎 `snapshot` 用 `&mut self`（偏离计划 §3.2 草案）

计划文档写的是 `fn snapshot(&self)`。实现里快照登记表在引擎内部，只读签名做不到。
改为 `&mut self`；调用方本来就独占 engine，不影响 UI 侧代码形状。

## D28 密钥隔离：目标不是"藏"，是"容器里没有可长期滥用的凭据"

前提写死：**PRoot 不是安全边界**（同 UID、ptrace、共享文件系统视图；loopback TCP 全设备可见）。
Android Keystore 的密钥不可导出，但同 UID 的代码可以让 App 自己解密，所以"密钥本身难提取"不等于"密钥安全"。

因此分五层（详见 `docs/secrets.md`）：

1. 密钥只以密文存在（Keystore / StrongBox 优先，TEE 回落）；
2. **凭据代理（broker）是唯一持有者**，通过 App 私有目录下的 Unix domain socket 交付（不用 abstract namespace，它没有任何权限控制）；
3. 容器侧零放置：不 bind 私有目录、密钥不走 env/argv、配置里只写占位符；
4. 蜜罐诱饵：把"如果这里有密钥就会被偷"变成可观测事件；
5. 硬边界只有 VM（AVF）：需要"容器碰不到 App 任何文件"时，PRoot 做不到。

## D29 容器里的 git / gh：凭据代理交付，而不是把令牌放进去

三条交付方式，可叠加：

| 方式 | 容器里出现真实令牌 | 覆盖 | 成本 | 定位 |
|---|---|---|---|---|---|
| **B. 透明 TLS 代理** | 不会 | git / gh / curl / 任意 HTTP | 中（rootfs 装 CA） | **Android 默认** |
| A. git credential helper | 会（仅进程内存，不落盘） | git | 低 | **Android 兜底**（绕不过代理的工具） |
| C. SSH agent 转发 | 不会（只给签名） | git over SSH | 中 | 可选 |

证书信任尾是 B 的唯一真坑（Python/Node/rustls 系要额外喂 CA 或环境变量），
所以 A 必须留着兜底。

约束：

- 默认只挂我们的 helper，**不挂 `store`/`cache`**，保证 `.git-credentials` 永不出现；
- 平台差异：GitHub 用 fine-grained PAT（可按仓库+权限+到期收窄）；Codeberg 的 token 基本是账号级，
  靠 broker 的审计与一键吊销补偿；
- 白名单域名固定写在策略里（GitHub 含 codeload / raw / objects 等，Codeberg 两个）；
- 每次交付写审计（host / 用途 / TTL / 允许或拒绝），令牌只记指纹不记明文。


## D30 平台策略：密钥保护各用系统原语，只有 Android 自研代理

| | Android | Linux 无桌面 | Windows |
|---|---|---|---|
| 静态保护 | Keystore | systemd-creds（TPM2/host key） | DPAPI |
| 容器 | PRoot（弱边界） | rootless podman / nspawn / bwrap（真边界） | 不做 |
| 原生命令 | 无 | 可选，默认关 | 可选，默认关 |
| 凭据代理 | **需要** | 不需要 | 不需要 |

**理由**：PRoot 是伪 chroot + 共享文件系统视图，容器与 App 同 UID，所以只能靠代理把令牌挡在外面；
Linux 的 mount namespace 是真边界，只要我们的启动器控制挂载列表、不把 podman socket 交出去，
密钥目录本来就不可见——再加代理只是多一个攻击面。

**不自研密码学**：三平台都用系统提供的"不可导出密钥"设施，我们只做加解密的调用方与策略层。

## D31 两层门：可选增强全平台默认关 + 助手绑工作区才可用

用户策略，落成 `core::policy`（可测试，不是文档约定）：

1. **绑定门**：没绑工作区 → 文件读写、目录/查找/搜索、容器命令、原生命令**一律不可用**（连只读都不给）。
2. **开关门**：绑了工作区也不自动拥有能力；容器 / 原生命令 / 网络 / 凭据代理各自默认关。

关键实现约束：

- 判定顺序**先绑定、后开关**。否则"开关开了但没绑工作区"会被写错的判断放过去（有测试钉住这条）。
- 工作区绑定默认**只读**，写与编辑要单独开。
- 容器要联网 = 容器开关 **且** 网络开关，两个都开才算。
- 拒绝必须给原因（`no_workspace` / `read_only_workspace` / `feature_disabled`）并附一句人话，
  UI 不能只把按钮灰掉让人猜。

这样"最坏情况"永远发生在用户显式打开之后，而不是默认就暴露。

## D32 技能系统：开关只是"提示存在"

按用户要求定死四条：

1. **自动发现** `SKILL.md`（大小写不敏感，`skill.md` 也认），扫描深度 2
   （`skills/<name>/SKILL.md` 与 `skills/<category>/<name>/SKILL.md` 都能找到）。
2. **开关只决定"要不要告诉模型有这么个技能"**：插进上下文的只有 `name` + `description`
   （描述默认截到 160 字符），正文不进上下文。模型需要时自己读全文。
3. **读取工具覆盖 skills**：技能根直接用 `Workspace` 打开，因此目录、查找、搜索、
   三级截断、`force_full` 全部复用同一套规则，不另造一套读法。
4. **容器开启时映射到 `/skills`（只读）**：路径稳定，技能正文里的相对引用不用改写。
   映射只在容器能力被打开时生效（见 D31）。

元数据缺 `name` / `description` 时用"目录名 + 首个标题 + 首段"兜底，并标 `inferred = true`，
UI 上要能看出这是猜的。

## D33 provider / model 层的两条硬顺序

1. **body 合并**：软件默认 → provider 自定义 → model 自定义 → **屏蔽最后执行**。
   屏蔽必须最后，否则刚设的值会被漏掉；数组整体替换不拼接（避免"越并越长"）。
2. **模型名解析**：剥 `[分组]` 前缀 → 统一分隔符 → 切尾部版本 → 精确别名 → 家族+版本 →
   家族最新 → 家族模糊（最长包含）→ 未知默认。

每一步都返回 `MatchSource`，且 `FamilyFuzzy` / `Unknown` 标记 `needs_review()`：
UI 必须显示"参数是猜的、可手动覆盖"。正则填出来的默认值不能装作事实。

## D34 模型元数据来自公开快照，只存事实字段

三个源分工（详见 `docs/model-data.md`）：models.dev（MIT）作主结构，
OpenRouter 与 aihubmix 的公开 API 补能力位与覆盖。

三条硬规定：

1. **只取事实**：上下文长度、输出上限、模态、能力布尔、价格数字。
   不复制描述文本 / 基准分数 / 链接——那些有表达性，而我们需要的是事实。
2. **快照是可选依赖**：运行时不联网，缺这份文件就退化为正则 + 保守默认，功能不塌。
3. **归一化规则两边必须一致**：脚本与 `core::model` 用同一套规则，
   Rust 侧有测试直接读快照并解析知名模型，规则漂移会立刻暴露。

另外把 `reasoning`（模型是否支持思考，模型事实）与 `thinking.field`（用哪个字段族，provider 事实）
拆开了：快照只存前者，后者在 `resolve()` 时按 provider 类型补上，用户仍可覆盖。
未知模型不再猜它能思考——注错字段可能直接 400。

## D35 逐参数覆盖：默认 / 已修改，改过的不跟随

`core::config` 把用户要求落成可测试的机制：

| 行为 | 语义 |
|---|---|
| 手动设值 | 与当前默认**相同**就不留标记；不同才标 `已修改`（所以"改回默认"会自然丢标记） |
| 自动跟随 | 只有 `默认` 状态的字段跟着新默认走；`已修改` 的一个字都不动 |
| 恢复按钮 | 值回默认 + 标记回 `默认`；另有"全部恢复" |

两个策略函数：

1. **思考字段族的默认**（`default_thinking_field`）：
   Claude 模型 → Anthropic 族，Gemini 模型 → Gemini 族，**无论挂在哪个供应商后面**；
   其余看 provider 类型——OpenAI 兼容用 `reasoning_effort`，开了 Responses 用 `reasoning.effort`。
   切换 provider 时只影响 `默认` 状态的字段。
2. **思考强度**（`ThinkingChoice { Off, Auto, Level }`）：
   - 滑块顺序：关闭在最左，紧随"自动"，然后从低到高；
   - **每个模型独立记忆，默认一律 `Auto`**（不指定，用 provider 默认档）；
   - "关闭"要诚实：元数据里有 `none` 才真关（`reasoning_effort: "none"`），
     没有就退化为"不注字段"并置 `off_is_best_effort`，UI 必须说明"这个模型关不掉思考"。

**档位数据来自元数据，且厂商自身数据优先**：跨 provider 求并集会把 DeepSeek 的
`low/high/max` 撑成 `none…max`，等于没有约束。所以脚本里加了 native 判定
（provider=deepseek 且 family 以 deepseek 开头 → 厂商数据），先到先锁。

排期：core 已实现（本条）；UI 在 P6 的设置页一起做；provider 切换时的字段族跟随已在 P2 具备。

另：Anthropic 的 `budget_tokens` 在 Claude 4.7+/5 上已被移除，新档位走 `output_config.effort`，
所以新增 `ThinkingField::AnthropicEffort`，旧的 `AnthropicThinking` 保留给 3.7–4.5。

## D36 世界书：格式对齐 kelivo，激活与注入都是确定性的

- 文件形态与 kelivo 导出完全一致（`version`/`type`/`data.entries`，字段用 `injectDepth`、
  `useRegex`、`caseSensitive`、`scanDepth`、`constantActive`，枚举用大写蛇形），
  用户现成的文件可以直接导入；仓库里放了示例做测试夹具（`data/lorebook.example.json`）。
- **激活是确定性的**：常驻激活 → 无条件；否则在最近 `scanDepth` 条消息里做关键词匹配
  （可正则、可区分大小写）。没有任何模型参与，所以"这条为什么进来"事后能复盘。
- **注入是新增消息，不是改写已有消息**：天然追加、不破坏缓存前缀；
  位置只决定插在哪一段（system 前 → system 后 → 对话顶 → 指定深度 → 对话底）。
- **坏正则不能带崩整本**：编译失败只让该条目不生效（有测试）。
- 同位置内按 `priority` 升序、再按条目 id 排——顺序确定，重放结果一致。

## D37 思考强度滑块：关闭与自动永远在，且关闭必须显式

用户口径 + 我补的一条限定：

| 档位 | 线上行为 |
|---|---|
| **关闭** | **必须显式**：发 `reasoning_effort: "none"`。早期版本在"档位里没有 none"时改成不注字段——那其实退化成了自动（线上请求一模一样），用户以为关了其实没关 |
| **自动**（默认） | 什么都不发，用 provider / 模型自己的默认档 |
| 具体档位 | 发对应值；只列模型元数据里支持的档位 |

补充限定（与用户说法的一点差异）：**"OpenAI 兼容 v1 的原始 `thinking` 字段算弃用"只对这一支成立**。
Anthropic 原生的 `thinking: {type: disabled}`（旧版预算式 3.7–4.5）与 Gemini 的 `thinkingConfig`
都是**现役**字段，不能一起当成弃用——所以 `ThinkingChoice::Off` 对 Anthropic 预算式字段走
`type: disabled`，对其余字段族走显式 `none`。

`ThinkingChoice::slider(supported)` 保证滑块最少是 `[关闭, 自动]` 两格；`none` 不重复出现在档位里。

## D38 传输层：core 只定接口，明文 HTTP 自己写，TLS 交给平台侧

**背景**：P2 要发真实 HTTP 请求，就得有个 HTTP 客户端。试过引入 `ureq`（3.2.1，MSRV 1.71.1，
本机 rustc 1.75 满足），**解析依赖树直接失败**：

```
failed to parse manifest at `.../zeroize-1.9.1/Cargo.toml`
Caused by: feature `edition2024` is required
  The package requires the Cargo feature called `edition2024`,
  but that feature is not stabilized in this version of Cargo (1.75.0).
```

原因是 cargo 1.75 解析依赖时**不看 `rust-version`**，只会挑最新版本；最新的 `zeroize` 用了
edition2024，于是本地连 `cargo check` 都做不了（D10 的"锁死版本"只锁得住已有依赖，
锁不住新引入的依赖树）。要绕过去有两条路：手动把一棵树里的每个包都降级到能解析（补丁套补丁，
每加一个依赖都要重来一遍），或者升 MSRV + 装新工具链（本机没有 rustup）。

**决定**：

- `core` 只定 `Transport` trait（`execute(HttpRequest) -> HttpResponse`），不绑任何 HTTP 库。
- 自带 `PlainHttpTransport`：std 手写的 HTTP/1.1，**只支持 `http://`**（本机 llama.cpp / ollama /
  本机代理这条路）。分块 / 定长 / 关闭定界三种响应体帧格式都实现了。
- 遇到 `https://` **明确报 `Unsupported`**，不静默降级、不假装成功——错误信息里直接指向本决策。
- TLS 将来落在平台侧原生栈（Android OkHttp / Windows WinHTTP / Linux 自定义），
  或升级工具链之后把 `ureq` 实现为一个 `Transport`。两者都能接，因为接口已经隔开了。

**代价（明说）**：云端端点现在还连不上。这是本轮唯一的功能缺口，不是设计取舍的胜利。

**待你拍板**：要不要为了 TLS 升 MSRV（连带 CI 的 MSRV job 一起动）。不升也行，但要接受
"云端 provider 要等平台侧传输"这个顺序。

## D39 usage 口径归一：`prompt_tokens` 一律表示全量输入

四家的 `prompt_tokens` 口径不一样，混用会把缓存命中率和预算都算错：

| 端口 | 上游给的 | 归一成 |
|---|---|---|
| OpenAI 兼容 | `prompt_tokens` 含缓存 | 原样；`cached = prompt_tokens_details.cached_tokens`（兼容 Anthropic 命名的 `cache_read_input_tokens`） |
| Anthropic | `input_tokens` **不含**缓存 | `input + cache_read + cache_creation`；`cached = cache_read_input_tokens` |
| Responses | `input_tokens` 含缓存 | 原样；`cached = input_tokens_details.cached_tokens` |
| Gemini | `promptTokenCount` 含缓存 | 原样；`cached = cachedContentTokenCount` |

- 归一后 `prompt_tokens` 表示"这次请求实际吃掉的输入"，可以直接和本地估算、窗口预算比。
- 缓存命中率只能拿归一后的值算（`Usage::cache_hit_ratio()`）。
- **思考 token 在 Anthropic 没有单独字段**（算在 `output_tokens` 里）→ 归一为 0，
  不要用 0 去推"没思考"。
- 流式 usage **可能压根没有**（实测 `relay-c/deepseek-flash` 怎么要都不给）→
  上层必须允许"没有 Usage 事件"，用本地估算兜底。

## D40 流式优先，缺的能力一律显式报错

- **本轮只做流式**。`stream: false` 报 `Unsupported`，不假装支持。
- **表示不了的消息一律报错，不静默丢**：工具调用 / 工具结果 / 归档指针消息都会返回
  `Unsupported` 并说明原因。静默丢一个工具块，等于把一轮工具循环悄悄改写成另一种对话——
  这种错误事后没法从记录里看出来。
- **断流不能当成正常结束**：没见到终止事件就 EOF 的流，补一条 `Interrupted` 事件，
  上层据此把消息标 `incomplete`（D21）。空回复则照旧走 `abort_turn`，不落库。
- **空 `messages` 前置拒绝**：实测上游对空 messages 回的是
  `HTTP 400 / upstream_rejected`，信息量为零；与其等它，不如在本地就说清楚。
- **超窗只能给线索，不能当判据**：`OverflowHint` 分 `Likely` / `Unreliable` 两档，
  而且三种不同的溢出失败里只有一种措辞提到了上下文（`docs/provider-runtime.md` §1.4 引用）。
  真正的兜底仍然是客户端自己维护预算。
- **密钥不进 Debug**：`ApiKey` 的 `Debug`/`Display` 都打码，`ChatRequest` 的 `Debug` 只印头部
  名字不印值（`ProviderConfig.extra_headers` 里很容易混进密钥）。

## D41 非流式与工具：同一套字段知识，两条出口

**非流式不是"另一种协议"，是同一批字段的另一种排布。**

- 流式出口：[`StreamEvent`]（边到边显示）；非流式出口：`Completion`（整段拿走）。
- 解析都放在 `core::stream`，字段来源与流式共用一份（`docs/provider-runtime.md`）。
- 模式由**方法**决定，不由字段暗地里决定：`chat()` 只吃 `stream: true`，
  `complete()` 只吃 `stream: false`，给错了明确报错。半路改主意就必须显式换方法。
- 非流式响应体有 **8 MiB 上限**（流式那条路没有）：整段解析本来就得先收完，
  而"上游吐了 10 GB"不该把客户端拖死。

**工具消息（历史里的 tool_calls / tool_result）四端口映射**：

| | 助手发起的调用 | 工具结果 |
|---|---|---|
| OpenAI 兼容 | `message.tool_calls[]`，`arguments` 是**字符串** | `role: "tool"` + `tool_call_id` |
| Responses | 顶层 `{"type":"function_call","call_id",...}` **item** | 顶层 `{"type":"function_call_output","call_id"}` item |
| Anthropic | `content` 里的 `tool_use` 块，`input` 是**对象** | **user 轮**里的 `tool_result` 块（`tool_use_id`） |
| Gemini | `parts[].functionCall`，`args` 是对象 | `parts[].functionResponse`，**只认函数名、不认 id** |

由此得到三条实现上的硬要求：

1. **`tool_call_id` 不能缺**：缺了就没法把结果对回调用，`build_body` 直接拒绝，不猜。
2. **Gemini 要自己把 id 翻成函数名**：它的 `functionResponse` 没有 id 字段。
   我们从历史里的 `tool_calls` 建 id→name 表；查不到就报错，不硬编个名字。
3. **`functionResponse.response` 必须是对象**：工具结果是纯文本时包一层
   `{"result": ...}`；是 JSON 对象就原样用。

**工具声明**：OpenAI 兼容 / Responses / Anthropic 三支按各家形状装好；
**Gemini 未做**——它要 OpenAPI 子集（`type` 大写、不支持 `$ref`/`oneOf`），
静默改写 schema 会让模型按错的形状出参数，所以宁可报 `Unsupported`。

**已知不确定项（未实测）**：

- Gemini 的 `functionResponse` 放在 `role: "user"` 还是 `"function"` 下，
  文档里两种写法都出现过（生成式语言 API 示例用 `function`，Vertex REST 示例用 `user`）。
  我们走 `user`（与 Vertex REST 的 `Content.role` 枚举一致），**没有真机验证**。
  若某天 Gemini 回 `400 INVALID_ARGUMENT`，先怀疑这一处。
- Responses 端口**没有** `stop` 参数：给了也发不出去（同名字段不存在），
  文档里记为未做项，不假装支持。
- 非流式的 `model` 字段可能回的是**别名**而不是上游真名（实测：同一次请求，
  流式回 `DeepSeek-V4.1-Flash`，非流式回 `relay-b/DeepSeek-V4.1-Flash`）。
  要用真名就认流式的 `Meta`，不要拿非流式的 `model` 做计费归因。

## D42 五类角色：能降级、单独记账、门控要说人话

**配置形状**：`RoleConfig { role, enabled, follow_chat, provider, model, thinking, max_tokens,
temperature, prompt }`。「跟随当前聊天模型」与「自己指定 provider+model」是互斥的两条路，
`follow_chat` 为真时后者忽略——界面也不会让你同时填。

默认值按 `docs/PLAN.md` §3.3 的表：

| 角色 | 默认开 | 跟随当前模型 | 思考默认 | max_tokens |
|---|---|---|---|---|
| 标题总结 | 是 | 是 | **显式关** | 1024 |
| 压缩 | 是 | 是（plan 要求同等能力） | 自动 | 8192 |
| 翻译 | 是 | 是 | **显式关** | 4096 |
| 视觉 | 否 | **否**（必须显式指定） | 显式关 | 1024 |
| 聊天建议 | 否（每轮都跑，默认省） | 是 | 显式关 | 1024 |

思考用 `ThinkingChoice` 复用 D37：`Off` 一定显式发 `none`，不发"什么都不注"。
字段族在发请求时才按 provider + 模型族决定——配置层不该知道 `reasoning_effort` 这个词。

**失败语义只有三态，永远不 `Err`**：

- `Ok(Completion)`：拿到了正文（空正文也算失败，见下）
- `Skipped(原因)`：没发请求（禁用 / 配置不全 / 视觉得指定模型），或发了但拿不到能用的东西
- `Failed(原因)`：真的出错（网络、上游拒绝）

**空正文 = 跳过，不是失败。** 实测（见下）这个端点上"关思考"根本不生效，
`max_tokens` 给小了就是"思考吃完、正文为空"。那时标题该保留原值——不是弹一个红字给用户。
`Skipped` 与 `Failed` 分开，界面才能决定"静默"还是"记日志"。

**单独记账**：`RoleMeter` 是独立账本，**不进 `Budget`**。把标题/翻译的开销并进会话预算，
会让上下文提前触发压缩——一个很难复现也难解释的 bug。

**视觉门控**：没指定模型 → `usable = false` + 人话原因（"没指定模型…"）。
这一条就是 plan 里"未指定则功能置灰"的实现。**图片通道没做**（P3.1）：
需要 `SourceTag::VisionBridge`（D22 要求、但枚举里还没有这个变体）、四种端口的图片内容块、
工作区的二进制读、尺寸与格式限制。现在视觉角色只有门控和请求形状，发不出图。

### 实测（2026-10-20，`relay-b/DeepSeek-V4.1-Flash`）

```bash
NMOI_SMOKE_MODE=title NMOI_SMOKE_MODEL="relay-b/DeepSeek-V4.1-Flash" cargo run -p nmoi-core --example provider_smoke
```

```
[role] 标题总结 ok（12 字）
[raw]   "SSE 流式解析空行规则"
[title] "SSE 流式解析空行规则"
[usage] prompt=106 completion=131 reasoning=121
[meter] 独立账本 1 条，合计 237 token（不进会话预算）
```

两点值得记住：

1. 模型这次很乖，直接吐了干净标题（没有 `标题：` 前缀）。清洗函数还是留着——
   它便宜，而且模型不乖的那天不需要改调用方。
2. **`reasoning=121 / completion=131`**：我们明明发了 `reasoning_effort: "none"`，
   它照样思考了 121 个 token。这验证了实验报告 §1.6 的"三个别名全部失去关闭思考的能力"。
   所以标题角色的 `max_tokens` 默认给 **1024** 而不是 64：给 64 的话，正文一个 token 都剩不下。
   "关思考"是尽力而为（`off_is_best_effort`），不是保证。

## D43 断流标记：`incomplete` 落在消息上，不只落在事件里

D21 早就定了"被中断的消息标 incomplete"，但一直只有 `StreamEvent::Interrupted` 事件，
没有字段——**事件一过就没了**。结果是：断流的回复和正常回复在库里长得一模一样，
事后谁也看不出它少了半句。这一条把数据侧补上。

- `Message.incomplete: bool`，`#[serde(default)]`：没有这个字段的旧 JSON 照样能读
  （导入、跨设备同步都会碰到）。
- 引擎两个出口：`finish_turn`（完整）与 `finish_turn_incomplete`（断流/被停止），
  后者等价于 `finish_turn_with(usage, true)`。
- 与 `abort_turn` 的分工不变：**一个 token 都没产出**用 `abort_turn`（整轮丢弃，不落库）；
  **已经吐了半句话**用 `finish_turn_incomplete`（留在历史里，但标清楚）。
- `Event::TurnCompleted` 带 `incomplete`：实时订阅的界面不用等下次载入才知道。
  光有字段不够——UI 正在等这一轮结束的消息，事件里没有它就是没告诉它。

**schema v2**：`ALTER TABLE messages ADD COLUMN incomplete INTEGER NOT NULL DEFAULT 0`。

- 只加列、不重建表：`ALTER TABLE ADD COLUMN` 是常数时间，老行的默认值 0 正好是"完整"，
  不需要回填，也就不需要一段"回填到一半失败"的恢复逻辑。
- 迁移测试钉住两件事：升版后**行数不变**，老行的新列是 0。
- 存储层的写后读回比对（`reloaded != unit` 就报 `Inconsistent`）顺带保证了
  列漏读/漏写会被测试抓到，不用另写一个"读回时字段对不对"的专项测试。

## D44 压缩：模型只写草稿，提交权在代码里；摘要挂在分界线上

P4 落地时顺手定下来的四条。

**1. 草稿不进上下文。** 四件工具（`compress_draft_append/edit/read/done`）操作的是
内存里的一个 `String`，不进上下文、不进归档、不参与缓存。反过来说：如果草稿是"消息"，
每追加一段就要把已写好的部分再算一次全量输入，而这个场景恰好在 0.85 水位上——最贵的时候。

**2. 提交权在代码里。** 模型调 `compress_draft_done` 只是"举手"，`commit` 才决定换不换历史。
覆盖率不合格就把缺失项回给模型（`CompressError::tool_text`），草稿保留、可继续补；
退回次数用完（默认 2 次）则状态转 `Forced`，此后草稿工具一律拒绝，只能走确定性兜底。

**3. 摘要不落消息表，挂在分界线上。** 计划原话是"把草稿作为一条新消息放到线下"，
但 `seq` 是整数：切点 `cut` 与它下面第一条消息之间没有编号空隙。硬插摘要只有两条路——
改编号分配器，或重排已有消息。两条都比"挂在线上"风险大。所以：

- `Divider.note` 存 `summary_ref`（内容寻址）与一行统计；
- `CompressionOutcome.summary_injection()` 把摘要装成一条 `SourceTag::InstructionInjection`
  消息，组上下文时放在窗口最前面；
- 好处顺带：摘要不进消息表，就不会被编辑、被归档、被退化检测误判，二次压缩时直接丢掉。

**4. 兜底必须是确定性的。** 模型不守协议（迟迟不 `done`、草稿空、退回用尽）时走
`commit_fallback`：每条线上消息的归档指针拼成摘要 + 照样画线。难看，但准确、可回灌、
零模型参与。压缩不能把会话卡死——这是安全阀，不是功能。

**本轮覆盖率校验只做宽松版**（关键字级）：线上 `protected` 消息 + 用户消息各抽一个
最有辨识度的 token（路径 > 错误码 > 命令 > 蛇形标识符），要求草稿里出现过；抽不出
关键字的算"跳过"，不判不合格。§3.6 的硬事实抽取（数字、未完成项、多值校验）留到下一轮，
理由是它错了会静默毁数据，值得单独一轮把它钉住。

## D45 数据可靠性：进程被杀是常态，不是异常

用户提的要求：安卓划掉卡片就清后台，任何时刻都可能被杀，数据必须可靠。

**先把两种事故分开**，否则对策会互相打架：

| 事故 | 丢什么 | 需要什么 |
|---|---|---|
| 进程被杀（划卡片 / OOM / `kill -9`） | 只丢还在本进程缓冲区里的 | 不需要额外动作——已 `write()` 的都在内核 |
| 断电 / 内核崩溃 | 内核页缓存里没落盘的 | `synchronous=FULL`（每次 commit 一次 fsync） |

我们现在的 `synchronous=NORMAL` + WAL 已经足以抗第一类。第二类要显式开 FULL，
所以做成**配置项**（`durable`），默认关：手机上一次 fsync 几毫秒，用户感知不到，
但把"每次提交两次 fsync"当默认值，在批量导入/压缩这种密集写场景会明显变慢。

**两条硬规矩**：

1. **ack 时机 = 事务提交之后**。UI 显示的"已发送/已保存"必须在仓库层返回 `Ok` 之后才点亮。
   反过来说：先点亮再写盘，就等于向用户承诺了一件没发生的事。
2. **不做异步批量写**。单条插入是微秒级，省不出时间，却把"丢最后 N 条"变成默认行为。

**草稿可以丢，原文不行**：压缩草稿只在内存里，被杀就没了——这是有意的。
兜底是 `commit_fallback`（确定性指针摘要），代价是摘要难看，收益是**不会出现半压缩状态**。
如果为了保住草稿把它写到 scratch，反而要处理"草稿在、原文已归档、线还没插"这种中间态。

**还缺的三件事**（P10，见 PLAN §3.8）：

- **启动收口**：开场扫一遍未闭合的工具单元、没有 `TurnCompleted` 的轮次，标 `incomplete`。
  字段早就有（D43），缺的是"启动时去查"这一步，否则被杀的那一轮永远显示成正常回复。
- **压缩提交跨表事务**：归档 + 分界线 + 摘要必须一个事务，否则会留下"有归档没线"或"有线没摘要"。
- **`kill -9` 测试**：fork 子进程，在写事务中途杀，父进程校验事务原子性与 `integrity_check`。
  桌面 CI 能跑；安卓侧跑不了 fork，只做"每次写后立刻读回"的强断言。

## D46 压缩的工具循环走非流式：流式下这个上游根本不发 `tool_calls`

实测（本机代理，`relay-b/DeepSeek-V4.1-Flash`）：同一份请求体，只改 `stream`，
非流式回 2 条 `tool_calls`（arguments 完整），流式整条流**一帧都没有**。详见
`docs/provider-runtime.md` §1.2.1。

第一次跑真机压缩就是这么翻的：8 次往返、0 次工具调用、草稿 0 字。
现象很像"模型不会用工具"，实际是上游把调用吞了——**这种错最难查，因为它长得像模型能力问题**。

所以 `compress::runner` 一律用 `complete()`（非流式）：

- 压缩是批量任务，没有"首字延迟"这回事，流式一点好处都换不到；
- 少一条依赖：不用赌上游的 SSE 实现是否完整；
- 代价是拿不到流式过程中的中途取消——上一轮已经用 `read_timeout` 兜住（每帧/整包读超时），
  再加一层轮次上限，够用。

**推广的教训**（写在这里是为了以后重复使用）：凡是"模型必须调工具"的流程，
推之前先用 curl 在目标端点上验一遍 `tools` + `stream` 的组合，别假设协议里有就会发。
响应里 `finish_reason` 是 `tool_calls` 而 `tool_calls` 是空数组的，同样要当异常报出来。

## D47 启动收口只报告不猜；压缩的三样东西必须一个事务

D45 定了原则，这一条是落地时定下的两个细节。

**1. 收口是只读的。** `Storage::reconcile()` 扫一遍全库，报三类东西：

- 会话以 `user` / `tool` 结尾 → 那一轮没等到回复（杀在流式中间）；
- 工具单元 `unit_closed = 0` → `tool_result` 丢失，连没等到结果的调用名一起报；
- 已有的 `incomplete` 计数（历史事实，不动）。

**不自动补、不自动删**。理由：补一个假的 `tool_result` 会让模型基于不存在的事实继续推理，
这比缺一轮糟得多；自动删又是在用户没同意的情况下丢数据。所以修由显式动作完成——
`abandon_open_unit()` 丢弃那个半截单元，这是唯一能让库重新自洽的办法。

**2. 压缩落库必须一个事务。** `Storage::commit_compression()` 把归档条目、摘要、分界线
放在同一个事务里。分开写会留下两种残局：归档写了线没插（下次启动看起来没压缩过，
但 ref 已被占）；线插了摘要没落（窗口里凭空少一段）。进程可能死在任意两条 SQL 之间。

顺带一个决定：分界线用 `INSERT OR IGNORE`。同一个 outcome 重放（崩溃后重试）必须是幂等的——
分界线 id 是 UUIDv7、每次压缩唯一，重复出现只可能是同一次提交。归档同理按 ref 幂等，
但**内容不同就报冲突**，不静默覆盖。

**还没验的**：真 SIGKILL（fork 子进程在写事务中途杀）没做。现在有的是"未提交事务在连接丢弃后
消失"的测试——对 SQLite 来说这和 SIGKILL 是同一件事，但不是同一个进程模型。留给桌面 CI。

## D48 导出与备份：先写 `.tmp` → fsync → rename，验证在发布之前

原来的备份是"`dest` 存在就 `remove_file` 再写"。这条在手机上必炸：进程被杀在
"删完还没写完"中间，用户就得到一个 0 字节或半截的备份文件——**而他以为有备份**。

改成三步，顺序不能换：

1. 写到 `<dest>.tmp`（SQLite Online Backup API 直接写临时文件）；
2. **在临时文件上**跑 `integrity_check` + `foreign_key_check`；
3. 过了才 `fsync` + `rename` 发布，最后 fsync 一次目录。

三个细节：

- **验证不过就不发布**。旧备份原样留着。一个验证不过的备份比没有备份更坏——它让人
  放弃做第二份。
- **rename 之后要清旧旁路文件**。旧备份可能留着 `dest-wal` / `dest-shm`；新库如果是
  DELETE 日志模式，一个孤零零的 `-wal` 会让 SQLite 以为有未合并的 WAL。
- **`.tmp` 永远是垃圾**。写之前先删残留（上次被杀留下的），它从来不是数据。
  `atomic::sweep_tmp()` 留给"用户看到脏文件"的手动清理。

对目录的 fsync 失败**不当错误**：Windows 打不开目录句柄，部分文件系统也不支持。
这种情况下 rename 仍然是原子的，只是"rename 之后立刻断电"那一瞬不保证——比"先删旧文件"
好得不是一个量级。

导出（Markdown / 分享）以后走同一个 `atomic::write_bytes`。

**踩到的坑（CI 的 windows job 抓的，本地完全看不出来）**：`File::sync_all()` 在 Windows 上
是 `FlushFileBuffers`，**要求句柄带写权限**——拿只读句柄 fsync 直接回 `ERROR_ACCESS_DENIED`。
Unix 上只读 fd 可以 fsync，所以本地 5 个单测全绿。`sync_file` 因此改成用可写句柄打开
（`OpenOptions::write(true)`）：不能为了"读文件"顺手打开再 sync，那在 Windows 上是另一个错误码。

**补记（2026-10-21，P6.1 的 C 侧验收抓到的）**：`rename` 只搬主文件。SQLite 在临时库旁边
留下的 `<dest>.tmp-wal` / `<dest>.tmp-shm` 会顶着一个已经不存在的主文件名留在目录里——
原来只清了 `dest-wal`（旧备份遗留的），没清 `dest.tmp-wal`（临时库自己的）。
现在 `atomic::remove_sidecars` / `remove_with_sidecars` 统一处理，四个清理分支都走它。
**这类 bug 单测抓不到**：单测断言"目标文件对不对"，没人去数目录里还剩几个名字；
是 C 程序用 `list_dir` 列了一遍才看见的——那条断言就留在了 `abi_smoke.c` 里。

## D49 硬事实分两级：漏抽会悄悄丢信息，过抽会当场卡死

§3.6 的抽取规则（`core::facts`）。核心不是"抽得全"，是**想清楚误判的两边代价不一样**：

- **漏抽** → 放行一份劣质摘要，几天后才发现信息没了；
- **过抽** → 摘要永远不合格，压缩当场卡住，只能走兜底。

两个都坏，但一个看得见、一个是暗的。所以抽得广、判得窄：

| 事实 | 严重度 | 缺失时 |
|---|---|---|
| 路径（带行号后缀、`./` 前缀都归一） | 硬 | 拒绝提交 |
| 错误码 / 常量 / 协议词（`E0282`、`INVALID_ARGUMENT`） | 硬 | 拒绝提交 |
| 命令行（`cargo` / `git` / ...） | 硬 | 拒绝提交 |
| 蛇形标识符 | `protected` 或用户说的 → 硬；助手自己说的 → 软 | 视上 |
| 数字（两位以上） | 同上 | 视上 |
| 未完成标记（`TODO` / `还没` / `未完成`） | 软 | 只提示 |

**为什么要区分"谁说的"**：用户说过的和系统标了必须保的话，一字都不能丢；助手自己
的措辞可以概括——"修复了 host 头拼装的函数"完全可以不出现函数名。一刀切要求所有
标识符会让摘要变成原文的目录。

**三道防过抽的闸**：每条消息最多 3 条（长的优先，长的更有辨识度）、硬项总数 48 /
软项 64、包含关系去重（`runtime.rs` 被 `crates/core/src/runtime.rs` 盖住时丢短的）。

**做不到的说清楚**：中文句子里"未完成项"没法用字面匹配验证（"启动收口还没写"抽不出
可比键）。这类只记一条软项提示，不阻塞提交。要让机器判断语义得靠模型，而"让模型
自查写得对不对"这件事不成立——它会说对。

真机验证（本机代理，`relay-b/DeepSeek-V4.1-Flash`）：4 次往返、4 次工具调用、
**0 次退回**，硬事实 4/4、软事实 2/2，4200 token → 418 token。收紧之后没有误拦。

## D50 工具层：形状 / 调度 / 权限三层分开，先门控再动手

P7 的第一步（`core::tools`）。三件事分开，是因为它们的变更频率完全不同：

- [`Tool`]（形状）：名字、一句话描述、JSON schema、`invoke`。平台侧要加工具就实现它。
- [`ToolRegistry`]（调度）：名字 → 工具，外加一份能直接塞进 `ChatRequest::tools` 的声明表。
- [`ToolContext`]（权限）：每个调用先过 `policy.check(capability)`，过了才拿到工作区。

**四条落地决定**：

1. **先门控再动手**，连路径都不解析。没绑工作区时调 `read_file` 得到的是
   `no_workspace`，不是"路径越界"——两者原因不同，用户看到的提示也不该一样。
   有测试钉住：只读绑定下 `write_file` 返回 `ReadOnlyWorkspace`，且磁盘上**没有**新文件。
2. **`specs_for(policy)` 在发请求前过滤**。没开写权限就别把 `write_file` 告诉模型：
   它看到就会去写，然后连吃几个"拒绝执行"，白烧好几轮。
3. **失败也是结果**。未知工具、参数不是合法 JSON、路径越界、匹配不唯一，全部变成
   `ToolOutcome`，由上层喂回模型（和压缩的草稿工具一个规矩）。拒绝的理由要说人话：
   `DenyReason::explain()` 给的是"该增强默认关闭，需要时在设置里手动开启"这种句子。
4. **不在 core 里跑 shell**。`container_exec` / `native_shell` 只留能力位和拒绝理由，
   执行是平台侧的事——Android 走 PRoot，Linux 走 podman/bwrap，标准库那套 `std::process`
   在手机上根本不是同一个东西。

**六个内置工具**：`read_file` / `write_file` / `edit_file` / `list_dir` / `find_files` /
`search`。都直接调 `core::workspace`，不另写一套文件访问——截断规则（D14）、越界检查、
二进制拒绝都是现成的，重复实现只会分叉。

**没做的**：通用多轮工具循环。压缩有一份专用的（`compress::runner`），但那是围着
草稿工具写的；通用循环等第二个真实用户出现再抽，否则会抽出错误的形状。

## D51 通用工具循环：非流式、失败即结果、轮数用尽不装做完

`core::agent::run_turn`。四条决定：

1. **非流式**（同 D46）。这个循环的整个用途就是工具调用，而实测这个上游在流式模式下
   不下发 `tool_calls`。走流式等于把命门交给上游的实现细节。
2. **工具失败也是结果**。越界、没权限、未知工具、匹配不唯一，全部变成一条工具结果塞回
   对话。模型看到"只读绑定，写入与编辑不可用"才知道换个办法或者求用户开开关。
3. **轮数用尽要诚实**。`TurnReport.finished = false` 表示"模型还没收尾"，接着跑还是
   打住由调用方决定。悄悄当成完成是最坏的选择——用户会以为事情做完了。
4. **和 `compress::runner` 故意不合并**。压缩循环里有它自己的语义：草稿不进上下文、
   覆盖率不合格退回去、用尽轮次转兜底、提交权在代码里。抽成"通用能力"之后会变成一堆
   只有压缩用得上的钩子。等第三个用户出现、看清共同点再抽。

**真机验证**（本机代理，`relay-b/DeepSeek-V4.1-Flash`）：4 轮 / 3 次工具调用
（`read_file` → `edit_file` → `read_file` 确证）/ 全部成功 / 正常收尾，
磁盘上的 `a.txt` 第二行确实变成了「改过了」。冒烟例子最后一行不看模型的话，
直接读磁盘——模型说改好了不算，文件变了才算。

## D52 会话编排：三段落库、判据不落库、空正文不落库

P6 的地基（`core::session`）。UI 只要三件东西：发一句话、看它怎么一步步做、库里留没留痕。
`run_session_turn` 就是这三步的确定性实现。

**落库顺序**（每一步都同步，没有后台队列，见 D45）：

1. **用户消息先落库**。用户说了什么，不因为后面模型失败就丢。
2. 模型跑完，工具调用与结果**成对落成 `tool_pair` 并当场闭合**——不闭合的单元启动收口
   会报出来（D47），那不是我们想要的残局。
3. 正文落成一条 `turn` 单元；没收尾的标 `incomplete`（D43）。
4. **压缩判据不落库**。它是"现在该怎么继续"的结论，不是历史。存进去只会让下次载入
   时看到一个过期的判断。

**空正文不落库**。模型只调工具、一句正文都没说的时候（轮数用尽时很常见），
不去造一条空消息：`Message::validate` 本来就拒，而且一条空消息进历史对下一轮就是噪声。
这种时候"没说完"由 `SessionTurn.report.finished = false` 交代。
后果是这一轮在库里以工具结果结尾——启动收口会把它报成"没等到回复"，**这是对的**：
用户下次打开就该看到"上一轮没跑完"。

**历史存储走 trait**（`HistoryStore`）：core 不能依赖 storage，依赖方向反了。
测试里用内存实现，SQLite 那边一行 `impl` 转过去。这样"编排对不对"和"写进库对不对"
是两件事，分开测。

**没做的**：跨会话的输入队列、取消（`abort`）、以及"压缩判据触发之后自动去压"。
最后一条是故意的——压不压是用户的决定，判据只负责把话说到位。

## D53 FFI 用 JSON 信封，不用结构体布局

跨语言传数据有两条路：`repr(C)` 结构体、或者序列化后的字符串。选了后者。

**理由不是"JSON 方便"，是"结构体 ABI 会静默错位"**：Rust 的 `u128`/`bool`/枚举判别值在 32 位
Android、MSVC、JNA 上的宽度和对齐规则各不相同，错位之后读出来是一个"看得懂但不对"的数，
比崩溃难查十倍。JSON 只有一种错法：解析失败，当场报错。

**代价认了**：每次调用一次分配 + 一次解析。这些调用是"打开会话 / 列目录 / 落一条消息"级别，
不在渲染循环里，测出来的开销不值得为它设计第二套 ABI。

配套的三条规矩写进 PLAN §3.11：`ok` 字段必在、`kind` 是稳定词表、字段名 `snake_case`。

## D54 句柄是整数 id，不是裸指针

UI 是多线程的，"后台任务拿着已经关掉的句柄回来"这件事必然发生（用户切走、会话被删、
Compose 重组的 stale lambda）。裸指针在那一步是 use-after-free，整个 App 崩；
整数 id 查一次表，返回 `invalid_handle`，UI 弹一句"这个会话已经关了"。

**id 单调递增、永不复用**。复用看着省空间，实际会把"旧 id 指向新对象"变成静默错误——
拿着旧句柄去写，写进了别的会话，而且一切正常。这种 bug 只能靠翻日志查。
几十个句柄的内存不值得换这个风险。

代价是每次调用多一次 `Mutex` + `BTreeMap` 查找。和 D53 同一个判断：这些调用不在热路径上。

## D55 一条失败路径：JSON 函数永不返回 null

失败有两种形状最折磨绑定层：`null` 和 `{"ok":false}` 混用，最后每个调用点都要写两个分支，
而且总有一个地方忘了判 null。

所以定了：**所有返回数据的函数，永远返回堆上的 JSON 字符串，失败写在 JSON 里**。
返回 null 只留给"标量函数"，而标量函数（版本、自检、panic 探针）本来就没有需要解释的失败。

配套：`nmoi_string_free` 是唯一的释放路径，ctx 参数不收、长度参数不收——
C 侧只需要记住"这个指针是我儿子，得还给它爹"。不还只是泄漏，不会崩，
所以忘一次不会毁掉一次调试会话。

## D56 FFI 不建线程、不回调（F1），F2 的回调也只在调用方线程上

F1 全部同步阻塞。这是故意的：Android 上"我们在后台帮你跑"等于"你不知道它什么时候完成、
也不知道它失败没有"，而 D45 已经把"不做异步批量写"定成硬规矩。

F2 要加事件回调（模型逐字吐、工具调用开始/结束），形状先定在这里：
**回调在调用方的线程上同步执行**，FFI 不 spawn 线程；回调里只允许读句柄、不允许再触发
`nmoi_turn_run`（否则就是递归调模型）。回调本身也进 `guarded`——回调 panic 不能穿过 FFI。

## D57 `open` 的阻塞状态不是错误，必须在 JSON 里说出来

`Storage::open` 有三种结局：`Ready`、`Blocked`（L3 语义损坏，等用户选恢复方式）、`Err`。
把前两种压成"成功/失败"会让 UI 少一条路：用户看到"打开失败"却不知道可以恢复。

所以 `nmoi_storage_open_json` 返回 `state`：`ready` / `blocked` / 失败时 `error`。
`blocked` 带 `issues` 计数与摘要，**不给句柄**——没通过 L3 的库不该被继续写。
恢复走单独的函数（`restore_defaults` / `restore_issues`），那是用户的决定，不是自动修复。

## D58 取消是协作式的，而且只在轮次边界生效

`run_turn` 在**每次模型调用之前**和**每个工具调用之前**看一次取消标志。这不是偷懒，
是因为"打断一次正在飞的 HTTP 往返"要动传输层（socket shutdown / 分段读里插检查点），
而传输层现在是手写的明文实现（D38），动它的风险大于收益。

说清代价：**点停止之后，最坏还要等一次往返**（受 `DEFAULT_READ_TIMEOUT=120s` 约束）。
所以这条不能当成"立刻停"卖给用户——按钮文案写"停止"可以，但别在 UI 上骗人说已经停了。

三条配套语义：

1. **已经执行完的工具调用照常落库**。它们是真发生过的事，抹掉等于伪造历史。
2. **这一轮标 `finished=false`，助手消息带 `incomplete`**（D21 / D43）。
   断流的回复和正常的回复在数据里长得一样，是这个字段存在的唯一理由，取消走同一条路。
3. **只对正在跑的轮次生效**：没在跑就是空操作，返回 `{"cancelled":false,"running":false}`。
   不做"预存一个取消请求等下一轮"——UI 上误触一次，会静默吃掉后面某一轮，
   而用户看到的是"我明明发了消息它没反应"。这种 bug 没人报得清。

## D59 turn 面不注入系统提示词，也不猜思考档位

FFI 的 `nmoi_turn_run_json` 只跑"用户说了这一句 → 模型怎么回"，两件事故意不做：

- **不自动加系统提示词**。系统提示是会话的一部分：用户要能看见、能改、能被压缩带走。
  藏在 FFI 里偷偷拼一条，UI 就永远渲染不出它，压缩也永远归档不到它。
  所以调用方先 `nmoi_storage_append_text_json(role="system")` 落库里，再跑轮次。
- **不发思考档位**。D37 定了"关闭必须显式"，而这一层不知道目标模型支持哪一档；
  猜一个等于替用户做决定，还可能被上游直接 400。等 P3.2（角色配置持久化）把
  每模型档位接上，再由配置显式给。

代价认了：F2 跑出来的请求是"没有思考设置"的请求。对一个本地客户端来说这不算缺功能——
思考档位本来就是按模型调的，没有模型档案之前给了也是假开关。

## D60 turn 期间 storage 句柄被取出，其他调用得到 `busy` 而不是等锁

`run_session_turn` 要 `&mut Storage`，而一整轮可能跑几十秒（含网络）。句柄表只有一把锁，
如果 turn 从头到尾攥着它，UI 那边读消息的调用会**静默卡住**——不报错、不超时，就是转圈。
静默卡死比报错难查得多。

所以 turn 开跑时把 `Storage` 从表里**取出来**（原位置留占位），跑完再放回去；期间
对该句柄的任何其他调用立刻返回 `{"ok":false,"error":{"kind":"busy"}}`。
放回走一个 guard：成功、失败、panic 三条路都会归还（panic 被 `catch_unwind` 拦住之后
回的也是正常 JSON，所以 guard 的 Drop 一定跑到）。

工作区不用取出：`Workspace` 是 `Clone` 的（只有根路径），turn 拿一个副本进去就够，
UI 那边继续能列目录、能读文件。

## D61 会话列表：排序要稳、分页给 `has_more`、预览要截断且说实话

UI 的第一屏是"选哪个会话"，所以列表接口的三件事都得先想清楚，而不是等 UI 写完了再补。

**排序 `updated_at DESC, id DESC`。** 第二键不是装饰：同一毫秒里建的两个会话只按时间排，
顺序由 SQLite 心情决定，每次刷新都可能不一样。用户在列表上看到"会话自己乱跳"，
第一反应是数据坏了——这种恐慌一次就够。UUIDv7 前缀是毫秒时间戳，跨毫秒时 id 顺序近似创建顺序；**同一毫秒里那部分是随机的**，
所以 id 只保证「顺序确定」，不保证「等于创建顺序」——这两件事别混。

**给 `has_more`，不给 `total_count`。** 分页要的是"还能不能翻"。为此跑一次全表
`COUNT(*)`（还有 `GROUP BY`）在手机上是白花几十毫秒，而 UI 拿到总数唯一会做的事
是显示"共 N 条"——一个没人看的数字。实现上取 `limit + 1` 行、多出来的那条只用来置
`has_more`，不返回。

**预览截断到 200 字符，并给 `last_text_truncated`。** 会话最后一条可能是工具结果：
`read_file` 的返回可以是几十 KB 的目录列表。不截断，等于"打开会话列表"要拖一个文件回来；
截了不说，UI 就会把半句话当全文显示。两个都要，缺一个都是骗人。

**`last_*` 指的是最后一条消息，不分角色。** 列表上要回答的是"这轮聊到哪儿了"，
不是"助手最后说了什么"——中间那条工具结果往往才是人记得的那一下。

`limit` 缺省 50、硬上限 200：UI 传个 1e9 不该把手机拖死，而"一次要一千条会话"这种需求
不存在（真要找会话是搜索，不是翻页）。

## D62 视觉覆盖：开着的时候，主模型一个媒体块都不收

用户 2026-10-21 定名并定语义："OCR 文字识别我们这边叫视觉覆盖，启用后聊天中的模型将不使用
自己的图片、视频等模态，相应信息将会发给设置好的默认视觉模型"。

**这一条的关键不是"多问一次视觉模型"，是"主模型不许再看到媒体"。**

如果开了覆盖、请求体里还留着 `image_url`，那就变成"同时问了两个模型"：
主模型照样按它自己的方式看，视觉模型的描述只是一段额外的文字。看起来更富，
实际是两个模型对同一张图说两套话，而用户完全无法判断哪套在起作用——也没法解释
"为什么它说的是图里的 A，而你给我的描述里是 B"。

所以 `VisionPlan` 的形状是硬的：
- `tasks`：要发给视觉模型的批次（图片按 `max_images_per_call` 分批，视频每个一条——视频的
  时间轴信息不能和别的混在一起）；
- `stays_with_main`：**开着覆盖时永远为空**；为空才是对的，非空就是实现漏了；
- `main_note`：给主模型的一句话交代（"3 个附件已转成文字描述，见下"），
  让它知道"有一段描述是从附件来的"，而不是把描述当成用户自己打的话。

**描述进历史，媒体不进。** 描述是一条 `SourceTag::VisionBridge` 的普通消息：参与 token 预算、
能被压缩、能被搜索。媒体本身留在本地库里（内容寻址），按需要可以换提示词重看、可以重放。
这样"上下文里有什么"仍然是可解释的——用户在窗口里能看见那段描述。

## D63 视觉提示词两套：图像一份、视频一份，且不互相复用

用户要求"默认提示词应该存两套，一份图像，一份视频"，图像那份他把现成的高精度提示词发过来了
（`data/vision.image.md`，逐字收，不改写——那是他一直在用的东西，改一个字都可能破坏它的口径）。

**视频那份不能复用图像的模板**，理由不是"内容不同"，是**丢的信息不一样**：
图像是一次快照，丢了细节还能靠"再看一眼"补；视频丢了时间轴，"什么时候发生了什么"
就永远补不回来了。所以视频提示词的核心是：分镜/场景切换点、镜头运动、主体动作的时序、
字幕与音轨、关键帧时刻，最后才是画面细节。

两份都放在 `data/` 里当纯文本（`include_str!` 进二进制），不写成代码里的字符串字面量：
- 提示词是要被人改的，改 `md` 比改 Rust 里带转义的字符串现实；
- diff 里看得见改了什么（那份图像提示词里有大量引号与反引号，塞进 Rust 字面量等于找罪受）。

用户可全局改、可按会话覆盖（P3.2 持久化之后）。

## D64 多模态：能力矩阵在前，缺能力显式报错，Gemini 先走 inline 再走 Files API

四种端口的模态支持差别很大（见 PLAN §3.15 的表），所以请求构造前必须先问**模型档案**：
这个模型能收图吗、能收 PDF 吗、能收音频吗。缺能力就报错（D40 那条"缺能力显式报错"的延伸）。

**不许静默降级。** 把图片悄悄丢掉、或者替换成"（图片）"两个字，是这个领域最常见的骗法：
模型说"我没看到图"，用户以为是模型笨，其实是客户端把图吃了。查这种问题要花一整天。

**Gemini 先做 inline，再做 Files API。** inline 是 base64 一次性塞进请求，简单、无状态，
适合图片和短视频；大文件必须走 Files API（先上传拿 URI），那是一条独立的状态机
（上传、轮询、过期、引用），而且**本机没有 key 验不了**——所以顺序是：inline 先落地并标注
"已实现未实测"，Files API 列进待办，不假装写了就算完成。

**"没人能测"怎么办：写探针，不写断言。** `scripts/modality_probe.sh` 对一个端点逐模态打一遍，
输出支持矩阵；本机只能跑通文本和图片，其余行写"未测"。别人有 key 就跑同一份脚本，
结论能对上号——这比在代码注释里写"应该支持"诚实得多。

## D65 签名密钥：CI 里的是副本，不是唯一一份

Android 的包名绑死签名：keystore 丢了，已发布的应用就再也更新不了，这不是"重新生成一个"
能解决的（Play 有 upload key 重置流程，但我们是自己分发，没有那条路）。所以第一条规矩是
**离线备份两份、放两处物理介质**，CI secret 只是其中一份副本。

存放与注入（细节在 `docs/signing.md`）：

- **GitHub 用 environment secret**（`release` 环境 + 人工批准），不用仓库级 secret：
  仓库级 secret 任何 workflow 都能读，被改坏一次就是全泄。
- **Codeberg / Woodpecker 用 repo secret + `event: tag`**，只在打标签时注入。
- **只在 tag 构建注入**。fork 的 PR 能跑 workflow，绝不能让它有机会摸到签名材料。
- **即用即焚**：解到 `$RUNNER_TEMP`（不进仓库、不进 artifact）、`umask 077`、
  结尾 `always()` 删、脚本禁 `set -x`、不 `echo`、不 `env`。两边的日志 mask 只挡日志，
  挡不住你把它写进文件。

**两处都存就是两份泄露面。** 主密钥建议只存 Codeberg（主仓在那儿）；
GitHub 只在确实要发 Release 时临时注入。哪天不在 GitHub 发版，这条配置直接不建。

workflow 文件**没有**直接放进 `.github/workflows/`：现在没有任何签名材料，放进去
CI 会天天红，红久了就没人看了。可粘贴的版本在 `docs/signing.md` 里，等材料到位再搬过去。

## D66 断块声明：ID + 块类 + 原因，中间不隔符号，而且 ID 是稳定的

用户给的形状（2026-10-21）：

```
1545374566161错误思考块原因:调用中途断开
16154544994949错误工具调用块原因:格式错误
```

**为什么不用分隔符**：用户的原话是"符号隔开的句子开头更容易中招（复读/退化）"。
这不是玄学：如果每一块都以同一个 `|` 或 `-` 开头，块与块之间共享的前缀就在反复强化
同一个 token，模型很容易接着往下"复制"上一块。纯数字 ID 开头则天然不同（每块一个随机长相），
中文块名跟在后面——整行唯一，复读就没有抓手。

**为什么 ID 不能真随机**（用户说"随机生成"，这里做成了"看起来随机、实际确定"）：
同一块每次请求都得是同一个 ID，否则
1. 每次请求体的这段就变了 → 断点缓存全部失效（附录 A 的回本周期白算）；
2. 模型看到的是"无穷多个新块"，而不是"同一块还在那儿"。
所以 ID = 单元 id 的 FNV-1a 哈希取 13 位十进制（补零）。自己实现 6 行，
不用 `DefaultHasher`——那个不保证跨 Rust 版本稳定，一次升级就换一批 ID，
看起来无害，实际是偷偷把缓存打掉一次。

**信息要留下**：声明下面接原始内容（工具名与参数、思考尾巴），截断到上限。
只写"这里坏了一块"，模型就不知道刚才想干什么——而那是它自己上一轮的动作。
删掉它等于让人重猜，留一句"坏了"等于给人看个疤不告诉他在哪。

## D67 断块在 UI 里是折叠卡，不是错误提示条

照 kelivo 的做法（用户给的折叠块设计）：断块默认折叠，标题就是那行声明（ID+块类+原因），
展开看到原始内容。

**不做成"红色报错条"的理由**：报错条在修复之后就该消失，但这段东西**不会**消失——
它成了历史的一部分，之后每一轮都要跟着走。做成报错条，用户会一直以为"应用有个 bug 没修"；
做成折叠块，它就是"这一轮当时断了"，像一条划掉的笔记。
错误提示是给操作者的，折叠卡是给读者的——这里的人是后者。

**边界**：修复只发生在请求构造时（`run_session_turn` 汇总历史那一步），
库里的原始单元一个字节都不动。已闭合的工具对不碰；用户可见的历史文本不重写。

## D68 字体：内置只用 OFL，导入字体单槽、改名、换走即删

用户 2026-10-21 的要求，加上我这边查到的事实：

- **工作区里只有一份字体**（`得意黑SmileySans-Oblique.ttf`，2.6 MB）。实测它有拉丁区 334 字、
  CJK 基本区 8057 字，`name` 表里写着 SIL OFL 1.1——可商用、可嵌入。
  但它是**斜体展示字**，放正文会让人读得累，所以定位是"标题/品牌/空状态"，不是默认正文字体。
- 正文字体另配：**Noto Sans SC**（中文，OFL-1.1，实测单文件 8.3 MB）+ **Inter**（拉丁，OFL-1.1）。
  不用 MiSans / HarmonyOS Sans / 阿里普惠那批"免费商用"：许可是厂商自拟的、保留解释权，
  真出争议只能拿"当时页面这么写的"说话；OFL 有固定条款，能拿文本说话。

三条行为是按用户原话落下来的：

1. **导入即改名**为 `Imported Font`（name 表 nameID 1/4/6/16）。这同时满足 OFL 对
   Modified Version 的改名要求；改不动就只改展示名并明说，不假装成功。
2. **单槽 + 换走即删**：切到内置/系统字体时删掉 `imported.ttf`。多槽会立刻长成一个字体管理器，
   那是另一个产品。
3. **系统字体按平台给**：Android 只给"系统默认"（厂商族名不稳定，兼容优先，用户原话）；
   Windows 枚举 DirectWrite 字体族并**必须带搜索**；Linux 走 fontconfig。
   导入字体不参与中文回退——用户选的就是它，缺字显示缺字，免得"我选了 A 怎么中文变了"。

## D69 思考强度图标：环数表示档位，颜色表示强度，针表示"现在在哪"

用户给的方案（2026-10-21）：外环深蓝、指针红、底部淡蓝封口线；high/xhigh 加一环（内环淡蓝）；
max 三环（紫/深蓝/淡蓝）；off 沿用上一版（环 + 中心点 + 斜杠）。

第二轮追加：max 的**环外**再撒一圈红色颗粒（不可见环带、每颗直径 1、位置固定但看着随机），用来表现「这一档烧得凶」。颗粒放环外而不是环内——环内再塞点状环，会和「内环=高一档」的语法打架，看起来像高一档又回来了。

**为什么是"环数"而不是六种不同图形**：这个控件会出现在输入岛上一次又一次，
六种互不相干的图形靠"记住"区分；环数是**可数**的——小尺寸下数环比认形状快，
而且它天然带顺序（多一环=高一档）。指针负责回答"当前在哪"，不需要记。

**为什么底部要封口**：开口的弧看起来像"加载中"，封口之后才像一块**仪表**。
淡蓝比深蓝弱一档，视觉上不会抢针。

**实测结论**：16px 时内环会糊（1.5 的线宽缩到 1px），UI 里用 18px（桌面 20px）——
这条写进 `docs/fonts.md` 与 §3.12，免得有人在工具栏里塞 16px 然后说"图标看不清"。

**标签规则**：名字 ≥ 6 字母就缩（minimal→min、medium→mid）。缩到 3–5 个字母是刻意的：
chip 要窄，英文名只是给"这几档叫什么"一个锚点。文字基线取 chip 中心 + 0.28em（3.4px），
`+4.3px` 试过明显偏上——**包围盒对齐不等于视觉对齐**。

## D70 自动重试：停止项优先，只在零字节阶段重试，等待必须可中断

用户 2026-10-21 给的设计（截图 + 口述）：一个"网络错误时自动重试"总开关，
四张可编辑列表——可重试状态码、重试关键词、停止重试关键词、重试时间点，
每张都带"添"与"恢复默认"。默认值照截图：状态码 `408 425 429 500 502 503 504 529`；
重试关键词 `并发/稍后/重试/访问量过大/繁忙/限流/rate limit/too many requests/overloaded/try again/timeout/超时`；
停止关键词 `余额/不足/额度/欠费/balance/insufficient/quota/invalid api key/unauthorized/permission/未实名`。

**判定顺序定死为：停止项 → 可重试状态码 → 可重试关键词 → 不重试。**
理由不是偏好：`429 rate limit` 的响应体里经常同时出现 `quota`，如果先看可重试关键词，
就会在一张余额已空的卡上重试到天亮，账单照样涨。**停止永远压过重试**。

其余四条：

1. **关键词只扫错误文本的前 2 KiB。** 把整个响应体当 haystack，正文里随便一句 "timeout"
   都能触发重试——那不是容错，是误伤。
2. **只在零字节阶段重试（沿用 D40）。** 已经吐出正文再重发，用户屏幕上会出现两遍开头。
   流到一半断了（`Interrupted`）**不自动重发**，标 `incomplete` 让人自己决定。
3. **等待必须可中断。** 3/15/30/60 加起来 108 秒，`thread::sleep` 会让"停止"按钮在这段时间里
   完全没反应。分片 sleep（50ms）+ 每片看取消标志。
4. **两个停止条件**：时间点列表用尽、以及总时长上限（默认 180s，可配）。
   只靠列表的话，加上每次请求自己的超时，最长能挂到四分钟，UI 上看起来就是卡死。

**列表为空 = 关闭**（用户原话）。开关开着但列表空，UI 要直说"列表为空，等同于关闭"——
否则用户以为开着，实际没重试。

## D71 重试时间点是"范围"，每一项进来时 roll 一次、等完即丢

用户 2026-10-21 追加：每一项写成一个范围，进到这一项时在范围内随机取一个数（两位小数）
作为实际等待；每次重新加载列表重新 roll，随计时结束销毁。

- **精度两位小数照做**：对网络抖动没意义，但成本为零，而且能让"这次等了 3.72 秒"这件事
  在日志里可读。
- **排序按范围下界升序**，下界相同按上界。用户说"自动从小到大"，但范围之间本可以重叠
  （3–5 和 4–6），所以必须定一个确定性规则，不能按"看起来谁小"。
- **随机源必须可注入。** 这条是 D66 的教训：随机且不可复现的东西等于不可验。
  core 里的 roll 走一个 `FnMut(f64, f64) -> f64`（生产用系统熵，测试给固定序列）。
- **UI 同时显示范围与本次取值**（`3.0–5.0s，本次 3.72s`）。只显示范围，计时器看着像在乱跳；
  只显示取值，用户以为自己填的数没生效。

## D72 图片压缩：原图不动，只生成"发送副本"

用户 2026-10-21：客户端上传时就处理，长边超过阈值才压，采样算法尽量用质量好的，
处理完才在输入框上方显示"已处理好 / 已加载"。

- **原图进附件库，一个字节都不改**；压缩产物是另一份内容寻址的"发送副本"。
  理由：压完才想调阈值，让用户重新上传一遍是不可接受的；而"用户给我的东西被我改了"
  是数据可靠性问题（用户明确数据可靠性优先于新功能）。
- **三条上限，取最先触发的**：长边（默认 1568）、总像素、字节数（默认 5 MiB）。
  只限长边挡不住"1600×1600 的 PNG 有 8 MB"；只限字节会放过 3000 宽的长条图。
- **不超上限就不重编码**：重编码会丢 EXIF、掉画质、还慢一倍。没有必要的处理不要做。
- **缩放用 Lanczos3**（默认），可选 CatmullRom / Nearest；缩小必须先预滤波，否则细密纹理起摩尔纹。
  **PNG 带 alpha 不转 JPEG**——透明底变黑是这类处理的经典事故。
- **状态机 `pending → processing → ready/failed`**，`ready` 才允许发送；`failed` 显示原因，
  不静默丢图（静默丢图等于用户以为自己发了）。

## D73 `view_image` 工具：返回值是文字，分析过程在隔离子上下文里

用户 2026-10-21：要一个能把 md 等文件里引用到的图片发给视觉模型的工具，
做成"带当前会话数据的、类似子 AGENT 的隔离分析，输出思考信息"。

- **返回值只能是文字描述**，不能是图片或图片引用。否则主模型绕过视觉覆盖直接收到图，
  D62 那条"开着覆盖就一个媒体块都不收"当场失效。
- **隔离子调用**的上下文只装三样：图片本体、任务锚点、最近 4 条会话文字。
  不带领取来的工具、不带写权限、不带全量历史——它的活儿是"看"，不是"干"。
- **思考信息落库**，位置是工具结果里的思考段（`SourceTag::ModelThinking` 的子块），
  UI 折叠：思考在上、结论在下。用户明确要"输出思考信息"，那就得能回看，不能只在流里闪一下。
- **路径与格式**：工作区根约束 + 拒绝符号链接越界 + 拒绝 `file://`；
  远程 URL 默认关（读一个 http 图片等于把"我在看什么"告诉第三方），要开就显式开。
  格式按**魔数**判断，不看扩展名；单张 8 MiB、单次最多 4 张；超限**报错**，不偷偷缩——
  缩了就是"看到了和原文不一样的东西"，那份描述会进历史。
- **缓存**：内容哈希 + 提示词哈希 → 复用结果。同一个文件被反复读、反复看，是这类工具最费的支出。

## D74 历史图片不按"张数"做上限，做完就摘、换成占位引用

用户 2026-10-21 问"上下文的图片会不会影响后续继续发送图片"，并建议识别完就把图转储、
用特殊引用表示。查到的事实（未实测，见 P3.4）：

- OpenAI 兼容端：不按张数限，按像素与字节折算 token，超窗口直接 400。
- Anthropic：单请求图片数有上限（现今 100），单图长边建议 1568。
- Gemini：inline 有请求体总大小限制（约 20 MB），Files API 有 48h 有效期。

**共同点：没有"历史累计 N 张就拒绝"的机制，限制落在每一轮请求的总 token / 总字节上。**
所以做"数量上限"是照错了靶子，要做的是"体积进预算"。

摘图的四条规矩：

1. **摘 = 发送的那一份**，库里的消息一个字节都不动（与 D66 断块修复同一个位置、同一个原则）。
2. **不在同一轮内摘**。模型刚说完"这张图里是……"，下一秒图没了，等于骗它。下一次请求再换。
3. **只在视觉覆盖开着时摘**。关着的时候图片是模型的输入本体，摘掉就是失忆。
4. **占位形如** `[image:att_7f3a2c1b 1600×1200 image/jpeg 视觉覆盖已转写]`，本体留在附件库，
   点得开、取得到。

这条**不新造机制**：它就是 `VisionBridge` 的落库形态（D22 / D62）。

## D78 断块在**写库时**就诊断并冻结声明，请求构造只读它

用户 2026-10-21 问"错误工具调用块和思考块是什么时候处理的"，并建议"最好是输出完成就检测出来"。

现状（`session.rs` 的 `run_session_turn`）：`repair::normalize(&units_before)` 在**凑历史的时候**跑，
也就是"下一次发消息时"。于是本轮的断块要等下一轮才会被翻译，UI 上也拿不到声明——
`nmoi_storage_load_units_json` 里那个 `broken` 字段现在是现算的。

改成两段，第一段提前：

1. **落库时就诊断**（这一轮结束，`finish_turn_incomplete` 那一带），把 `id / 块类 / 原因`
   冻进消息（或单元的元数据）。UI 立刻能画折叠卡，不用等下一轮。
2. **请求构造只读声明**，不再重新诊断。

好处是三条：UI 与请求里看到的是同一个声明；声明一旦落地就不会因为"上游多来了一条结果"而变形
（否则每次请求的 prompt 都变，断点缓存全废）；排查时库里能查到"当时判成了什么"。
代价是旧库里的块没有声明，需要**懒补**（读的时候发现没有就补一次，补完写回）。

## D79 设置分三个轴，任何一轴变化都不改写另外两轴；只有数据坏了才回退

用户 2026-10-21 点名不接受的 kelivo 行为：切到一个没有推理选项的模型，思考强度变成 `null`；
切回来还是 `null`。工具那边同理——切到没开工具的模型，MCP 与本地工具被关，工作区没被关，
因为"不是一套实现判断"。用户原话：**这种切过去切回来丢设置的问题绝对不能有**。

根因是把"能不能发"和"要不要发"活在同一份数据里，于是"暂时发不出去"必须写成 `null`。

**三个轴，各存各的：**

| 轴 | 谁说了算 | 存在哪 | 变化时 |
|---|---|---|---|
| 模型能力 | 模型元数据（`reasoning` / `supported_efforts` / `capabilities`） | 快照 + 用户覆盖 | 只影响"这次能不能发" |
| 用户设置 | 用户（每模型 / 每助手 / 每会话） | 持久化表 | **永不因换模型被改写** |
| 这一份请求 | 上面两者的交集 | 不落库 | 构造请求时现算 |

**发不出去时不是"清零"，是"这次不发"**（`core::config::ThinkingEmission::Dropped`）：

- 模型不做推理 → 一个思考字段都不发（"不发"本身就是关，再写 `none` 是瞎猜，可能 400）；
- 模型有推理但没这一档 → 不发（**不降级到最近的档**：降级等于替用户做决定，而且降级也是改写）；
- 只能开/关（`supports_toggle`）而用户选了档位 → 不发；
- `supported_efforts` 为空 = **没数据**，照发——别把"我们不知道"变成"你不能用"。

`effective()` 与 `emission()` 必须同源：前者已经改成走后者，两条路各算各的迟早分叉。

**工具那条路径按同一套办**：助手的工具开关属于"用户设置"，`capabilities.tools` 属于"模型能力"，
请求里的工具声明 = 两者取交，交出来的结果**不写回任何一边**。这就是 kelivo 那个"工作区没被关"
的窟窿——MCP 和本地工具走了另一套判断，两边不同源。

**唯一的回退**：值本身坏了（解析失败、类型不符、越界到任何场景都用不了）→ 回退默认值，
并在 `settings_repair` 记一条（哪一项、原值摘要、原因、时间），UI 上告诉用户"这一项被重置了"。
回退必须是**事件**，不能是静默。用户原话："如果是设置数据错误了变成软件任何场景根本无法使用的数据，
就回退默认值就行，这种是可以的。"

## D80 技能启用 = 只注入 name + description；禁用不代表环境里用不了

用户 2026-10-21：技能启用只代表 `SKILL.md` 的 name 与 description 进上下文。有命令环境时，
即使禁用，文件还在 `/skills` 映射里，照样能读；没有环境时走工作区那套读取工具也能访问。

这句话拆成两条互不影响的规则：

1. **上下文侧**：启用 = 注入 name + description（省 token，也让模型知道"有这么个技能"）；
   禁用 = 这名字和描述都不进上下文，模型不知道它存在。
2. **访问侧**：文件在不在，跟"启用"无关。有容器就映射 `/skills`（只读），没有就用工作区工具读——
   但那是**模型自己找过去**的，不是我们告诉它"这里有个技能"。

所以"禁用"是**让模型不知道**，不是**让模型够不着**。这两件事混在一起会出现"我关了它，
模型还在偷偷读"的困惑——其实模型只是读了它刚好看见的文件，那不是 bug，是它该有的能力。
UI 文案要说这一点（禁用项的副标题写"仍可通过文件读取使用"）。

## D81 世界书是两级门：设置里关了就彻底不加载

用户 2026-10-21：设置里启用 → 聊天窗口加载；实际生效由聊天窗口里的勾选决定；
**设置里禁用了就不加载、不生效**。

这与 `core::policy` 的能力门控同一个形状（两级门、下级不能越过上级）：

| 级别 | 作用 | 关掉的后果 |
|---|---|---|
| 设置级（世界书本身启用开关） | 总闸 | 连列表都不出现，一条都不注入 |
| 会话级（聊天窗口里的勾选） | 生效选择 | 只在开了总闸的里面选；没勾的不注入 |

关键在"加载"与"生效"分开：设置关了，**不加载**（连解析都不做，省得坏文件拖慢启动）；
设置开着、会话没勾，**加载但不注入**（UI 上要能看见"有这本书，但这次没用"）。

## D84 模型编辑页用紧凑网格，不要一条一行

用户 2026-10-21：添加模型页那种松散排版不喜欢；输入模式这类枚举**每排三项、多排**，
太宽操作效率低。落地成通用规则：

- 枚举/多选（输入模式、输出模式、能力位）→ **三列网格**，每项一个 chip + 勾选态；
- 标量输入（上下文窗口、最大输出、定价）→ 两列（标签 + 数字框），同组放一张卡；
- 每张卡最多 6 行，超过就分组换卡（避免一页无限长）。

模型页三个页签（基本设置 / 推理 / 高级设置）保留，与截图一致。

## D85 工作区归到"工具"里；工具开关也是三轴

用户 2026-10-21：工作区在工具里面；工具项参考 kelivo 做。

- **导航**上：工具页 = 内置工具（含工作区读写/编辑/列目录/查找/搜索）+ MCP + 权限与能力门控。
  工作区不再单独一页——它本来就是一组工具，单独一页会让人以为"工作区"是另一种东西。
- **开关**上：`能力门控（policy）` × `助手允许的工具` × `会话临时开关` 求交（同 D79）。
  门控是安全边界（默认关），助手是偏好，会话是临时。三者互不写回。

**修订（用户 2026-10-21 后半段的更正，三类的开关位置不一样）：**

| 类 | 开关在哪 | 说明 |
|---|---|---|
| 工作区工具 | **跟着工作区走** | 工作区设置里有开关；**绑定**工作区看那个开关。工具本身不单独设开关——绑了就有，没绑就没有 |
| 本地工具 | **聊天面板** | 会话/聊天这边显示与切换 |
| MCP | **两级门** | 启用才去连接；**连不上就不进工具表**（不是进了表再报错） |

工作区工具不给独立开关的理由：它是"工作区存在"的一部分。给了开关就会出现
"绑了工作区、工具却是关的"这种没人说得清的状态——用户只会问"我明明绑了为什么读不了文件"。
MCP 那两级门的理由：连不上的服务器如果先进工具表，模型会一次次调用一个不存在的工具，

## D86 设置存成文档，一张表装四类

Schema v3 只加两张表：`settings(scope, doc_key, doc_version, payload, updated_at)` 与
`settings_repair`。四类文档（`model_overrides` / `assistant` / `conversation` / `roles`）
共用一个作用域字段。

**为什么不分四张表**：它们的形状不同，但用法完全一样——按 `(scope, key)` 整份读写，
没有人会去查"所有把 thinking 设成 max 的模型"。分表的收益是字段有类型约束，
代价是**UI 每加一个开关就要迁移一次 schema**；迁移脚本只增不减，`validate` 要跟着改，
旧库打开越来越慢。这类迁移做一次丢一次。

**为什么 `doc_version` 高了就当坏数据**：新版本写的字段我们读不懂，硬读会丢掉它们；
再写回去就等于把用户的设置静默删除。所以：版本高于程序 → 不读、记一条 `settings_repair`、
用默认值。这是 D79 允许的"回退"的唯一场合，而且**必须是事件**。

**`old_digest` 只存哈希前 16 位**：设置文档里可能夹着自定义 header 的密钥，
修复记录是"给人看最近出了什么事"的地方，不是存原值的第二个地方。

**读取返回三态** `Loaded::{Missing, Ready, Reset}`：`Reset` 不是错误——
把它做成 `Err`，每个调用点都要写一遍同样的兜底。

## D88 求交层单独成一个模块，四个函数不硬凑一个入口

`core::gate` 只做一件事：把"存着的设置"和"模型能做什么"算成"这一轮发什么"。
它**只读不写**——算完不回头改任何输入，这是"切过去切回来丢设置"不会复发的结构保证。

四个函数分开写，因为四种东西的语义本来就不一样：

| 函数 | 语义 | 关键判据 |
|---|---|---|
| `visible_skills` | 启用 = 名字 + 描述进上下文 | 顺序跟发现顺序走，不按勾选顺序重排（prompt 要稳定） |
| `gate_instructions` | 关了就一个字都不进 | 命令类开关 |
| `gate_world_books` | 两级门 | 设置级关 → `NotLoaded`（连解析都省） |
| `plan_tools` | 三轴求交 + MCP 两级门 | 见下 |

**工具三轴怎么分**：按 `Capability` 分，不按名字猜。读写/检索 → 工作区类（跟绑定走，
没有独立开关）；执行/联网/凭据 → 本地类（聊天面板开关）；`mcp__` 前缀 → MCP。

**MCP 认不出服务器就不声明**：名字必须是 `mcp__<server>__<tool>`。认不出来就丢掉并说明——
猜一个服务器然后声明出去，模型会去调一个不存在的工具，每次失败花掉一轮上下文。

**判定顺序是"开关优先于门控"**：先看用户关没关，再看 `policy`。反过来的话，
"没开权限"与"用户关了"会报成同一个原因，用户会跑去改错地方。

## D89 一轮开自己的连接，句柄不再被借走

用户 2026-10-21：A 会话用 A 模型跑着，B 会话就能用 B 模型跑。旧做法（D60）是一轮把
storage 句柄整个取出，表里留占位，于是**同一个库上的所有调用**都吃 `busy`——
A 会话在跑，B 会话连列表都刷不了。

改成：句柄永远在表里（`Entry::Storage(Box<Storage>)`，不再有 `None` 占位），
一轮用 `Storage::attach(path)` 开**第二条连接**跑自己的活。理由：

- WAL 下读不挡写，写与写按 `busy_timeout` 排队，SQLite 自己会处理；
- `attach` **不做** L0/L1/L3：库刚被主连接打开过，再从头校验一遍只是让"开一轮"慢几百毫秒，
  而 L3 阻塞态在那一步已经处理过了；
- 同一个会话的第二轮仍然被 `Registration` 挡成 `busy`（那条更早、更准，取消 flag 也靠它）。

代价与边界：不同会话并发写同一张表时，仍会在 SQLite 层面排队——**这是正确的**，
数据可靠性优先于吞吐（D45）。真正并行的是"一条在等模型回包、另一条在读列表"。

## D90 压缩两条线：建议线与绝对线，单位可切

用户 2026-10-21：两条线都能自定义；可切百分比与 token；触发建议线后，**本轮生成结束**
再压；触发绝对线，**立刻截断并压缩**。

```
                建议线（advisory）              绝对线（absolute）
轮开始前估算 ──── 已过 ──────────────┐         已过 ─→ 先压再发（这一轮别带着超载的上下文出门）
                                    │
生成中（流式）  ────────────────────┘  已过 ─→ 立刻停止生成 → 标 incomplete → 压缩
                                    │
生成结束 ── 已过建议线 ─────────────┴─→ 落库后压缩（不打断这一轮）
```

四条定死的规矩：

1. **内部统一用 token 存**，百分比是"当前有效窗口的占比"换算来的。存百分比的话，
   用户换模型（窗口从 128K 变 200K）阈值会跟着漂，而他改的是"我要在 70% 时被提醒"这件事。
2. **只在两处判定**：构造请求前（估算一次）、生成结束（有真实 usage 就用真实值）。
   流中间**每帧都跑 BPE 是不可接受的**——又慢又抖；绝对线在流里用字符数增量近似判断。
3. **绝对线截断必须标 `incomplete`**（D21）：被压的上下文和"模型自己没说完"是两件事，
   但在数据上都是"这一条不完整"，标记要一致，否则事后分不清。
4. **压缩不可重入**：压缩自己那一轮跑的模型不再触发压缩（A 套 A 会无限递归）。

默认值（可改，等实测调）：建议线 0.75、绝对线 0.92。旧的 `TriggerPolicy` 里的
`force_ratio` / `emergency_ratio` 就是这两条线的旧名字，映射过去即可；
成本判据（`Soft`）保留为"建议线的第三种理由"，与阈值谁先到用谁。

## D91 token 估算：本地 BPE + 真实 usage 校准，在线服务默认不用

用户 2026-10-21 问的三件事，逐条答（**全部未实测，标在这里**）：

**1. 有没有国内外都能直连的 tokenizer 服务？** 我没有找到一个能当默认依赖的。
事实层面我知道的：OpenAI 没有公开的 count-tokens 端点（那是本地库 `tiktoken`）；
Anthropic 有 `POST /v1/messages/count_tokens`（要 key、要跨境）；国内几家（智谱/百炼/火山）
没有对等的公开端点。就算有，也不该默认用——把整段上下文发给第三方换一个数字，
是**为了省钱花掉隐私**，而且高频调用等于滥用（用户原话）。

**2. 名字匹配与兜底。** 顺序：模型名 → 分词器家族（`cl100k_base` / `o200k_base` /
DeepSeek 系 / Qwen 系等）→ 都不匹配就用**中文混合基准**（DeepSeek 系的口径）。
这一条依赖已有的 `core::model` 家族-版本表（1729 条），不需要新数据。
为什么兜底选 DeepSeek：它的中文合并率在国产系里居中，估高了安全（安全阀宁可早触发）。

**3. 真正该做的事：用真实 usage 校准。** 网关会改写模型名（`relay-a/DeepSeek-V4-Flash`
这种东西），名字匹配迟早不可靠；但**每次响应回来的 `usage.prompt_tokens` 是真的**。
所以三级策略：

| 级别 | 手段 | 成本 | 用在哪儿 |
|---|---|---|---|
| L0 字符近似 | 现有 `estimate_tokens`（ASCII 4 字符≈1、CJK 1 字符≈1） | 零 | 流式增量、每帧判断绝对线 |
| L1 本地 BPE | 按家族选词表，全量算一次 | 未实测（估计几十 ms / 10 万 token） | 造请求前、压缩判据 |
| L2 真实 usage | 端点回的 `prompt_tokens` | 零（本来就有） | 每轮结束后**反推一个比例因子** |

**L2 是关键**：`factor = 真实 / 估算`，按 (模型, 语言构成) 存一份滑动平均（存 settings 文档），
下一次 L1 直接乘上去。一次真实值校准后面 N 次估算——这比任何在线服务都便宜且准。
端点不给 usage（本机的 `relay-c/deepseek-flash` 就不给）时才只能靠 L1。

**验证方法**（等做的时候跑，别口头说"差不多"）：

1. 造三段固定文本（纯 ASCII / 纯中文 / 中英混排），1k / 10k / 100k 字符各一份；
2. `cargo test --release` 里量 L0 与 L1 的耗时（**release**，debug 数字没意义）；
3. 拿本机代理端点（`relay-b/DeepSeek-V4.1-Flash`，有 usage）发同一段文本，
   记录 `prompt_tokens`，得到"估算 vs 真实"的误差表，按语言分开；
4. 结论写进 `docs/token-estimation.md`，并把这三种文本存成测试夹具，防止以后改算法悄悄退化。

**依赖风险先说**：`tiktoken-rs` 之类 crate 对 rustc 1.75 的兼容性**没验**（本机没有 rustup，
升不了工具链）。验不过就退到"手写 BPE + 自带词表"或干脆只用 L0+L2 校准——
D38 那条"不升 MSRV"在这里同样适用，不能让一个 tokenizer 把整条构建链拖走。

**补记（2026-10-21，L0 已实测）**：用 `scripts/token_check.py` 对本机 `relay-a/DeepSeek-V4-Flash`
对了账，结果与上面"估高了安全"的直觉**部分相反**：

| 文本种类 | 真实/估算 |
|---|---|
| 纯 ASCII | 0.62 |
| 纯中文 | 0.63 |
| 中英混排 + 全角标点 | **1.32（低估 32%）** |
| 类 JSON 代码 | 1.01 |

误差随内容种类变化，两个长度上都稳定（系统性而非噪声）。结论有三条：

1. **不能乘一个全局系数**——乘 0.62 会把混排从低估 32% 变成低估 58%。
2. **混排那种正是 Agent 会话的主料**（工具输出、markdown），也就是最危险的方向。
3. 所以 L2 校准要按 **(模型, 会话内容构成)** 算，不按语言分类；未校准时绝对线判定
   先乘 1.3（测出的最坏低估幅度）。

明细见 `docs/token-estimation.md`（含未测项：L1 耗时、crate 兼容性、多轮模板开销）。

## D92 消息块按原始顺序渲染，不给工具调用与思考固定位置

用户 2026-10-21：「工具调用块、思考块、直接输出的位置，不需要死板的指定，按原始顺序渲染」。
我同意，而且这比"排版偏好"更要紧。

**理由**：模型的输出本来就是**交错**的——先说两句，再调工具，拿到结果又想一段，再调一个，
最后写结论。硬把"思考"钉在最上面、"工具"钉在下面，等于替它编了一个它没经历过的顺序。
事故排查时最常问的恰好是"它先想了才调，还是先调了才发现想错了"——顺序被排版抹掉，
这个问题就永远答不上来。

**做法**：

1. 流式到达什么就按什么顺序落进时间线；块类型只决定**长什么样**，不决定**在哪儿**。
2. 同一个工具调用与它的结果是一个**折叠块**（D67），整体占时间线上的一个位置；
   并行调用按到达顺序排，不按名字排。
3. 段落下场后**不再重排**。谁先到谁在上面，后来的一律追加——重排会让正在读的段落跳走。
4. 思考块默认折叠、标题显示"思考"，但位置不动；想要"只看结论"的用户用折叠，不用搬家。
5. 断块（D66/D67）也是这条时间线上的一个位置，不额外贴到顶部或底部。

**唯一的例外**：流中途被取消/截断时，末尾那条 incomplete 的消息后面会追加一条
"已停止"的分隔提示——那是 UI 的标记，不是模型说的内容，带自己的样式，不参与排序。

## D93 世界书内部格式用酒馆（SillyTavern）的，导入兼容 kelivo / RikkaHub

用户 2026-10-21：**存储与导出用酒馆格式**；导入时能读 kelivo 与 RikkaHub 的格式。
示例在工作区：`/workspace/世界书示例-kelivo.json`、`/workspace/世界书示例-rikkahub.json`（**不在仓库里**，
实现时自己造夹具，别把外部样例提交进去）。

**为什么以酒馆为准**：它是这类文件的事实标准，别人家的世界书基本都能导进来，
而我们导出去的也能被别人的工具读。以自家格式为中心，等于让用户替我们做转换。

**入口只认三种形状，出口只有一种**：

| 形状 | 识别 | 说明 |
|---|---|---|
| 酒馆 world info | 顶层有 `entries` 且是**对象**（键是 `"0" "1" …`） | 原生格式，导出用这个 |
| 酒馆 character_book | 顶层有 `entries` 且是**数组** | 角色卡里嵌的那种，导入要认 |
| kelivo / RikkaHub | `{"version":1,"type":"lorebook","data":{…}}` | 两家同一套外壳，差别在枚举大小写 |

**字段映射（这是最容易写错的地方）：**

| 酒馆 | kelivo | RikkaHub | 坑 |
|---|---|---|---|
| `key[]` | `keywords[]` | `keywords[]` | — |
| `content` | `content` | `content` | — |
| `comment` | `name` | `name` | 酒馆里条目名是 `comment`，不是 `name` |
| `constant` | `constantActive` | `constantActive` | — |
| `order` | `priority` | `priority` | kelivo 默认 0，RikkaHub 有的条目是 10001——**不能当序号用**，它就是排序值 |
| `disable` | `enabled` | `enabled` | **语义相反**：`disable:true` = 关闭。读反了就是"整本书全禁用"，且看起来一切正常 |
| `position` 0–4 | `AFTER_SYSTEM_PROMPT` 等字符串 | `after_system_prompt` 等小写 | 数字与字符串两套枚举，0–4 的对应关系照酒馆文档，别自己排 |
| `role` 0/1/2 | `SYSTEM/USER/ASSISTANT` | `system/user/assistant` | 同上 |
| `depth` | `injectDepth` | `injectDepth` | 只在 `position=4`（@depth）时有效 |
| `caseSensitive` / `useRegex` | 同名（驼峰） | 同名 | — |

**做法**：解析分两步——先把三种形状**统一成内部结构**（`core::lorebook::Lorebook`），
再让注入逻辑只认内部结构。绝不让"注入"那一层去判断来源是酒馆还是 kelivo：
那样每加一个来源，注入代码就要多一个 if，而且顺序与互斥的规则会被来源污染。

**导入必须是"能说清丢了什么"的**：不认识的字段记一条（不报错、也不静默丢），
条数对不上、枚举值不认识都写进导入报告。**静默丢弃最坏**——用户以为全导进来了，
实际少了三条，等到模型答歪了才发现。

**格式只管字段，不管顺序**：注入顺序、槽位、互斥规则在
`test/世界书注入顺序与互斥矩阵.md` 与 §3.21 里定，改格式不动那套。

## D94 token 估算 L1＝tiktoken-rs，两个词表，按模型家族挑

D91 定的三级里 L1 一直挂着"未验"：悬着的问题是 `tiktoken-rs` 能不能在 rustc 1.75 上编
（D38 不升 MSRV，本机没有 rustup）。**已实测：`=0.5.9` 在 1.75 上编过**，
`cargo check` 32.9s，依赖树里没有 edition2024 的 crate。

**两个词表，不搞"一个打天下"**：

| 词表 | 给谁 | 依据 |
|---|---|---|
| `cl100k_base` | `gpt-4` / `gpt-3.5` / `gpt-3`，`claude` 也借它近似 | 这些模型的真实分词器就是它（claude 那家没有公开实现，cl100k 是最近的替身） |
| `o200k_base` | `gpt-4o` / `o1 o3 o4` / 中文各家（deepseek、qwen、glm、kimi、doubao…）/ **认不出的所有模型** | 实测在中英混排上最贴；中文压缩率也最接近中文各家 |

映射**只看模型名**（不查表、不联网、不读远端 config）。认不出就 o200k——D91 说的
"中文混合基准"落到具体就是它。

**为什么两个都要，而不是只留 o200k**：同一段 1000 汉字，cl100k 切 1218，o200k 切 781，
差 **1.56 倍**。只留 o200k，gpt-4/claude 的中文会话会被低估 36%，而且方向是危险的
（该压缩时不压缩，撞窗口才报错）；只留 cl100k，中文会话高估 1.94 倍，窗口用了 39% 就开火，
等于白扔一半窗口。多链一个词表贵 1.64MB，换掉两个方向的系统性错，值。

**用 `encode_ordinary` 而不是 `encode_with_special_tokens`**：用户正文里写
`<|endoftext|>` 这种串不罕见（贴文档、贴 prompt），那里它就是几个普通字符，
按特殊 token 吞掉会把长度算少。

**成本（release / PRoot / aarch64 Android，实测）**：

| 项 | 数字 |
|---|---|
| o200k 首次初始化 | **691ms**（解析 3.6MB 排名表） |
| cl100k 首次初始化 | 296ms |
| 16k 汉字编码 | 26ms |
| 10k 字符编码 | 12–17ms |
| strip 后二进制 | 空 395KB / +cl100k 3.67MB / +o200k 5.64MB / **两个 7.28MB** |

初始化近半秒，所以：单例 `OnceLock`（每进程一次）+ **`warm()` 让调用方能在后台线程预热**——
UI 启动时热，别等到第一轮请求再造。结果缓存键 = (词表, 内容 FNV-1a 64)，上限 4096 条、
满了整清；不做 LRU：淘汰策略的复杂度换不来收益，清空只是重算一次。

**留一个 feature `bpe`（默认开）**：关掉之后 `tokens` 退回纯 L0 + L2，二进制不增。
容量敏感的分发（手机安装包）由打包方决定，代码不为它分叉——两条路都走同一个 `Estimator`。

## D95 L2 校准键＝(模型, 级别, 内容类)

校准就存三样：`ratio`（真实 / 估算）、`samples`、`updated_at`。

- **样本门槛：估 ≥ 1500 token 才收**。请求里有模板、工具 schema 这类固定开销（几百 token），
  小请求里它占比一大，比例就虚高；1500 以上固定项摊到 15% 以内。宁可少收样本，也别收脏样本。
- **EWMA α=0.3**，第一个样本直取；`samples ≥ 3` 才算校准过（1 个样本碰上端点口径差异就废了）。
- `ratio` clamp **[0.7, 1.8]**：端点把 cached 也算进 prompt、或请求被截断，都会造出离谱比例，
  一个异常样本不该把因子甩出去。
- **两级都按内容类分桶**。L0 的偏差是 0.62–1.32（差 2.1 倍），显然要分；L1 压到
  0.80–1.06（差 1.3 倍）——**小了一半，但没消失**。合成一个桶的话，用中文会话校准出来的
  0.80 套到英文请求上就是低估 21%，而且这种错只有在切了语言习惯的会话里才冒出来，最难查。
  我一度想让 L1 用一个桶（`class = Any`），算了一下跨类误差就否了：1.3 倍不值得省样本。
- 分桶的代价是每个桶各自攒 3 个样本。可接受：一次会话的内容构成基本稳定，
  真正在用的那个桶三轮就收敛，别的桶本来也不参与。

**放 `settings` 表，新加 scope `calibration`**（doc_key 形如 `relay-a/deepseek-v4|l1|mixed`）。
不加表、不迁移：D86 那套 (scope, key, 整份读写) 正好够用，而迁移脚本只增不减。
它是派生数据，但寿命跟设置一样长——每次冷启动都归零，等于永远停在最坏情况。

## D96 未校准的安全系数只作用在绝对线判定，不写回估算值

- L0 未校准 ×**1.3**（实测最坏低估 1.32），L1 未校准 ×**1.1**（实测最坏低估 1.056）。
- 系数**不进** `Estimate.tokens`：给用户看的、给 breakdown 用的，都是"我估多少"；
  写成"我怕成多少"，用户看到 8k 被报成 10k，只会以为在乱报。
- 校准之后系数归 **1.0**。它是未校准时的补丁，不是永久乘子——永久乘子会让绝对线
  永远提前 10% 触发，而这件事没人会发现，因为看起来一切正常。

## D97 两条线的单位是"双写"，动作表只写在一处

D90 说"内部统一存 token，百分比只是换算"。真做的时候撞上一个问题：**如果只存 token，
换模型就是一场灾难**——用户在 200k 的模型上把建议线设成 0.75（=150k），换到 32k 的模型上，
那个 150k 的绝对阈值会让**第一次请求就触发压缩**，而用户什么都没改。

所以 `Threshold` 存两个单位 + 一个 `mode`，由 `mode` 决定谁是权威：

| 模式 | 谁说了算 | 换窗口时 |
|---|---|---|
| `Percent` | `percent` | 按新窗口重算 `tokens` |
| `Tokens` | `tokens` | 数字不动，超过窗口时夹住 |

判定一律走 `resolve(window) -> u64`，**比较的是 token**，不是浮点比例——这是 D90 那句
"内部统一存 token"落到实处的地方：**决策路径上没有 f64**。

**动作表 `decide(trigger, point)` 一张表管三处**。为什么不让每处各写一个 if：
三处的判据只看两件事（越过哪条线、现在在哪个时刻），写三遍就会出现"生成中建议线压了、
造请求前没压"这种只在一个入口露头的错。表在 `budget::decide`，测试把 3×3 全穷举。

**造请求前过绝对线 = 拒绝这一轮**（`SessionError::CompactionRequired`），而且**判定在落库之前**。
core 自己没有 provider、没有 archive，压不了；能做的只有两件：说清楚、别留下烂摊子。
留烂摊子的具体形态是：先把用户消息写库、再报错，调用方压完重试 → 同一句话落两条。

**生成中过绝对线 = 就地停**（`TurnReport.truncated` + `finished = false`）。
工具循环每轮只累加**新增字符的 L0 估算**（D90 的"流中间只算字符增量"），不重算整份上下文：
每轮重算一次 200k 上下文，光是估算就能吃掉首字延迟。停下之后不再发起下一次请求——
下一轮请求只会更大，发出去就是把上游的硬上限当抽奖。

## D98 估算只有一档：面板、判据、校准用同一个 `Estimator`

D97 把两条线接上了，但"现在用了多少 token"这件事当时有三个来源：落库时的 `message.tokens`（L0）、
判据里的 `estimate_tokens`（L0）、BPE 那边的 L1。三套数必然对不上——面板说还剩 20k、
判据说已经过线，用户会当成 bug 报上来，而实际上每一处都在按自己的定义老老实实算。

**做法**：

1. `budget::breakdown_of_units(units, Option<&Estimator>)`：给估算器就**按内容重算**，
   不给就信库里的 `message.tokens`。重算时把三样都算进去——`content`、`reasoning`、
   `tool_calls[].arguments`（参数不在 `content` 里，漏了它工具那一行永远偏小）。
2. 会话的"用了多少"改成 `breakdown(...).total()`，判据、面板、校准从此同源。
3. 模型名跟**冻结值**走（D76）：`plan.model` 有就用它，没有用 `base.model`。
   压缩判据读一个模型、工具循环读另一个，是最难查的那类不一致。

**校准那一对数字怎么配**（这是这一条里唯一需要判断的地方）：

- 真实值取**最后一次请求**的 `usage.prompt_tokens`。工具循环会发好几次，前面几次的 prompt
  更短；拿第一次去配整份估算，因子会被系统性地算低。
- 我们的估算按**同一批文本**摊平：历史单元（含 reasoning 与工具参数）→ 用户 → 本轮正文 →
  工具结果。少算一段因子就虚高，多算一段就虚低。
- 已知偏差：我们的估算**不含** system 模板与工具声明，端点算的含。这正好被比例吸收进去——
  它是"每个模型的固定开销"，本来就该摊在因子里；样本门槛 1500 token 保证摊得动（D95）。

**FFI 侧闭环**：`nmoi_turn_run_json` 现在自己做两件事——跑之前 `calibrations(model)` 读出来、
跑完把 `turn.calibration` 写回去。写失败不让这一轮失败：用户的话已经落库了，为一条派生数据
把整轮判成错误是本末倒置。

**已知的洞**：`nmoi_context_breakdown_json` 拿不到会话的模型名（`session` 表没存），
所以那条接口只能按 L0 给数（`None`）。要补的话得先给 `session` 加 `model` 列——那是 schema v4 的事，
排在 UI 之前，现在不硬塞。

## D99 两层重试各有名字：`ReconnectPolicy`（立刻重连）与 `RetryPolicy`（时间点）

原来 `runtime::RetryPolicy` 是"零字节阶段立刻重连、600ms 起指数退避"，
§3.19 要的是另一件事：**按用户填的时间点范围再来一轮**。两个东西都叫 `RetryPolicy`，
接线的时候一定有人接错——排错时看到"重试了 3 次"根本分不清是哪一层。

**改名 + 分层**：

| 层 | 类型 | 干什么 | 次数 |
|---|---|---|---|
| 底层 | `runtime::ReconnectPolicy`（原名 `RetryPolicy`） | 一个字节都没收到时立刻重连，指数退避 | `max_attempts` 默认 3 |
| 上层 | `retry::RetryPolicy` | 整轮失败后按 `{min_s, max_s}` 范围等一次再来 | `bands` 条数（默认 3），总预算 180s |

**两层不叠次数**（§3.19）：底层那几次跑完仍然失败，才进上层的计时。
叠起来的话用户填"等 2 秒"，实际可能等到第 3 次退避之后——他填的数就成了假的。

接线落在 `ChatClient::complete_retrying(request, &policy, cancel)`：
- 返回 `Result<Completion, RetryError>`，`RetryError { error, reason }`——UI 要两样东西：
  原始错误（用户看懂发生了什么）和停止原因（"因为响应里有 quota"和"次数用完了"是两句话）。
- `written_any` 恒为 `false`：`complete()` 成功才交正文，走到错误分支就是零字节。
- 取消沿 `retry::wait` 的 50ms 分片生效，返回 `GiveUpReason::Cancelled`，**不算失败**。

测试里发现的两件事，写在这儿省下一次踩坑：
1. `chat_request()` 造的是流式请求，`complete()` 会直接拒——测重试要先 `.without_stream()`。
2. 底层没关时，`MockTransport` 里排队的 503 会被底层重连吃掉，"发了 3 次请求"说不清是谁发的。
   测上层就 `with_retry(ReconnectPolicy::off())`。

**补记（0.8 接线）**：策略落到 `agent::run_turn` 的**每一次工具往返**上——
第 2 轮撞了 503，重发的是那一次请求，不是整轮。整轮重发会把已经执行过的工具再跑一遍，
副作用（写文件、发请求）会真的发生第二次。

`SessionConfig::retry: Option<&RetryPolicy>` 转发到工具循环；`None` = 不重发。
**FFI 这条路现在传 `None`**：设置的界面（D70 要求"列表为空 = 关闭，UI 要写明"）还不存在，
一个用户关不掉的开关比没有这个开关更糟。等设置面板做出来再打开。

## D101 会话记住"最近用哪个模型"：`conversations.model` 一列，NULL 表示还没跑过

`nmoi_context_breakdown_json` 之前只能按 L0 给数：它拿不到会话的模型名，而 L1 必须按模型挑词表
（D94——同一段 1000 汉字，cl100k 切 1218、o200k 切 781，差 1.56 倍）。补的办法不是让调用方
每次把模型名传进来，而是让会话自己记住它：schema v4 给 `conversations` 加 `model TEXT`。

- **写入时机**：`nmoi_turn_run_json` 造请求之前写一次（`Storage::set_conversation_model`）。
  写失败不让这一轮失败——为了一个显示用的列把用户刚说的话丢掉不值，同 D98 的校准写回。
  另给一条 `nmoi_storage_set_conversation_model_json`，让 UI 在用户换模型时立刻落库
  （用户常常先建会话、再挑模型，把参数塞进 `create_conversation` 会让 C 侧所有调用点跟着改）。
- **NULL ≠ 空串**：NULL 是"这个会话还没跑过"，面板该据此说"这是粗估"；空串是调用方的 bug，
  FFI 按 `bad_argument` 拒绝。
- **不改 `updated_at`**：换模型不是会话活动，列表不该因为它跳到最上面。
- **为什么不 per-message 存**：那要动 messages 表的全部写入路径。会话头只需要"现在用哪个"；
  将来真要按轮追溯再扩，语义不用改。
- 列表页每行带 `model`，UI 画会话头不用再跑一次查询。

配套改了 `Estimator::level()`：报告**实际**会走的那一级（`bpe` 没编进来时是 L0），
这样面板不会把字符近似的数当 BPE 的数展示。`breakdown` 的出参因此多了 `model` 与 `level`。

## D105 图标运行时用 PNG，打"图标包"：原版不可删、可导入导出、正则规则可自定义

界面图标不从 SVG 运行时渲染，而是**预生成 PNG**（动作 24/48/72、品牌 40/80/120）打成一个包。
理由：Android 没有系统级 SVG 渲染器，为十几张小图引一个渲染库不划算，PNG 解码是系统自带的；
同时"包"这个形状天然支持换皮、导入导出与回滚。规格在 `docs/ui/icon-packs.md`。

- **原版包 `pack_id = "nmoi-original"` 永远可用、不可删除**：删除接口对它是硬错误，
  UI 上连按钮都不出现。导入包里出现这个 id 直接拒绝——保留 id 被冒用，回滚就没路了。
- **取图五级**：用户规则 → 包内预设规则 → provider `kind` 直配 → 模型名首段 → 首字母方块。
  规则是**正则**（`regex` 已是 `core` 的依赖，不新增依赖），大小写不敏感，匹配归一化后的 `provider/model`。
- **自建图标优先于包内图标**：同 key 时覆盖，删掉自建就回落到包内。规则写坏了逐条跳过并标红，
  不让一条烂正则把整个界面搞挂。
- **zip 自己写**（禁令：不用 Rust 的 zip 系 crate）：store 不压缩、只实现读中央目录 + 取数据，
  CRC32 手写。能力边界就写清楚——只保证读得动我们自己生成的包，不声称解任意 zip。
- 供应商图标与模型图标**分开两套**：`providers/`（公司）与 `models/`（模型家族）。
  智谱的供应商图标用 `zhipu`，不是 `chatglm`——后者是早期模型命名，放在 `models/` 里。

## D106 第三方声明随每一份副本走：LICENSE 只放自己的

MIT / ISC 的原文只要求一件事——版权与许可声明出现在**每一份副本**里。所以：

- 根 `LICENSE` **只放**本项目 GPL-3.0-only 全文，不并第三方。聚合说明另开
  `THIRD-PARTY-NOTICES.md`，各许可全文放根 `LICENSES/`（按来源命名，逐字保留上游文件）。
- **每个产物都要带**：APK 的 `assets/notices/`、桌面安装目录的 `licenses/`、
  便携包 zip 的根目录、导出的图标包 zip 里的 `NOTICE.txt`。占不到 10 KB，没有"先不带"的理由。
- 桌面端的 `icon-packs/original/` 放在安装目录里，**不藏起来**，用户可以直接解压覆盖；
  因此那里的路径与文件名是对外契约，改名等于破坏用户已经解压好的包。
- 声明里必须写"**我们改了什么**"（描边 2→1.75、`1em`→24、删 `class`/`style`），
  以及"哪几家没有彩色版"。改过不说，比没写更糟。
- 依赖清单还没进这份文件——1.0 之前必须补（`cargo metadata` 或 `cargo-about`），
  在那之前这份文件只覆盖图标，不覆盖 crate。

## D107 图标规则：优先级是人的意图，具体度是机器的兜底

规则排序只在 `core::icons::rank_key` 一处决定：

```
(priority 升序, source(user<preset), 锚定 true 优先, 有效字面量长度 降序, 通配符数 升序, pattern, id)
```

- **0–1000，数字越小越优先，默认 500**。用户能"钉死"（0–99）也能"兜底"（901–1000），
  数字要在列表里用小号字显出来——不然没人知道自己调的是什么。
- **同优先级用户规则赢预设**。用户是主动加的，一加就该生效；靠改数字去抢位置太绕。
- **"具体度"不用字符串长度**：`(?i)`、转义、`(?<name>)`、`[Cc]` 都会虚增长度，
  而 `^(alibaba/|dashscope/)?qwen` 比 `^claude-opus` 长得多却远不具体。
  改算"有效字面量长度"：剥内联标志与元字符、转义还原成 1、**可选组与多选一组里的字面量不算**、
  顶层分支取最长那支、`^` 算锚定。它是可解释的近似，不是语义精确度，
  所以设置页要把分数显示出来，让人看得懂排序。
- **最后要落到 `id`**：加载顺序（文件遍历、导入包、UI 拖动）不稳定，用它兜底会让
  同一份配置在两台设备上给出不同图标。全序之后任何顺序结果一致，这条有单测钉着。
- **规则必须声明 `field`**（`model` / `provider_kind` / `provider_host` / `provider_name`）：
  一条 `openai` 不该同时吃掉"供应商叫 openai"和"模型名含 openai"。供应商侧按
  kind → host → name 的顺序问，kind 只有五个值，比域名可靠，域名比用户起的名字可靠。
- **大小写**：`keyword` 有开关；`regex` 置灰，以写法为准（要忽略就写 `(?i)`）。
- **上限**：规则 ≤ 500、pattern ≤ 200 字节、key ≤ 64 字符且只允许 `[A-Za-z0-9_-]`（它同时是文件名）。
  超限**不许保存**并给具体改法（`RuleError::suggestion`）；坏正则逐条跳过并标红，不拖垮整个界面。
- 匹配用 `regex 1.10.4`（已在依赖里，不新增）。它没有回溯与反向引用，用户写不出灾难性回溯。

## D108 zip 自己写：store-only，能力边界写成拒绝清单

图标包要能导入导出，而项目有一条禁令——不用 Rust 的 zip 系 crate。于是自己写，
放在 `core::zip`（字节层）与 `core::iconpack`（语义层）。

- **只写 store（method 0）**：包里是 PNG，已经压过，再 deflate 一遍只费 CPU。
  读也只认 store，遇到 deflate **报错**而不是试着解——"读不懂就说读不懂"。
- **拒绝清单**（每一条都有单测）：zip64、加密标志、分卷、非 UTF-8 名字、
  `..` / 绝对路径 / 盘符 / 空段路径、重名条目、单文件 >512 KiB、文件数 >512、
  解压后总量 >8 MiB、CRC 不符、中央目录越界。
- **路径安全在读的时候也校验**，因为它防的是"解出来的文件跑到包目录外面"。
- CRC-32 手写一张表（20 行），不值得为它引依赖。标准向量已对过：
  `"" → 0`、`"123456789" → 0xCBF43926`。
- **语义层整包拒绝**：schema 版本不认识、`pack_id` 为空或冒用 `nmoi-original`、
  条目重复、key 不是安全文件名、文件不在对应 `kind` 的目录下、缺 1× PNG、PNG 魔数不对——
  任何一条不过就全拒。半个包比没包更糟：用户会以为图标"坏了"，而不是包"不对"。
- 缺 `NOTICE.txt` **不拒**（别处拿来的包可能没带），但会给 warning，且**导出时补一份**——
  MIT/ISC 要求声明随副本走，这条不能靠用户自觉。

## D109 面板与遮罩：位移进出、遮罩滑动不关闭、动画中不可点

侧栏与底部子窗口压在聊天之上，行为统一在 `docs/ui/overlays.md`。

- **遮罩纯黑 alpha 0.60**，覆盖到系统栏下面（否则状态栏亮一条）。点它关闭；
  **在它上面滑动不关闭**——面板里多是长列表，从边缘上滑时手指先落在遮罩上，
  一滑就关会让人以为"列表弹回去了"。代价是手感像失灵，所以遮罩拖动给 8dp 阻尼位移：
  看得见在动，但不产生关闭结果。
- **只位移、不缩放不淡入**：缩放让文字发虚，淡入分不清"新页面还是浮层"。
  侧栏从左边缘、底部窗口从下边缘伸出。
- **动画时长不自己乘系数**：Compose 动画读 `MotionDurationScale`
  （来自系统"动画时长缩放"），手动再乘会变成"系统 0.5×、实际 0.25×"。
  用户关掉动画时应瞬间到位，不留一帧半透明还在动。
- **动画未落位前，面板内不可交互**：`clickable(enabled = settled)` 之外还要
  `semantics { hideFromAccessibility() }`——只关点击不关语义，读屏用户仍能点到空气。
- **关闭三条路**：点遮罩 / 拖拖柄或贴边那侧往屏幕边缘拖（位移过 35% 或速度过 800dp/s，
  spring 弹回）/ 系统返回（`BackHandler` 注册在面板层，不能注册在 Activity）。
  Android 13+ 开 `enableOnBackInvokedCallback` 并把关闭动画接到回调上，否则返回会先缩一下再弹回。
- **同时只开一个面板**：两层 60% 会变成 84%。旋转屏幕收掉面板，避免"半开"的中间态。

## D110 Android 工具链只钉一套版本，模块里不写版本号

`android/` 是仓库里唯一的 Gradle 工程。Gradle 8.7 / AGP 8.5.2 / Kotlin 2.0.21 /
Compose 编译器插件 2.0.21 / JDK 17 / compileSdk 34。

- **这三个数互相卡**：AGP 8.5.2 要求 Gradle ≥ 8.7；KGP 2.0.21 要求 Gradle ≤ 8.8、AGP ≤ 8.5。
  交集只有 `Gradle 8.7 | 8.8`。所以"想升 Gradle"从来不是一件事，是三件事一起算。
- **Compose 编译器版本等于 Kotlin 版本**，不是 Compose 的版本。Kotlin 2.0 起它从 AGP 里
  拆出来成了 `org.jetbrains.kotlin.plugin.compose`；忘了跟着改，报错会说
  "requires Kotlin version X but you appear to be using Y"。
- **版本只在 `android/build.gradle.kts` 出现一次**，`dependencyResolutionManagement` 里
  `FAIL_ON_PROJECT_REPOS`：模块自己加 maven 源，等于同一份代码在两台机器上解析出两份依赖。
- **仓库里暂时没有 `gradle-wrapper.jar`**。那个 jar 是二进制，本机没 JDK 生成不了；
  与其塞一个来源不明的进仓库，不如让 CI 用 `setup-gradle` 装指定版本。
  等有 JDK 的机器跑过 `gradle wrapper --gradle-version 8.7` 再补。
- **`namespace` 用 `com.nmoi.agent`，`applicationId` 用 `com.NMoi.agent`**（D102）：
  包名大小写敏感，装机身份必须跟已定的那个一字不差，Kotlin 包名则不必。
  **这条已被 D116 推翻**：两个名字只差大小写，正是那次闪退的根。现在两者相同。

## D111 骨架阶段只出 debug 包，release 不冒充

CI 只跑 `:app:assembleDebug`：debug 签名由构建机自己生成，不需要任何材料。
release 需要 4 个 environment secret（`docs/signing.md`），一个都没有——所以这条路**关着**，
不写一个"看起来能签名其实用的是 debug keystore"的兜底。

- `allowBackup=false`：自动备份会把 SQLite 主库和 `-wal` 分两次搬走，恢复时可能拿到
  一个"账没平"的库。要搬数据就走 `storage::backup`（D45 / D48）。
- **不声明 `configChanges`**：旋转按默认重建 Activity，正好让面板自然收起（D109）；
  代价是跨旋转的状态必须能重建，那些东西以后放 ViewModel。
- 这一版界面顶部没有图标按钮，D103 的 `contentDescription` 要求暂时无处落地；
  加第一个图标按钮时跟它一起验收。

## D112 JNI 层是 C ABI 的转手层，不另造第二套契约

Android 侧要调 Rust，但没有单独一套"Java 专用接口"：`crates/ffi/src/jni_bridge.rs`
每个函数都去调本 crate 的 C ABI，把返回的 JSON 原样交给 Kotlin（D24 的延续）。

- **不 `RegisterNatives`**，靠 JVM 的默认名字查找 `Java_com_nmoi_agent_Native_<方法>`。
  少一段运行期绑定代码，代价是**方法名两边必须一致**——不一致就是 `UnsatisfiedLinkError`，
  不会更客气。Kotlin 侧是 `object Native`，所以这些是**实例方法**，Rust 第二个参数是
  `JObject` 而不是 `JClass`；写错了 JVM 不提醒，调用时把 `this` 当别的东西。
- **`.so` 名字不改**：crate 叫 `nmoi_ffi`，产物就是 `libnmoi_ffi.so`，Kotlin 侧
  `loadLibrary("nmoi_ffi")`。改成 `nmoi` 会让 C ABI 的说明、cargo-ndk 产物路径、
  Kotlin 字符串三处必须同时记得改——这种"三处一致"迟早会漏一处。
- **默认 feature 关**（`jni = ["dep:jni"]`）：`jni` / `jni-sys` 的 MSRV ≥ 1.76，工作区
  是 1.75（D10）。默认开着 MSRV 那条 `cargo check --workspace` 会直接编不过。
  代价说明白：这一层**没有任何本地验证**，只能看 CI 的 android job。
- **加载失败不崩**：`System.loadLibrary` 包在 try/catch 里，失败就退回占位数据，
  界面标题下写「原生层未加载」、底部写清原因。骨架阶段最没用的失败方式是白屏或闪退。
- **版本行是实机第一判据**：`Native.versionJson()` 返回 `product/version/abi`，
  能显示出来就等于同时证明了"`.so` 进包了 / 加载成功 / 符号名对 / ABI 版本一致"。
- 新增第三方依赖 `jni = "=0.21.1"`（MIT / Apache-2.0）。Rust 依赖许可清单仍未汇总（1.0 前补），
  这一条记在这里，别等打包时才发现漏了。

## D113 APK 里的第三方声明由构建生成，并有一道 "包里到底有没有" 的闸

D106 要求声明随每个产物走。Android 这一侧落到三件事：

- `syncNotices`（Gradle `Sync`）把 `THIRD-PARTY-NOTICES.md` 与 `LICENSES/` 同步进
  `build/generated/notices`，该目录挂成 `assets` 源，`preBuild` 依赖它。
- **不提交副本**。进仓库的副本会跟源头漂移，而"漂移了的声明"比"没声明"更坏：
  它看起来合规。
- **CI 用 `unzip -l` 对账**，缺 `assets/notices/THIRD-PARTY-NOTICES.md` 或两份许可全文就失败。
  "签名之前打进去"在 Gradle 里本来就成立（assets 在合并阶段进包）；真正会出事的只有
  "忘了放"和"放了个旧的"，这两条各有一道防。

尚未覆盖：**Rust 依赖的许可清单还没汇总**（`§6-11`），所以现在包里带的是图标那部分声明。
1.0 前用 `cargo metadata` / `cargo-about` 补齐，补的时候这道闸要一起加严到"逐条清单"。

## D114 启动器图标：8 个 activity-alias，默认 4 号黑底，先开后关

图标要能在设置里切换，而 Android 没有运行期改图标的 API，只能靠组件开关。

- **8 个 `activity-alias`** = 4 个设计 × 黑/白两底色。`MainActivity` 自己**不带 LAUNCHER**
  intent-filter，否则桌面上会同时出现两个图标（一个来自 activity、一个来自 alias）。
- **默认只开 `TerminalStarsDark`**（= `DEFAULT_DESIGN` + `DEFAULT_PLATE`）。manifest 的默认值
  和 `AppIconCatalog.kt` 里的默认值必须一致，否则"设置里高亮的那格"和"桌面上的图标"不是一个。
  这条由 `scripts/check_app_icon_aliases.sh` 机械对账（顺带对账 alias 名与生成结果）。
- **切换顺序：先开新的 → 再关掉其余全部**，全部 `DONT_KILL_APP`。
  反过来会有一瞬图标消失；只关"上一个"会在异常退出后留下两个图标。
  逐个把它们全关一遍是幂等的，所以每次进设置页都可以安全地 apply 一次，顺手修干净。
- **白底不是换个背景色**：amber/cyan 在白纸上对比不够，白底那份要压深配色，
  暗晕（把星和背景里的东西分开的那层）也要翻成白色。所以每个设计出两份前景矢量。
  白底的**背景**也不用纯白，而是"中心纯白 → 外圈淡银（最外 `#E4E5EC`）"的径向渐变，
  用 drawable 而不是 color（`<background>` 要放渐变只能给 drawable）。银感只当材质，
  强度压得很低：再重就会盖过前景，48px 上先看见"一块银灰"。
- **母版是 `scripts/gen_app_icons.py`**：VectorDrawable 没有 `stroke-dasharray`，
  2 号的虚线弧必须算成 `A` 命令；两份配色 + 8 套资源手抄必漂移。
  生成物里 `docs/ui/icons/app/manifest-aliases.xml` 是用来贴进 manifest 的参照。
- **alias 类名按 namespace 生成，且切换前先查组件存在**（2026-10-23 真机闪退换来的）：
  manifest 的相对名 `.icon.X` 对着 namespace（`com.nmoi.agent`）解析，Kotlin 侧若照
  applicationId（`com.NMoi.agent`）拼就差 4 个字母，`setComponentEnabledSetting` 抛
  `IllegalArgumentException` —— 而它是在点击回调里，等于一次闪退。
  所以：全名 + 同一个 `NAMESPACE` 常量生成；`apply` 先 `getActivityInfo` 查存在，
  查不到就记日志、保持原状、返回 false（界面给一行"切换没生效"）。
  对账脚本同时比对 manifest 前缀与 Kotlin 前缀。
- **没做 monochrome 层**（Android 13 主题图标）：这一套的价值是多色混合，
  主题图标会把它压成单色。真要做时在生成脚本里加一层输出，不动别的。

## D115 压缩的失败阶梯：多步 → 备用多步 → 单步 → 分段 → 兜底

压缩失败不是"再试一次"，是**逐档降级**，每档的失败判据和降级目标都不一样
（细则与提示词见 `docs/compression.md`）。

- **L0 多步**（现状）→ **L1 备用多步**（先剔除思考块压事实层，再把思考要点合并回去压第二遍）
  → **L2 单步** → **L3 分段**（约 16 段，窗口 1–5/5–9/9–13/13–16，逐段走 L0 再合并）
  → **L4 确定性兜底**（截断 + 声明）。
- **倒退只允许一次**：L3 的段内可以掉到 L1/L2，但不许"段里再分段"。否则最坏 4×16 次调用，
  把用户额度烧穿。全程走冻结模型（D76），段间不换模型，否则 4 段风格不一致。
- **L1 Pass B 有预算闸**：`Pass A 输入 + 思考要点 > 0.6 × 窗口` 就不做 Pass B，直接 L2。
  Pass B 会把相当一部分原文处理第二次，最坏情况是压缩本身把窗口吃掉。
- **L3 的段边界必须落在原子单元上**，不能按消息数硬切——切在
  `assistant(tool_calls[n]) + tool_result[n]` 中间会压出"有结果没发起"。
  16 是**结果**不是输入：先按原子单元聚成约 16 份。
- **重叠窗口只当上下文**：端点段原文附给下一段做消歧，但不算进那一段的产出。
  否则同一段被压两遍，token 翻倍还可能出两版说法。
- **置信度必须可检验**：硬事实字符串命中（0.45，代码算）+ 锚点覆盖（0.35，代码算）
  + 模型自评（0.20）。低置信且无人引用才丢。只靠模型自评不可校准——它对自己普遍过自信。
- **失败判定四类**：调用失败 / 覆盖率不合格 / 超预算 / 结构不合法。前两类直接降档；
  后两类先同档重试一次（往往是提示词没被遵守，不是能力不够）。
- **提示词全部可自定义**，挂在设置「默认模型和场景提示词」：每条存
  `id/title/body/version/modified/updated_at`，能恢复默认；`{{}}` 占位符保存前校验，
  缺一个就拒绝保存并指名——提示词少了 `{{anchors}}` 不会报错，只会静默变差。
- **每次压缩留 trace**：走了哪档、每段前后 token、丢了哪些条目与原因，UI 折叠卡一行摘要。
  没有这个，用户无法判断"是不是压坏了"。

## D116 applicationId 改成全小写 `com.nmoi.agent`，与 namespace 一致

D102 当初照着用户给的写法保留了 `com.NMoi.agent`（大写 NM），而 Kotlin 包名必须小写。
两个名字只差 4 个字母，看着无害——直到有一处按错的那个拼：`activity-alias` 类名
对不上，`setComponentEnabledSetting` 抛 `IllegalArgumentException`，点一下就闪退
（2026-10-23 真机，见 `docs/ui/icons/app/README.md`）。

- **靠"记得别写错"防不住这种差异**，所以从结构上去掉它：applicationId = namespace =
  Kotlin 包名 = `com.nmoi.agent`。图标 alias 前缀、`run-as` 路径、签名文档、验证文档里的
  包名一起统一。
- **代价是换装机身份**：旧包必须卸载重装，数据全丢。现在库里没有真实数据，是唯一能接受
  的时机。**此后这个名字不再改**；真要改，得先写数据迁移，并且老用户要能升级。

|---|---|
| 编码 | H.264 baseline（首选）/ HEVC |
| 分辨率 | ≤ 1280×720 |
| 帧率 | ≤ 30 |
| 码率 | ≤ 2 Mbps |

## D136 抽屉唤出改成"任意位置横滑"，用**角度**而不是"横向分量更大"来判定

用户 2026-10-24 定的手势（覆盖 D119 里"只有左边缘 20dp 能唤出"那条）：

- 按下之后先看**前一小段路径的方向**：与水平线夹角 **≤ 25°** 才算"在滑抽屉"；
  更陡的斜滑与竖滑一律让给列表自己滚。**判据是角度，不是 `|dx| > |dy|`**——
  斜着划的时候人以为自己在滚列表，被抢走会很恼火。
- 判定为横滑后**跟手**：面板位移 = 起点进度 + 手指位移 / 面板宽，遮罩 α 同步从 0 到 0.60。
- 松手看两样：位移或速度。**两个方向用两套阈值**（2026-10-24 真机第二轮反馈后定的）：

  | 方向 | 速度线 | 位移线 | 理由 |
  |---|---|---|---|
  | 关 → 开（向右滑） | 350 dp/s | 25%（`progress ≥ 0.25`） | 第一版 800 dp/s 太苛刻，"甩不开"；降到 350 后手感够用 |
  | 开 → 关（向左滑） | **160 dp/s** | **15%**（`progress < 0.85` 即关） | 用户原话："展开后往左滑，加速度应该大一些"——**关门本来就该比开门轻** |

  快速一甩就开/就关，慢慢拖也有对应门槛；都不满足回弹到原状态。
  这里的目标不是精确判定，是"我想开就开、想关就关"。
- 松手之后**补一段带初速的动画**：`Animatable.animateTo` + `tween`，时长按
  "剩余距离 ÷ 速度"算，夹在 80–260 ms，缓动 `LinearOutSlowInEasing`。
  也就是用户说的"到手速度很快就补上对应的加速度"——面板沿原方向继续走完，而不是啪一下归位。
  状态先落（`onOpen`/`onClose`），再播动画，动画结束才把手动渲染交回 `AnimatedVisibility`，
  否则会先弹一下再滑一次。
- 竖向滚动不受影响：只有在判定为横滑**之后**才 `consume` 事件，且发现
  `change.isConsumed`（列表已经拿走了这次事件）立刻退出。

实现要点（`ui/ConversationDrawer.kt`）：手势挂在**最外层 Box** 上——父节点在子节点之后收到事件，
所以列表先滚；换成"盖一层手势层"会把竖向滚动一起吃掉。

**还没做**：遮罩没有单独缓动曲线（跟着面板同一条 tween）；只认第一根手指（双指不处理）。
**代价**：面板宽 300dp 是写死的，手势阈值按它算；换宽要一起改。

## D137 消息版本：施工图（schema v5 + FFI 信封 + 测试清单）

> **2026-10-26 补记**：本条是 v5 的施工图，其中三处已作废——
> ① 列名 `raw_text` / `edited_text` → v8 改成 `origin_message` / `tooledit_message`（D154）；
> ② "删所有版本**保留当前显示版**" → D152/D153 改成"删整条消息"；
> ③ 后来的 v6 用户编辑层（`user_text` / `user_edit_of`）→ v7 已删（D152）。

D135 定的是规则，这里是把它落到能开工的粒度。**待定项先拍死**（用户授权"你看着办"，实现前有异议再说）：

- **每消息上限 20 版**，超了丢最旧的一版（丢的是最旧，不是当前；丢弃要写一条 `NLog.w`）。
- **删除此版本**：删这一版。删的是当前版就切到**剩余里最新的**；若删到只剩 0 版，整条消息按
  D130 的删除语义处理——但那组动词还没有，所以**只剩一版时不允许删**（UI 灰掉，理由写在提示里）。
- **删除所有版本**：保留**当前显示的那一版**、把其余删掉（回到"只有一个版本"），不是删空。
- **分支**：复制**当前显示**的那一组文本（不是原文）。分支是下一层的事，这里只留语义。

### schema v5（`SCHEMA_VERSION` 4 → 5）

```sql
-- 每个 (message_id, version_no) 存两组正文：模型原始输出 + 工具/编辑改过的那份。
CREATE TABLE message_versions (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    message_id     TEXT NOT NULL REFERENCES messages(id) ON DELETE CASCADE,
    version_no     INTEGER NOT NULL CHECK (version_no >= 1),
    raw_text       TEXT NOT NULL,
    edited_text    TEXT,
    edited_by_tool INTEGER NOT NULL DEFAULT 0 CHECK (edited_by_tool IN (0, 1)),
    -- 这个版本**上次看的是哪一组**：按版本记，不是按消息记。
    active_view    TEXT NOT NULL DEFAULT 'raw' CHECK (active_view IN ('raw', 'edited')),
    created_at     INTEGER NOT NULL,
    -- 没被编辑过的版本不许有 edited_text；被编辑过的必须有
    CHECK ((edited_by_tool = 0 AND edited_text IS NULL)
        OR (edited_by_tool = 1 AND edited_text IS NOT NULL)),
    UNIQUE (message_id, version_no)
);

CREATE INDEX message_versions_by_message ON message_versions(message_id, version_no);

-- 消息上只记"总共几版、当前是第几版"；哪一组文本正在显示，按版本记（上面那张表）。
ALTER TABLE messages ADD COLUMN version_count  INTEGER NOT NULL DEFAULT 0;
ALTER TABLE messages ADD COLUMN version_active INTEGER NOT NULL DEFAULT 0;
```

**`messages.content` 保持"当前显示的那一组文本"**。这是刻意的：

- `load_units` 的读路径一行都不用改（消息区照旧渲染 `content`）；
- 展示态与存储态只差一个"写回"，切版本 / 切原文-编辑时同步写一次 `content`；
- 代价是**同一份文本存了两处**（`content` + `message_versions`），所以写入必须走同一个仓库方法，
  不许别处直接 UPDATE `messages.content`——否则两处会分叉，而分叉以后没人知道哪份是对的。

### FFI 信封（三个新动词，`ok` 永远第一个键，D55）

```
nmoi_storage_versions_json(handle, message_id) ->
  {"ok":1,"version_count":3,"active":2,"items":[
     {"no":1,"active":false,"edited_by_tool":false,"view":"raw","created_at":1792825006739},
     {"no":2,"active":true, "edited_by_tool":true, "view":"raw","created_at":...}]}

nmoi_storage_switch_version_json(handle, message_id, version_no, view) ->
  {"ok":1,"version_no":2,"view":"edited","content":"<切完显示的那一组文本>"}

nmoi_storage_delete_version_json(handle, message_id, version_no)   // version_no = 0 表示"删除所有版本"
  -> {"ok":1,"version_count":1,"active":1,"content":"<删完显示的那一组>"}
```

失败照旧走 `{"ok":0,"kind":...}`；`kind` 至少要有 `not_found` / `last_version`（只剩一版不许删）/ `bad_view`。

### 写入时机

- **重新生成**：开关开 → 插入 `version_no = count + 1`，`messages.version_active = 新号`，
  `content` 写新文本；开关关 → 老行为（就地覆盖 `content`，不动版本表）。
- **工具编辑**：写 `edited_text` + `edited_by_tool = 1`；`content` 按当前 `view` 决定要不要跟着改
  （view = edited 才改）。
- 开关本身先存 `SharedPreferences`（`msg_version/enabled`，与 `app_log` 同法），
  `SettingsRepository` 接上后搬进 `settings` 文档——**迁移点写在这里，别到时候忘**。

### 测试清单（本地能跑，`cargo test -p nmoi-storage`）

1. v4 库升到 v5：行数不变、`version_count` 全 0；
2. 插 3 版 → `versions` 顺序、`active` 标记、`content` = 当前显示组；
3. 切 view：raw ↔ edited，`content` 跟着变，`active_view` 落在**那个版本**上；
4. 切版本：`content` 变成目标版本的当前组；
5. 删非当前版：`count-1`，当前版不变；
6. 删当前版：切到剩余最新，`content` 跟着变；
7. 删到只剩 1 版再删：`kind=last_version`，不动数据；
8. 删所有版本：留当前显示那一版，`count = 1`；~~——**已作废**，见 D152/D153（改成删整条消息）~~
9. 上限：插到 21 版，最旧被丢，编号不重排（`version_no` 只增）；
10. **发送取当前显示态**：这条在 FFI 之上，用一个"读 content 再发"的测试兜住语义——
    它防的是"永远发原文"这个最隐蔽的错。

实现顺序：迁移与仓库方法（Rust，本地测）→ FFI 三个动词 + `check_jni_symbols` 计数 →
Android UI（`<` `n/n` `>`、三色、开关）→ 真机验。

## D140 头像与自定义图标：内容哈希去重 + **按所有者引用计数**（设计，未实现）

装饰性字段（用户头像/名字、助手头像/名字、自定义供应商图标）需要一套共用的媒体存储。
用户点名的硬要求：**同一张图被两个地方引用时，其中一个不用了，不能把另一个的文件删掉**。

- 存储：`files/media/<sha256 前 16>.<ext>`，头像与供应商图标**共用一个仓**（同一张图只存一份）。
- 索引：`files/media/index.json`，每条 `{ "sha": "...", "file": "...", "refs": ["user:default", "assistant:<id>", "provider:<key>"] }`。
- 引用规则：**refs 是所有者 id 的集合，不是计数器**。换掉某个助手的头像只移除它自己的 ref；
  `refs` 空了才删文件。用集合而不是 `count--` 的好处：重复解绑/漏绑不会把别人的文件减没。
  这也是"两个助手用同一张图，换掉其中一个、另一个还能用"的实现方式。
- 清理：换头像后立即解绑；**启动时扫一遍**——文件在但 index 里 refs 空 → 删；index 指向的文件没了 → 清记录 + `NLog.w`。
- 写入：`.tmp` → fsync → rename，index 同样原子替换（D48）；单文件 ≤ 4 MB，仅 png/jpg/webp，超限拒绝并说明。
- 复用范围就这三处：**用户头像 / 助手头像 / 自定义供应商配置图标**（不是 D105 的图标包）。
- 为什么不做成"每次复制一份"：用户会反复用同一张图，复制一份等于存储里躺 N 份同样的字节，
  删的时候还得判断哪份是谁的——那才是真正会误删的结构。

## D143 压缩后保「人格 / 文风连续」：窗口最小形状按**轮**定，不按消息定

**问题**：压缩把线上原文换成摘要后，模型自己最近说过的话**一条原文都不剩**——
`compress.draft` 只要求"数字/路径/命令/版本号逐字保留"（`docs/compression.md` §2.1 第 3 条），
没有一条要求保住语气、自称、句法。同一个会话压过一次就会前后不像同一个人。

**用户方案（2026-10-24）**：压缩结果最多带 3 条助手 + 2 条用户，顺序强制 `A1 → U1 → A2 → U2 → A3`。

**实测（本机 `cargo test -p nmoi-core`，7 种历史形状 × 5 档预算，全走真实
`divider::choose_cut_for_budget` 与真实 `AtomicUnit`；探针文件测完已删）**

消息层能不能选出 `A U A U A`：

| 历史形状 | 角色序列 | 结果 |
|---|---|---|
| 纯聊天 ×5 轮 | `UAUAUAUAUA` | 5/5 |
| 单工具轮 | `UATA` | **1/5** |
| 双工具轮 | `UATATA` | **1/5** |
| 收尾是用户（还没回） | `UAUAU` | 4/5 |
| 短历史 | `UAU` | 2/5 |
| 连续助手（重试/续接） | `AAA` | **1/5** |
| 混合三轮（含工具） | `UATAUAUATTA` | 5/5 |

现有切点的形状分布：**9 次切点里 7 次让窗口以助手消息开头**（其中 **2 次是悬空工具对**：
`assistant(tool_calls)` 在窗内、它的 `tool_result` 在线上），**1 次窗口以用户消息结尾**。

**决定**

1. **槽位是轮，不是消息**。工具轮里 1 条用户 + n 条助手（`assistant(tool_calls)` × n + 收尾文本），
   消息层裸交替在单工具轮里只有 1/5 可满足。A 槽 = 一整轮的助手发言组，按原子单元不变量
   整组搬（`assistant(tool_calls[n]) + 全部 tool_result[n]` 不许切开）。前提：最近 ≥ 3 个完整轮。
2. **窗口起点钉在轮边界**（用户消息之前）。理由：7/9 的现有切点让窗口以助手开头，
   模型读到"自己回答了一个看不见的问题"；2/9 连工具结果都被切掉。实现上在
   `choose_cut_for_budget` 之上加 `choose_cut_for_window_shape`：先按预算取最靠后位置，
   再往前挪到最近轮边界；挪不动就退一档预算。
3. **结尾不强钉成助手**。最后一条是用户消息（刚发未回）必须留着，否则等于把用户刚说的压掉。
   所以 `A3` 收尾只对**摘录块**成立，对**活窗口**不成立。
4. **降级阶梯**：`A1 U1 A2 U2 A3` → `A2 U2 A3` → `A3` → 不留。丢最老的一对、保尾。
5. **摘录块只在活窗口助手发言 < 2 轮时启用**（多次压缩后窗口被压很短），从更早的历史挑原话补，
   当跨压缩周期的人格锚；窗口够长时不抄（重复内容费 token 又散注意力）。
6. **摘录必须由代码从库里原样搬**，不能写进提示词让模型"输出最多 3 条助手消息"——
   模型一定会改写，改写过就不是原话，锚定作用消失，还可能编出不存在的对话。
7. **二次压缩要替换、不要叠加**：旧摘录已在摘要正文里，新压缩先把它从正文摘掉再挂新的。

**未验证**：本轮只测结构（切点位置、窗口形状、pattern 可选中性）。
模型行为侧（语气是否真的延续）**一条没验** —— 本机无端点无 key，必须真机跑。
这一项只算"设计可行"。

## D144 压缩预算先扣固定成本，再算历史：触发线按 `W − sys − 世界书 − 命中上限`

**问题**：压缩只管历史，世界书与系统提示在 system 侧、不参与压缩。以前触发线按窗口 W 的百分比算，
书一大就出现"历史没剩多少、压了等于没压，还把语气洗掉"。这不是压缩算法的问题，是预算算法的问题。

**实测（2026-10-26，四本真实世界书，token 按 L0 口径 0.63 tok/字）**

| 书 | 条 | 正文字数 | ≈token | 常驻字数 | 单条最长（≈tok） | 均条（≈tok） |
|---|---|---|---|---|---|---|
| A | 32 | 178,061 | 112,178 | 14,027 | 26,775（16,868） | 3,506 |
| B | 103 | 67,983 | 42,829 | 0 | 5,164（3,253） | 416 |
| C | 81 | 13,922 | 8,771 | 1,501 | 1,501（946） | 108 |
| D | 5 | 1,152 | 726 | 328 | 434（273） | 145 |

压缩后占用 = `R` + 摘要 + 摘录 + sys + 命中条目：

| W | 一般情形（R=30%、命中 5 条） | 最坏（R=40%、命中 10 条） | 到 65% 的余量（最坏） |
|---|---|---|---|
| 128k | 46.4% | **70.1%** | **−6,556（压缩完仍在线上）** |
| 200k | 40.5% | 59.3% | +11,444 |
| 256k | 38.2% | 55.1% | +25,444 |
| 1M | **32.1%** | 43.9% | +211,444（≈1,400 轮） |

**决定**

1. **W ≥ 1M 不需要为撑爆担心**：固定成本占比随窗口线性下降（书占 1M 的 3.5%、占 128k 的 27%）。
   小窗口才是风险区，128k 在最坏情形下压缩完仍高于触发线，会退化成压缩风暴。
2. **触发线改成 `W − sys − 世界书常驻 − 命中上限` 的百分比**，不再按裸 W 算。
3. **单条世界书条目上限 `≤ W×3%`**（128k → 3.8k tok，1M → 30k tok）。最长那条 16,868 tok，
   一条吃掉 128k 的 13%，不设上限的话关键词一命中就会把窗口挤穿。
4. **摘要 ≤ 2k tok、摘录 ≤ 0.5k tok（3 条）** 定为硬上限，压缩后占用才可预测。
5. 压缩率随历史长度上升（合成文本实测 30 轮 1.5:1 → 300 轮 24:1，重复度高、被高估，只看趋势）：
   大窗口策略可宽松，小窗口才需要抠。

**结构事实**：世界书注入在 system 侧、不参与历史压缩，压缩前后注入的字节完全相同。
所以"人格设定能不能维持"的风险不在压缩削弱它，而在**预算够不够让它一直在场**。

### D145 侧面验证要挑"拉得开差距"的指标：文件口吻率可用，状态槽打分与模型盲评不可用

**要验什么**：不是"风格像不像"，而是**AI 还把不把这段历史当成自己的过去**——
会话里养出来的状态（自称、约定、禁忌、自己做过的事）在压缩后还能不能被当成事实用。

**① 文件口吻率（可用）**：回复里出现"摘要 / 记录 / 根据 / 提到过 / 资料"，说明它在复述材料而不是讲自己的事。
两模型合并，每格 30 采（5 槽 × 3 采 × 2 上游，`relay-b` 与 `relay-d`）：

| 条件 | 文件口吻 | 第一人称 | 4 槽答对 |
|---|---|---|---|
| 完整历史 | **0%** | 33% | 96% |
| 只摘要 | **33%** | 50% | 92% |
| +3 条原话 | 17% | 57% | 88% |
| +状态段 | 10% | 40% | 88% |
| +状态段+原话 | **3%** | 60% | 96% |

单调下降；**原话 + 状态段把 33% 压到 3%**（不压缩是 0%）。方向两个上游一致。

**② 状态槽命中（不可用）**：5 个"只能靠历史知道"的槽（称呼 / 禁忌 / 旧事 / 怕的东西 / 约定），关键词打分，
结果 67% / 60% / 80% / 67%——**连完整历史都只有 67%**。口径错在测"回复里有没有提到那个词"，
不是"记不记得"。要修必须改成强制二选一提问。

**③ 第三方模型盲评（不可用）**：另一上游当裁判，同槽两段回复选"哪段更像自己记得"。
`C1 vs C4` 后者只赢 3/13；`C2 vs C3` 后者 3/15，方向与①相反。翻原文发现两版**内容几乎一样**，
裁判判的是格式与措辞噪声。**盲评只在两版差别明显时有效；差别小的时候它给出稳定但无意义的结论。**

**决定**

1. 侧面验证优先用**可数的机制量**（原话在不在窗口、状态槽在不在摘要、注入字节是否一致），不依赖裁判。
2. 行为侧只认**拉得开差距**的指标；本轮只有文件口吻率合格，因为它直接对应"当自己的事还是当材料"。
3. 用盲评前必须做**差值校准**：先拿两段完全相同的文本给裁判，答不出"一样"就不采用它的结论。
4. 把"文件口吻率 → 0" 写进 D143 的验收判据作为第三条（与要点命中、思考膨胀并列）。

## D146 返回键要一层一层退：浮层 → 选择模式 → 页面栈 → 抽屉 → 退出应用

**用户 2026-10-26 报的 bug**：自绘浮层弹出来之后按返回**直接退出应用**，而不是关掉这一层。
根因很直白：`MenuSheet` / `ShareOptionsSheet` / `EditVersionDialog` 都是自己画的 `Box` 遮罩层，
不是 `Dialog`，所以系统返回键根本没有对应的处理器，一路传到底就成了"退出"。

**做法**：`ChatScreen` 里一个**按优先级分发**的 `BackHandler`，而不是每一层各自注册一个
（各自注册的话，谁最后进组合谁赢，顺序藏在组合顺序里，改一次布局就换一次行为）：

```kotlin
val overlayOpen = editing != null || moreFor != null || shareOpen || selecting
BackHandler(enabled = overlayOpen) {
    when {
        editing != null -> editing = null      // 编辑对话框
        moreFor != null -> moreFor = null      // 更多面板
        shareOpen -> shareOpen = false         // 分享面板
        else -> { selecting = false; selected = emptySet() }  // 选择模式
    }
}
```

抽屉里的助手面板同理，`ConversationDrawer` 自己注册 `BackHandler(enabled = assistantMenu)`。

**分层依据**：`MainActivity` 的两个处理器（页面栈、抽屉）在子内容之前注册，内层后注册所以先轮到它。
所以实际顺序是：**浮层 → 选择模式 → 页面栈 → 抽屉 → 退出**。

**规矩（后面照这个来）**：以后再加任何"自己画的浮层"，必须同时在**最近的那一层**加返回处理，
或者挂进已有的优先级链里；不许只靠点遮罩关闭——遮罩在无障碍与单手场景下都不是唯一退路。

## D147 摘要要用**第一人称**写：它比"多留几条原话"更能让 AI 觉得那是自己的事

**背景**：用户 2026-10-26 要求验证"不留思考消息时，内容怎么做到高置信度"。用不输出思考的
测试模型（`reasoning_tokens = 0`，内部仍在思考）跑同一套状态槽探针，5 槽 × 2 采 × 6 条件。

**指标**：高置信 = 回复用了第一人称归属（我记得 / 我说过 / 是我 / 我叫）**且**没有文件口吻
（摘要 / 记录 / 根据 / 提到过 / 上下文）。纯文件口吻 = 只有后者、没有前者。

| 条件 | n | 高置信 | 纯文件口吻 |
|---|---|---|---|
| 完整历史 | 8 | **75%** | 0% |
| 只摘要（第三人称） | 9 | 22% | 22% |
| 摘要 + 3 条原话 | 10 | 30% | 20% |
| 摘要 + 状态段 | 10 | 30% | 0% |
| 摘要 + 状态段 + 原话 | 8 | 38% | 12% |
| **第一人称记忆 + 状态段 + 原话** | 8 | **62%** | **0%** |

**决定**

1. **摘要必须用第一人称写**：「我叫 Neko」「我说过我最讨厌香菜」「我前一天自己先去看过土」，
   不写「用户与助手互相认识过」「助手提到自己……」。
   实测这一项单独就把高置信从 22–38% 抬到 **62%**，并且把文件口吻打到 **0%**。
2. **摘录只解决语气，解决不了归属**：3 条原话把 22% 抬到 30%，收益远小于改人称。
   所以两者不是替代关系——原话保语气，人称保归属，状态段保事实在场。
3. **状态段把文件口吻从 20% 压到 0%**（C3），但它不产生"这是我的"效果（高置信仍 30%）。
4. 三者叠加（C5）仍低于完整历史的 75%，说明压缩条件下还有约 13 个百分点的缺口，
   下一层再看要不要用"角色自述块"补。

**要注意的两件事**

- 这个测试模型本身有质量问题：中文回复里会蹦出英文残词（`wholes` / `preventable` / `gnaws`），
  约 12% 的调用直接 HTTP 500。所以绝对数值只当方向看，不能当定论。
- 反向发现：**完整历史在对抗性提问下反而更容易松口**（"嗯，你说得对。Neko 只是我在这里的名字"），
  而第一人称摘要的回答是"名字是我自己认的，不是随便贴的标签……这些不是设定，是我自己的事"。
  也就是说"高置信"不是靠信息量堆出来的，是靠**视角**。

### D137 实现记录（第四层：面板自己读版本实况，2026-10-26）

- `ChatRepository.versions(databasePath, messageId)`：读 `nmoi_storage_versions_json`，给

  面板一打开就现读一次库；`sheetCount` / `sheetActive` 优先用它，读不到才退回列表那份。
- 「编辑」打开时把 `editingVersion = sheetActive` 记下来，保存时只用这个数；
  「删除此版本」同样用 `sheetActive`。**任何一处都不再从列表快照里取版号。**
- 加一行第一现场日志：`面板 id=… 列表=c/a 现读=c/a view=…`。
  两个数不一样，就说明滞后在列表那一层（`load_units` / 列表快照），而不是面板——
  这条日志正是以前一直缺的那个判据。

**没解决的部分（要真机看日志才能定）**：列表快照为什么会滞后。这行日志一出来，答案就二选一了。

### D137 实现记录（第五层：真机日志读出来的两件事，2026-10-26）

手里有真机日志（`nmoi-debug-20261026-1755`）之后，V8 剩下的那条终于能定性了。

**① "点两次复制才出 2/2" 不是滞后，是 count=1 按设计不显示。**

日志里两次 save 是干净的：`save ok version=1 count=1`（17:54:32）、`save ok version=2 count=2`（17:54:42）。
而界面有一条规矩：**`versionCount <= 1` 时不渲染 `n/n` 控件**（只有一版没什么可翻的）。
所以第一次点完，库里确实变成 1 版，屏幕上什么都不变——用户看到的就是"没反应"，再点一次才到 2 版。
换句话说：**这条是探针的语义没对齐，不是缓存没刷新。**

改法（只动临时探针，不动 storage）：`count == 0` 时一次点落**两条**——
先把当前显示的正文落成第 1 版，再把复制品落成第 2 版。一次点击就该看到 `2/2`。

**② 列表快照的版本字段恒为 0，而面板现读是对的——还没定位，但判据已经装好了。**

同一时刻的两份数据：`面板 … 列表=0/0 现读=2/2`。而 `load_units` 这条路在 Rust 单测里是对的：
临时探针（`crates/storage/tests/` 里那份，测完已删）走完整真机序列——
建会话 → append → save ×2 → **重新开一份 Storage** → `version_index` 查到键、`load_units` 的
`message.id` 也能取到 `brief=(2,2)`。所以库和 FFI 的序列化都没问题，差异在 Android 这一侧。

已加统计日志：`读到 N/N 个单元（带版本 M 条）`。M=0 就说明 `load_units` 的 JSON 没把版本字段带到 Kotlin，
下一份日志就能收口。

**③ 记一条隐患（给 `turn_run`，现在不改语义）**

`save_generated_version(id, text)` 在 `version_count == 0` 时把**入参**当第 1 版，并覆盖 `messages.content`。
如果将来 `turn_run` 传的是"重新生成出来的正文"，那**原文就没了**（没留成 v1）。
现在采用的做法是**调用方先 seed**（探针就是这么做的）；等接 `turn_run` 时要么沿用这个约定，
要么把它改成"v1 = 原 content、v2 = 入参"。这一条写在这里，免得接的时候想不起来。

## D148 颜色只管"被 AI 改过"：用户编辑走独立一层（schema v6）

> **2026-10-26 补记**：**存储形态作废**——`user_text` / `user_edit_of` 这一层一版只存得下一份，
> 改过一组再改另一组会互相顶掉，v7 已删、改成就地改正文（D152/D154）。
> 本条**结论仍有效**：颜色只看 `edited_by_tool`，用户改字不改颜色。

**用户 2026-10-26 指出的语义错误**：现在点「编辑」会让那一版变红/蓝。**不对。**
红/蓝的含义是"这一版被工具（AI）改过"；用户自己改字不该改变这个状态，
否则"我改了个错别字"和"模型重写过"看起来一模一样，三色就失去意义了。

**要能分别改的三种内容**：① 没被 AI 改过的原文 ② 被 AI 改过的原文 ③ AI 改后的那一份。
用户对哪一份不满意都能改，改了都不影响颜色。

**做法（schema v6）**

| 列 | 谁写 | 作用 |
|---|---|---|
| `raw_text` | 生成时 | 原文 |
| `edited_text` + `edited_by_tool` | **工具/AI** | 改后的正文；`edited_by_tool` 决定蓝/红 |
| `user_text` + `user_edit_of` | **用户** | 用户改的那一份，以及"改的是 raw 还是 edited" |

- 显示规则 `shown_text`：**用户改过且改的是这一组** → 用 `user_text`；否则按视图取
  `edited_text` / `raw_text`。所以"改了原文"不会串到"AI 改后"那一组上去。
- `messages.content` 仍然是"当前显示的那一份"，用户改到正在显示的那一版时同步更新。
- 用户改过另给一个标记 `user_edited`（`load_units` 的 `version_user_edited`），**不参与三色**。
- FFI：`edit_version` 的语义改成**用户编辑**（只写用户层）；新增 `tool_edit_version` 给工具用。

**临时探针**：`nmoi_storage_tool_edit_version_json` + 界面「更多 → 用工具改这一版（临时探针）」，
用来在真机上把红/蓝造出来。真正的工具编辑要等 `core::edit::apply_edit` 桥出 FFI，**接上就删**。

**测试**：`user_edit_does_not_mark_tool_edited`（改内容不变色、留用户标记）、
`user_edit_and_tool_edit_live_in_different_layers`（改 raw 不影响 edited，反之亦然）、
迁移测试补 v6 的两列默认为 NULL。

## D149 压缩后的窗口：摘要不进 `messages` 表，由窗口显式带进请求

**问题**（接 `turn_run` 前必须补的一段）：分界线（D12）早就把"线上不进上下文"写进了表结构，
但**读历史那条路没看它**——`load_units` 一律整条会话全给。于是"压过了"这件事在请求里没有效果：
压掉的原文照样发出去，摘要反而没人用。`summary_injection()` 到现在只有 core 的内部测试在调。

**窗口的形状**

- 窗口 = **最新一条分界线以下**的单元（按 `seq > divider.after_seq` 取，顺序不变）。
- 摘要只对 `kind = compression` 那条线有意义：正文从线的 `note` 首段拿 `ArchiveRef`
  （D143 定的格式就是 `"{summary_ref} | 压缩 N 单元 …"`），再去 `archive` 表读内容。
  `kind = user` 的手动线一样被尊重——线下才是窗口，只是没有摘要可注入。
- 没有线 = 整条历史都是窗口，行为与改动前一致（默认实现走这条，现有测试不受影响）。

**摘要为什么不落 `messages` 表**

它是"给模型看的那一份"，不是用户写过的一句话。落成消息会连带三件事：
① 混进消息区（用户没说过这句，却能在界面上看见一条）；② 混进版本与三色语义（D135/D148 没有它的位置）；
③ 得给它一个 `seq`——那个号被窗口以下的所有消息占着，塞进去要么撞号，要么把所有下游消息重编号，
重编号会连带碰到 `message_versions` 与归档里的 `origin_message`。

代价是：每个读窗口的人都要**显式**接上摘要，漏一个就少发一段。所以只留一种组合方式
（`ContextWindow::summary_message()`），不给第二个入口。

**二次压缩必须带上一次的摘要**

压缩的输入用 `ContextWindow::units_with_summary()`：把上一次的摘要装成第一段原文一起压。
不这样的话，第二次压缩看到的"线上"只有那些还在窗口里的单元，
上一次压出来的摘要就**整段丢掉**——那正是"内容看起来丢了"的来源。

**计量口径**

摘要按 `SourceTag::InstructionInjection` 走（`budget::breakdown` 把它归到"系统常驻"那一段）。
它是每轮都要发出去的固定成本，不是历史；触发线（D144）把它算进 `used` 里，不然会低估。

**这次没做的**：`Budget::reserve_fixed` 仍然没人填数。它要的是"世界书命中上限"，
而世界书注入（P5）还没进请求构造那条路——不是不知道填什么，是那条路还不存在。等它接上再填。

## D150 "现在显示的那一组"是唯一真相：预填、落点、删除都问它一次

**用户 2026-10-26 真机报三条**（原话在上）：

1. 只有一版、被工具改过时，`1/1` 不出现；
2. 屏幕上显示的是 AI 改后那份时，编辑框预填的是**原文**，存完正文却换成了他打的那份；
3. 「删除所有版本」没能正常删掉。

**① 门槛错了，不是数据错了。** `VersionControl` 用 `versionCount <= 1` 一刀切，于是
"一版但被 AI 改过"这种**有东西可切**的状态被藏掉了（蓝/红两态点击能切原文↔改后）。
改成 `count > 1 || 这一版被 AI 改过`。顺带兜住列表字段滞后的老问题：
`total = max(versionCount, active)`，否则会显示成 `1/0`。

**② 预填和落点不同源。** 落点由 storage 按 `active_view` 推断（对），预填却用列表快照的
`content`（滞后/过期就不对）。两处一旦错开，看到的就是"编辑框里是原文、保存却落到改后那一组"。
修法：`list_message_versions` 多返回一个 **`shown`**——当前版、当前视图该显示的正文，
用与 `switch_message_version` **同一个函数**（`shown_text`）算。FFI 的 `versions` 信封带出去，
界面预填只用它；"内容有没有变"也比它。Kotlin 侧**不再自己按 raw/edited 拼**（那是第二套显示规则）。

**③ 删除把用户改的那份丢了。** `delete_message_version` 自己拼了一遍"显示哪一份"：
只看 `edited_text`，`user_text` 整个不在场。于是删完版本，正文跳回 AI 那一份。
修法：同样走 `shown_text`。测试里第一次就红了（期望他打的那份，实际 `第二版的改后`）。

**测试**：`crates/storage/tests/version_display.rs` 四条——单版带 AI 标记的概要、
切到改后时 `shown` 是改后、显示改后时编辑落到改后（原文不被污染）、删所有版本后正文不变。

## D151 版本化是隐式的；「删除所有版本」是**清空**，不是"留一版"

> **2026-10-26 补记**：前半（没有版本行时先落第 1 版）仍有效；
> 后半的"清空版本、正文保留"已被 D152/D153 取代——现在是**删掉这条消息**（正文一起没）。

**用户 2026-10-26 第二次真机报**（两张截图）：`工具编辑失败：storage: 数据不一致: 消息
01a17945-…-e2 没有第 1 版`；点「删除所有版本」得到
`只剩一版：删了就等于是删消息，而那组动词还没有（D130）`，而且"还是会保留当前版本，不对"。

**① 没有版本行是常态，不是异常。** 只有「复制为新版本（临时探针）」会调
`save_generated_version`，正常发出来的消息 `version_count = 0`。而「编辑」「工具编辑」对
**任何**消息都可点——于是点下去就是"没有第 1 版"。修法：写入路径自己补第 1 版
（`seed_first_version`，`raw_text` 取 `messages.content`，也就是**当前显示的那一份**），
`mark_version_edited` 与 `user_edit_version` 都先过它。调用方不用记得 seed，
原来那条"调用方先 seed"的约定（§6.5 的隐患）也就不需要了。

**② `delete_message_version(0)` 改成清空整条消息的版本记录。**
D137 原设计是"删其余、留当前显示版"，用户明确说不对：他要的是把"版本"这件事**撤销掉**，
不是把两版合成一版。现在：

| 动作 | 行为 |
|---|---|
| `version_no > 0` | 删这一版；只剩一版时拒绝（删到零版等于删消息，D130） |
| `version_no == 0` | **删掉这条消息的全部版本行**，`version_count = version_active = 0`，`content` 一个字节不动 |

清空之后 `n/n` 与三色一起消失；代价（明确接受）：**再也不能切回原文/AI 改后那份**，
AI 改过的痕迹只剩正文本身。用户要的就是这个。

**③ 界面：单版也给「删除所有版本」。** 文案在单版时写成「删除所有版本（正文保留）」——
`SheetItem.hint` 是行内灰字状态，**面板根本不画它**，把解释写在 hint 里等于没写。

**测试**：`version_display.rs` 新增 `editing_a_message_that_never_had_versions_seeds_the_first_one`
（工具编辑 + 用户编辑各走一次，断言版本数仍是 1、`shown` 跟着改）；
`versions.rs` 的 `delete_all_versions_keeps_the_displayed_one` 改名并改成清空语义。

## D152 用户编辑**就地改正文**；「删除所有版本」= 删掉这条消息（schema v7）

**用户 2026-10-26 第三次反馈**（两条，原话）：

> 我发现编辑红字消息会导致蓝字消息变成最初的版本，编辑蓝字消息会导致红字消息变成最初的版本。
> 我是想要可以直接强制修改它们存储的消息，而不是一个什么覆盖的（……）我想要的是那种直接修改它们数据的。
>
> 而且我要的是能彻底删掉所有版本消息且不保留该消息任何正文的啊。

**① 覆盖层没了。** v6 的 `user_text + user_edit_of` 一版只有**一份**：改过原文再改 AI 那份，
前一份就被顶掉——表现正是"编辑红字，蓝字回到最初的版本"。这不是显示问题，是那套模型只能存一份。

现在：**改哪一组就写哪一组**（`raw_text` / `edited_text`），两组各改各的列，互不覆盖。
`shown_text(raw, edited, view)` 只剩三个参数，覆盖层整个删掉。

- schema **v7**：先把 `user_edit_of` 指到的那一组正文回填进 `raw_text` / `edited_text`，
  再 `DROP COLUMN user_text` / `user_edit_of`（用户之前改过的内容一行都不丢）。
- **D148 的存储形态作废，结论保留**：颜色只看 `edited_by_tool`；用户改字不改颜色。
  `user_edited` 这个标记一并删了——"用户改过"和"原文本来就是用户写的"已经不可区分，留着只会误导。

**② 删除版本与删除消息分开。** `delete_message_version(0)` 这个暗号取消（传 ≤0 直接报错，

- 只允许删**单元里只有它一条**的消息。工具往返是 `assistant(tool_calls) + 全部 tool_result`

- FFI：`nmoi_storage_delete_message_json`；JNI：`Native.deleteMessageJson`；
  Kotlin：`ChatRepository.deleteMessage`。
- 界面：面板项改成「**删除这条消息（含所有版本）**」，任何消息都给（不限版本数），
  点了先出确认框（正文/版本数/首 80 字预览 + 红色「删除」）。破坏性动作必须确认。

**测试**：`editing_one_group_never_resets_the_other`（先改原文再改 AI 版、再改回来，两轮都不能丢）、

## D153 「复制为新版本」取**现在显示的那一份**；删除按**单元**删

**用户 2026-10-26 第四次反馈**（原话）：

> 修改后复制为新版本不是基于当前状态的（当前切换在红就复制红，当前切换在蓝就复制蓝，
> 为什么它给我复制的是原来的蓝，我明明已经改了？）你明白什么叫所见即所得吗？

> 还有整单元删也补上吧。

**① 复制的源文本现读。** 原来 `saveVersionProbe` 用的是列表快照里的 `content`——快照滞后一拍，
于是就"我明明改了，它复制的还是旧的"。现在先 `versions()` 现读，用 `shown`
（= 屏幕上显示的那一组，含他自己改过的字）当源；没有版本时才退回消息正文。
同一条口径也用在编辑预填（D150）上：**看得见的那份 = 唯一的源**。

工具往返是 `assistant(tool_calls) + 全部 tool_result`，只删半边会留下
`unpaired_tool_call`（L3 校验会报、模型也读不懂）。用户点的是"这条消息"，
它和它的工具结果本来就是一件事。界面据 `removed` 说话："已删除这条消息（连同它的 2 条工具往返）"，

**测试**：`deleting_a_tool_message_takes_the_whole_unit`（2 条一起走；删完重开库过语义校验）。

## D154 一版只有两种正文：`origin_message` / `tooledit_message`（schema v8）

**用户 2026-10-26 第五次反馈**（原话）：

> 红就是 tooledit_message，这样区分来就行了，只存这两种，有 tooledit 消息的时候就会显示红蓝状态，
> 只有 origin 的时候就是正常的不显示红蓝的。不然要是有那种看不见但是存了的消息数据，这不成屎山了？

`RENAME COLUMN` 一个字节都不搬，`CHECK` 表达式里的引用由 SQLite 自己跟着改。

**规则钉死**：

| 库里有什么 | 界面 | 行为 |
|---|---|---|
| 只有 `origin_message` | **不显示红蓝** | 正常正文；点不到"切改后" |
| 有 `tooledit_message` | 显示 `n/n`，蓝=看原文 / 红=看改后 | 点数字在两组之间切 |

## D155 UI 状态里不放数据对象，只放 id

**上一次真机留下的那条诊断**（§6.1）：日志里 `面板 … 列表=0/0 现读=2/2`，
以及更早的"点两次才出 `2/2`""看着 2/2、编辑落到 1/2"。三件事根子在一处。

**根因**：`moreFor` 与 `editing` 存的是 `ChatMessage` **对象**——点开那一刻的副本。
面板的显示用现读的库，动作却用这个副本，于是两边的版本号/正文可以不同步；
日志里"列表"那个数也是副本的，所以它看起来像"列表恒为 0"，其实只是**那份副本旧了**。

**修法**：两个状态都改成只记 id（`moreForId` / `editingId`），渲染和动作时从
`allMessages`（当前快照）现取。找不到就 `LaunchedEffect` 里把浮层收掉——
否则按返回会先"退"一个看不见的层，用户以为返回没反应。
日志也改成**同一刻两个来源**的对照：`行内=c/a view=… | 现读=c/a view=…`。

**为什么这条比修 case 值钱**：UI 状态里放对象，等于给自己留了一份看不见的副本——
正好撞在 D152–D154 那条线上（不许有不可见的数据；动作的源必须是屏幕上此刻显示的那一份）。
以后凡是"点开某个东西"的状态，**存 id，用时现取**。

**验证**：Kotlin 侧没有本地编译（CI 的 android job 编），行为要真机看那行日志两边是否相等。

## D157 供应商多套 + 模型表；`turn_run` 接到 UI

D156 只做了"一套端点 + 一把钥匙"。发请求那条路要用哪一套、用哪个模型，一直没地方答。
这一条把它补成能用的形状，并把 `nmoi_turn_run_json` 接进聊天页。

**数据**（`settings(provider, <id>)`，一个供应商一个 key）：

```json
{
  "name": "本机中转",
  "kind": "openai_compatible",
  "base_url": "https://example.com/v1",
  "models": [{ "id": "vendor/model-a", "max_tokens": 8192, "temperature": 0.7 }],
  "active_model": "vendor/model-a"
}
```

- 当前用哪一套：`settings(provider, "active")` = `{"id": "<id>"}`。
  **不设 `enabled` 字段**——`active` 是"用哪一套"的唯一答案，多一个开关就会有两个答案。
- 密钥按条目分文件：`vault/provider-<id>.bin`；`id = default` 沿用 D156 的
  `vault/provider.bin`，**升级上来不用重填密钥**。
- 老形状（只有 `base_url` / `model` / `kind`）在读取时**就地解释**成"模型表里只有一条"，
  不做一次性迁移：迁移要写库，写库就可能把没读懂的字段洗掉。
- 没有 `active` 标记时兜底：`default` → 只有一个供应商时就是它；**多套又没选过就报错**，
  不替用户挑（挑一个等于替他决定花谁的钱）。

**模型表只存真会被用到的三样**：名字、`max_tokens`、`temperature`。
上下文窗口 / 定价 / 输入输出模态那些看着更"完整"的字段这一版没有——
`crates/core` 里没有任何一处读它们，存下来就是"存了但不生效"，正是用户最反感的那种
（撞 D154 那条：不许有"存了但看不见/没用上"的东西）。

**界面**（`ui/ProviderScreens.kt`，形状参考别的客户端那套"列表 → 详情"）：列表页
（搜索框 + 首字圆标 + 名字 + 类型/模型数 + 「当前」标记）→ 编辑页（页签「配置 / 模型」，
配置 = 名称 / 类型 / Base URL / API Key（打码、显隐只在输入时生效）/ 保存 / 设为当前；
模型 = 一行一个，点行设为当前、铅笔改、＋添加）。
不做这些按钮：是否启用开关、多 Key、Response API 开关、账户余额、网络代理、
自定义 Header/Body、API 路径、上下文窗口/定价——**它们在本项目里一条代码都没有读**。

**发请求**（`ui/TurnRepository.kt` + `NmoiFfi.turnRun` + JNI `turnRunJson`）：
按顺序解析——现读"当前供应商"（不是界面快照）→ `Vault` 现解一次钥匙（解不开也照发，
本地端点常常不要钥匙，真 401 时错误里会带状态码）→ `turn_run`。
`run_session_turn` 第一步就把用户那句话落库，所以**失败时它可能已经在库里**：
失败后现读一次库（`wasUserTextSaved`）判断草稿要不要清，判不出来就保守当成没存。

**取消**：`turn_cancel` 接到同一个按钮（生成中 ↑ 变方块）。它只置标志，
真正的停点在回合边界（D58 那条代价，界面文案照实说"停在这一次请求回来之后"）。

**为什么把 `turn_run` 排在多套供应商之后**：发送要用"哪一套 + 哪个模型"这个答案；
先有多套再发，才不会出现"发了才发现改不了用哪套"。

## D158 块级编辑与一次性补全（基建；界面在下一层）

增强编辑要落到"改哪一块"上，而一套消息里的三样东西存在**不同的列**里：
`content`（正文）/ `reasoning`（思考）/ `tool_calls[].arguments`（工具参数）。
以前只有"整段正文再存一版"，块级编辑的接口在 `core::edit` 里躺着，没人调用。

- storage：`Storage::apply_block_edit(message, BlockSelector, content)`——
  查出这条消息所在的单元 → `core::edit::apply_edit` → `save_message_edit` 写回那一行
  并往 `edits` 审计表记一笔（同一个事务）。五种拒绝都带原因：单元不匹配、消息不在单元里、
  **被用户锁定**、没有第 N 个工具调用、**内容没变化**。
- **工具调用只允许改参数**：名字与 `call_id` 不在射程里。名字决定下一轮怎么解释这一块，
  `call_id` 决定它跟哪条结果配对；让编辑改这两样，等于把一条历史换成另一条。
- FFI：`nmoi_storage_apply_block_edit_json(handle, message, block, content)`，
  `block` 只认 `output` / `thinking` / `tool:<0–63>`，单块上限 200 KB；
  `nmoi_complete_json(config)` = **一次性补全**，不落库、不进历史（`ChatRequest::from_turns`
  + `without_stream`）。用 `turn_run` 做这件事会在历史里留下"用户让我改"和"模型回了新正文"
  两条假对话，下一次压缩会把它们当真。
- `load_units` 补两个字段：`reasoning`（以前只存不带出去，界面上永远看不见）与
  `tool_call_args`（名字 + 参数原文）。**存了但看不见**正是铁律 ② 要挡的。
- 测试：`crates/storage/tests/block_edit.rs` 5 条（思考不动正文、工具参数不动名字与 id、
  锁定拒绝且不记账、未知消息/越界索引报错、无变化拒绝）。
- 界面（Kotlin 的 EditRepository + 「更多 → 增强编辑」）**还没接**，这一条只到"底座能用"。

## D159 命令工具的命名、注入门槛与容器口径（已定形状，未动工）

**两把工具，名字分开**（用户 2026-10-27 定）：

| 名字 | 是什么 | 平台 |
|---|---|---|
| `System-Shell` | **平台原生**命令（App 自己的身份跑） | 三端都有 |
| `WorkSpace-EnvirShell` | **隔离环境**里的命令（proot 根文件系统） | Android / Linux |

- 连字符在四家的函数名规则里都合法（OpenAI `^[a-zA-Z0-9_-]+$`、Anthropic 同、Gemini 允许 `.-`），
  所以名字照用户给的写，不做 snake_case 改写——改写会让界面上和日志里的名字对不上。
- Windows **只有** `System-Shell`（容器那套不往 Windows 上搬）。它的描述必须先写
  "这是本机原生命令，谨慎操作"。
- 两把工具的描述都写一句：**没有用户明确允许时不要调用**。
- 结果形状（界面那两页 stdout/stderr 的输入）：
  `{"exit_code":0,"stdout":"…","stderr":"…","truncated":false,"duration_ms":123}`；
  stdout / stderr 各自封顶 64 KB，截断要标出来；超时杀**进程组**（`setsid` + `kill -PGID`），
  不是杀一个 pid——否则 `sleep 1000 &` 会漏。
- 开关按工具、按平台摆：Android/Linux 两个（原生、隔离环境），Windows 只摆原生。

**世界书预设：只有对应工具开着才注入**

- 每条预设带 `applies_to`（工具名 / 能力位）。注入在 `TurnPlan::freeze` 里解析，
  **按 `plan_tools` 算出来的声明表过滤**——工具没开，它那几条提示词一起消失。
  不在请求构造时临时判断：一轮跑到一半改预设就变声明，缓存全废、模型看到两套指令。
- 这也解释了为什么"冻结"和"注入"必须在一处：门槛的输入（声明表）本身就是冻结的产物。

**`base-version` 的口径**（用户 2026-10-27 提出，我加了五条）

- 官方原文放 `assets/presets/`，词条只记 `base_id` / `base_version`（整数）/ `base_hash`
  和用户改后的正文。版本号会说谎（改了没递增），哈希不会。
- 四种状态：跟随官方 / 已改写 / 官方有新版 / **两边都变（冲突）**。冲突给三个选择，
  **绝不自动覆盖**。
- `base_version` 在应用内**双层不可改**：编辑器置灰 + 保存路径忽略它；导入时**重算**
  `base_hash`，不一致标"base 被改写"。
- 基线条目不可删，只能禁用。
- 预设只准改**描述正文**：工具名与参数名是 wire 契约，预设里出现未知工具名当场报错。
- 注入了哪几条、版本多少，进**请求日志**（用户要的位置），不另做面板。

**Shizuku：只在本地，不进导出**

- `System-Shell` 有一个"经由 Shizuku 执行"的开关。打开时**必须真的拿到 Shizuku 授权**，
  否则开关打不开（给一句具体原因：没装 / 没授权 / 版本太老）。
- 这个选择**只存本地**（SharedPreferences），**不进库、不进导出/导入**。
  理由：授权是"这台设备上的这个安装"的状态；导入一个 `true` 只会得到
  "界面看着开着、实际跑不了"，比没有更糟。
- 启动时重新校验一次授权，被撤销就把开关打回关，并在开关那一行写明原因。

**工作区与容器**

- 工作区根：`/data/user/<uid>/com.nmoi.agent/files/workspace`（**不是** `/sdcard`），
  走 `nmoi_workspace_open_json` 绑定，零权限。
- 容器：proot + Ubuntu 最新发行 rootfs，**首次使用时下载**。下载源两项：
  「Ubuntu」（官方地址）与「自定义」（自定义时输入框才亮）。

## D160 工作区落地 + `System-Shell` + 工具结果卡（D159 的第一段）

**工作区**：`filesDir/workspace`（真实路径 `/data/user/<uid>/com.nmoi.agent/files/workspace`），
不进 `/sdcard`。Kotlin 先 `mkdirs()` 再 `nmoi_workspace_open_json` 绑；每轮开、轮末关
（`try/finally`）。绑不上不中断这一轮——文件工具与命令不可用，聊天照旧。
六件文件工具从这一版起在真机上**真的能跑了**（以前 FFI 那条路从来没传过 workspace 句柄）。

**`System-Shell`**（`crates/core/src/shell.rs`）：

- 只有 `Capability::NativeShell` 门控放行才可能被调到；没有工作区绑定连门都过不去
  （`check` 回 `no_workspace`）。
- 平台壳：Unix 是 `/bin/sh -c`（Android 上优先 `/system/bin/sh`），Windows 是
  `powershell -NoProfile -NonInteractive -Command`。
- 起进程 `process_group(0)`，超时 `kill(-pgid, SIGKILL)`（**不是**只杀子进程，
  否则 `sleep 1000 &` 会留在后台）；Windows 用 `taskkill /T /F`。
- stdout / stderr 各开一个读线程（单读一个会在管道写满时互锁），各封顶 64 KiB，
  超了继续读但丢弃并在结果里标 `truncated`。
- 结果 JSON：`command` / `exit_code`（被信号杀是 `null`）/ `stdout` / `stderr` /
  `truncated` / `timed_out` / `duration_ms`。
- 默认超时 30 s，上限 300 s；`cwd` 只能用工作区内的相对路径。
- 6 条测试：门控先于一切、没工作区拒绝、两个流分开、cwd 是工作区根、超时被杀（退出码 null）、cwd 越界被拒。

**开关**：`native_shell` 由 FFI 的 turn 配置带进来（默认 `false`），
Kotlin 侧存 SharedPreferences（`nmoi.local`），**不进库、不进导出**（见 D159 的理由）。
界面：设置 → 工具与工作区 → `System-Shell` 开关 + 一次确认卡；
`WorkSpace-EnvirShell` 这一版是**灰的说明行**（运行时没打包，拨了也不生效的开关比没有更糟）。

**结果卡**：工具往返展开后按 `call_id` 配对，一条调用 = 一块：
「命令」+ 等宽框 + 复制，「输出」+ `stdout`/`stderr` 页签 + 复制，
右上角写退出码 / 超时 / 截断。失败且 stderr 非空、stdout 为空时**默认停在 stderr**。
配不上结果的调用单独标「没有结果（这一批里它没跑完）」。
