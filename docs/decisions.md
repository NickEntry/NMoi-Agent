## D226 代理：默认不碰容器，透明要走 VpnService（设计已定，core 已落地）

用户 2026-11-02：发请求前检查连通性，不通就试着连，连不上报错停下；四种类型照截图。
补的一条更要紧：**容器内不映射系统代理，要像 TUN，别留检测痕迹**。

- 四种类型：SOCKS5 / HTTP / HTTPS / HTTPS（本地凭据）。前三种的差别只在"到代理那一段"，
  到目标都是 CONNECT；明文 http 走 HTTP 代理时用绝对 URI（不 CONNECT，兼容性最好）。
- **「本地凭据」= 本机信任库**（系统根 + 用户装的 CA），另一档是内置 Mozilla 根。
  Android 7 起 App 默认不信任用户 CA，所以这一档要 `network_security_config` + 平台 TrustManager；
  这一版**明确报 `Unsupported`**，不假装能验。
- **容器内不注入 `http_proxy`/`all_proxy`**：那是最好检测的痕迹（`env`、`/proc/self/environ`）。
- **容器内透明代理不做**（用户 2026-11-02 明确「VpnService 这种不行的，不能做就不做」）。
  技术事实：proot 不是 namespace，容器与 App 共享网络栈，所以 App 的监听容器连得到；
  但**没有任何机制会自动改道** `connect()`，除非环境变量 / 动态链接器垫片 / 内核层。
  内核层在 Android 上只有 VpnService（排除），proot 里没 root 没 netns，iptables 与 DNS 改道都不成立。
  所以无痕方案不存在。将来若要"少留痕"，只有垫片 + unix socket，且必须标注可被检测、
  静态程序无效——默认状态是**什么都不注入**，容器命令直连。
- **实时生效**：`ProxyHandle`（Arc<RwLock<Option<ProxyConfig>>>）每次请求现读；
  本地端点也拿同一个句柄，换上游不用重启。
- **持久会话**：垫片必须**常驻**（`/etc/ld.so.preload` 与代理开关解耦），代理开关只写/删
  `/etc/nmoi-net.conf` 与起停端点；垫片**每个新连接**读一次配置，所以关→开、开→关都即时，
  已经建立的连接不重路由。垫片缺失时界面不显示"已开启"。
- 已落地：`crates/core/src/proxy.rs`（握手、绕过匹配、TLS 到代理、`ProxyHandle`）+
  `crates/core/src/proxy_server.rs`（本地 SOCKS5 端点，随机凭证，上游热改）+ 两个 transport 的
  `proxy` 字段，15 条单测用本机假代理/假端点跑真 socket。
- 已接线：FFI 四条（`nmoi_proxy_apply/status/server_start/server_stop`）+ 设置页
  （工具与工作区 → 网络代理：开关 / 类型 / 地址 / 端口 / 用户名 / 密码 / 绕过 / HTTPS 凭据来源），
  密码进 Vault，保存即 apply，**启动时也 apply 一次**（否则重启后是直连）。
  未做：探测与 60 秒缓存、供应商级覆盖、垫片（需 NDK 构建）、「本地凭据」档。

### D226 补记：垫片用真 IP + 映射，不用假 IP

用户 2026-11-02 问「关掉代理会不会让某些有校验的工具失效（npm？）」。
查下来真正的坑不在校验，在**假 IP 残留**：如果 `getaddrinfo` 返回 198.18.x.x，
代理一关，程序或它自己的 DNS 缓存里那些地址没人能连——表现是"某些工具突然连不上，重启才好"。

- 改成 proxychains-ng 那套：`getaddrinfo` 照常拿**真**地址并记 `IP → 域名`；
  `connect` 命中映射且代理开着才走端点，否则原样直连。
- 配置缺失时两个钩子都不做任何改写，完全透明。
- 关掉代理不会影响 TLS/签名校验（域名、SNI、证书链都没变）；会失效的是
  "设备本来只能靠代理上网"的场合，以及绕过垫片的 Go / 静态程序。
- 最该防的是垫片加载失败（架构不对/缺依赖）：`ld.so.preload` 里写一个加载不了的 `.so`，
  容器里所有动态程序都起不来。所以只在"文件存在且架构对"时才写，并留一个"移除垫片"的入口。

### D226 补记二：我们的代理是隧道，不制造"证书校验失败"

用户 2026-11-02 说别的客户端开代理时有些工具校验过不了。三类根子要分开：

1. **上游代理做 TLS 中间人**：证书链被换，工具报 `certificate verify failed`。直连不会有。
   我们不 MITM（`proxy_server` 只 `io::copy` 字节），所以走我们的代理与直连结果一致。
   上游自己 MITM 时，要么关掉它，要么把它的根证书装进容器的系统信任库
   （`update-ca-certificates`），不设 `SSL_CERT_FILE` 这类环境变量。
2. **风控/指纹**：出口 IP 变了，目标回 403/challenge。不是证书问题，也不该混进证书错误里。
3. **容器自己的 CA 库或时钟**：直连一样会失败。rootfs 的 `ca-certificates` 与时钟要在体检里先看。

垫片两条硬规则：loopback 永远直连（否则自己连自己死循环）；`getaddrinfo` 不改写地址。
环境页加「网络体检」：时钟 / CA 张数 / 直连一行 / 走代理一行，四行并排看归因。

## D227 重试 = 在同一条消息上开一个空白新版本，就地渲染（设计已定，未动工）

用户 2026-11-03：现在重试会在底部另起一个「助手 / 正在生成…」的块，看着别扭；
希望**在同一条消息上开一个空白新版本，然后就地渲染**——流式开着就逐字长进去，
关着就先把版本置空、等结果回来再填。

同意。这不只是好看：现在的做法在库和界面之间留了一个"还没落库的临时气泡"，
而版本是库里的东西，两者对不上（铁律②的边角）。改成"新版本先落库、界面渲染它"，
临时状态就只剩"这个版本还没内容"这一件事，而它本身是可见的。

### 形状

1. **开始**：`begin_blank_version(message_id)` —— 一个事务里插一条空版本、把 `active_view`
   切到它。界面立刻显示成空白（带一行「正在生成…」）。
2. **进行中**：这一轮的部分正文渲染在**这条消息**上，不再另起一个块。
   流式开着时逐字长；关着时保持空白，直到结果回来。
3. **完成**：`turn_regen` 带 `fill_version`，把结果写进那个版本，**不再新建**。
4. **失败**：删掉空版本、把 `active_view` 切回上一版，提示「没写进去，已回到上一版」。
   留着一条空版本比报错更让人以为消息被吞了。
5. **取消**：保留这一版，写入已收到的部分并标 `incomplete`——和普通取消一个口径。

### 两条硬约束

- **一次只开一个**：同一会话已经有一轮在跑时，不允许再开空白版本（否则会出现两个空版本）。
- **空版本必须可见**：它显示为「正在生成…」，不是一条 0 字的消息；失败要回收，
  不能留在列表里当一条空消息。

### 还没想好的

- 用户消息重试时，下面没有助手消息可挂：仍然新建一条（现状），但同样先落空版本再填。
- 空白版本的 `seq` 与时间戳：沿用被重试那条的 `seq`（版本不占新消息位），时间戳用这一轮的开始时间。

## D228 重试失败：三选一弹窗（保留上一版 / 保留这一版 / 都保留）（设计已定，未动工）

配合 D227（重试先开空白版本）。失败时不再只写一句提示，弹一个必须处理的对话框：

| 选项 | 做什么 |
|---|---|
| 保留上一版 | 删掉这次产生的版本（空或残），`active_view` 切回上一版 |
| 保留这一版 | 删掉上一版，只留这次这一版 |
| 都保留 | 两版都留着，当前显示这次这一版（可以切回去） |

- **这一版一个字都没有时**，「保留这一版」灰掉并写原因（「这一版是空的」）——
  留着一条 0 字消息比报错更让人以为消息被吞了。
- 默认选中「保留上一版」：失败之后最常想做的是回到能看的那一版。
- 对话框是**必须处理才能继续**的那种（不是底部面板）：它决定库里的东西，不能点外面关掉。

## D229 过程块：思考与工具合成一个大块，只展开最新两个（设计已定，未动工）

用户 2026-11-03 给的参考图：一次回合里的「深度思考 / 运行命令 / 写入文件」串成一条时间线，
外面一个大块，头部「收起」或「展开更多 N 步」。

规则（用户口述，逐条落）：

1. **分组**：一次 assistant 回合里**连续**的思考与工具项合成一个大块；中间夹了正文就断开。
2. **折叠阈值**：小块数量 **≥ 3** 才折叠；折叠时**保留最新 2 个**可见，其余收起。
3. **正在跑的不折**：正在执行的工具、正在输出的思考**永远展开**——折起来就看不见它在动。
4. **折叠只发生在结束之后**：一个块结束才参与折叠计算。
5. **折叠状态只在本次浏览会话内记忆**：切到别的会话再回来，恢复默认（最新两个 + 其余折叠），
   不沿用刚才手动展开的样子。
6. **工具块运行中显示最多 3 行最新输出**（没有输出就不显示这 3 行）；结束后收成一行 + 右侧 meta
   （`exit 0 · 302ms`）。
7. **思考块输出中显示最多 3 行最新思考**；结束后回到原来的折叠态（一行「深度思考 (1.8s)」）。
8. 大块头部：折叠时「展开更多 N 步」，展开时「收起」；左侧一条竖线把小块串起来。

## D230 服务启动：进程自己停了要问「重新启动」（设计已定，未动工）

持久会话里的**服务**（D219）在开关开着的时候进程退出，不能静默变成"开关是开、进程不在"：

- 弹一个提示条/对话框：「服务 <名字> 已停止（exit N）· 重新启动 / 保持停止」。
- 选「保持停止」→ 开关跟着关掉（一个状态只有一个答案）。
- MCP 那边不一样：它还有 HTTP / SSE，连不上是"重试连接"而不是"重启进程"。
  所以 MCP 的文案是「重试」，服务的文案是「重新启动」——两件事，别合成一句。

## D227 落地记录：重试就地渲染（2026-11-03，0.15as）

设计见上面那条。落地时改了**一处**设计，理由写在下面——这不是"顺手优化"，
是原方案在这套数据上会直接把会话读崩。

### 落成了什么

1. **重试走流式**：`nmoi_turn_regen_json` 多一个 `stream`（默认 `false`，界面传 `true`）。
   增量照 `turn_run` 那一套进 partial 表，界面轮询 `turn_busy` 拿尾部 + 总量。
2. **就地渲染**：`ChatScreen` 多一个 `regenTarget`（消息 id）。非空时
   - 底部那块 `LiveReplyRow` 不画；
   - 这一轮的正文与思考画在**目标消息**的正文位置（`AssistantMessage(live = …)`）；
   - 生成期间不画动作行（复制/版本/编辑指的都是库里那份，而屏幕上这份还没落库）。
3. **目标为空时仍在底部**：用户消息重试、下面没有回答可挂 → `target = null`，
   结果会落成一条新消息，那个位置就是它要去的地方。
4. **续话不流式**：它的落库正文是"原正文 + 续文"，流里只有续文那一截。
   边写边画就得在 Kotlin 里再实现一遍 `join_continuation`（中文不加空格、英文加一个），
   两份规则迟早分叉。所以续话期间显示原正文 + 一行「正在生成…」，收尾再换。

### 改了哪一处：**不预先落一个空版本**

原方案第 1 步是 `begin_blank_version`：先插一条空版本再请求。**做不到**，两个原因：

- `Message::validate` 把"正文空 + 没有思考 + 没有工具调用"判成 `EmptyMessage`，
  而 `load_units` 会走这条校验。库里真有一条空正文的消息，**整个会话都读不出来**——
  实测（`crates/storage/tests/versions.rs` 里那条临时用例）：`load_units` 直接
  `Unit(EmptyMessage(...))`，聊天页一片"正在读…"。
- 就算把它设成非当前版，用户点一下 `<2/2>` 切过去，`content` 也会变成空串，
  下一次读同样是 `EmptyMessage`。空版本在这套 schema 里不是"一个可以存在的状态"。

所以改成：**版本在结果回来时才建**（`save_generated_version` / `append_generated_version`，
与现状一致），运行中的"还没内容"这件事只活在界面上（那一行「正在生成…」）。
代价是进程被杀时库里不会留下一条空壳——这反而是好事。

## D228 落地记录：失败三选一（2026-11-03，0.15au 的一半）

配合 D227。触发条件：**重试/续话失败，且这次有目标消息**（`target != null`）。

- 弹窗（不是提示行）：`保留上一版`（默认）/ `保留这一版` / `都保留`。
- **必须处理**：遮罩不吃点击、返回键在这一层什么也不做——关掉等于替用户选了"保留上一版"。
- 这一轮**一个字都没收到**时，后两项灰掉并写「这一版是空的」。
- 「保留这一版」= 把这次收到的残文 `save_generated_version` 存成一版，再删掉上一版；
  「都保留」= 只存不删。都走现读库（铁律①）：版号是存完之后现读的 `active - 1`。
- 残文取的是**内存里这一轮收到的正文**（`live.text`），它还没落过库，所以是唯一的一份。
- `target == null`（结果会落成新消息）时不弹：没有两版可选，只给一行提示。

D230（服务停止询问）**没动**：它依赖 D219 的持久会话，而那一层还没动工。

## D227 补记：续话也流式（0.15av，2026-11-03）

上一版把续话排除在流式之外，理由是"落库正文是原正文 + 续文，流里只有续文那一截，
边写边画就得在 Kotlin 里再实现一遍拼接规则"。用户当天要求续话也流式——那就把规则搬回去，
而不是在 Kotlin 里再写一份。

**做法**：拼接规则只有一份，在 core（`session::join_continuation`，这轮改成 `pub`）。

1. FFI 在 `append && stream` 时先读目标消息**现在显示的正文**（`Storage::message_content`）。
2. partial 缓冲的第一段增量垫上「原正文 + 连接符」（`seeded_delta` → `join_continuation`），
   所以 `turn_busy` 的 `text_len` / `text` 自始至终是**全文**。
3. 工具往返会清空缓冲，换轮时**再垫一次**（`fresh` 标志由 round hook 置回）。
4. 界面把 `live.text` 预置成原正文（`LiveReply.prefix`），换轮时也回到 `prefix`。
   这样 `growText` 只补"新长出来的那一段"，长消息不会因为 8 KiB 尾部而丢掉开头。
5. 落库仍走原来的 `join_continuation`——流里看到的和库里存的是同一个函数算出来的。

**顺带修掉一个更早就存在、这轮才会被撞上的毛病**：native 的 partial 缓冲上限 50 KB，
超了砍头；这时 `text_len` 比界面手里的还少，`growText` 会认为"没有新字"，
屏幕上卡住不动。现在界面看到 `total < have` 就从尾部重来（不假装完整）。

## 动作行里的重试（0.15av）

那一排第二颗一直是灰的（`刷新（重新生成，待接 turn_run）`）——一个点了没反应的假开关。
现在接上：

- `enabled` 的判据是「有没有东西可跑」：会话已落库 + 这条能当重试目标（`canRetry`）。
  思考块 / 工具调用 / 工具结果 / 断块都不给；会话还没落库也不给。
- 描述写实：助手那条是「重试这一轮」，用户那条是「重试这条之后」；灰着时后面加
  「（现在不可用）」，长按能看到这句话（`IconActionButton` 本来就支持）。
- 点下去只传消息 id，动作发生时按 id 现取（铁律①）；取不到就说「这条消息已经不在列表里了」。
- 「⋯」菜单里的重试**保留**：两个入口打开的是同一个动作，不是两套说法。

## D229 落地记录：过程块合并与折叠（0.15at，2026-11-03）

用户 2026-11-03 给的参考图：一次回合里的「深度思考 / 运行命令 / 写入文件」串成一条时间线，
外面一个大块，头部「收起」或「展开更多 N 步」。落成了，逐条对：

1. **分组**：连续的思考与工具合成一组；中间夹了正文就断开。分组是**纯渲染**——
   `ChatUnit` 与库里一一对应，一个新字段都没加（`ProcessRows.kt` 的 `buildRows`）。
2. **≥3 才折，折起来保留最新 2 个**。两项不折——一次工具调用单独画一张卡就是现在的样子，
   加竖线和缩进只是多一层壳。
3. **正在跑的不折**：`!unit.closed` 的组永远展开。折起来就看不见它在动。
4. **折叠状态只在本次浏览会话内记忆**：`openGroups` 是 `remember(sessionId)` 的
   `mutableStateMapOf`，切走再回来是一张新表。键取**组的第一项 id**，不取整组——
   这一轮又多跑一次工具、组里多一项，键变了的话用户刚展开的大块会自己收回去。
5. 大块头部：折叠时「展开更多 N 步」，展开时「收起」；左侧一条 1dp 竖线把小块串起来
   （`drawBehind`，不用嵌套布局量高度）。

## D233 容器覆盖安装 + 装完自检（0.15ay，2026-11-03）

容器坏掉之后，原来的「重新安装」只会**先删干净再重解**：解包失败就什么都不剩，
用户装在容器里的东西也一起没了。这一轮加的是「覆盖安装」这条路，外加一条装完就写的自检记录。

1. **覆盖安装（`EnvirRepository.repair`）**：解包前**不删** rootfs，`TarGz.extract` 直接解到已有那棵树上
   （同名条目按 `clearBeforeWrite` 先删后写，目录 `mkdirs`，用户自己装的东西不在包里就留着）。
   解包失败也**不删**——把仅剩的一份删掉，等于把"需要修复"变成"什么都没了"。
2. **来源沿用 `state.json` 里那一条**（label / url / sha256 / bytes），不读来源卡片：

   归档在装完就删（35 MB 白占），所以覆盖安装**要重新下 33.4 MB**，提示里写了。
3. **装完自检**：`/bin/sh -c 'echo ok'` + `/usr/bin/ldd /bin/sh`，一次 proot 跑完。

   只跳过缺库那一半——否则一个能跑的容器会被判成坏的。

5. **坏了就不发给模型**：`TurnRepository` 只在 `health != NeedsRepair` 时把容器坐标交给 core。
   开关开着、容器坏着的时候，模型看到一个一调就失败的工具，比没有更糟。

6. **重新安装改成破坏性动作**：文字按钮 + 确认卡（红色实心，写清"容器里你自己装的东西会没掉"）。

## D234 工作区：用户建的目录 + 助手绑定（v13 / 0.15az，2026-11-03）

D231 那套（`conversations.workspace_mode` 两档：`chat` / `shared`）是**错的模型**，用户
2026-11-03 纠正过：工作区不是"每个会话一个开关"，而是**用户建的、可复用的、天生共享的目录**；
会话自己的东西（附件、工具产物）另有一处，叫 `/chat`。这一轮按纠正后的模型重做。

**1. 工作区是目录，不是表。**

`files/workspaces/<id>/`，每个目录里一个 `.nmoi-workspace.json`（只有 `name`）。
不建 `workspaces` 表，理由三条：

- 它除了名字没有第二个字段（创建时间没人读、大小要现算）；一张表会变成一个 `name` 列加一串空列。
- id 一旦生成就不再变，改名只改那个文件——**助手文档里存的是 id，改名不用去改任何助手**。
  要是 id 跟着名字走，改一次名就有一批助手指向不存在的目录，看起来就是"文件没了"。
- 名字跟着目录走（不是另存一份索引）：目录在、名字就在，删目录不会留下一条"看着有、点进去是空的"记录。

默认工作区是老的 `files/workspace`（id 固定 `default`）：升级上来文件还在老地方，谁都不用搬。
它不能改名、不能删——老会话最后的落脚点。

**2. 绑定在助手身上，不在会话身上。**

`assistants.workspace_id`（settings 文档里的字段，不占 schema）。一个助手一个工作区，
会话通过它的助手拿到；换工作区**不搬文件**。入口只有一处：助手编辑页那一格。
工作区页只做列 / 新建 / 改名 / 删除——同一件事不给两个入口。

**3. 容器里两个挂载点，各管各的。**

- `<工作区>:/workspace`，`-w /workspace`（工具根也是它）；
- `<sessions/<id>/chat>:/chat`，附件目录再单独一条 `/chat/images`。

为什么附件不搬进 `chat/`：D216 的路径（`sessions/<id>/images/`）已经写进了库、写进了存储页，
搬一次要做数据迁移；两条 `-b` 比一次迁移便宜。顺序要紧：先 `/chat` 再 `/chat/images`，
否则第二条的目标在 guest 里还不存在（`shell.rs` 有一条测试钉住这个顺序）。

**4. schema v13 把 `workspace_mode` 删掉。**

它和"助手绑哪个工作区"回答的是同一个问题（这一轮的工具根在哪）。两份答案摆在一起，
下一个读代码的人得先猜哪一份算数。删的时候顺手把它带来的 FFI（`workspace_mode_json` /
`set_workspace_mode_json`）与 Kotlin 桥一起删了——JNI 符号 48 → 46。

**顺带清掉的**：D231 的 `ChatRepository.workspaceMode` / `setWorkspaceMode`（从来没有界面调用点，
属于"有代码没入口"）、D232 的迁移提示（新模型下不需要迁移：老会话本来就看得见 `files/workspace`）。

**没做**：备份带上 `sessions/` 与 `workspaces/`（0.15ai）；工作区里"打开文件夹"（没有文件选择器）；
`/chat` 的清理入口（0.15ai 的存储分类一起做）。

**验证**：`cargo clippy --workspace --all-targets -D warnings` 本地零告警；
`workspace_v13` 两条（v12 库升上来列没了、行还在；新库没有那一列）本地通过；
`shell.rs` 新增 `envir_binds_chat_before_its_images`。Kotlin 只过了 clippy 那一轮的类型检查之外的
括号自查，真正编译看 CI。真机 V60 未走。

## D235 覆盖安装解包失败：条目名不能按真实路径解析（2026-11-03）

真机第一次试覆盖安装就挂了：「没装成：解包失败：/data/data/com.nmoi.agent/files/envir/ubuntu/usr/bin」。

**原因**（本机拿真 rootfs 复现过）：`TarGz.resolve` 用的是 `File(...).canonicalFile`，
也就是**跟着目标树里已有的链接走**。第一次装的时候树是空的，字面路径与真实路径恰好一样；
覆盖安装时 `bin` 那条符号链接（`bin -> usr/bin`）已经在了，`canonicalFile("bin")` 算出来是
`usr/bin`——于是"在 `bin` 上建链接"变成了"在 `usr/bin` 上建链接"，`usr/bin` 是个非空目录，
`createSymbolicLink` 抛 `FileAlreadyExistsException`（消息就是那个路径），整次解包中止。
同一个毛病还会把 `usr/bin/[` 这类链接算到它指向的目标上，删掉/覆盖掉不该动的文件。

**改法**：条目名**按字面拼**（`..` 弹栈、绝对路径拒绝），不跟随任何已有链接；
越界仍然挡，但挡的是**父目录的真实路径**必须还在 dest 里——"先建一个指向外面的链接、
再往链接里写"这一手照样拦得住。链接/文件/目录三种落点各自先清同名旧条目
（同名是**非空目录**时跳过并记一笔：删目录等于删用户的东西）。

**顺带的**：
- 每个条目包一层 `try/catch`，失败时把**条目名与类型**写进消息（`条目 bin（类型 2）落不下去：…`），
  不再只留一个裸路径。
- 硬链接的源取 `toRealPath()`：覆盖安装时源本身可能是上一次退化成符号链接的那一条，
  对着链接建硬链接得到的是"链接的链接"。
- 目录条目遇到同名非目录先删掉再 `mkdirs()`，否则后面每一条子条目都会以"Not a directory"失败。

**验证**：拿 `ubuntu-base-26.04.1-base-arm64.tar.gz`（6564 条）在本机做了两遍解包模拟
（禁止硬链接，模拟 Android 的 SELinux）：第一遍 `文件 5407 / 目录 755 / 链接 402+0`，
与真机 state.json 里的数字一致；第二遍（覆盖安装）同样 0 跳过、`bin -> usr/bin` 保持、
`usr/bin/coreutils` 仍是普通文件、`cat`/`ls`/`sh` 的链都能走到底。
`TarGzTest` 四条（首次解包、解第二遍不跟随已有链接、越界拒绝、目录挡住链接）进 CI 的
`testDebugUnitTest`。真机复测见 V59 第 2 条。

## D237 容器起不来的真凶：我们自己注入的 bionic 垫片（2026-11-04）

现象：容器里 `/bin/sh` 报
`error while loading shared libraries: libdl.so: cannot open shared object file`；
覆盖安装修不好，删掉重装才好。

**原因**：`ProxyContainer` 把 `libnmoi_netshim.so` 复制进 rootfs 并写进 `/etc/ld.so.preload`。
那个 `.so` 是 `cargo ndk` 按 **`aarch64-linux-android`（bionic）** 编的，而容器是 Ubuntu 的 glibc：
bionic 的 `libdl.so` 在 glibc 里不存在（rootfs 只有 `usr/lib/aarch64-linux-gnu/libdl.so.2`，
本机核对过包里没有 `libdl.so`）。preload 一写，**容器里每一个动态程序**都起不来。

覆盖安装修不好，是因为 `etc/ld.so.preload` **不在 rootfs 包里**（本机核对：包里没有这个文件），
重解一遍它还在原处。删掉整个 `files/envir` 才会把它一起带走——这就是"删了重装才好"。

**改法**：

- `ProxyContainer.sync` **不再注入**垫片、也不再写 `/etc/nmoi-net.conf`（没人读了）。
  代理只作用于 App 自己的请求；容器里直连。`installShim` 整个删掉——留着就是个会再犯的入口。
- `ProxyContainer.cleanStale(rootfs)`：只摘**我们写的那一行**，别人的 preload 原样留着；
  摘空了就把文件删掉。装在每次安装/覆盖安装之后跑（`EnvirRepository.installBlocking`）。
- 自检失败时把"容器里还有 /etc/ld.so.preload：<第一行>"写进原因，不再只留一句 loader 报错。
- 环境页自检卡加一颗「清容器垫片」：不重下 33 MB 也能救。

**没做**：把垫片改成按 glibc 交叉编译（要一套 aarch64-linux-gnu 工具链 + 与容器 glibc 版本对齐，
是另一件事，而且设计稿本来就写着"默认不注入"）。`crates/netshim` 与 CI 里那条 `cargo ndk` 还在，
只是没人再往里塞——下次动它时一起决定删不删。

**验证**：`cargo clippy` 零告警；真机见 V62。

## D241 发图前压缩 + 附件显示尺寸（2026-11-04）

用户当天两条：「图片显示尺寸太大了，调小点」「各种图片文件应该保持比例把尺寸压到设定范围，
应用设置里可调：自动压缩开关、长边像素、短边像素、图像质量；默认开、2048 / 2048 / 90%」。

**压缩在选图那一刻做**（`ImageCompress.apply`），不在发送时：这张图后面要落库、落盘、
base64 编进请求，三处都按同一份字节算，压得越早越省。三条规矩：

1. **等比**，只缩不裁——裁掉的是用户没同意丢的东西。
2. **只缩不放**：原图比上限小就原样发（把 800 像素放大到 2048 只是变糊变慢）。
3. **格式跟着来源走**：`image/png` 出 PNG（可能有透明，转 JPEG 会变黑底），其余出 JPEG 并按质量压。
   质量参数只对 JPEG 有意义，这一点写在设置页上，不假装对 PNG 也生效。

压完反而更大（小图重编码常见）就退回原图——不做负优化。
解码先按 2 的幂 `inSampleSize` 省内存，再精确缩：一步到位在 8 MB 的图上会 OOM。

**显示尺寸**：以前只给了 `widthIn(max = 220dp)`，高度不设限——一张竖屏截图能占满整屏
（用户截图里就是）。现在按位图比例**算出一个 240×200 的框内尺寸**再 `ContentScale.Fit`，
不留黑边。

## D242 生成状态在"去设置转一圈"之后丢了（2026-11-04）

现象：发出去之后去设置看一眼再回来，「正在生成」没了，那句「发送中…」还挂着；
提示行写「上一轮没收尾（原生那边已经没有它了），已接管」。

**原因**：事件（`Started` / `Finished` / `Failed`）是发给"正看着这个会话的那一页"的。
离开页面 → 组合销毁 → 收集器取消；那一轮在这期间跑完或失败，事件没人收。
回来时 `live` 是 `remember(sessionId)` 的新实例（null），对账那一支**只写了提示、没清 `pending`**，
于是那句「发送中…」一直挂着，而回答早就结束了。

**改法**：

1. 对账到"原生那边没在跑"时，把 `pending` / `live` / `settling` / `busy` 一起收干净，并 `reloadKey += 1`。
2. `TurnRunner` 留一份**每会话最后一轮的结果**（`takeRecent`，取走即清）：页面回来时补领，
   把"上一轮到底怎么了"说出来，而不是让用户看到一句"已接管"。
3. 还在跑的那一支：`pending` 也清掉（用户那条消息已经落库了，库里那份顶上来），`live` 重新立起来。

**顺带**：`LiveReply.sawDelta` 记"这一轮收到过增量没有"。收尾时如果一次都没收到，
提示行必须说清是哪一种：助手把「逐字输出」关了，还是端点不认流式（core 已退回非流式）。
不说的话，用户只会看到"等半天一下全出来"，然后问"流式意义何在"。

## D246 非持久命令：超时放宽到 10 小时 / `"inf"`，以及"用户点关闭"（2026-11-04）

0.15ak 的前两片。用户 2026-11-02 提的：「超时放长 + 手动关闭」。之前 `timeout_ms` 夹在
1 000–300 000 毫秒，撞上就杀进程组——一条 `cargo build` 或 `apt install` 跑过 5 分钟
就被砍，而结果里只有一句 `timed_out: true`，看起来像命令自己坏了。

**① 超时**

- 范围改成 **1 000–36 000 000 毫秒**（1 秒 – 10 小时，用户说的 1–36000 秒）。
- **`"inf"` = 不设闹钟**，而且是**唯一**一种"不超时"的写法。`0` 不合法，直接报错：
  两个写法并存的话，"没设"和"设成不超时"在日志里长得一样，事后分不清。
- 越界**报错，不静默夹到边界**。夹边界的代价是：模型以为给了 300 秒，实际 5 秒被杀，
  而它只会看到 `timed_out: true`——这种错查起来比一句报错贵得多。
- 报错点名范围与拿到的值（`timeout_of` 在 `crates/core/src/shell.rs`）。

**② 手动关闭**

- `crates/core/src/kills.rs`：进程内的 `(session, call_id) → AtomicBool` 登记表。
  为什么按会话分：多会话并发（D203）时两条会话都可能有 `call_1_0`，不分会话会关错人。
- 登记凭据 `CallHandle` **靠 `Drop` 摘除**——工具结果一回来就不该再算"在跑"。
  人手 `remove` 迟早漏一处，而漏了的表现是界面上永远有一条关不掉的灰行。
  同一个 `call_id` 被重新登记时，老的 `Drop` 不会把新的带走（`Arc::ptr_eq` 判一下）。
- `ToolContext` 多两格：`call_session`（`session.rs` 填，`run_turn` 拿不到会话 id）
  与 `call`（`agent.rs` 每条调用现造一份 `ToolContext` 填进去）。
- `shell::execute` 的等待循环**每 20 ms 看一眼**，先看关闭再看超时（同一拍成立时，
  用户按下的那一下更该被记住）。杀的是整个进程组，和超时同一条路。
- 结果里 **`killed_by_user` 与 `timed_out` 分开**，并补一句
  `note: "被用户关闭（不是命令自己退出）"`——只说 `exit_code: null` 的话，
  模型会当成"命令自己挂了"，然后照着同一条命令再试一次。
- FFI：`nmoi_tool_cancel_json({"session","call_id"})` → `{"cancelled","found"}`；
  `found:false` = 已经结束了，**不是错误**（用户点晚了一拍不该看到红字）。
- `turn_busy` 多一项 `calls: [{call_id, name, elapsed_ms}]`（没在跑时是空数组，
  同 D236 那条口径）。界面靠它画"哪一条在跑、跑了多久"，「关闭」点的是这里的 `call_id`。
- JNI：`NativeBridge.toolCancelJson(config)`，符号 **46 → 47**。

**③ 界面**

正在跑的工具调用画在**正在生成的那一块**里，一行一条 + 右侧「关闭」文字按钮。
为什么不在工具卡里：工具卡是落库之后才有的，而"正在跑"这段还没落库（D229 那条
"没有单条调用的实时输出通道"指的就是它）。收尾后整块被库里那份替掉，这一行自然消失。

- 点了之后**先改屏幕再发请求**：那一行立刻变「已请求关闭」。反过来的话，
  一条要跑几十秒的命令会让人觉得"点了没反应"。
- 「已请求关闭」要**跨快照保住**（`advanceLive` 里按 callId 合并），否则 native 还没杀完的
  那几拍里按钮会闪回可点状态，用户会再点一次。
- 时间跟着 native 走（`elapsed_ms`），不是点下去那一刻冻住的值。

**④ 整轮停止也停命令**

`nmoi_turn_cancel_json` 现在顺手把这个会话里在跑的调用一起置上（`kills::cancel_all`，
回包里带 `calls_cancelled` 计数）。只停模型不停命令的话，一条 `"inf"` 的命令会在
用户按了停止之后继续跑——屏幕上那一行还写着"正在跑"，而它确实还在跑。

**测试**：`kills::tests` 5 条（登记/Drop/跨会话/重登记/整轮全置）、`shell::tests` 4 条

`nmoi_tool_cancel_json` 3 条、`turn_busy` 的 `calls` 1 条、`LivePollTest` 3 条

## D249 「正在生成」卡死：状态收尾放进 finally，再加一条以原生为准的对账（2026-11-04）

用户报（原话）：「好像现在还卡住了，不发请求了，但是显示上还没停止，我的中转工具后台几分钟看着
没有新请求了」。同一轮还报了「点重试，显示的还是这个旧版本」。

**根因**：`busy` 只有两个地方会清——发送那条路等 `TurnEvent.Finished`，重试那条路等
`regen(...)` 返回。两条都会漏：

1. `regen(...)` 只要**抛出来**（而不是回 `Result.failure`），协程就死在那一行，
   后面的 `busy = false` 永远不执行。界面上"正在生成"一直转，原生那边早就没有请求了。
2. 事件丢了（页面刚重组完、切走再切回）也一样——`Started`/`Finished` 是 `SharedFlow`，
   没有重放。

于是三件事一起发生：`busy` 一直是 true → 「重试」进 `busy -> notice` 分支**什么都不做**
（所以"显示的还是旧版本"）→ 发送键一直是停止形态 → 一条新请求都发不出去。

**改法三条**：

1. **收尾进 `finally`**：`runRegen` 与"只存不发"都包 `try/catch(Throwable)/finally`，
   `busy`、`runningSession`、`GeneratingTracker`、`live`、`regenTarget` 一律在 `finally` 里收。
   `CancellationException` 单独 rethrow（页面走了，不该在这里写 state）。
2. **对账**（`LaunchedEffect(sessionId, busy)`）：`busy` 为真时每秒问一次 `turn_busy`，
   **连续三拍**说没在跑就收——判据跟 D236 一样"以原生为准"。三拍是因为刚点下去那一小段
   native 还没登记，一看见 false 就收会误杀刚起的一轮。
3. **「停止」键也用它**：点停止时原生说 `cancelled:false`（那一轮早结束了），
   顺手把界面收干净，别留一个转着的"正在生成"。收尾与补领结果抽成 `clearStuckTurn()`，
   watchdog 与停止键共用一份。

**重试的观感**：`LiveReply` 多一个 `regen` 位，说明行改成「正在重写这一版…（旧的留着，切得回去）」。
正文在生成期间**只画流里那一份**（旧的那版暂时不画），落库之后才换成库里的 `<n+1>/<n+1>`。
为什么不在点下去时就建一个空白版本：空正文的版本会让 `load_units` 整页读不出来
（`pitfalls.md` 2026-11-03 那条 `EmptyMessage`），"还没写"只能活在界面上。

**没做**：给 `turn_run`/`turn_regen` 加客户端侧的硬超时。原生那条路有 120 秒读超时兜底，
而"界面卡住"这一半已经由对账解决了；真出现"原生也卡住"时，用户点停止 + 对账会把界面放出来。

## D250 思考跟着版本走 + 「停」不再报成「到了轮数上限」（2026-11-04）

用户 2026-11-04 报（原话）：「好奇怪啊，你看看这是什么问题」——三张截图连起来看是：
重试中思考 6721 字 → 点停止 → 十秒后落成 `<3/3>`，正文只有两句，上面那块还写着
「深度思考 · 1373 字」，提示行写「到了工具轮数上限」。

**两个独立的毛病，凑成了一个看不懂的现象。**

### ① 「到了工具轮数上限」其实是他自己点的停止

`regen` 的返回体里**没有** `cancelled` / `truncated` 两个字段，Kotlin 侧 `parseRegen`
把 `cancelled` 写死成 `false`。于是 `finished=false` 全被读成"轮数上限"那一支：

```
cancelled -> "已停止…"        ← 从来没走到过
truncated -> "上下文到了绝对线…"
!finished -> "到了工具轮数上限…"  ← 全落到这里
```

修法：FFI 的 regen 回包补上 `cancelled` / `truncated`，`parseRegen` 读它们。
这也正是 `pitfalls.md` 那条"状态文案别把两种故障合成一句"的第三次复发。

### ② 版本只存正文，思考留在消息上

`message_versions` 没有 `reasoning` 列；`push_version` 只改 `messages.content`，
`messages.reasoning` 保持旧值。所以重试之后屏幕上是**新正文 + 上一版的思考**
（截图里 142 字的正文配 1373 字的思考）。

修法：**schema v14**，`message_versions` 加 `reasoning`。

- `push_version` 写这一版的思考；`NULL` = 这一版没有思考（切过去那块该消失，不是留空壳）。
- `save/append/overwrite_generated_version` 都带 `reasoning`（`*_with` 后缀那三个；
  老的两参版本留着当包装，测试与 FFI 的"只存正文"那条 C ABI 用它）。
- `switch_message_version` 连着 `messages.reasoning` 一起切。

**测试**：`reasoning_follows_the_version`（两版各带思考，来回切，正文与思考一起换）、
`a_version_without_reasoning_clears_it`（第二版没思考 → 切过去是 `None`）。

**没做**：工具往返那几条单元（`tool_pair`）仍然属于消息、不属于版本——切版本时它们不跟着变。
那是另一件事（一次重试要不要重跑工具），现在重试只重写正文与思考，工具块留在原位。

## D253 按轮落库：每一轮的正文都要进库，同一轮的调用装一个单元（2026-11-04）

用户 2026-11-04：「现在真机验证挡着吗？如果可以继续修就先修，修好再验证我觉得会更合适」。

**现象（实测出来的，不是推的）**：一轮里模型"先说一句 → 调工具 → 拿到结果 → 再说一句"，
屏幕上两段话都在，库里只有最后那段。`agent.rs` 每轮都写 `report.text = visible.clone()`，
而落库只读 `report.text` 一次——前面几轮的正文被覆盖掉了。用户重开会话，前面那几段就没了。

**修法**：`TurnReport` 多一个 `rounds_detail: Vec<TurnRound>`（每轮自己的 text / reasoning /

1. 每一轮先落正文（非空才落，思考跟着这一条），再落这一轮的全部调用与结果。

   0.15an 的并行批次与单条关闭都没地方挂。
3. `incomplete` 只标在**最后一轮**的正文上：前面的轮次都以工具调用收尾，它们说完了。

**为什么正文单独成一条消息、而不是塞进 tool_call 那条的 `content`**：塞进去更贴近 wire 形状，
但界面上的工具单元只画过程行、不画正文（`UnitBlock` 的 `isToolPair` 分支），
塞进去等于"存了但看不见"——铁律②。单独成一条 `turn` 单元，界面一行代码都不用改，
顺序天然是「正文 → 过程块 → 正文」。

**wire 侧的安全**：历史里会出现"assistant(正文) 紧接 assistant(tool_calls)"。三家端口都验过形状：
Anthropic 与 Gemini 的 `push_*_blocks` 本来就把连续同角色的块并成一条（各有单测），
OpenAI 兼容端口不要求角色交替。

**测试**：`every_round_text_reaches_the_database`（先红后绿：旧代码上是
`["读一下 a.txt", "", "文件里是 hello"]`，第一轮正文是空的那条 tool_call 消息）；
`three_tool_calls_in_one_message_yield_three_paired_results` 改成盯"一个单元装三条"。

**没做**：并行执行（0.15an）、按调用单条关闭的界面（kills 那层按 call_id 已经能关，缺的是每行一个按钮）。

## D254 工具批次并行：四条车道，结果按调用顺序回填（2026-11-04）

用户 2026-11-02 问「一次要调好几个工具能不能并行」，设计在 `docs/tool-execution.md`。
这一条落地的是其中的 **0.15an-a**：`Tool::lane()` + 批次执行器。

**改动**：`agent::run_turn` 里那个 `for call in &outgoing` 换成 `execute_batch`。
一次 assistant 消息里的 N 个调用算一个批次，按车道分组、组内并行，收齐后按**调用顺序**回填。

| 车道 | 并发度 | 谁在上面 |
|---|---|---|
| `read` | 4 | `read_file` / `list_dir` / `find_files` / `search` / `View-Image` |
| `workspace` | 1 | `write_file` / `edit_file` / `edit_message`，**以及所有没声明的工具** |
| `process` | 4 | `System-Shell` / `WorkSpace-EnvirShell` |

**为什么默认是 `workspace`（串行）**：新工具不知道碰不碰共享状态，猜错一次就是两个写撞在一起。
宁可慢一点，也不要"我明明写了两版，怎么只剩一版"。

**三条实现上的决定**：

1. **结果按调用顺序排，不按完成顺序**。wire 上顺序无所谓（都带 id），但历史里顺序乱了
   以后排查会疯，界面上的行也会每批换一次顺序。用 `Mutex<Vec<Option<ToolRecord>>>` 按 index 放。
2. **工具 panic 只让这一条失败**（`catch_unwind`），整批跟着炸掉的话用户会以为三条都没跑。
3. `Cancellation` 加了 `Send + Sync`：取消标志现在会被工作线程读，`Cell` 那一套测试实现
   换成了 `AtomicUsize` / `AtomicU32`。这是契约变了，不是顺手改的。

**单条关闭**（0.15an-b 的界面那一半）**本来就有**：`kills` 按 `(session, call_id)` 登记，
界面上每条正在跑的调用自己一行、点开弹窗底部有「关闭」，`nmoi_tool_cancel_json` 只置那一条。
并行之后这三样天然对上，没有新增界面。

**没做**：`session:<id>` 车道（`Session-*` 工具本身还没做，见 0.15aj）；
Gemini 老接口的同名并行（`functionResponse` 只认函数名，要等 Interactions 的 `call_id`）。

**测试**：`read_lane_runs_a_batch_at_once`（三条同时在跑，峰值 3）、
`workspace_lane_keeps_calls_serial`（峰值 1）、`batch_records_come_back_in_call_order`
（完成顺序 2、1、0，回填必须是 0、1、2）、`a_cancelled_batch_dispatches_nothing`。

## D255 消息 = parts：第一批（内存模型）（2026-11-04）

用户 2026-11-04 拍板「全做 / 全存 / 升」，这一条记第一批落地的东西。

**改了什么**：`Message` 不再有 `content` / `reasoning` / `tool_calls` 三个字段，
只剩 `parts: Vec<Part>`；`content()` / `reasoning()` / `tool_calls()` 都是从 parts 投影出来的方法。
`Part` 五种：`Text` / `Reasoning` / `Tool` / `Image` / `Notice`。

**为什么先做内存、后做库**：库的形状一改，读写两侧必须同时改完才能编译；
而内存模型可以先把 358 个调用点搬完、让 648 条测试全绿，再单独动 schema。
顺序反了就是"库已经换了、代码还没跟上"的半天不可用状态。

**两条顺序规则**（写进代码）：

1. **思考 → 正文 → 工具**。`set_reasoning` 插到最前，`set_text` 插在第一个工具块之前。
   模型是"先想、再说、再调工具"；顺序反了，界面上读起来像两次回答。
2. **`ToolPart.part` 与 `ToolPart.call_id` 分开**。前者是"这条消息里的第几块"（稳定、不复用），
   后者是模型给的调用 id（结果按它配对）。合成一个字段，改一次调用 id 会把 part 的身份也改掉。

**这一批的代价**：`content()` 返回 `String`（不是 `&str`），几处"把 `as_str()` 传进迭代器"的
地方要先把值 bind 出来（`budget::breakdown_of_units`、`session::request_pieces`）。
`request_pieces` 因此从 `Vec<&str>` 变成 `Vec<String>`——多一次分配，换来不用管生命周期。

**没做**：库还是老列（`content` / `reasoning` / `tool_calls`），读写两侧在 `repo.rs` 里做投影；
v15 的表、折行、版本 `parts_json`、编辑按 part id 都在后面的批次（见 `docs/message-parts.md` §12）。

**测试**：`parts_are_the_only_source_of_text_reasoning_and_calls`（投影与顺序）、
`set_text_replaces_instead_of_appending`（改正文是替换，不是追加）。

## D256 schema v15：正文 / 思考 / 工具调用搬进 `message_parts`（2026-11-04）

D255 把内存里的消息改成了 parts，这一条把**库**也换过去：`messages` 上的 `content` /
`reasoning` / `tool_calls` 三列删掉，改由 `message_parts(message_id, part_id, ord, kind, body)` 存。

**为什么删列而不是留着**：留着就是两份答案（铁律②）。旧版应用打开新库会被
`SchemaError::SchemaTooNew` 挡住，不会读到半份数据——所以"回滚方便"这个理由不成立。

**迁移的顺序**（`SCHEMA_V15`）：建表 → 回填 → 删列。回填读的就是那三列，先删就读不到了。
回填的块顺序是 **思考 → 正文 → 工具**，与内存里 `set_reasoning` / `set_text` 的插入位置一致；
`part_id` 按 `p1..pn` 顺排，工具块的 ord 接在正文后面。

**写入路径收敛成一个函数**（`parts::write_parts`）：追加单元、块级编辑、切版本三条路都走它。
三条各写一份 INSERT 迟早对不上——v11 那次 attachments 重建就是先例。

**切版本现在改的是块**：`versions.rs` 里那七处 `UPDATE messages SET content = ...` 全改成
`parts::set_part_text`（没有正文块就补一块，`ord` 按"思考在前、正文在后"挤位）。
`seed_first_version` 读正文也改成读 `text` 块。

**读路径**：`load_units` / `load_unit_in` 先取消息，再一次批量取 parts 挂上（不是每条一次，
那是 N+1）。`message_content` 与会话列表的 `last_text` 都改成从 `text` 块里取。

**校验**：`check_malformed_tool_calls` 从"`messages.tool_calls` 是不是合法 JSON"改成
"每一块的 `body` 是不是合法 JSON"；两个"配对不上"的查询改成 join `message_parts`。

**代价**：一行的正文/思考/工具调用拆成了 1–N 行，读一条消息要多一次 join；
换来的是 part id 稳定、编辑能按块定位、版本能带着工具块一起切（下一步）。

**测试**：`v14_rows_become_parts_in_display_order`（回填顺序 + 三列确实删了）、
storage 13 个测试二进制全绿（含 roundtrip / block_edit / versions / window）。

## D257 按 part id 编辑 + part id 不再随重建换号（2026-11-04）

D255 把消息拆成块、D256 把块写进库，这一条把**编辑**也挪到块上。

**改了什么**：

1. `BlockSelector::Part { id, output }`：`part:p3` 改这一块的主字段（正文 / 思考 / 工具参数），
   `part:p3:out` 改工具块的输出。序号轴（`tool:<i>`）保留，旧调用方不用改。
2. `Message::set_tool_calls` **保留还在的调用的 part id**。以前是"清空重建、按 `len()+1` 重新发号"，
   于是删掉一个调用之后，后面每一块的 id 都变了——而这正是序号轴那个毛病换了个样子。
3. `next_part_id` 改成"现有最大号 +1"，删掉的号不复用。
4. FFI 的 `load_units` 每条消息多一个 `parts: [{id, kind}]`：界面要按 id 定位，就得先看得见 id。

**为什么先做这一条、而不是先折行**：折行会把工具结果并进同一条消息，那时候**只能**按块定位
（一条消息里好几个工具块，序号轴更靠不住）。先把按块定位做出来，折行才有落点。

**代价**：`BlockSelector` 不再是 `Copy`（里面装了 `String`），几处 `*block` 改成 `clone()`。
这个类型本来就只在编辑路径上出现，拷贝一次可以接受。

**测试**：`part_selector_survives_a_deleted_neighbour`（删掉第一个调用之后，第二个块的 id 不变、
按 id 改的还是它）、`part_selector_refuses_an_unknown_id`（找不到就报错，不改别的块）。

## D258 折行：工具结果并进调用块，wire 单独一层（2026-11-05）

D255/D256/D257 把消息拆成块、把块写进库、把编辑挪到块上；这一条把**工具结果**也并进来。
以前一轮是"1 条 assistant + N 条 `role=tool`"，现在**一条消息 = 一轮**。

**核心形状**：`ToolPart` 多两栏 `output` / `status`（`ok` / `error` / `killed`；
`pending` 只活在内存里）。`Message::tool_result` 与 `Message.tool_call_id` 一起删掉——
留着就是"还能造出旧形状"的路。

**写入**：`agent::run_turn` 跑完一批之后直接写回那条 assistant 的块
（`set_tool_output`），不再往历史里 push 结果消息。没跑成的那几条写 `killed` +
"这一条没有执行（整轮被停）"：它确实发出去过，界面上要能指出来。
`session` 落库时一轮写一条消息（`text` / `reasoning` / 若干 `tool` 块），
`TurnRound.call_ids` 换成 `calls: Vec<OutgoingToolCall>`——被取消的那几条没有 `ToolRecord`，
只留 id 的话名字和参数就丢了，落库会少一块。

**只存结束落在写入路径**：`Storage::append_unit` 见到 `pending` 就拒。
`AtomicUnit::validate` 不拒——老库里真有开口单元，读路径要能读出来交给 `reconcile` 报。

**wire 单独一层**（`crates/core/src/wire.rs`）：`expand(&[Message]) -> Vec<WireMessage>`，
四个端口共用。规则：走 parts，攒正文；一组连续的 `tool` 块发成一条带 N 个 `tool_calls`
的 assistant，紧跟 N 条 `tool` 消息；工具之后的正文另起一条 assistant。
`ChatRequest.messages` 仍是库里那份，展开只在 `build_body` 里做一次。

**删除与编辑**：`ToolResult{index}` 落到**同一条消息**（`output` 那栏）；
删工具块 = 摘掉这个 part（两个选择器指同一块时只摘一次）。
摘空了就整行删掉——不留"没有块的消息"。`UnpairedDelete` / `ManyCalls` 两条规则退场：
一块就是一对，不存在"删一半"。

**schema v16**：先回填 `output` / `status`，再重映射 `dividers.after_seq`，
再断言 `attachments` 没有挂在工具行上（挂了就中止，不猜），最后删 parts 与行。
旧结果的状态按文本前缀判：`失败：` / `拒绝执行：` → `error`，其余 `ok`，没有结果行 → `killed`。

**没删的三列**：`unit_id` / `unit_kind` / `unit_closed` 留着，值由块形状决定
（一条消息一个单元）。删它们要重建 `messages` 表，而 `attachments` 与 `message_parts`
都外键引用它——那是单独一批的事，混在折行里风险不成比例。

**FFI / UI**：`tool_call_args` 每项多 `part` / `output` / `status`，`tool_call_id` 字段退场；
界面那一行摘要、弹窗正文、编辑文档全读这一份，不再跨消息按 `call_id` 配对。

**测试**：core 650（新增 `an_unfinished_tool_block_is_refused_instead_of_sent`、
`an_old_role_tool_row_is_refused_instead_of_guessed`、`deleting_one_side_removes_the_whole_tool_part`）、
ffi 59、storage 13 个测试二进制（新增 `v15_tool_rows_become_output_of_the_call_part`）。

## D259 一版 = 这条消息全部块；单框编辑器升 v2（2026-11-05）

折行（D258）之后一轮就是一条消息，工具块也在里面。版本只存正文的话，重试一轮带工具的回复
会得到"新正文 + 旧工具块"——切版本也换不掉它们。这一条把整份块存进版本。

**schema v17**：`message_versions.parts_json`。存 `[{id, kind, body}]`，与 `message_parts`
的列一一对应，不是 `Part` 的 serde 形状（读的人不用先猜 Rust 的枚举）。

**谁说了算**：正文与思考仍以 `origin_message` / `reasoning` 两列为准（视图切换靠它们），
`parts_json` 负责**其余那几块**（工具 / 图片 / 通知）。所以切版本是"先恢复块，再铺正文"，
不需要在快照里存两份正文。

**写入**：
- `seed_first_version` 快照消息现在的块（第一版就是眼前这一份）；
- `push_version`（重试）写的是**新的一轮**：[思考?, 正文]，旧工具块跟着旧版本走；
- `switch_message_version` / `delete_message_version` 走同一个 `apply_version`：恢复块 → 铺视图那一份正文。

**回填**：当前版且带工具块的，快照现在的块；其余版本只有正文与思考。
旧版本本来就没存过工具块，回溯等于编造。

**顺带修掉一个"两份答案"**：`unit_kind` / `unit_closed` 以前由调用方写，切版本把工具块摘掉之后
它们还停在 `tool_pair` / `1`，`load_units` 当场报 `ToolPairNotAssistant`。
现在 `parts::write_part_list` 这个唯一写入口顺带把它们按块形状改掉——
这两列从此是**派生值**，不再有第二个答案（离"删掉它们"只差一次重建表）。

**单框编辑器升 v2**：`<nmoi:tool index="0">` → `<nmoi:tool part="p3">`，头是 `v="2"`。
`part` 为空的文档按 v1 写、按 v1 读——草稿里存的老文档照样打得开。
v2 文档里写 `index=` 直接拒（那等于把序号轴又抄一遍）。
界面发来的 op 也从 `{block:"tool", index}` 换成 `{block:"part", id, output?}`；
工具参数的 JSON 校验跟着**块的实际种类**走（以前只看选择器名字，`part` 这条路会漏）。

**测试**：`switching_versions_restores_tool_parts_too`（切回旧版工具块回来、切到新版走掉）、
`v16_versions_gain_a_parts_snapshot`、`tool_blocks_use_part_ids_in_v2`、
`v1_documents_still_parse`、`v2_document_refuses_index_tags`。

## D260 迁移要能重复执行：加列挪到 Rust，事务里重读版本（2026-11-05）

真机第一次打开 v17 时撞了：`迁移到版本 17 失败: duplicate column name: parts_json`。

**根因**：`openStorageJson` 在四个地方被调（`ConversationRepository` ×2、`ChatRepository` ×2、`NmoiFfi`），
两个连接同时从 v16 起跑：先到的把 `ALTER TABLE` 与 `user_version=17` 一起提交，
后到的那份还拿着开头读到的 16，于是再 `ALTER` 一次——撞"列已经存在"。
`ALTER` 本身是事务性的（本地验过：同一事务里 ALTER 之后报错，回滚后列不在了），
所以问题不在回滚，在**版本号读得太早**。

**两处修法**：

1. `Migration` 多一个 `prepare: Option<fn(&Connection) -> Result<(), rusqlite::Error>>`。
   SQLite 没有 `ADD COLUMN IF NOT EXISTS`，v17 的加列改在 Rust 里：先查 `pragma_table_info`，没有才加。
   这样"列加上了、版本号没跟上"的半截库也能自己走过去。
2. 每个迁移拿到写锁（`BEGIN IMMEDIATE`）之后**再读一次 `user_version`**；已经追上就空提交跳过。
   这一条对**所有**迁移都成立，不只 v17。

**判据**：`v17_heals_a_database_that_already_has_the_column`——造一个 v16 + 已有 `parts_json` 的库，
迁移要成功、回填要走、版本落到 17。

**没做的**：四个入口各开一次库这件事本身没动。SQLite 允许多连接，代价是每次都要跑一遍
完整性检查与语义扫描；要不要收敛成一个单例，是另一件事（会牵动 UI 的初始化顺序）。

## D261 真机四条：即时显示、一次调用一个弹窗、工具轮的正文与思考、跑完的也能点（2026-11-05）

用户 2026-11-05 晚报了四条，逐条落地。

**1. 发送后没有即时显示。**
`TurnEvent.Started` 是在 `TurnRepository.send` **之前**发出来的，那一刻用户那条还没落库；

**2. 两次调用"粘一块"。**

**3. 工具那一轮的正文与思考被吞。**

## D263 重试 = 整轮替换；一版 = 一整轮（2026-11-06）

真机报的是两件事，其实是同一个根因：

1. **重试完**：工具块是上一轮的，最后的思考与正文是这一轮的。
2. **重试途中**：旧那一轮还挂在屏幕上（用户原话：「重试过程不要显示旧版本啊」）。

**根因在库，不在渲染。** 折行（D258）之后一轮回答是 N 条消息（每轮一条），
而 `regenerate_turn` 只把最后那条落成新版本：前面几轮的消息原样留在库里，
新的那一轮（连同它的工具块）根本没落库——`report.rounds_detail` 只被用来拼最后一句话。
于是屏幕上必然是「旧工具 + 新正文」。

**改法（三层一起）：**

1. `HistoryStore::replace_turn(session, after, units, keep_version)`：一个事务里
   "快照旧的那一轮 → 删掉 `after` 之后的全部行 → 写新的 N 条 → 记版本"。
   `after` = **最后一条用户消息**（重试时就是 `up_to`；续话时 `up_to` 是目标消息自己，得往前找一条）。
   不再用「只换最后一条」那条路。
2. **一版 = 一整轮**（`message_versions.parts_json` 存 `{"turn":[{role,source,created_at,incomplete,parts}]}`）。
   切版本 = 删掉这一轮的全部行、按快照写回来；轮数不一样时消息 id 会重排，
   版本行跟着搬到新的落点上（否则 `<n/n>` 会消失）。
   老库里的一版仍是 `[{id,kind,body}]`（只管一条消息），靠有没有 `turn` 键分开。
3. 界面：重试/续话期间**整轮都不画**（以前只藏 `ChatRow.Process`，折行之后工具那半行是
   `ChatRow.Single(ToolsOnly)`，于是留在屏幕上），live 一律画在底部——
   目标那一行已经被藏掉了，画在它身上等于把旧的又放出来一半。

**为什么版本要跟着改成整轮**：只换最后一条的话，`<1/2>` 切回去是「旧正文 + 新的工具」，
和这次的 bug 是同一个形状。既然重试换的是整轮，版本就必须能表达整轮。

**判据**：
- `cargo test -p nmoi-storage --test turn_replace`（4 条：整轮替换 / 切回整轮 / 轮数变少 / 关掉新版本）；
- `cargo test -p nmoi-core --lib regenerate_replaces_the_whole_turn_not_only_the_last_message`；
- 真机 V79。

## D264 过程卡吸附、空正文不画、工具弹窗实时（2026-11-06）

顺带修了 `ThinkingProcessRow`：它以前一律读 `message.content`，跟着正文一起进来的思考

**判据**：`ProcessRowsTest` 14 条（新增吸附 3 条 + 字节判据 1 条）；

## D266 抽屉只画一份（2026-11-06）

真机录屏（2.2 秒、66 帧）逐帧量出来的现象：

- 拉出途中：抬头「我 / 晚上好」与搜索框的 y 与全开时**完全一致**（396–511）；
- 但选中那一行的紫色底从 552–689 跑到 842–981 —— **正好高了两行**（每行 146px）；
- 松手/动画一结束就跳回正确位置。

原因：抽屉有**两套渲染分支**——拖动/惯性走 `manual`（`Surface` + `offset`），
点开走 `AnimatedVisibility(slideInHorizontally)`。两份 `DrawerPanel` 是两个组合实例，
各有各的 `LazyColumn` 状态；而且点开那条分支**只有打开时才组合**，
第一次打开要现场排整个列表（用户说的"刚启动拉出侧边栏卡一下"）。

改法：**只剩一份**。内容按最终宽度排一次，开合只移动它（`offset`），
位置由一个 `Animatable`（`settle`）跟着 `open` 走；手动阶段交棒时先 `snapTo(target)`
再撤手动状态，避免闪一帧。遮罩的透明度跟着同一个位移算。

判据：拉出途中选中行与全开时的 y 一致；第一次打开不再现场组合列表。

## D268 置顶顺序不再等"打开"；停止键按下即灰（2026-11-06）

## D294 `/tmp` 会话隔离（2026-11-09）

工具里的 `/tmp` 现在落到 **`sessions/<id>/tmp`**，容器里的 `/tmp` 挂的也是它——两边是同一份；
另一个会话读不到。系统 shell 不做这个映射（它跑在宿主机上，没有"会话"这个概念），
但**两把 shell 的说明里各写了一句**，否则模型会以为两边是同一份。

落法（三处，都必须一起）：

1. 文件工具：`target()` 只认一个固定前缀 `/tmp`，其余绝对路径照旧拒绝——放行绝对路径等于
   把 `Workspace::resolve` 那道"只许落在根里"的检查作废。
2. 容器：`EnvirSpec::session_tmp` 绑到 guest 的 `/tmp`，**绑之前 `create_dir_all`**：
   目录不存在时 proot 的 `-b` 静默不生效，表现是"容器里写的 /tmp 不见了"。
3. 存储：`HistoryStore::session_tmp_dir` 默认 `None`，SQLite 实现给
   `<库目录>/sessions/<id>/tmp`，与 `images/` 同级，删会话时整目录一起删（先删库再删目录）。

没有会话上下文时 `/tmp` **报错，不回落**宿主的 `/tmp`：回落等于让两个会话共用一份，
那正是这一层要隔离掉的东西。判据：`tmp_in_a_file_tool_lands_in_the_session_scratch`、
`the_scratch_of_one_session_is_invisible_to_another`、`tmp_without_a_session_is_an_error_not_a_fallback`、
`the_scratch_still_refuses_to_escape`、`envir_binds_the_session_tmp_and_creates_it_first`；
真机 **V104**。

## D304 文件附件：只收读得出文本的（2026-11-09）

## D305 压缩接上 FFI 与界面（2026-11-09）

- **两步，故意的**：`nmoi_compress_plan_json` 只读库算切点（不调模型、不动数据），
  `nmoi_compress_run_json` 真跑（同步阻塞几十秒）。压缩**永久移走一段历史**，

- **没有百分比进度**：模型往返几次只有它自己知道。给的是已用秒数 + 一句"它还在跑"。

- **密钥跟多 Key 模式走**（D302）：多 Key 时从池里挑一把，单 Key 时读那个文件。

## D308 世界书的粘性 / 冷却 / 延迟（2026-11-09）

- `sticky`：命中之后再多带 N 条仍然算激活。做法是把扫描范围从 `scan_depth` 伸到
  `scan_depth + sticky`，再看最近一次命中离末尾多远。
- `delay`：窗口里还不到 N 条时不激活（会话刚开始，设定别急着塞）。
- `cooldown`：最近 N 条里提到过就先不注入。**判据是"最近一次提到"，不是"上一次生效"**——
  后者要跨轮存状态，而跨轮状态一旦进库就会和归档、压缩打架（窗口就是真相）。
  这一条写进代码注释与界面里，别让人以为是 ST 那个精确语义。
- 三个都默认 0 = 关：老数据行为不变。

## D317 归档物化到 `/archive`：标记行自带可读路径（2026-11-11）

- **一个名字，两处都能用**：文件工具把 `/archive/...` 解析到这条会话的归档目录；
  容器里同一份也挂在 `/archive`（`EnvirSpec.archive`，FFI 的 `envir.archive`，Kotlin 侧
  `ToolingRepository.sessionArchiveRoot`）。容器里叫 `/chat/archive`、工具里叫 `/archive`

- **归档只读**：`write_file` / `edit_file` 打 `/archive/...` 直接拒，并说明原因

- **文件不在就明说**：`/archive/<hex>.txt` 不存在时回"取不到了，只能按标记那一行处理"，

- **复制会话要带上归档**：`copy_conversation` 把副本里引用到的 ref 从库里照抄一份到新会话目录，

## D324 压缩的提交必须落在 run 里；中断的那一半不做接续（2026-11-12）

用户 2026-11-12 问：压缩跑到一半中断要不要也做成可以接续的？

先查了一下现在到底会不会"到一半"，结果撞上更前面的一个问题：**压缩跑完从来没有落过库**。

`Storage::commit_compression`（D45 定的"归档 + 摘要 + 分界线，一个事务"）写得完整、幂等、
也有 storage 层的测试，**但全仓没有调用点**。`nmoi_compress_run_json` 拿到 `CompressionOutcome`
之后只把它变成 JSON 交回界面，`outcome.divider` 于是只活在返回值里：

- `archive` 表多出 N+1 行（`finish` 里逐条 put，各自一个事务）；
- `dividers` 表一行都不多 → 窗口没变 → 下一次请求照样把整段历史发出去；
- 而界面照样报"归档 N 条 · 摘要 M 字"。

也就是说 V115 第 5 条（"被压走的那几条不在窗口里了"）从来不可能通过，只是没人走到过。

**修法**：`nmoi_compress_run_json` 在拿到 outcome 之后调 `storage.commit_compression`，
返回值多一个 `divider` id 供界面对账。放在 run 末尾而不是独立的一步，是因为 plan 已经让用户
看过切点并按下了开始——那一按就是"允许写"，中间再插一道确认只会变成第二道闸。

**为什么压缩不做接续**（回答用户那个问题）：

1. `CompressionJob` 整个住在内存里：冻结的 `above` / `below` 快照、草稿、ops 一样都没落库。
   进程一死，没有可续的东西；要"续"就得把草稿写进库，等于给压缩开一张"未完成的压缩"表，
   跟 D252「只存结束，不存进行时」正面撞。
2. 生成中断能续，是因为"已经吐出来的字"就是进度；压缩不是——中断那一刻只有半个草稿，
   覆盖率基线（哪些单元的关键字还没进草稿）没存，切点也可能已经过期。
3. 重来的代价是几十秒，判错的代价是一条会永久移走历史的链路。

所以压缩只有两种形态，接上事务之后都安全：drive 阶段死 → 什么都没写；事务里死 → 回滚 → 什么都没写。
界面上要说的是一句"这次没压成，历史一条没动"，不是"压了一半"。

判据：`crates/ffi/tests/compress_e2e.rs`（假服务两趟往返：追加草稿 → `done`）跑完后
**另开一个连接**读 `dividers`，必须正好一条、`load_window` 已压缩、`load_units` 条数不变。
先在旧代码上红过（`分界线：[]`），修完绿。ffi 67 条不变；JNI 符号不变（55）。

## D326 自动压缩：默认关、只认绝对线、只在轮末（2026-11-12）

用户 2026-11-12：「自动压缩也做一个开关吧」。

开关本身很小，麻烦的是**判据**。core 早就算好了（`TriggerPolicy` 两条线 + 成本回本判据），
`SessionTurn::should_compress()` 一直在，但只有测试在调；Kotlin 把 `trigger` 拼成一句中文
放在提示行里就完了。所以这一批不是"加一个开关"，是**把那根线接上**。

四条规矩，每条都有理由：

- **默认关**。压缩会永久移走一段历史，"第一次"必须是用户自己按下去的。这跟世界书那条同源：
  默认全选是个坏默认值。
- **只认绝对线（0.55）**，建议线只提示。建议线的意思是"该压了"，拿它自动动手等于在用户
  正看着的那一段中间插一刀。
- **只在轮末**（`turnDone` 变了才动）。进会话就压会让人莫名其妙——他可能只是回来看看。
- **过一次线压一次**（`armed`）。压完窗口确实会变小，但万一还压不动（没有可压的切点），
  没有这一道就会每次重组都试一遍。

**判据用屏幕上那个百分比**，不另算一个数：用户看到 56%、线画在 55%，压缩就是他预期的。
另算一个"core 那边的数"只会让两个数字在界面上打架——这正是 D315 那条"同一个概念留一个出处"
的同一个道理。

**顺手修了一个会咬人的地方**：`contextPercent` 原来拿**全量**算（压过之后全量还是满的，
占用率会永远显示 98%）。现在按窗口算：线下单元 + 摘要自身（`divider.summary_tokens`，
由 FFI 用 core 的估算器算好带出来）。这不只是显示问题——自动压缩拿它当判据，不改就会反复触发。

**`CompressionSignal` 从中文串改成结构**（`trigger` / `action`）：拿中文串去 `contains("absolute")`
是拿正则猜状态，跟多 Key 那次把 401 压成一句自然语言是同一个毛病。

判据：`compress_e2e` 里多一条 `divider.summary_tokens > 0`；真机 **V135**（六步）。
JNI 符号不变（56）——这一批没有新符号，只多了一个 JSON 字段与界面。

## D327 断流：已经说出来的那半段是用户的（2026-11-12）

用户 2026-11-12：「反正就是某些错误如果可以接续，做个接续就行」。

查下来最该修的不是"加一个接续按钮"——**残文根本没进库**。
`ChatStream::collect_all` 中途报错就把手上那段扔了（自己 `?` 出去），`run_turn` 拿着 `Err`
一路 `?` 出去，`run_session_turn` 连落库都走不到。屏幕上那半段话、库里那条消息，一起没有。
用户看到的是一张"重试 / 放弃"的卡，而他刚才明明读了一半。

**一条规矩**：收到过字，就按断流收尾；一个字都没有，才算失败。

- 收到过字：合成一个 `Collected { interrupted: Some("连接在生成途中断了") }`，
  顺着 D194 那条老路走——`finished = false`、`truncated = true`、残文进 `report.text`，
  落库时 `round_units` 自己会标 `incomplete = 1`，界面那一行「有 N 条没说完 · 续话可接着写」
  是 D323 早就做好的。
- 一个字都没有：还是 `Err`。这种没有可以接的东西，给"续话"等于给一个点了不动的按钮。

**`cut` 单独一个字段**，不借 `truncated`：断流也置 `truncated`（"没说完"的老判据不变），
但那时界面上写的是「上下文到了绝对线」——用户什么都没满，这句话是错的。
现在 `cut` 非空就说「连接断了（…）：已收到 N 字，可以续话」。
三种"没说完"终于有三句话：上下文满了 / 网络断了 / 用户点了停止。

判据：`crates/core/src/agent.rs` 新增 `a_stream_that_dies_midway_keeps_what_it_said`
（响应体读到一半返回 `ConnectionReset`）——`report.text` 是那半段、`finished = false`、`cut` 有值。
core **713**（+1）；真机 **V136**（五步）。

## D328 「摘要」那张卡的齿轮：能改语气，不能改格式（2026-11-12）

0.16e 的最后一块。消费者 D322 早就在跑了（索引摘要），但那张卡一直没有入口——
面板里写着能配、程序不用，比没有这个框更坏。

三件事定死：

- **角色那段排在脚手架之后，不替换它**。`summary::SCAFFOLD` 不只是语气，它是**格式契约**：
  `parse_lines` 数的是 `1. …` 这种行，超过 48 字直接丢。让用户那段替换它，一句"随便写"
  就能把整条链路冲成空手而归，而且不报错。所以拼法跟别的角色一致：脚手架 → 全局 → 角色。
- **摘要不摆世界书**。`SummaryTarget` 里没有这个字段——摆一列勾选框就是"点了什么也不发生"。
  别的五个角色都有那条路，只对摘要收起来。
- **空框说清空了会怎样**：占位写「留空：只用内置的索引规则（段号、每段一行、48 字以内）」。
  不摆一个空框让人以为"这里能调，只是我没填"。

拼装只在 `TurnRepository.summaryJson` 一处：`PromptVars.compose(null, 全局, 角色)` 再 `fill`
站位字符串，跟压缩那条（D318）同一套写法，不另起一份。

判据：`crates/core/src/summary.rs` 新增 `the_role_prompt_lands_after_the_scaffold`
（假传输层记请求体，断言脚手架那段在前、角色那段在后）。core **714**（+1）；真机 **V137**（五步）。

## D329 命令执行前询问：能力开关不等于"随便跑"（2026-11-13）

`NativeShell` / `ContainerExec` 的字面意思只是"能用命令"，可它一打开就是全放行——
中间缺一道"这一条要不要点头"。补上：

- **两个开关**：`shell.ask`（默认开）、`shell.blacklist_mode`（默认开）。都只存本机
  （跟能力开关一样：换台机器导入一个 `true` 只是句空话）。
- **判定三段式**：拆子命令 → 归一化（去引号、还原反斜杠、剥 `sudo`/`xargs`/`timeout` 套壳、
  不展开变量）→ 匹配。危险参数走**结构化判据**，不是正则：`rm` 看 argv 里有没有
  `r`/`R`/`--recursive`，所以 `-rf` `-fr` `-vrf` `-f -r` `-R` `--recursive` 全命中。
  正则留给自定义规则（≤200 字、线性、编译失败拒绝保存）。
- **`rm` 不带 `-r` 也问**：删一个文件同样收不回来；`-r` 只是把"一个"变成"一片"，
  所以两条规则分开，标签分别写 `rm` / `rm -r`。`rm --help` 不问。
- **拒绝档**（`rm -r` 打到 `/`、`~`、`$HOME`、`/usr` 这类）不给"允许一次"，并且
  **不受组开关影响**——地板不该被一个批量开关抬走。
- **超时 = 拒绝**（60 秒）。等待时如果用户按了停止，立刻按拒绝收尾，不挂在那儿。
- 询问列表并进 `turn_busy.asks`；回答走 `nmoi_tool_answer_json` / `Java_..._toolAnswerJson`。

判据：`shellguard` 13 条、`shellask` 5 条，core **732**（714 + 18）；真机 **V138**。
未验：Kotlin 只过了本机那次类型检查的**准备**没跑成（`/tmp` 清空后要重下 kotlinc，
本机网络超时），所以界面这一层目前只有 CI 的 `testDebugUnitTest` 与 android job 会碰它。

## D330 `Voice-Caps`：先让模型问得出"这一条支持什么"（2026-11-14）

`Speak` 的参数该有哪几格，取决于**选中那一条**的能力表：`tts-1` 不收 `instructions`，
`gemini-*-tts` 收自然语言风格、输出还是裸 PCM。先定 schema 就是拿一个猜出来的并集去顶所有家，
每家都收到自己不认的字段；先让模型能问，schema 才有依据。

- **一个只读工具**，`{tts, asr, sing, note}`。`tts` / `asr` 带 name / provider / model /
  voice / language / supports / known_* / has_key。没配的那一条**显式给 `null`**：
  缺字段与"没有"是两件事，模型没法从缺失里读出"这条没配"。
- **新能力位 `Capability::Voice`（默认关）**。两层都满足才声明：请求里带了 `voice`（Kotlin 只在
  总开关开着、且至少有一条选中或唱歌真的能用时才带），且 `VoiceCaps::any()` 为真。
  为什么两层：`Capability` 说"这一档允许"，`any()` 说"这一轮有东西可答"。
  只装了声库、引擎没接的时候不算——它只会回一句"唱不了"，占着声明位让模型白试一次。
- **密钥不过这一层**：`has_key` 是布尔值。`Voice-Caps` 不上网，`Speak` 落地时才谈密钥怎么走。
- **`sing` 的判据与工具页同源**：`svsEngine()` + `VoiceBankRepository.installed`。
  界面能拨、模型问不出，或者反过来，都是两份真相。
- `known_*` 只是快捷清单，不是白名单——这一条写进了返回体自己的 `note` 里，模型不会把它当枚举。

判据：`crates/core/src/voicecaps.rs` 9 条、`crates/ffi/src/turn.rs` 2 条（坏字段点名到
`voice.tts.model`；`voice` 缺席与 `null` 等价；能力位跟着条目走、只装声库不算）。
core **758**（749 + 9）、ffi **69**（67 + 2）；Kotlin 全量类型检查只剩那 9 个已知 `R`。
真机 **V139**（六步）。未实测：真机一次都没走，FFI 那条路目前只有单测。

## D331 `Speak`：先接一家形状，其余明确回"还没接"（2026-11-14）

`Voice-Caps`（D330）回答"这一条支持什么"，`Speak` 就是照着那句回答动手的那一步。

- **只接 OpenAI 形状**。`{model, input, voice, response_format, speed}` → `POST <base>/audio/speech`。
  MiniMax `t2a_v2`、Gemini 的音频模态、系统 TTS、本地模型各有各的请求体，硬凑一个"通用体"
  会得到一个各家都不认的 400，而报错还看不出是谁的错。所以它们在这里**按名字回一句"还没接"**，
  并说清现在支持哪一种（"provider=openai，或者按 custom 配一个兼容基址"）。
- **`response_format` 写死 wav**。`trim` / `normalize` / `fade` 只认 16-bit PCM；
  收 mp3 就只能原样落盘，于是"后处理"变成一个说法而不是事实。回包不是 WAV 时，
  报错带**开场 16 字节**——这一条认不认 wav，看那一眼就知道。
- **两种写法**：`text` / `script`。分段是**每段一次请求**，再按 `concat` 拼；每段自己的
  `rate` 与 `pause_ms`。末段之后的停顿清零（多一截静音没有意义，还会让时长判据错）。
- **参数按能力表裁**：`rate` 只在 `supports` 含 `speed` 时接受。这是判据 5 的落点：
  不支持的参数**点名拒绝**，而不是悄悄忽略——忽略会让模型以为它生效了。
- **落点 `sessions/<id>/audio/<hash>.wav`**，先写 `.part` 再改名。删会话整目录一起删
  （`session_dir` 本来就整目录删，这一层不用另加清理）。
- **密钥只走一步**：Kotlin 从 `Vault` 读出来塞进这一轮的 `voice.tts.api_key`，core 只拿它拼
  `Authorization`。结果、日志、库里都不出现；`Voice-Caps` 的回包里也没有。
  **只给 TTS**：ASR 那条链还没接，用不上的东西不往前递。
- **听得见才算做完**：工具详情里认回包的 `path`，就地一个播放键（`MediaPlayer`，
  关弹窗 `DisposableEffect` 释放）。只给路径的话，用户拿到的是一句"文件在某个私有目录里"。

判据：`speak` 9 条（真 socket 假端点：`POST /v1/audio/speech`、`Authorization`、
`response_format=wav`、产物是能解析的 wav 且峰值接近 0.95；分段两次请求 + 时长含停顿；
三家不支持各自点名；缺密钥 / 缺基址；两种写法同时给；`rate` 不被支持；非 WAV 回包带字节；
能力位关着不声明；密钥不出 `Voice-Caps`）。
core **767**（758 + 9）、ffi **69**、storage 全绿；kotlinc 只剩那 9 个 `R`。
真机 **V140**（七步）。未实测：真端点一次都没打过（本机端点只有 chat 那条路），
真机也没装过这一版。

## D332 工具面板逐项开关：关掉 = 不声明（2026-11-14）

`NativeShell` / `ContainerExec` 那些开关管的是"这台机器允不允许"，语音那一层管的是
"这一条支不支持"。还差一层：**用户不想让模型看见某个工具**——它占着声明位、被模型反复调用、
每次都要占一轮上下文。补上（b1）：

- **清单从 native 读**（`NativeBridge.toolNamesJson()` → `nmoi_tool_names_json`）：
  在 Kotlin 里另列一份 13 行，下一个工具落地时没人会记得加，而且两处数字迟早对不上。
- **关掉的名字随这一轮下发**：`tools_off: ["read_file", "Speak"]` → `SessionConfig.tools_off`
  → `ToolContext.tools_off` → `specs_excluding(policy, off)`。**不声明**，不是声明了再拒绝。
- **两条路同一份语义**：`gate::plan_tools` 也认 `ToolSwitches.disabled`，理由单列
  `ToolDrop::ToolOff`（"这一项在面板里关着"）。冻结那条路现在没接，但语义不能两样。
- **顺序**：先看"用户关没关"，再看"权限开没开"。前者是他自己的决定，后者要他去别处改；
  报错报成后者，他会去改错地方。
- **清单只存名字**：`tool.off.<name>` 存本机（跟别的工具开关一样不进库）。注册顺序会变，名字不会。
- **面板上只有一行规则**："关掉的不发给模型"。不逐行写解释——一屏十几行小字，没人读。

判据：`specs_excluding` 2 条（关掉的不出现、名字对不上时整张表不受影响）、`plan_tools` 1 条
（`ToolDrop::ToolOff` 与"权限没开"分开）、ffi 1 条（`tools_off` 只认字符串、缺席为空）。
core **769**、ffi **70**、JNI **59**；kotlinc 只剩那 9 个 `R`。真机 **V141**。
