## D184 计划与设计稿冲突的六条（按严重程度）

这一节是"按设计稿为主"的落地清单，不是评论。

**① 编辑参数必须是单元，不是消息（§4.2 / §4.7 硬约束）。**
设计稿：「所有编辑工具的参数类型是 `unit_id[]`，不是 `message_id[]`；从类型层面消除误用可能。」
我们现在的 `edit_message` 是 `message_id` + `blocks` → **修**：工具参数改成 `unit_id`
（消息 id 仍可用于只读查看），工具内部先把 unit 解析出来再动。

**② "改块正文/思考/参数/结果"不在设计稿的操作集里。**
设计稿的操作集是 `ctx_compress / ctx_discard / ctx_restore / ctx_reorder / ctx_pin / ctx_finish`，
**内容是 extractive 处理的（头尾截断），不许 LLM 重写**。用户要的"模型能改一切块"是产品功能的扩展，
不是模式四原生能力 → **处置**：两套工具分开，别混名。
`ctx_*` 走上下文级（unit 数组）；`edit_message` 明确标注为"单元内内容编辑（本项目扩展）"，
并且必须满足：以单元为单位、成对改/删、不产生孤儿 call。

**③ 没有 undo 的原材料（§4.4）。**
我们的 `edits` 表只存 `before_hash/after_hash` —— **恢复不了任何内容**。设计稿要求
"所有编辑记录 diff（含原值），undo 日志可导出"。→ **修**：编辑前把原文写进 undo 日志
（`settings(scope="undo")`，不进 schema），可导出；`edits` 表保持"审计索引"的角色。

**④ 没有快照，而模式四 `require_snapshot=true`（§4.8）。**
进入编辑态前必须冻结当前上下文，退出时保留或回滚。→ **排期**：先有 undo 日志（③），
快照用"整会话消息 JSON 的只读副本"实现（不搬归档），回滚 = 用快照覆盖消息表。

**⑤ 没有覆盖率校验（§3.6），编辑前没有质量门。**
设计稿要求执行前抽硬事实（路径、命令、错误码、数字、未完成项）并在处理后校验。
→ **修**：`core::coverage` 纯函数；**先接在"删除单元 / 删除工具对"上**（删除是最不可逆的一步）。

**⑥ 压缩后没有任务锚点（§2.3.0，v1.1 强制项）。**
实测：缺锚点 3/8，加一句"当前任务：…"后 8/8；而且**唯一有效载荷是任务陈述本身**，
"历史已结清"单独存在时 0/4。→ **修**：凡是有摘要（压过）的会话，请求里在当前轮之前
注入一条"当前任务：<最后一条 user 消息原文>"（不概括、不改写），角色 user。

**另外三条不算冲突，但要说清**：

- **输入框**：设计稿 §2.3 明确"Android 的文本输入要用 `AndroidView` 包原生 `EditText`"，
  Compose 的 `BasicTextField` 镜像慢一帧/不刷新。我们现在聊天输入区与消息编辑页都是
  `BasicTextField` → 新的"单框编辑器"**必须**用 EditText 岛（它要编辑的是整条消息，长文本）。
- **`ctx_finish` / `max_ops` / `timeout`**：我们一个都没有 → 编辑可以无限次、没有提交点。
  先把 `max_ops` 折算成"一轮最多改 N 块"（现在 8），提交点等快照做完再上。
- **归档有表、没有回灌工具**：`fetch_archive(ref)` 是设计稿里"唯一真正的理论改进"
  （确定性恢复 vs 检索式恢复）。我们的 `archive` 表没有任何工具能读回来 → 排期。

## D185 这一轮先落地哪两条（理由）

- **⑥ 任务锚点**：成本最低（一句话）、收益最大（3/8 → 8/8），而且它只改"发出去的请求"，
  不动存储，风险可控。
- **⑤ 覆盖率校验（接到删除上）**：删除是唯一不可逆的一步，先给这一步装门。
  纯函数，可单测，不需要真机。
- ③④ 的 undo/快照要动存储与导出面，和"edit_message 改成 unit 级"一起做更顺 → 下一轮开头做。

## D183 三个名字对齐：档位4 = 模式4 = F4（2026-10-29 用户确认）

同一个东西在三个地方有三种叫法，检索时三个都得能搜到：

| 说法 | 出处 | 是什么 |
|---|---|---|
| **档位 4 / 模式 4 / F4** | 用户口语 / 设计文档 §4 / 用户简称 | 灰烬模式：模型对上下文有**完全编辑权**，可 compress / discard / restore / reorder / pin，对象是**原子单元** |
| **档位 3 / 模式 3 / F3** | 同上 | 打标模式：模型只 `mark_context`，**不执行**；可操作范围被限制在「倒数第二条 assistant 消息 → 末尾」 |
| **F3 形态 / F4 形态** | 设计文档 §2.2 | 内容形态：F3 = masking 占位符、F4 = 仅指针。**与上面的档位不是一回事**，只是共用 F3/F4 这两个符号 |

三条容易混的推论，写死在这里：

1. **范围限制只属于模式 3**（窗口到"倒数第二条 assistant"）；**模式 4 覆盖当前上下文能覆盖的全部范围**。
2. **内容级改写（改正文/思考/工具参数/结果）不是设计稿的模式 4 操作集**，是我们的扩展，见 D184。
3. 搜索时用 `rg "档位4|模式4|F4"` 三个词都能命中这一条。

## D184 内容改写＝模式 4 的扩展（1A–8A 的结论，2026-10-29）

用户逐条拍了板（1A 2B 3A 4B 5 6A 7A 8）：

- **3A**：undo 日志存 `settings(scope="undo")`（存 before/after **原文**，可导出），不动 schema。

## D185 上下文隔断 = 分段独立会话；重试 = 前缀重发（用户 2026-10-29）

**隔断**（分界线，divider）：把会话切成 A/B/C 段。

- **请求只发当前段**（Q1=a）：不带其他段的明文、不带摘要、不带跨段锚点。用户原话："既然是隔断那肯定是完全访问不到其他段的消息"。
- **显示上仍是同一个会话**：滚动能看见 A/B/C，段与段之间画线。
- 段的边界：最后一个分界线之后 = 当前段；没有分界线 = 会话开头起算。

**重试 = 前缀重发**（不是"再发一遍那句话"）：

| 重试谁 | 发给模型的内容 | 结果落在哪 |
|---|---|---|
| 用户消息 U | 段首 → **U（含）** | U 下方那条助手消息的**新版本**（`n/n` +1）；下方没有就**插入**一条，不动下面的 |
| 助手消息 A | 段首 → **A 之前**（不含 A） | A 的**新版本**（`n/n` +1） |

「允许生成新版本」开关（0.15m，默认开）：关着时**覆盖**那条助手消息，不产生新版本。
「新版本」的时间戳取**生成时刻**，`n/n` 里排在最后——用户要的是"目前这个时间的新答案"。

**续话**（长按发送）：不新增用户消息、不改旧消息，把当前段原样再发一次；
**最新是助手消息时，结果合并进那条**（追加正文）；最新是用户消息时照常落一条新助手消息。

## D186 版本 = 一整条消息的块账本（Q3，2026-10-29）

用户："难道不是一起存储在一条消息的数据内吗？肯定是跟着它所在的消息走啊。"

所以：**一个版本不是"两份正文"，而是「正文 + 思考 + 工具参数 + 工具结果」的一整套**；切 `n/n` 时四块一起切。

落地（不动 schema，选 3A 的同一套思路）：

- 正文仍走 `message_versions` 的两列（`origin_message` / `tooledit_message`）——那是 D152–D154 定的。
- 思考 / 工具参数 / 结果在"这一版"的取值放 `settings(scope="edit_blocks", key="<消息 id>:<版本号>")`，整块 JSON 覆盖；没有就退回 `messages` 里的现值。
- 切版本 = 先按版本号取块账本，再整条重画；**不许把某一版的思考叠到另一版上**（那就成了"看不见的覆盖层"，铁律②）。

## D188 0.15f 落地口径：成对、落红、上限（2026-10-29，实现时定的三处细化）

D184 定了"内容改写是模式 4 的扩展"，实现时有三处必须写死，否则下一个人会按字面把库改坏：

1. **"成对"只对删除成立**。工具块**改**不要求成对（改参数不动 `call_id`，配对不受影响）；
   **删**必须成对——只删调用是孤儿调用，只删结果是孤儿结果，下一次请求直接 400。
   D184 那句"调用 + 结果成对改或成对删"，按这一条收紧。
2. **落红之后要切到红**。写 `tooledit_message` 只完成一半：`mark_version_edited` 原来只在
   `active_view='edited'` 时才同步 `messages.content`，而绝大多数消息是 'raw'——
   照搬的话，用户改完在屏幕上**什么也看不见**。`apply_unit_edits` 因此自己写三条：
   seed 第 1 版（读旧 `content` 当原文）→ 写 `tooledit_message` + `edited_by_tool=1` +
   `active_view='edited'` → 更新 `messages.content`。顺序反了原文就没了。
3. **一条消息带多个工具调用时，不许只删其中一个**。删的是整条消息；它带着别的调用就会
   一起消失。报"要删就整条删，或者别删"，不替用户做那个决定。

接口与账本：

- 纯逻辑 `nmoi_core::edit::{BlockOp, plan_ops, PlannedOp, UnitPlan}`——校验、成对、算 before/after，
  **不改 unit**；落库 `Storage::apply_unit_edits` 一个事务做完改列 / 落红 / 删行 / 记账。
- 工具名 **`edit_unit`**（0.14y 的 `edit_message` 不再注册；参数上留了兼容：
  `ops` 缺席时按旧的 `blocks` 读，旧提示词与旧记录都不作废）。收尾认两个名字。
- undo 日志 `settings(scope="undo")`，key = `<会话 id>/<uuid v7>`，值是
  `nmoi_storage::blockedit::UndoRecord`（before/after **原文**，可导出）。**不加表、不加列**。
- 每会话上限 50 处：数 undo 日志里这个会话的条数（不是数 `edits` 表——那张表也记用户手动编辑）。
4. **覆盖率校验不查工具参数**。`{"path":"a"}` 里的键名永远只出现在它自己里面，照查的话
   每一对工具块都删不掉；参数的风险由"成对删"管，不留孤儿就够了。结果 / 思考 / 正文的删除
   照查（路径、命令、标识符），判据是"出现次数 > 被删块里的次数"——同一事实在别处还有就放行。

## D189 模型选择面板：一块面板、两处入口、收藏落库（0.15x，2026-10-31）

用户给的参考图是「搜索框 + 按供应商分组 + 每行（图标 / 名称 / 类型·窗口 / 心形）+ 底部供应商 chips」，
原话是"参考一下…但是不要一比一复刻"。所以结构照借、参数用自己的：行高 52、面板上圆角 20、
遮罩 0.32、chips 用 `secondaryContainer`（与工具卡 stdout/stderr 页签同一套）。

1. **一块面板，两处共用**。`ModelPickerSheet`（`internal`，新文件）同时给聊天页顶部那条模型条
   和输入岛那颗模型图标用——**它们开的是同一个面板**。助手页的「被调用时指定模型」也调它，
   只是选中项写进 `sub_agent.provider_id/model_id` 而不是助手自己的模型。
   输入岛那颗原来写的是"模型选择待接：要先有供应商与密钥页（P3）"——P3 早做完了，
   那句话现在是假的；接上真面板，顺手把假提示删掉。
2. **收藏放库里，不放 `AppSettings`**。`settings(scope="model_favorites")`，key =
   `<供应商 id>/<模型 id>`，值 `{}`——只有"在或不在"，时间由 `settings` 行自己的 `updated_at` 记。
   理由：收藏指向的是 `settings(provider, …)` 里那份模型表；放 SharedPreferences 的话，
   删掉一个供应商就在手机上留一串指向空气的键，导出/恢复时也和配置分了家。
   **加 scope 不是加迁移**（settings 表本来就有），所以这一步不动 schema。
3. **清死键**。打开面板时按"此刻真有的模型"清一遍收藏；`alive` 为空时**只读不删**
   （那说明供应商一条都没读出来，不是"全都不存在"）。这是铁律 ② 的同一条：
   库里的每一样东西都要能在界面上指出来，指不出来的先删掉。
4. **徽标只写真有的数**。窗口填了才画（`128k` / `1M`），没填就不画；
   **不显示"模型类型"**——`kind`（chat/embedding/image）、能力位、定价现在一个读取点都没有，
   画上去就是"存了但不生效"的前身。等 0.15x 后半把模型编辑页的三页签做出来再上。
5. **面板外壳抽成 `SheetFrame`**。「更多」那张 `MenuSheet` 与这张面板共用同一个壳
   （遮罩 / 圆角 / 抓手 / 标题）。复制一份的结局一定是两边圆角、遮罩慢慢分叉，
   而两个面板会同时出现在同一个屏幕上，分叉看得见、却没人知道哪个是对的。

## D190 助手页的「被调用时用哪个模型」（0.15x 后半，2026-10-31）

同一块 `ModelPickerSheet` 的第二处入口：助手编辑页 →「可作为子 AGENT 被调用」打开后 →
「被调用时用哪个模型」一格。选中写进 `sub_agent.provider_id/model_id`，空 = 跟这个助手自己的模型。

1. **钉死是有意义的**。不指定时，子 AGENT 每一轮读的都是"当前助手"的模型——用户切一下主助手，
   子 AGENT 的口味就跟着变。指定之后那一轮锁定在它自己那对 id 上。
2. **🚫 只在"已经指定了"时出现**。没指定时它没有可清的东西，摆着就是一个点了没反应的按钮
   （「空位可以、假开关不行」）。
3. **标签三态**：没指定（"用这个助手自己的模型"）/ 指定了且还在（"供应商 / 模型"）/
   指定了但那个模型已经不在供应商列表里（显示原始 id + 一行 `error` 色的说明）。
   第三种必须单独写：显示一个看着正常、真调用才发现对不上的名字，是最难查的一类。
4. **选中不立刻落库**。这一页的其它字段（名字、调用 ID、描述）都是"填完点右上保存"，
   模型这一格跟着走同一套；提示行写「已选 X：点右上「保存」生效」，不给"选了就算存了"的错觉。
5. **面板挂在 `Surface` 那一层**（它的内容本身就是一个 Box），不塞进上面的 `Column`：
   塞进去 `fillMaxSize` 只能拿到剩余高度，遮罩会变成只盖住下半屏（ui-taste 2026-10-27 那条）。

## D191 模型编辑页：整页、两页签、类型真的有读取点（0.15x 后半，2026-10-31）

模型原先是个弹窗（5 个输入框）。按「配置类的东西用整页」改成整页，但仍然**不是**设计稿里的三页签。

1. **整页，但是供应商页上的一层浮层，不是路由。** 模型是供应商草稿的一部分：
   拆成路由就有两个写者（模型页直接落库 / 供应商页按「保存」），用户在供应商页改了一半的端点
   会被下一次保存盖掉，而这件事在界面上看不出来。做法：全屏页面长在 `ProviderEditScreen` 里，
   `BackHandler` 只关这一层（后注册者优先，轮不到页面栈那条）。
2. **两页签：基本 / 采样。** 基本＝ID、显示名、类型、上下文窗口；采样＝最大输出、温度。
   这三项采样/窗口都**真会被发出去或真会参与判据**（`TurnRepository` 取 `assistant.x ?: model.x`）。
3. **类型（`kind`）加了，而且给它找了读取点**：`AssistantRepository.choices()` 只把 `chat` 型交给
   聊天页与助手页的选择器——嵌入 / 图像模型混在聊天选择器里，用户点下去只会得到一轮 400。
   老数据没有这个字段 → 一律按 `chat` 处理（否则它们会凭空从选择器里消失）。
   供应商的模型列表上，非聊天型会带一个类型前缀，让"它为什么不在选择器里"能在原处看到答案。
4. **第三页（推理：方言 / 级别 / 允许关闭 / 回放）与高级（始终保留采样 / 推理回放 / 回放字段）
   先不做**：这些字段现在**没有任何一处读**，摆上来就是"存了不生效"。设计稿里它们是对的，
   但顺序该反过来——先有读取点，再放控件。等 `apply_thinking` 认得"这个模型支持哪几档"、
   请求组装会回放推理内容时，再各开一页。

## D194 0.15n 第一层：把流收成 `Completion`（2026-10-31）

`ChatStream::next_event` 早就有，但**没有一处代码消费它**——`engine.push_delta` 只有测试在调。
所以"流式"在代码里一直是个半成品：`run_turn` 里写着 `request.stream = false`，走 `complete()`。

这一层只做一件事：**把一条事件流收成与 `complete()` 同形的 [`Completion`]，并把增量交出去**
（`ChatStream::collect_all`）。它现在**没有界面效果**，是下一层的地基。

1. `Collected { completion, interrupted }`：断流（没等到终止信号）**不算失败**——
   正文留着、`interrupted` 给一句原因、`finish` 记 `Unknown("interrupted")`。
   假装成 `Stop` 会让落库把"被掐断的回答"标成完整（D21 的 incomplete 就没了）。
2. **工具参数是分片过来的**（Anthropic / OpenAI 都按 `index` 分组）：`BTreeMap<index,…>` 拼，

3. `Usage` 是**快照**不是增量，直接覆盖最后一个。
4. 新增 `ChatError::Provider`：流内报错（HTTP 200、错误在 body 里）与 `Http`（一个字节都没开始）
   分开。前者不重试——重发会把前半段和后半段拼成一条不存在的回复（D40）。
5. 方法叫 `collect_all` 而不是 `collect`：`ChatStream` 实现了 `Iterator`，同名的话
   读者分不清调的是哪个（第一次编译时编译器也分不清，报的是 `Iterator::collect` 的错）。

**下一层**：`run_turn` 走 `client.chat()` 并把 `on_delta` 接到 FFI 的会话表里（增量缓冲）→
`nmoi_turn_busy_json` 带出 `text`/`reasoning` → 界面在"正在生成…"期间轮询并逐字画。

回调面只能靠 CI 验；轮询复用现成的 `Registration` 表与 `turn_busy`，每一层都能在本机测。

## D197 0.15n 第二层第二步：FFI 的增量通道（2026-10-31）

`nmoi_turn_run_json` 现在认一个 `stream`（默认 `false`）：为真时这一轮真的走 SSE，

1. **两张表分开**：取消标志那张只放 `Arc<AtomicBool>`；增量另起一张 `session → PartialText`。

## D199 流式拿不到字就退回非流式（2026-10-31）

界面上线时会整轮带 `stream: true`（D198）。如果某个中转忽略这个字段、回一段普通 JSON，
解析器会把它看成"空流中断"——这一轮就变成**空回答**，而以前非流式是能成的。

**一个字都没收到**才退回：用非流式重发这一轮一次。已经收到正文的不退回——
重发会把前半段和后半段拼成一条不存在的回答（D40）。
代价：不支持流式的端点上，用户等的是"整段"而不是"逐字"，但拿到的是对的回答。

## D203 多会话并发 + 发送队列（用户 2026-10-31 深夜定）

用户原话的四条语义，逐条落地：

1. **不同会话可以同时跑**——原生本来就支持（`Registration` 按会话登记、每轮自己
   `Storage::attach` 一条连接），卡在客户端：请求挂在 `ChatScreen` 的 `rememberCoroutineScope()`
   上，离开页面协程就取消 → JNI 还在跑、收尾那几行不执行 → 下次进来只能说"上一轮没收尾"。
   现在 job 归 `TurnRunner`（进程级 `SupervisorJob` + `Dispatchers.IO`），页面只**订阅事件**，
   事件带 `sessionId`，不是当前会话就丢掉——顺带治好了"A 跑完把 B 的按钮点亮"。
2. **会话正在响应时，发送仍然可用**：这一句进**这个会话的队列**（`SendQueue`，按会话分开），
   提示行写"已排队（第 N 位）"。不报错、不丢字、不弹"上一轮还没结束"。
3. **正常结束 → 自动继续**：`TurnRunner` 在这一轮成功后取队首接着发；
   **非正常结束（失败 / 被停止）→ 队列阻塞**。`cancelled=true` 也算非正常：
   用户按停止是**有意的中断**，自动往下发等于把"停"当成"继续"。
4. **手动排序 + 手动发送**：队列小窗里 ↑ ↓ 调顺序、× 删一条、清空、
   「发送下一条」（只在**这个会话没在请求**时可点，按钮文案会说明为什么灰）。
5. **入口在发送键的长按菜单**里（用户指定）：新增「发送队列（N）」一项；

   上下文被压缩之后模型忘了 id，用 `Session-List` 找，不猜。
3. **游标 + 环形缓冲**：每会话 256 KiB，溢出丢头并报 `dropped_bytes`；
   比游标更旧的请求返回 `gap: true`——不假装完整。
4. **服务会话只能用户关**：模型 `Session-Close` 服务会话一律拒绝并指路（用户原话：
   「持久性不能在会话的调用块点取消，而是要在持久会话管理里面操作」）。
5. **`enabled` 不入库**：存了它，重启后开关是「开」而进程不在，界面上就有两个答案。
6. **应用被杀时**子进程靠 stdin EOF 自己退出；这是唯一跨进程的收尾，文档里写清，不假装可靠。

完整设计（JSON 形状、失败表、验收）在 `docs/persistent-sessions.md`。

## D222 工具批次并行：按车道跑，结果按调用顺序回填（设计已定，未动工）

用户 2026-11-02 问「能不能并行调用和阻塞调用」。查完三家：**都支持模型一次吐多个调用**
（OpenAI `parallel_tool_calls` 默认开；Anthropic 一条 assistant 消息里多个 `tool_use`；
Gemini 文档里专门有一节 Parallel function calling）。卡住的是我们自己的循环：
`agent::run_turn` 是 `for call in &outgoing`，一个跑完才跑下一个。

- **批次**：一次 assistant 消息里的 N 个调用算一批，并发执行，结果按**调用顺序**回填
  （不是完成顺序）；`seq` 收齐后再分配。
- **车道**：`read` 4 / `workspace` 1 / `session:<id>` 1 / `process` 4；默认 `workspace`，
  新工具不声明就串行——宁可慢，也不要两个写撞上。
- **阻塞**：`Session-Open(block_ms=30000)` 只占一条车道，读的照常跑完；但**整轮仍要等它**，
  因为下一轮请求必须带齐所有结果。所以工具描述里写「起服务用 block_ms=0」。
- **取消**：每个调用一个 `call_id → AtomicBool`；整轮停止 = 全置上，单条关闭 = 只置一个。
  结果里 `killed_by_user` / `timed_out` / `cancelled` 三件事分开写。
- **Gemini 的坑**：老接口 `functionResponse` 只认函数名，同名并行配不上；
  要等 Interactions 那套 `call_id`，在那之前 Gemini 上不并行同名工具。

完整设计（车道表、撞车表、验收）在 `docs/tool-execution.md`。
