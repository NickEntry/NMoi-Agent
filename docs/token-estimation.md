# token 估算：实测对账（D91）

**状态**：L0（字符近似）与 L1（本地 BPE）都已对账实测，2026-10-21。
L2（比例校准）已实现并落库，**没在真端点上报过样本**（见文末"还没测的"）。

对账脚本：`scripts/token_check.py`；被对账的实现：`crates/core/src/tokens/`（运行时同一份，
由 `crates/core/examples/token_estimate.rs` 暴露出来，**不在 Python 里重写**——两份实现迟早分叉，
那样对出来的误差是假的）。

> **脱敏约定（2026-10-23）**：本文里的实测端点都是**本机的一个第三方中转**，它和上游各家的真实别名一律不写进仓库，统一记为 `relay-a/` `relay-b/` `relay-c/` `local/`（映射只在本机笔记里）。数字、延迟、token 数都是原始实测值，**没有因为脱敏改动过任何一个数**；要复核就照同样的请求体打同样的端点，结论不依赖它叫什么名字。

端点：`http://127.0.0.1:8790/v1`，模型 `relay-a/DeepSeek-V4-Flash`（用户指出这个能正常回 usage）。
请求方式：把整段文本作为唯一一条 `user` 消息，`max_tokens=1`，读 `usage.prompt_tokens`。

## L1 结果（2026-10-21 实测）

同一批文本、同一个端点，估算换成 `tokens::Estimator`（L1，`o200k_base`）：

| 字符数 | 文本种类 | L0 估算 | L1 估算 | 真实 | 真实/L0 | 真实/L1 |
|---:|---|---:|---:|---:|---:|---:|
| 1000 | 纯 ASCII 单词流 | 270 | 163 | 167 | 0.619 | **1.025** |
| 1000 | 纯中文（单句重复） | 1000 | 781 | 628 | 0.628 | **0.804** |
| 1000 | 中英混排（含全角标点） | 448 | 557 | 591 | 1.319 | **1.061** |
| 1000 | 类 JSON 代码 | 358 | 343 | 360 | 1.006 | **1.050** |

`10000` 字符那一档是同一批文本离线算的（真值用下表同一端点早先测出的数字）：
ASCII 1612 / 1616（1.002）、中文 7813 / 6254（0.801）、混排 5516 / 5825（1.056）、
代码 3413 / 3600（1.055）——**两个长度上比例一致**，所以这不是抽样噪声。

**结论**：

1. L1 把"随内容种类摆动 2 倍"压到 **0.80–1.06**，Agent 的主料（混排、代码）从
   "低估 32%"变成"低估 6%"。
2. 剩下的最大偏差是**纯中文高估 24%**（方向安全），不是低估。
3. 因此未校准的 L1 安全系数取 **1.1**（最坏低估 1.056），L0 仍是 **1.3**（D96）。

**cl100k 要不要**：同一批文本用 `cl100k_base` 是 163 / 1218 / 618 / 343。中文上它比真实值高
1.94 倍，所以中文会话**只**用 cl100k 会在窗口用了 39% 时就触发压缩。但 gpt-4/gpt-3.5/claude
的真分词器就是 cl100k，对它们用 o200k 会低估中文 36%（危险方向）。两个词表各自用在哪一类
模型上见 D94——这是"多花 1.64MB 换掉两个方向的系统性错"。

**成本（release / PRoot / aarch64 Android）**：o200k 首次初始化 691ms、cl100k 296ms、
16k 汉字编码 26ms、10k 字符 12–17ms。strip 后二进制：空 395KB / +cl100k 3.67MB /
+o200k 5.64MB / 两个 7.28MB。所以有 `bpe` feature（默认开）：关掉退 L0 + L2。

## L0 结果

| 字符数 | 文本种类 | 估算 | 真实 | 真实/估算 |
|---:|---|---:|---:|---:|
| 1000 | 纯 ASCII 单词流 | 270 | 167 | **0.619** |
| 1000 | 纯中文（单句重复） | 1000 | 628 | **0.628** |
| 1000 | 中英混排（含全角标点） | 448 | 591 | **1.319** |
| 1000 | 类 JSON 代码 | 358 | 360 | **1.006** |
| 10000 | 纯 ASCII 单词流 | 2686 | 1616 | 0.602 |
| 10000 | 纯中文（单句重复） | 10000 | 6254 | 0.625 |
| 10000 | 中英混排（含全角标点） | 4442 | 5825 | 1.311 |

两个长度上同一种文本的比例几乎一样（ASCII 0.619 → 0.602；中文 0.628 → 0.625；
混排 1.319 → 1.311），说明**误差是系统性的，不是抽样噪声**；但也说明它随内容种类变化，
不是"乘一个系数"能救的。

## L0 结论

1. **纯中文与纯英文，L0 高估约 1.6 倍**（真实/估算 ≈ 0.62）。方向是安全的：
   安全阀宁可早触发。
2. **中英混排 + 全角标点，L0 低估约 32%**（真实/估算 ≈ 1.32）。方向是**危险**的：
   按这个数去卡绝对线，会越过窗口才动手。
3. **类 JSON / 代码文本，L0 几乎正好**（1.006）。有点意外，但也说得通：
   估算里"每个 ASCII 串向上取整"的粗糙，和 BPE 在短串上的碎片化，恰好互相抵消。
4. 而第 2 条那种文本**正是 Agent 会话的主料**（工具输出、markdown、中英夹混的说明）。
   所以"L0 高估所以安全"这个直觉**只对纯文本成立**。

**因此**：不能给 L0 乘一个全局系数（乘 0.62 会把混排从低估 32% 变成低估 58%）。
必须是 D91 那套三级：

- **L0** 保持不动（它便宜、方向在多数场景下保守）；
- **L2 校准**按 (模型, 会话内容) 算因子，而不是全局一个数——同一段对话里内容构成稳定，
  用这个会话上一轮的 `真实/估算` 推下一轮，比任何语言分类表都准；
- **未校准时给小预算留余量**：绝对线判定前乘 1.3（就是这里测出的最坏低估幅度），
  校准过之后再用真实因子。

## 还没测的

- **L2 校准本身没跑过真样本**：`Calibration::observe` 有单测，但还没有一轮真实对话把
  `usage.prompt_tokens` 反推回来过。要等 0.7 把它接进轮末（`observe_usage` → `put_calibration`）。
- **多轮对话与工具 schema 的整体误差**：上面测的是"单条长消息"。真实请求里还有
  system 模板、工具声明、`tools` 字段的 JSON，这部分固定开销没测——这也是为什么 L2
  只收 ≥1500 token 的样本（让固定项摊薄）。
- **非 DeepSeek 家族**：只测了 `relay-a/DeepSeek-V4-Flash`。`usage.prompt_tokens` 的口径各家
  不全一致（有的算模板 token、有的不算），换端点要重跑这张表。
- **gpt-4 / claude 家族**没有真端点可测（没有 key），cl100k 那条路目前只有离线推理支撑。
