# 图片上下文（2026-11-04，已实现一半）

> 用户 2026-11-04 给了别的客户端的截图，并纠正了一处语义：
> **「查看图像」是一个工具，作用是把图片加入上下文**——不是"看用户发的那张图"。
> 这一份记的是现在的实现，以及还没做的那几块。

## 1. 一句话

上下文里的图有两个来源：**用户发消息时带的图**（跟着消息走，D208）和
**模型用 `View-Image` 拉进来的图**（跟着"这一轮的清单"走，D248）。
后者有上限、新的在前、满了先丢最旧的。

## 2. 已经实现的

### 2.1 `View-Image` 工具

```
参数：path —— 会话附件目录里的文件名（`xxx.jpg` 或 `/chat/images/xxx.jpg`）
返回：{"file","attachment","in_context":3,"limit":12,"count":3,"dropped":["..."],"note":"已加入上下文（第 3/12 张）…"}
```

- 只认会话自己的附件目录（`sessions/<会话>/images`），带目录、带 `..` 的一律拒。
- 单张上限 **5 MB**（Anthropic 的 API 上限，三家最弱）；只收 jpg / jpeg / png / webp / gif。
- **不返回图片内容**：图是给模型看的，登记完下一轮请求就带上它。
- 清单满了先丢最旧的，并在结果里点名丢了哪张——不静默。

为什么不做成"把图塞进工具结果"：OpenAI 的 `role: tool` 只收文本，Anthropic 的
`tool_result` 能带图，Gemini 的 `functionResponse` 又只认文本。走"清单 + 请求级附件"
这条路，三家都是同一种形状（消息上的图），不用为每家写一套。

### 2.2 清单（`crates/core/src/images.rs`）

- 按会话分（多会话并发时互不相干），**进程内**：重启之后清单为空。
  图还在盘上、消息里也还在，只是"这一轮要发它"这件事得重新说一次。
  持久化它等于给"看不见的上下文"开口子。
- 新的在前（`insert(0)`）；同一张重复加 = **挪到最前**，不产生第二份。
- 上限：默认 **20**（用户 2026-11-04 定的），硬上限 **100**。
  三家的单请求上限：OpenAI 500、Gemini 3 600、Anthropic 100 —— 取最弱的 100。
  填得比它大，换一家端点就 400。
- 上限存在应用设置里（`context.image_limit`），界面是**一个输入框**（1–100，默认 20），
  旁边「用这个值」/「恢复默认」两颗 chip。

### 2.3 请求构造

`run_turn` **每轮发请求之前**都并一次（D269）：`View-Image` 可能就在这一轮的某一轮里
把图加进清单，整轮只挂一次的话要等下一次对话才带得上。

挂到**最后一条用户消息**上。为什么不另起一条 `role: user`：多一条会改变对话的形状，
模型会以为用户又说了句话；`build_body` 也只认用户消息带图。

字节按 id 缓存在这一轮的内存里：`request` 每轮从 `base` 重建，所以每轮都要重挂，
但同一张图只读一遍盘。读的是 `sessions/<会话>/images/<文件名>`，**不查 `attachments` 表**——
工具自己写进 `/chat/images` 的图在表里没有行，查表会静默少一张。

文件读不到就跳过这一张，不报错（清单里可能留着一条已经被删掉的 id）。

### 2.4 界面

- 输入区上方一行：`图片上下文 3/20 ›`（**没有图就不摆**——常驻一行"0 张"像坏了）。
- 点开是半屏面板：`这一轮发送 3 / 20 张 · 新的在前，满了先丢最旧的`，
  每张一行（缩略图 56、大小与格式、等宽附件 id、右侧「移出」），底部「清空这一轮的图片上下文」。
- 移出**不删文件、不改消息**，只是下一轮不带它。面板上有一句话写清这件事。
- 工具块的中文名：`View-Image` → 「查看图像」，`System-Shell` / `WorkSpace-EnvirShell`
  → 「运行命令」/「运行命令（容器）」。

## 3. 还没做的

| 项 | 说明 |
|---|---|
| 图钉（固定优先保留） | 参考图里每行右侧那颗图钉：钉住的不会被"满了先丢旧的"挤掉。要清单里多一个 `pinned` 位。 |
| 自动管理开关 | 参考图的「自动管理历史图片」：优先保留用户上传的、分批收起较早的工具图片。现在只有一条 FIFO 规则。 |
| 再加到输入框 | 参考图里那颗 `＋`：把这张图重新挂到输入框当待发附件。 |
| 用户发的图与清单的关系 | 现在两份并存：消息带的图按消息走，清单是额外的。要不要把"用户发的图"也算进 12 张的额度里，得先想清"超了丢谁"。 |
| token 估算 | 面板上只报张数与大小，没报 token（各家图像 token 口径不同，见 `docs/token-estimation.md`）。 |

## 4. 边界

- **不搬文件**：清单只记 id，路径不变（D216 的路径已经写进库、写进存储页）。
- **不改消息**：移出之后那条消息仍然显示原图。
- **界面不能加**：只有 `View-Image` 能往清单里加。界面能加的话，模型就不知道上下文里
  多了什么——那正是"看不见的上下文"。
