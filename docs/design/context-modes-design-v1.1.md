## 0. 总览

### 0.1 四个模式解决什么问题

长线任务里，上下文管理要同时应对三个互相拉扯的目标：

| 目标 | 优化对象 | 度量 | 对缓存的偏好 |
|---|---|---|---|
| **成本** | 每轮花费 | $/任务 | append-only |
| **容量** | 任务能跑多久 | 轮数 / 累计处理字节 | 必须破坏缓存 |
| **质量** | 推理准确度 | 任务成功率、轨迹长度 | 偏好删除干扰项 |

四个模式是这组矛盾的四种取舍，不是四个产品特性。它们共享同一套底层设施（第 5 章），
各自决定"谁来决策、什么时候决策、能改到多深"。

### 0.2 缓存代价的正确位置：成本项，不是约束

**两种代价的量纲不同，不能直接比较。**

| | 缓存代价 | 上下文代价 |
|---|---|---|
| 性质 | 确定性支出 | 概率性损失 |
| 时间分布 | 一次性 | 持续 |
| 可计算性 | 可精确计算 | 只能估计 |
| 上限 | 有（`L × (w−r)`） | **无**（可能毁掉整个任务） |

把它们折算成同一量纲，才能做决策：

```text
编辑划算 ⟺ P_fail × L_fail > C_cache + λ × T_cache

C_cache = (L − i) × (w − r) × price_in       // 重算的金钱成本
T_cache = (L − i) / prefill_speed             // 重算的延迟
λ       = 延迟权重（交互式高，批处理低）
P_fail  = 上下文污染导致任务失败的概率
L_fail  = 失败的损失（重跑成本 + 错误交付成本）
```

**临界概率**：

```text
P_fail* = (C_cache + λT_cache) / L_fail
```

基准平台估算（`L = 200k`，`w − r = 0.96`，`price_in = $0.15/M`，
`L_fail ≈ $0.18`，即重跑一个 30 轮任务的输出成本）：

| 编辑位置 | 重写量 | `C_cache` | `P_fail*` |
|---|---|---|---|
| 尾部 | 20k | $0.0029 | **1.6%** |
| 中段 | 100k | $0.0144 | **8%** |
| 头部 | 200k | $0.0288 | **16%** |

**即使最贵的头部编辑，只要失败概率超过 16% 就划算。**
而实证显示多轮任务的失败率是 65%（单轮 58% → 多轮 35%）。

**结论：在这个平台上，"为保护缓存而牺牲上下文质量"是不理性的。**

三个推论：

1. **缓存是成本项，不是约束。** 约束是"不能违反"，成本项是"可以付，只要收益更大"。
   把缓存当约束，会导致系统退化成 append-only，最终在窗口最满的时候被迫做最贵的全量重算 ——
   **缓存保护主义反而制造更大的缓存破坏。**

2. **缓存代价的正确角色是试错预算。** 一次尾部编辑 $0.003，意味着可以大胆试错；
   一次头部编辑 $0.029，意味着要谨慎。代价本身在告诉你"这件事值不值得想清楚"。

3. **唯一真正的硬约束是延迟。** 交互式场景下每次冷启动 5–10 秒，用户能感知。
   这不是钱的问题，是体验问题。所以批处理任务可以激进，交互式任务要保守。

**但有一个前提必须成立：编辑必须真的降低失败概率。**
无意义的整理收益为零，纯亏。所以问题从来不是"缓存 vs 上下文"，
而是"**这次编辑是否真的有用**"。前者是伪命题，后者才是要回答的。

### 0.3 模式矩阵

| | 决策者 | 决策时机 | 可操作范围 | 缓存代价 | 主要收益 | 主要风险 |
|---|---|---|---|---|---|---|
| **1 全量保留** | — | — | — | 零 | 完全可复现 | 必爆窗口 |
| **2 规则路由** | 确定性规则 | 写入时刻 | 单条内容 | 零 | 容量 + 零幻觉 | 规则漏判 |
| **3 模型决策** | 模型打标 | 尾部窗口内 | 原子单元 | 低（尾部锚定） | 语义精度 + 注意力净化 | 打标被忽略 |
| **4 灰烬模式** | 模型 | 任意位置 | 任意单元 | **故意最大化** | 注意力质量 | 不可逆误删 |

### 0.4 模式选择决策树

```text
任务预计轮数 × 每轮 token < 窗口 × 0.85 ?
├─ 是 → 模式 1（不要因为"应该压缩"而压缩）
└─ 否 → 内容类型可预判？
         ├─ 是（大量工具输出、大文件、日志）→ 模式 2
         └─ 否（语义判断依赖任务进展）→ 模式 3
                   │
                   └─ 卡壳 / 需要清空失败路径 / 需要精确回忆 → 模式 4（临时启用）
```

### 0.5 一句话概括四个模式

- **模式 1**：什么都不做，但有一个安全阀。
- **模式 2**：内容进来时就决定它的形态，永不事后改写。
- **模式 3**：模型只判断"什么没用了"，什么时候执行由策略层决定。
- **模式 4**：给模型完全编辑权，代价是缓存全破，收益是注意力干净。

## 1. 模式一：全量保留

### 1.1 定义与适用边界

**定义**：所有内容以原始形态进入上下文，不做转储、截断、摘要、屏蔽。

**适用**：

- 短任务（预计轮数 × 每轮 token < 窗口 × 0.85）
- 需要完全可复现的调试场景
- 其他模式的对照组
- 基准平台上 1M 窗口的常规任务 —— 这是本模式最容易被低估的适用范围

**不适用**：

- 预期会超窗的长任务（必须切模式 2 或 3）
- 上下文已出现注意力退化迹象（重复先前动作、忽略早期约束）

**为什么它必须存在**：它是其他三种模式的对照组。任何新模式上线，先用模式 1 跑一遍基线，
才能量化"省了多少 / 贵了多少 / 成功率变化"。没有基线就没有结论。

### 1.2 上下文组装规则

```text
[稳定前缀]  system prompt + 工具定义 + 项目约束      ← 永不改动
[历史]      全部消息，按时间顺序追加                  ← 只追加
[动态状态]  任务清单 / 已读文件树 / 归档索引          ← 放尾部，或做成工具查询
```

三条硬规则：

1. **稳定前缀逐字节不变**。任何时间戳、随机 ID、动态计数都不能进前缀。
2. **历史只追加**。不重排、不替换、不删除。
3. **动态状态放尾部**。放头部会导致每轮从该位置起缓存全部失效。

### 1.3 溢出兜底（必须有）

模式 1 不做主动管理，但**不能没有安全阀**。一次超限就是整轮失败，代价远高于一次强制压缩。

```text
在原子单元边界检查 used / window：
  used > 0.90 × window  →  强制进入第 6 章的压缩流程
  used > 0.98 × window  →  强制截断最旧的原子单元，并记录告警
```

安全阀属于安全机制，不属于模式语义。它的存在不改变"模式 1 = 不处理"的定义。

### 1.4 参数

| 参数 | 默认值 | 说明 |
|---|---|---|
| `hard_limit_ratio` | 0.90 | 触发强制压缩 |
| `emergency_ratio` | 0.98 | 触发强制截断 |
| `check_point` | 原子单元边界 | 见 §5.2 |

### 1.5 验收标准

- 短任务全程无压缩，`used` 曲线单调上升
- 缓存命中率接近理论上限（只有新增 token 未命中）
- 人为构造一个超窗任务，安全阀能正确触发且不产生非法消息序列
- 同一输入重放两次，上下文逐字节一致

## 2. 模式二：规则驱动选择性保留与转储

### 2.1 定义与适用边界

**定义**：由确定性规则在**写入时刻**决定每条内容的形态，一次定终身，永不事后改写。

**适用**：

- 工具输出占大头（读文件、跑命令、抓网页）
- 内容类型可预判（代码、日志、JSON、二进制）
- 需要零幻觉保证的场景（本模式全程 extractive，不改写原文）

**不适用**：

- 需要语义判断"这条现在还有没有用"（那是模式 3）
- 内容形态无法预判的开放任务

**本模式的核心价值不是省钱，是两件事**：

1. **容量**：让任务处理远超窗口的数据量
2. **零幻觉**：默认全程 extractive，原文一个字不改，不引入摘要幻觉
   （v1.1：若启用摘要，此项降级为"低幻觉"，必须配合长度下限与覆盖率校验）

### 2.2 内容形态分类

五种形态，按"信息保真度"从高到低：

| # | 形态 | 表示 | 幻觉风险 | 上下文成本 |
|---|---|---|---|---|
| F1 | **全文** | 原始内容 | 无 | 100% |
| F2 | **截断 + 尾注** | 头 N + 尾 M + `[… 8.2k tok 已归档 ref#a3f9]` | 无 | 可配 |
| F3 | **masking 占位符** | `[output masked: 8.2k tok, ref#a3f9]` | 无 | ~10 token |
| F4 | **仅指针** | `[archived ref#a3f9 \| 8.2k tok \| tool:read_file \| src/x.ts:120-380 \| 退款状态机实现，3 个 TODO]` | 无 | ~40 token |
| F5 | **索引摘要** | 一行描述，不含内容 | 无（不承担内容职责） | ~20 token |

**注意：这里没有"用摘要替换原文"这一档。**
摘要在本设计中只承担索引职责（F4/F5 里那一行描述），不承担内容职责。
原因见附录 B：摘要会引入可测量的幻觉，并让 agent 多走 15% 的步数。

> **v1.1 修正（实测）**：上述"摘要不可用"的结论**在受控条件下未获支持**。
> 本地对照实验（附录 E）显示：把三条硬约束埋在 25 条规范里、摘要器给足条件时，
> 单次与三次级联压缩均稳定在 3500–4400 字符并满分，v1.0 引用的"22 字符坍缩"无法复现。
> 修订后的立场：
> - 摘要**可以**承担内容职责，但必须叠加**长度下限保护**（压缩后长度低于阈值即判失败并回退）
> - 摘要**不得**作为唯一恢复路径；引用式回灌仍是确定性手段
> - 附录 B 的"摘要慢 15%"来自软件工程 agent 场景，不能直接外推到长线对话

### 2.3 路由规则

规则按优先级从上到下匹配，命中即停。所有阈值都是**建议初值**，必须实测调整。

| 优先级 | 条件 | 形态 | 备注 |
|---|---|---|---|
| 1 | 来源 = user / system / 工具定义 | F1 | **永不自动路由** |
| 2 | 内容被标记 `protected`（失败、错误、异常） | F1 | 见 §2.3.2 |
| 3 | base64 / data URI / 高熵二进制 | F4 | 熵检测 + 魔数检测 |
| 4 | 同一路径 / URL 的第 2 次及以后读取 | F4 + 差异 | 见 §2.3.3 |
| 5 | 空输出或纯重复行 | F3 | |
| 6 | 长度 > `huge_threshold`（32k） | F4 | |
| 7 | 长度 > `large_threshold`（8k） | F2 | 头 1k + 尾 1k |
| 8 | 长度 > `small_threshold`（2k） | F2 或 F1 | 按内容类型决定 |
| 9 | 其他 | F1 | |

#### 2.3.0 任务锚点（v1.1 强制项）

**任何掩码/截断/归档操作之后，必须在压缩后上下文的头部注入一条当前任务陈述。**

v1.0 的路由规则是纯位置的（"保留最近 N 轮"），实测在 20k 上下文即失效：
模型取回了正确的归档原文，却转头去回答历史里的旧问题。这不是召回失败，是
context distraction——注意力被历史主导。

修复方式是补一条任务陈述，**极简即可**：

```text
（压缩后上下文头部，一条 user 消息）
历史已结清。当前任务：<用一句话复述最后一条用户指令>
```

实测结论（附录 E.3）：

| 变体 | 角色 | 成分 | 成功率 |
|---|---|---|---|
| 无锚点（v1.0 行为） | — | — | 3/8 |
| 完整长锚点 | system | 历史结清 + 任务陈述 + 指针声明 | 8/8 |
| 完整长锚点（降级措辞） | user | 同上 | 1/4 |
| 历史已结清 + 任务陈述 | system | 一句话 | 4/4 |
| 历史已结清 + 任务陈述 | user | 一句话 | 4/4 |
| 仅"历史已结清" | system | 无任务陈述 | 0/4 |

**唯一有效载荷是任务陈述本身。** 角色（system/user）不重要，位置不重要，
措辞强弱不重要，"历史已结清"这句话单独存在时无效。

实现约束：

- 锚点放在**压缩块之后、当前轮之前**，或整个上下文头部（两者等效）
- 内容从**最后一条 user 消息**提取，不要自己概括（概括会引入偏差）
- 锚点本身计入 token 预算，成本可忽略（一句话）
- 锚点不进归档，不参与后续压缩


#### 2.3.1 按内容类型细化

| 内容类型 | 识别方式 | 默认形态 | 理由 |
|---|---|---|---|
| 源代码 | 扩展名 / 语法特征 | F2（头 + 尾 + 行号范围） | 中段常可推断 |
| 编译/测试输出 | 关键字 | F2（保留错误行 + 尾部） | 中间是噪音 |
| JSON / 结构化数据 | 首字符 + 解析 | F2 或 F4 | 保留 schema 骨架 |
| 日志 | 行模式 | F3 + 错误行提取 | 重复行无信息量 |
| 网页正文 | HTML 剥离后 | F2 | |
| 图片 / 二进制 | 魔数 | F4 | |

#### 2.3.2 不可路由标记（protected）

以下内容**只能 F1**，无论多大：

- 报错信息、异常栈、非零退出码
- 失败的尝试及其原因
- 用户明确说"记住这个"的内容
- 未完成的 TODO、未验证的假设

**理由**：模型自我压缩有信息损失偏差，倾向把失败总结得很漂亮，而失败细节往往最有价值。
这条规则的作用是**从机制上禁止模型改写这类内容**，而不是依赖它自觉。

#### 2.3.3 重复读取的处理

第二次读同一路径时：

```text
if 文件未变（mtime + size + hash 相同）
    → F3 masking，附 "内容未变，见 ref#a3f9"
else
    → F2，只保留 diff 部分 + "相比 ref#a3f9 有 N 处变化"
```

这能消掉 agent 循环里最常见的浪费：反复读同一个文件确认同一件事。

### 2.4 归档与回灌

#### 归档条目结构

```text
ArchiveEntry {
  ref            // 全局唯一，内容寻址或 UUIDv7
  content        // 原文，逐字节保存
  tokens         // 原始 token 数
  source         // tool:read_file / tool:bash / web:fetch ...
  origin         // {session_id, message_id, turn}
  descriptor     // 一行描述，用于指针展示（索引职责）
  protected      // bool
  created_at
  content_hash
}
```

#### 回灌语义

```text
fetch_archive(ref) → 追加一条新消息，内容为完整原文
```

三条硬规则：

1. **只能追加到尾部**，不能插回原位。插入会破坏从该位置起的所有缓存。
2. **回灌是确定性的**：ref 存在则必然返回完整原文，ref 不存在则明确报错。
   不做相似度匹配，不做模糊查找。
3. **原文可能出现两次**（当初的指针 + 现在的全文）。用 ref 去重展示，
   但不要试图删除第一次出现的位置 —— 那会破坏缓存。

#### 为什么必须是引用而不是检索

```text
检索式：query → 相似度 → 可能返回片段，可能召回失败
引用式：ref   → 直接寻址 → 必然返回完整原文
```

检索失败不会报错，它静默地让模型基于缺失信息继续推理，然后编一个看起来合理的答案。
在长线任务里，一次静默召回失败可能毁掉后面几十轮，而且这个错误会被归因为"模型能力不足"。

### 2.5 完整流程

```text
内容产生（工具返回 / 网页抓取 / 文件读取）
    │
    ├─ 1. 脱敏扫描（凭据模式匹配 → 替换占位符）
    ├─ 2. 全文写入归档（无条件，永不跳过）
    ├─ 3. 规则匹配（§2.3 优先级表）
    ├─ 4. 生成形态（F1–F4）
    ├─ 5. 生成描述符（一行，≤ 60 字）
    ├─ 6. 追加到上下文（只追加，不改已有消息）
    └─ 7. 记录计量（tokens / 形态 / 规则 ID）
```

**关键：第 2 步在规则匹配之前。** 先存再决定形态，避免"判断出错导致原文永久丢失"。

### 2.6 工具接口

```text
// 只读
fetch_archive(ref)                    // 追加原文到尾部
search_archive(query, limit, scope)   // 搜归档，返回指针列表（不返回全文）
archive_stat()                        // 归档统计：条目数 / 总 token / 最大 ref

// 不可用：本模式不提供任何编辑工具
// 模型不能删除、压缩、重排任何已有消息
```

### 2.7 参数默认值

| 参数 | 默认 | 说明 |
|---|---|---|
| `small_threshold` | 2k tok | 以下默认 F1 |
| `large_threshold` | 8k tok | 以上走 F2 |
| `huge_threshold` | 32k tok | 以上走 F4 |
| `truncate_head` | 1k tok | F2 保留头部 |
| `truncate_tail` | 1k tok | F2 保留尾部 |
| `descriptor_max` | 60 字 | 指针里的描述长度 |
| `protected_patterns` | 错误/异常/TODO | 见 §2.3.2 |

### 2.8 失败模式与兜底

| 失败 | 表现 | 兜底 |
|---|---|---|
| 规则漏判 | 该压缩的没压，上下文增长快 | 监控增长率，超阈值降级到模式 3 或触发器 |
| 指针信息不足 | 模型不知道该不该取回，盲目 fetch | 描述符必须含"来源 + 位置 + 一句话内容"；统计误取回率 |
| 回灌风暴 | 模型反复 fetch 同一条 | 同一 ref 短窗口内重复 fetch 直接返回缓存副本，不重复追加 |
| 脱敏漏检 | 凭据进归档 | 写入时刻扫描 + 导出时二次扫描（§5.6） |
| 归档索引膨胀 | search 变慢 | 分层（热/温/冷），不删原文 |

### 2.9 验收标准

- 构造 100 条不同形态的内容，路由正确率 ≥ 95%
- 全程无摘要生成调用（本模式不应有任何 LLM 压缩调用）
- 任意 `fetch_archive(ref)` 返回内容与原文逐字节一致
- 缓存命中率：除新增 token 外无额外失效
- 同一输入重放两次，形态决策完全一致（确定性）

## 3. 模式三：模型决策的保留与转储

### 3.1 定义与适用边界

**定义**：模型负责**判断**什么内容没用了，策略层负责**决定何时执行**。两者分离。

**适用**：

- 内容价值依赖任务进展，规则无法预判
- 需要"这条试过了、不行"这类语义判断
- 上下文里失败尝试堆积，干扰后续推理

**不适用**：

- 短任务（判断成本高于收益）
- 需要绝对可复现的场景（模型判断本身不确定）

#### 3.1.1 定位修正：它真正的价值是"捞"，不是"压"

这是本模式最容易被设计错的地方。

按 §3.3 的范围约束，模式 3 的窗口极小（最后两条 assistant 消息之间）。
如果把它定位成"清理者"，它会和模式 2 严重重叠——窗口内只有两三条消息，
规则完全够用，模型的语义判断发挥不出来。**这是本模式的结构性张力**：
窗口越小缓存越省，但语义判断的空间也越小。

解开这个张力的方式是换定位：

```text
模式 2（规则）：负责压。命中规则就压缩，不看语义。
模式 3（模型）：负责捞。把规则误杀的内容救回来。
```

**为什么"捞"比"压"更适合小窗口**：

| | 压（清理） | 捞（保护） |
|---|---|---|
| 发生频率 | 高（每轮都有垃圾） | 低（偶尔才误杀） |
| 需要的窗口 | 大（要看到历史才知道什么没用） | **小（看到被压的那条就够）** |
| 判断难度 | 高（要预测未来是否用到） | 低（只要认出"这条还有用"） |
| 失误代价 | 大（信息永久丢失） | 小（多留一点 token） |

**代价是不对称的**：多压一点只浪费 token，误杀一条可能毁掉后面几十轮，
而且这个错误不可见——它表现为"模型能力不足"。

所以正确的分工是：

```text
规则激进地压 → 模型在窗口内检查有没有被误杀 → 有就标 keep
```

这带来三个好处：

1. **窗口小不再是问题**，因为救火是低频事件
2. **与模式 2 职责不重叠**，一个压一个捞，不抢同一件事
3. **可测量**：误杀率下降多少，就是本模式的收益

**这条修正也改变了打标的默认倾向**：模型的主要动作不是 `discard_candidate`，
而是 `keep`。`discard_candidate` 保留，但它是次要用途——用于模型自己产生的废料
（比如它自己的退化思考），不是用于历史内容。

### 3.2 决策权与执行权的分离

这是本模式最重要的设计点。为什么不让模型直接执行：

```text
模型看得到 token 数，看不到缓存成本。
所以它的理性行为是"每轮都调"。
每轮一次突变 = 每轮一次冷启动 = 缓存永不命中。
```

所以拆成两个动作：

```text
模型侧：mark_context(unit_id, priority, reason)   // 只记录，零缓存代价，本身也是追加
策略层：在 epoch 边界按标记批量执行               // 一次突变付一次冷启动
```

**必须给模型一个可预测的承诺。** 静默丢弃标记是最容易犯的错误，它会让模型在几轮内
不再认真打标。`mark_context` 必须返回处理结果：

```text
recorded | queued(epoch#N) | rejected(reason)
```

### 3.3 可操作范围

#### 3.3.1 定义

```text
anchor = 倒数第二条 assistant 消息（从新到旧数第 2 条，不区分是否含 tool_call）
下界   = anchor 的位置
上界   = 最新消息
范围   = [anchor, 末尾] 之间的全部消息，不分角色
```

**范围包含该区间内的所有消息**：user、assistant、tool_result 以及其他任何角色，
全部都是可操作对象。下界只是一个**位置锚点**，不是角色过滤条件。

#### 3.3.2 这个定义好在哪

**(1) 天然对齐原子单元，且不需要额外约定。**

原子单元总是以 assistant 消息开头（§4.2）。所以任何 assistant 消息作为下界，
窗口边界必然落在单元起点，不可能切开 tool_call/result 对。

这比"倒数第二个回合终结符"更强：不需要区分"回合终结符"和"带 tool_call 的 assistant"，
任何 assistant 消息都合法。**定义更简单，性质更好，实现时不需要额外的类型判断。**

**(2) 变更点压到最靠近末尾。**

变更点距末尾的距离 = 最后两条 assistant 消息之间的内容量，而不是整个 epoch 的长度。
代价公式 `(L − i) × (w − r)` 里 `(L − i)` 最小化。

**(3) 自带滑动淘汰。**

每产生新的 assistant 消息，下界就前移一格，旧内容自动滑出窗口。不需要额外的过期逻辑。

#### 3.3.3 三个必须处理的后果

**(1) 窗口可能非常小，这是特性不是缺陷。**

密集工具循环时，倒数第二条 assistant 可能只是倒数第二次工具调用，
窗口就只剩最后两三条消息。这看起来"什么都做不了"，但它换来的是缓存代价最小。
**不要为了"窗口看起来有用"而放宽下界** —— 那会把代价推回中段改写的级别。

**(2) 锚点会漂移，所以标记必须绑 ID，不能绑位置。**

```text
轮 N：模型标记 unit#abc（当时在窗口内）
轮 N+3：unit#abc 已滑出窗口
```

如果执行时按"窗口内第 k 条"定位，会解析到错误的内容。**`mark_context` 的参数
必须是 `unit_id`，执行时按 ID 查找。**

**(3) 这个下界与"打标 + epoch 延迟执行"存在逻辑冲突。**

```text
打标发生在轮 N，执行发生在轮 N+k
→ 轮 N 窗口内的内容，在轮 N+k 时已滑出可编辑范围
→ 若强行执行，变更点远离末尾，缓存代价回到"中段改写"级别
```

这是本模式最需要决策的地方。三种解法：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A 即时执行** | 打标后立刻在本回合内执行 | 每轮一次突变，缓存收益归零 |
| **B 放弃尾部锚定** | 改用 `since_last_epoch` 做大窗口 | 变更点远离末尾，缓存代价高 |
| **C 双层**（推荐） | 日常层用 `W_tail` 即时执行；epoch 层用大窗口批量执行 | 实现复杂度上升 |

**推荐 C**，因为它让两种清理各归其位：

```text
日常层（每回合）：W_tail 窗口内，只处理"刚产生的垃圾"
  - 刚收到的超大工具输出
  - 刚发生的退化长思考
  - 刚被消费完的中间结果
  → 变更点贴末尾，缓存代价最小
  → 等价于"损伤控制"，不是"历史管理"

epoch 层（低频）：since_last_epoch 大窗口，处理"积压的旧内容"
  → 变更点远，代价高，所以必须低频、批量
  → 由第 6 章的触发器驱动
```

#### 3.3.4 定位结论

**采用这个下界，模式 3 的定位就是"尾部清洁工"，不是"上下文管理器"。**

它能处理的内容量 = 最后两条 assistant 消息之间的全部内容。在纯对话里这是"一个回合"，
在密集工具循环里可能只有最后两三次工具调用。历史中段的清理不可能由它完成 ——
那必须靠模式 2 的写入时刻路由（在内容产生时就决定形态）和触发器的 epoch 压缩。

这不是缺陷，是分工。但如果把它当成"能管理整个历史"来设计，会在实现时发现
"模型想标记的东西够不到"，然后被迫放宽下界，最终退化成方案 B（大窗口、高代价）。

**所以必须在产品层面明确告诉模型**：你只能处理最后两条助手消息之间的东西，
更早的内容已经不在你的可编辑范围内，需要靠 `fetch_archive` 重新拉回来才能处理。

#### 3.3.5 边界对齐

窗口边界必须落在原子单元边界上（§5.2），不能落在单元内部。
由于下界是 assistant 消息，而原子单元总是以 assistant 消息开头，这一点自动满足。

唯一例外：如果锚点之后存在尚未闭合的原子单元（并行工具调用只返回了部分 result），
则窗口必须等到该单元闭合后才可编辑。

### 3.4 打标规则与固定提示词

#### 3.4.1 固定提示词注入：上下文卫生

模式 3 需要一个**完全静态**的提示词片段，插在 system prompt 之后，用来告诉模型
"什么算垃圾、什么时候该清、什么绝对不能动"。

**它必须逐字节稳定**（不能含 token 数、窗口比例、时间戳），否则会破坏稳定前缀。
因为它插在系统提示词之后、对话之前，属于缓存前缀的一部分，静态即零代价。

```text
## 上下文卫生

你可以整理最近的上下文。可操作范围是从【倒数第二条助手消息】到当前消息之间的全部内容。
更早的内容不在你的权限内——那些已经滑出窗口，需要先用 fetch_archive 取回才能处理。

### 什么时候该整理

1. 退化思考
   如果上一轮思考里出现大量重复内容（连续数十次 "Hmm"、"让我想想"、
   同一句话反复出现、长时间没有推进），说明那一轮陷入了空转。
   这段内容对后续推理没有价值，应当清理。

2. 废料堆积
   如果最近几轮产生了大量已被消费完的中间结果（读过的文件、跑过的命令输出、
   试探性的失败调用），而它们的结论已经被你记住或写进回复，这些原文可以移出上下文。

3. 重复读取
   如果你发现自己在反复读同一个文件、反复跑同一条命令确认同一件事，
   说明上下文里的信息没有被有效利用。先检查已有内容，再决定是否重读。

### 什么时候不该整理

- 失败与错误：永远保留原文。失败的尝试、报错信息、非零退出码是最有价值的上下文，
  不允许压缩或改写。
- 未完成的事：待办、未验证的假设、用户的硬性约束，标记为 keep。
- 不确定时：保留。误留只浪费 token，误删会丢正确性。

### 怎么做

- 先 ctx_list 看当前可操作的内容，再决定
- 用 mark_context(unit_id, priority, reason) 标记，reason 写清为什么
- 你只负责判断，不直接修改上下文。执行由系统在合适的时机统一完成
- 被移出的内容仍可用 fetch_archive(ref) 取回

### 定期校准

每完成一次清理，或者每隔 10 轮，用一句话重述当前目标：
"我要做的是【X】，目前进行到【Y】。"

如果这句话和你最开始理解的目标不一样，说明发生了任务漂移——
最近几步的上下文压过了原始要求。这时候应该回读最初的任务描述，
而不是顺着当前方向继续。

### 清理轮的约定

如果你是在用户中断后恢复，并且发现上一轮有退化思考或大量废料：
先完成标记，然后结束本轮输出，不要在同一轮里继续任务。
让用户确认清理结果后再继续，避免清理和工作混在一起无法验证。
```

**这段提示词的五条设计约束：**

| 约束 | 理由 |
|---|---|
| 逐字节静态 | 动态内容会破坏稳定前缀，每轮缓存全失效 |
| 工具名与实现一致 | 提示词提到不存在的工具会导致模型调用幻觉 |
| 范围写死 | 明确"倒数第二条助手消息"是唯一权限边界，防止模型尝试越界 |
| **只标记不执行** | 模式 3 的权限设计（§3.2）；若提示词暗示可以直接改，模型会尝试调不存在的编辑工具 |
| 清理轮单独一轮 | 清理与任务混在同一轮，无法验证清理是否正确 |

**一个必须知道的边界**：模型在思考过程中**无法调用工具**。所以这段提示词只能做到
"事后清理"，做不到"事中止损"。如果一轮思考已经退化成五分钟的 "Hmm"，
这一轮的 token 已经烧掉了，提示词救不回来。真正的止损要靠外部流式退化检测
（连续重复 n-gram / 熵骤降 / 长时间无工具调用）主动中断生成。

两者的分工是：

```text
流式检测   → 在退化发生时中断，这段思考根本不写回上下文（事中止损）
固定提示词 → 用户中断后恢复时，让模型主动清掉上一轮的残留（事后清理）
```

用户的实际操作路径正好是后者：看到模型在空转 → 停止 → 要求继续 →
模型在"继续"这一轮先清理残留 → 结束本轮 → 下一轮在干净上下文上工作。

#### 3.4.1.1 退化传染：机制、检测、清理协议

事中止损不是必需的，原因是一个实际观察到的现象：**大量 "Hmm" 留在上下文里，
后续任务里模型会极其容易继续 "Hmm"。**

**机制**：上下文中的模式会成为下一次生成的先验，模型倾向于补全它看到的模式，
而不是重新推理。三条强化路径同时作用：

| 路径 | 表现 | 后果 |
|---|---|---|
| **直接模仿** | 继续输出相同的 token 模式 | 新一轮也退化 |
| **动作重复** | 重复历史中的先前动作而非重新推理（Context Rot 的 context distraction） | 无效循环 |
| **注意力占位** | 大量重复 token 稀释注意力预算 | 真正有用的内容被淹没 |

**文献依据**：

| 研究 | 结论 |
|---|---|
| Holtzman et al. 2019, *The Curious Case of Neural Text Degeneration* | 贪心 / beam 搜索必然把模型推入重复；nucleus sampling 缓解但不消除 |
| Xu et al., *Learning to Break the Loop*（Apple） | **句子级重复有自我强化效应：一句话在上下文里出现越多，继续生成它的概率越高**；初始概率高的句子，强化效应更强 |
| Duan et al., circular reasoning | **语义重复先于文本重复** —— 模型先"卡在一个想法上"，然后才出现相同措辞；伴随 V 型注意力模式 |
| Liquid AI, *Antidoom* | 机制明确：先前上下文强化循环，每次重复让循环 span 内每个 token 的概率向 1 爬升。LFM2.5-2.6B 上 10.2% 的困难任务出现循环，针对性干预后降到 1.4% |
| *LoopGuard* (2026) | **基于注意力重要性的 KV cache 驱逐会自我强化**：塌缩的注意力反复保留相同的重复状态，降低 cache 多样性，进一步放大循环 |

**两条直接影响设计的推论**：

1. **检测必须看语义，不能只看 n-gram。** Duan et al. 发现语义重复先于文本重复——
   "卡在一个想法上"的阶段还没有出现重复词，但回路已经形成。只看 n-gram 会晚一步。
   检测信号应该包含：语义相似度（连续几轮在说同一件事）、无新实体引入、无状态变更。

2. **KV 层的注意力驱逐可能加剧退化。** LoopGuard 的结论对模式 4 的 KV 方案是直接警告：
   如果驱逐策略依赖 attention score，塌缩的注意力会反复保留同一批重复状态，
   形成"越驱逐越重复"的正反馈。**若走 KV 层路线，不要用纯 attention-based 驱逐**，
   需要引入多样性约束（如按内容去重、强制覆盖不同位置）。

**所以清理的定位变了**：

```text
清理退化思考 ≠ 省 token
清理退化思考 = 打断一个自我强化的回路
```

它不是一个可选的优化，而是**防止质量持续劣化的必要动作**。
留着一轮不清理，下一轮就多一分继续空转的概率；清掉，回路立刻断开。

##### 检测（三层，任一层命中即触发）

```text
流式层（生成中）：
  - 同一 n-gram 连续重复 ≥ degenerate_repeat_n 次
  - token 熵骤降（滑动窗口）
  - 超过 N 秒无工具调用且无新内容
  → 主动中断生成（事中止损，可选）

轮末层（一轮结束后）：
  - 本轮 thinking token 数 > 阈值
  - 有效信息密度 = 新增事实数 / 总 token < 阈值
  → 标记为待清理

跨轮层（连续多轮）：
  - 连续 ≥ 3 轮出现退化标记
  → 判定为任务级问题，见下方"防复发"
```

##### 清理协议（四步，缺一不可）

| 步骤 | 动作 | 失败后果 |
|---|---|---|
| 1 定位 | 找到退化单元的 `unit_id` | 清错内容 |
| 2 清理 | 删除整段 thinking 或整条 assistant 消息 | — |
| 3 **复核** | `ctx_list` 确认该单元已不在上下文中 | 残留片段仍会诱导，等于没清 |
| 4 记录 | 写入日志：轮次 / 长度 / 检测依据 | 无法统计与调参 |

**第 3 步最容易被跳过，也最关键。** 只清一半比完全不清更糟——残留的片段仍然是模式先验。

##### 清理后必须给"重启锚点"

删除之后，模型可能试图回忆被删的内容，从而产生幻觉（"我之前好像查到过…"）。
所以清理动作必须附带一条状态说明：

```text
[已清理：第 N 轮的退化思考，共 12k token，原因：连续重复]
当前状态：任务 X 进行中，已完成 A/B，下一步是 C。
```

这条说明本身是追加的（不破坏缓存），但它给了模型一个明确的起点，
避免它去重建被删的内容。

##### 防复发

| 现象 | 判断 | 动作 |
|---|---|---|
| 清理后下一轮正常 | 清理有效 | 继续任务 |
| 清理后 2 轮内又退化 | 上下文里还有残留，或任务本身模糊 | 检查是否清干净；检查任务描述 |
| **连续 ≥ 3 轮都退化** | **不是上下文问题，是任务问题** | **停止清理，拆分任务或向用户澄清** |

最后一条很重要：**如果反复清理仍然反复退化，继续清理是无效的**。
退化是症状，任务定义不清、目标过大、缺少可验证的中间态才是病因。
这时候正确的动作是问用户，不是继续删。

##### 两条执行路径

退化思考的检测条件是机械的，清理动作也是机械的，所以它可以完全自动化：

```text
自动路径：检测到退化 → 下一轮开始前自动清理 → 记录日志 → 注入重启锚点
提示词路径：模型根据固定提示词主动调用 mark_context 标记 → 策略层执行
```

模型参与的价值在"判断哪些是废料"这类语义问题，不在"这段是不是 Hmm"。
追求响应速度走自动路径，追求可控性走提示词路径。**两条可以并存，
但不要指望提示词路径能做到即时** —— 它需要模型先意识到问题，至少晚一轮。

**平台差异**：删除思考内容是否合法取决于 provider。有些平台要求回传完整的
reasoning 内容（含签名），有些允许丢弃。**实施前必须按 provider 确认**，
不能假设所有平台都允许删 thinking。

#### 3.4.1.2 语义卡死与退化循环：两种病，两种治法

这两种失败经常被混为一谈，但它们的机制和对策不同。分不清会导致"清了很多次还是卡"。

| | 退化循环 | 语义卡死 |
|---|---|---|
| 层次 | token / 生成层 | 想法 / 策略层 |
| 表现 | 同样的词句反复出现 | 反复尝试同一个思路，但**用词不同** |
| 机制 | 概率塌缩，自我强化（§3.4.1.1） | 策略空间被锁定，找不到新分支 |
| 出现顺序 | 较晚 | **较早**（Duan et al.：语义重复先于文本重复） |

**检测要分开做**：

| 信号 | 退化循环 | 语义卡死 |
|---|---|---|
| n-gram 重复率 | 高 | 可能完全正常 |
| 连续轮次语义相似度 | 高 | 高 |
| 新实体引入速率 | 低 | 低 |
| 状态变更（文件 hash / 命令输出） | 无 | 无 |
| 输出长度 | 异常长 | 正常 |
| 换个说法后是否仍重复 | 是 | 是 |

只监控 n-gram 会漏掉语义卡死——那时候输出很"干净"，只是毫无进展。

**对策完全不同**：

| 手段 | 退化循环 | 语义卡死 |
|---|---|---|
| 清理上下文 | **有效** | **无效** |
| 调整温度 / 采样 | 有效 | 部分有效 |
| 注入新信息 | 不必需 | **必需** |
| 重述目标 | 辅助 | 有效 |
| 换模型 | 兜底 | 兜底 |

##### 核心结论：清理只是移除状态，吸引子还在

退化是一个动力学吸引子。清掉上下文只是把系统从吸引子里拉出来一次，
**如果输入条件不变，它会重新落回去**。

所以完整的恢复动作是三段，不是两段：

```text
清理残留 → 注入重启锚点 → 改变一个输入变量
```

第三段最容易被省略，也最关键。可选的"改变"：

- 让用户给一句方向提示
- 读一份之前没读过的参考材料
- 缩小或重划子目标
- 换一种验证方式（比如先写测试再改代码）
- 显式禁止当前方案（"不要再试 X"）

**没有第三段，清理就是治症状不治病。** 这也解释了为什么"连续 3 轮都退化 = 任务问题"
这条判据成立（§3.4.1.1）：如果每次清理后都回到同一个坑，说明吸引子由任务本身构成，
不是由上下文构成。

#### 3.4.2 打标规则

模型在正常工作中顺带打标，不额外发起一轮。

| 标记 | 什么时候用 | 执行语义 |
|---|---|---|
| `keep` | 未完成的 TODO、未验证的假设、当前错误、硬约束 | 永不自动处理，等同 protected |
| `low` | 失败尝试，结论已提取；已消费的中间结果 | 可 masking（F3） |
| `discard_candidate` | 已完成的工具调用 + 输出已被后续动作完全消费 | 可转储（F4），保留归档 |

**打标必须给理由**，理由写入归档元数据。这不是形式要求 —— 事后诊断时，
"模型当时为什么认为这条没用了"是唯一的排查线索。

**给模型的指导原则**（写进 system prompt）：

- 判断依据是"这条内容对**剩余任务**是否还有用"，不是"它是否重要"
- 失败尝试的**结论**要留，**过程**可丢
- 不确定时标 `keep`。误标 keep 只损失 token，误标 discard 损失正确性

### 3.5 执行策略

```text
epoch 边界到达
    │
    ├─ 1. 收集本 epoch 全部标记
    ├─ 2. 按优先级排序：discard_candidate → low
    ├─ 3. 检查 protected / keep，跳过
    ├─ 4. 计算成本：本次变更的回本轮数 N*（附录 A）
    ├─ 5. 若 N* > 剩余轮数估计 → 本 epoch 只执行一部分（按收益排序）
    ├─ 6. 批量执行（一次突变，一次冷启动）
    └─ 7. 记录 undo 日志 + 告知模型执行结果
```

**第 5 步是本模式唯一需要策略层"聪明"的地方**：它必须能拒绝执行。
如果每个 epoch 都全量执行标记，就退化成了"每轮突变"。

### 3.6 质量门：覆盖率校验

模型自我压缩有信息损失偏差。执行前必须跑客观校验：

```text
从将被处理的内容中抽取硬事实：
  - 文件路径、命令、URL
  - 错误码、退出码、异常类型
  - 数字、版本号、标识符
  - 未完成项、未验证假设、硬约束

检查处理后的上下文是否仍能回答：
  - 全部 protected 条目是否可见（可 masking，但条目不能消失）
  - 全部 keep 标记是否可见
  - 全部"第 N 步的细节在第 M 步才变关键"的约束是否可检索

缺失率 > threshold → 拒绝执行，回退并要求补全
```

这是把"模型自己审自己的草稿"从主观变成客观的唯一办法。

### 3.7 完整流程

```text
[正常轮次]
  模型工作 → 顺带调用 mark_context(...)
  → 标记写入日志（追加，零缓存代价）
  → 返回 recorded / queued

[epoch 边界]
  收集标记 → 排序 → 过滤 protected → 成本计算
  → 决定执行子集 → 批量执行 → 覆盖率校验
  → 通过：提交新上下文（或原地变更，见 §3.10）
  → 不通过：回退，要求补全
  → 告知模型：哪些标记被执行、哪些被拒绝、为什么
```

### 3.8 工具接口

```text
mark_context(unit_id, priority, reason)
    → recorded | queued(epoch#N) | rejected(reason)

ctx_list(scope, filter)          // 列单元：id / 角色 / 来源 / token / 指针
ctx_inspect(unit_id)             // 查看完整内容（只读）
fetch_archive(ref)               // 追加还原
search_archive(query, limit)     // 搜归档
```

**本模式不提供** `ctx_compress` / `ctx_discard` / `ctx_reorder`。
模型只能打标，不能直接改。这是刻意的权限限制。

### 3.9 参数默认值

| 参数 | 默认 | 说明 |
|---|---|---|
| `epoch_trigger` | 见第 6 章 | 由触发器或手动触发 |
| `max_marks_per_epoch` | 50 | 防止一次标记过多 |
| `coverage_threshold` | 0.95 | 覆盖率校验通过线 |
| `min_execute_gain` | 2k tok | 收益低于此不执行（避免碎片化变更） |
| `degenerate_repeat_n` | 20 | 同一 n-gram 连续重复次数阈值 |
| `degenerate_min_tokens` | 2k | 低于此长度不判定为退化 |
| `cleanup_delay_turns` | **0** | 退化清理延迟轮数。**默认必须为 0**（§3.4.1.1） |

### 3.10 失败模式与兜底

| 失败 | 表现 | 兜底 |
|---|---|---|
| 打标被静默丢弃 | 模型不再认真打标 | `mark_context` 必须返回处理结果 |
| 过度压缩 | 后续轮次重复劳动 | 覆盖率校验 + 保留最近 N 轮不动 |
| 模型美化失败 | 失败细节丢失 | protected 标记 + 只允许 extractive 处理 |
| epoch 太频繁 | 缓存全破 | 策略层成本判据（§3.5 第 5 步） |
| 模型从不打标 | 功能形同虚设 | 监控标记密度；过低则提示或降级到模式 2 |
| **退化清理被延迟** | **下一轮继续空转，传染扩大** | **`cleanup_delay_turns = 0`，退化清理不走 epoch** |
| 原地变更破坏可复现 | 无法回滚 | 优先 fork 新上下文；原地变更必须写 undo 日志 |

### 3.11 验收标准

- 打标阶段不产生任何上下文变更（`used` 不变）
- 执行阶段只发生一次突变（缓存冷启动次数 = 1）
- 覆盖率校验能拦住人为构造的"丢失关键约束"场景
- 模型在收到 `rejected` 后的后续打标行为无退化（对比实验）
- 全部执行可回滚到执行前状态

## 4. 模式四：灰烬模式（注意力优先）

### 4.1 定义与适用边界

**定义**：给模型对上下文的完全编辑权——可压缩、丢弃、还原、**重排**任意原子单元，
代价是缓存可以被完全破坏。

**命名校正**：模型的智力是固定的，改上下文不会让它变聪明。它换来的是
**在有限注意力预算下，把上下文整理成最有利于推理的形态**。
准确的定位是"注意力优先模式"。

**它的目标函数与前三种不同**：

| 模式 | 优化目标 | 度量 |
|---|---|---|
| 1 / 2 / 3 | 成本 × 缓存命中 × 容量 | 花费、上下文增长率 |
| 4 | 单位上下文的信息密度与注意力质量 | **任务成功率、卡壳解除率、轨迹长度** |

**这意味着模式 4 的收益无法用省钱衡量。它天生是亏钱的。**

**适用**（成本不敏感、质量敏感）：

- 卡住了要换思路，需要清掉所有失败路径
- 需要精确回忆某段历史，把归档拉回并重排到合适位置
- 复杂规划，需要把所有干扰项移出注意力

**不适用**：长跑的日常轮次。

**必须做成临时模式，不是常驻模式。** 开启方式：

- 手动：用户卡壳时开一轮
- 自动：连续 N 轮无状态变更 / 重复同样操作 → 提示

#### 4.1.1 定位精确化：它不是"低性价比"，是"用钱买成功率"

一个常见的误读是"模式 4 牺牲性价比换质量"。这个说法不准确，会误导使用策略。

```text
正常任务上用模式 4  → 纯浪费（付出成本，收益接近零）
卡壳时用模式 4      → 性价比最高（卡壳的代价是无限时间，此时成功率的边际价值极高）
```

所以它的准确定位是**高成本、高收益的工具，用在收益最高的时刻**，
而不是"一个效率较低的模式"。这两者的使用策略完全相反：
前者应该尽量少用，后者应该在关键时刻果断用。

##### "纯度"需要形式化，否则无法验证

如果"纯度"只是感觉，就没法判断一次模式 4 会话是否成功。可测量的代理量：

| 指标 | 定义 | 目标 |
|---|---|---|
| 干扰比 | 与当前子目标无关的 token / 总 token | 越低越好 |
| 失败路径残留 | 已放弃方案的消息数 | 0 |
| 冲突陈述 | 相互矛盾的信息条数 | 0 |
| 目标清晰度 | 目标陈述是否包含可验证的完成条件 | 是 |
| 任务信息完整度 | 完成任务所需的最小信息集是否齐全 | **必须为 100%** |

##### 纯度悖论：过度提纯会损害任务

纯度不可能达到 100%，也不应该追求 100%。因为上下文里必须保留：

- 任务本身的材料（代码、文档、需求）
- 历史决策（否则重复劳动）
- 失败记录（否则重犯）

存在一个**最小信息集**，低于它就信息不足。所以模式 4 的目标不是"最大纯度"，
而是**最优信噪比**：

```text
信噪比 = 有用信息 / (有用信息 + 干扰信息)
```

最大化纯度会让分母趋零，但分子也可能下降。**提纯的边界是"最小信息集完整"**，
越过这条线，纯度上升而表现下降。

##### "绝对智力"的实际上限

模型的参数能力是固定的。上下文只能让它**发挥出**能力，不能让它**超出**能力。
所以"绝对智力"= 该模型在最优上下文下的表现上限，这个上限是可测的：

```text
上下文贡献 = P(最优上下文) − P(常规上下文)
```

如果这个差值很小（比如 3 个百分点），说明该任务的瓶颈不在上下文，
模式 4 的收益上限就只有 3 个百分点。**这个测量应该在投入实现之前做**（附录 D）。

##### 它的本质：上下文的随机重启

模式 4 在机制上等价于优化算法里的**随机重启**（random restart）：

| 类比 | 对应 |
|---|---|
| 陷入局部最优 | 卡壳，反复尝试同一类方案 |
| 随机重启 | 清空上下文，从干净状态重新开始 |
| 模拟退火升温 | 引入扰动（换模型、换温度、换视角） |

随机重启有一个已知的理论性质：**它的收益取决于地形**。
单峰任务重启无效；多峰任务重启有效。所以模式 4 的适用性不是普适的，
它取决于任务是否存在"多个可解的路径"。**这也是可测的**：
同一任务多次重启，成功率是否提升。

### 4.2 权限边界：原子单元

**这是本模式唯一的硬约束，违反即产生非法消息序列。**

协议层要求：

```text
assistant(tool_calls=[c1, c2])  →  必须跟随  tool_result(c1), tool_result(c2)
```

| 约束 | 说明 |
|---|---|
| 配对完整 | 每个 tool_call 有且仅有一个 tool_result |
| 顺序固定 | result 必须紧跟对应的 call |
| 无悬空 | 不能有"有 call 无 result"或反之 |
| 角色交替 | 多数 provider 要求 user / assistant 交替 |

**原子单元定义**：

```text
单元 A：assistant(tool_calls[n]) + 紧随的全部 tool_result[n]
单元 B：一条完整的 user 或 assistant 文本消息（无 tool_call）
```

**并行工具调用**：一个 assistant 消息含 N 个 tool_call 时，必须等 N 个 result
**全部到齐**才算单元闭合。未闭合的单元禁止任何编辑。

**所有编辑工具的参数类型是 `unit_id[]`，不是 `message_id[]`。**
从类型层面消除误用可能。`message_id` 只用于 `ctx_inspect` 这类只读操作。

### 4.3 编辑操作集

| 操作 | 语义 | 缓存代价 | 可逆 |
|---|---|---|---|
| `ctx_compress(units, instruction)` | **extractive 截断**，不生成摘要 | `(L−i)×(w−r)` | ✅ |
| `ctx_discard(units)` | 移出上下文，原文保留在归档 | `(L−i)×(w−r)` | ✅ |
| `ctx_restore(refs)` | 追加还原 | 零（追加） | — |
| `ctx_reorder(units, order)` | 单元间重排 | `(L−i)×(w−r)` | ✅ |
| `ctx_pin(units)` | 标记不可动 | 零 | — |

**`ctx_compress` 必须是 extractive 的。** 它只做"保留头尾、中间打标记"，
不允许调用 LLM 重写内容。理由：摘要幻觉 + 轨迹延长（附录 B）。

**`ctx_reorder` 的语义**：只在原子单元之间重排，不改变单元内部顺序。
它的理论依据是 lost-in-the-middle —— 模型对上下文中间的信息系统性低估（附录 B.6 位置层），
把关键单元移到头部或尾部理论上能提升利用率。**但这条从未被测量过，属于赌注。**

##### 重排的布局规则

```text
[头部]  当前目标 + 硬约束 + 关键失败记录
[中段]  参考材料、已完成的中间结果、可丢弃内容
[尾部]  最近的工作状态 + 当前错误 + 下一步
```

| 内容 | 放哪 | 理由 |
|---|---|---|
| 目标与约束 | 头部 | 对抗任务漂移（附录 B.6 目标层） |
| 关键失败记录 | 头部或尾部 | 对抗重复失败；放中间会被忽略 |
| 最近状态 | 尾部 | 对抗近因偏置导致的"忘了自己在干什么" |
| 参考材料 | 中段 | 它们的作用是"可查"，不是"常驻注意力" |
| 已确认无用但可能被引用 | 中段或移出 | 放中段保留可检索性，代价最小 |

**三条重排约束**：

1. **`ctx_pin` 的单元不参与重排**。目标和约束应该被 pin 在头部。
2. **重排后必须验证单元完整性**。重排是搬整个单元，不是搬单条消息；
   搬完用协议校验器过一遍，确认没有切开 tool_call/result 对。
3. **重排的代价按第一个被移动单元的位置计算**。如果把头部单元也挪了，
   代价就是整个上下文（`L × (w − r)`）。所以**重排应该只动尾部区域**，
   头部保持稳定 —— 这既是缓存考虑，也是"目标不该漂移"的要求。

**一个反直觉的限制**：重排的收益随次数递减。第一次重排把关键内容放到头尾，
收益最大；第二次、第三次继续调整，收益接近零而代价照付。
所以**每次模式 4 会话只做一轮重排**，做完就进入工作，不要反复微调位置。

### 4.4 快照与 undo

模式 4 允许不可逆的破坏，所以必须有完整的回滚能力。

```text
进入模式 4
  → 创建快照 snapshot_id（冻结当前上下文，只读）
  → 所有编辑记录 diff：{op, unit_ids, before_hash, after_hash, timestamp}
  → 退出时：
      ├─ 保留（切换为新上下文，原上下文仍可回滚）
      └─ 回滚（恢复到 snapshot_id，丢弃全部编辑）
```

**undo 日志必须可导出**。没有可导出的 undo 日志，一次错误删除就永久丢失，
而且无法事后诊断"当时为什么删了这条"。

### 4.5 固定提示词注入：编辑纪律

模式 4 的提示词与模式 3 完全不同。模式 3 是"只判断不执行、范围受限"，
模式 4 是"完全编辑权、全史范围"，所以它的提示词必须讲**代价**和**纪律**，
而不是讲"怎么克制"。

同样必须**逐字节静态**，插在 system prompt 之后，属于稳定前缀。

```text
## 上下文编辑

你现在拥有对上下文的完全编辑权：可以压缩、丢弃、还原、重排任意原子单元。
这个权限的代价是缓存会被破坏，所以下面的纪律不是建议，是使用条件。

### 代价

每一次编辑都会让从变更点到末尾的缓存失效。所以：
- 不要边想边改。先想清楚要做什么，再一次做完
- 不要做小修小补。要么不动，要么一次改到位
- 改完立刻进入工作，不要在编辑状态里停留

### 什么时候值得用

1. 卡住了
   连续多轮没有进展、反复尝试同一类方案、思路在原地打转。
   清掉所有失败的尝试路径，比继续尝试更有效。

2. 需要精确回忆
   某段历史很关键，但被大量无关内容包围。
   用 fetch_archive 取回原文，再用 reorder 把它放到头尾。

3. 干扰项太多
   上下文里有大量语义相近但无关的内容在稀释注意力。把它们移出去。

4. 退化残留堆积
   如果上下文里有多轮 "Hmm" 之类的退化思考残留，
   一次性全部清掉。它们会持续诱导后续轮次继续退化，
   清一半等于没清。

### 什么时候不该用

- 失败与错误：永远保留。删掉失败记录等于允许自己重犯。
- 用户的硬性约束：永远保留，并且放在头部。
- 未完成的事：待办、未验证的假设，保留。
- 只是想省 token：不要为了省 token 编辑。这个模式不省钱。

### 怎么排

模型对上下文中间的内容注意力最弱。所以：
- 当前任务的目标和约束 → 头部
- 最近的工作状态 → 尾部
- 已确认无用但可能被引用的内容 → 中间，或移出
- 关键错误和失败记录 → 头部或尾部，不要放中间

### 怎么做

1. ctx_list 看全貌
2. ctx_inspect 看具体内容
3. 决定操作：compress / discard / restore / reorder
4. 每次操作后检查结果
5. ctx_finish 提交

### 提交前的三个确认

- 任务目标还在吗？
- 用户的硬性约束还在吗？
- 失败记录还在吗？

三个都是"是"才提交。

### 一条判断

如果连续多轮都卡住，问题可能不在上下文，而在任务定义。
这时候应该向用户澄清，而不是继续清理。
```

**与模式 3 提示词的对照**：

| 维度 | 模式 3 | 模式 4 |
|---|---|---|
| 权限说明 | "你只负责判断，不直接修改" | "你拥有完全编辑权" |
| 范围 | 倒数第二条助手消息之后 | 全部历史 |
| 核心风险 | 越界、误删 | 缓存爆炸、不可逆 |
| 提示词重点 | 克制（只标记） | 纪律（一次做对） |
| 退化处理 | 标记待清理 | **一次性全部清掉** |
| 失败保留 | 相同 | 相同 |
| 收尾 | 结束本轮，等用户确认 | 提交前三个确认 |

**两条共有的约束**：失败与错误永远保留；不确定时保留。
这两条在两种模式下都不能松，因为它们是防幻觉的底线。

### 4.6 完整流程

```text
[用户或检测器触发]
  → 创建快照
  → 注入"上下文编辑模式"临时指令（标记为脚手架）
  → 模型循环：
       ctx_list → ctx_inspect → 决定操作 → ctx_compress / discard / reorder / restore
       （每次操作都是一次工具调用，追加式，可逐步检查）
  → 模型调用 ctx_finish()
  → 覆盖率校验（同 §3.6）
  → 通过：生成新上下文，切换；原上下文保留为可回滚快照
  → 不通过：回退，要求补全
  → 清理脚手架消息
  → 记录 trace：操作序列 / 每步代价 / 最终 used
```

### 4.7 工具接口

```text
ctx_list(scope, filter)                 // 列单元
ctx_inspect(unit_id)                    // 只读查看
ctx_compress(unit_ids[], instruction)   // extractive 截断
ctx_discard(unit_ids[])                 // 移出（保留归档）
ctx_restore(refs[])                     // 追加还原
ctx_reorder(unit_ids[], new_order)      // 单元间重排
ctx_pin(unit_ids[])                     // 标记不可动
ctx_finish()                            // 提交（幂等）
fetch_archive(ref)                      // 同模式 2
search_archive(query, limit)            // 同模式 2
```

**全部编辑工具必须满足**：

- 无副作用（除上下文外不改任何状态）
- 参数是 `unit_id[]`，收到半个单元必须拒绝并报错
- `ctx_finish()` 幂等：重复调用返回同一结果
- 任何工具都不得删除归档条目

### 4.8 参数默认值

| 参数 | 默认 | 说明 |
|---|---|---|
| `max_ops` | 50 | 单次会话最大编辑次数 |
| `timeout` | 300s | 超时回退到最后有效状态 |
| `require_snapshot` | true | 无快照禁止进入 |
| `require_coverage_check` | true | 提交前必须过覆盖率校验 |

### 4.9 失败模式与兜底

| 失败 | 表现 | 兜底 |
|---|---|---|
| 非法消息序列 | provider 400 | `unit_id` 类型约束 + 单元闭合检查 |
| 不可逆误删 | 上下文损坏 | 强制快照 + undo 日志 |
| 模型无限编辑 | 卡死 | `max_ops` + `timeout` |
| 编辑后质量更差 | 成功率下降 | 保留原快照，可一键回滚；A/B 对比 |
| 脚手架泄漏 | 污染后续上下文 | 脚手架不进新上下文、不进归档 |
| 缓存全破后成本爆炸 | 账单异常 | 模式 4 默认限时；成本监控告警 |
| **退化残留只清一半** | **下一轮继续空转** | **提交前用 `ctx_list` 复核；一次性清完，不分批** |

### 4.10 验收标准

- 任意编辑序列都不产生非法消息序列（用协议校验器验证）
- 任意操作都可回滚到快照状态
- 提交前的覆盖率校验能拦住人为构造的"删掉关键约束"
- 模式 4 的收益用**任务成功率 / 卡壳解除率 / 轨迹长度**衡量，不用成本衡量
- 与模式 3 对比：在同一卡壳任务上，模式 4 的解除率是否显著更高
- 注入 3 轮退化残留，模式 4 能一次清完，且清理后下一轮不再退化（这是最直接的验收）

## 5. 共享基础设施

四个模式共用。可以先建这一章，再建任何模式。

### 5.1 消息 ID 与命名空间

```text
session_id  = 每次 fork 新生成
message_id  = {session_id}:{seq}
ref         = 全局唯一，内容寻址（hash）或 UUIDv7，跨会话/跨 fork 稳定
```

**归档条目必须记录**：来源 session + 来源 message_id + 内容哈希。
否则回滚到旧会话后，`fetch_archive(ref)` 会解析到错误的上下文。

### 5.2 原子单元

见 §4.2 的定义。它是所有编辑操作的最小单位，也是触发器检查点的最小单位。

实现建议：把原子单元做成消息层的**不可变视图**，编辑接口只接受 `unit_id[]`。

### 5.3 来源标签

每条内容片段标注来源：

```text
system / instructionInjection / history / toolCall / toolResult /
memory / worldBook / skills / workspace / search / modelThinking
```

**这是整套架构的地基。** 没有它，模式 2 的规则无从下手
（无法"只归档工具输出、不动用户输入"），模式 3 的语义判断也没有依据。
从零开始建，先建这一层。

### 5.4 归档层

结构见 §2.4。三条原则：

1. **默认永远存**，不存在"是否存储"的开关。存储不占上下文、不花钱。
2. **永不自动删除**。需要控制的是索引查询成本，不是存储量。
3. **分层**：热（本会话最近）/ 温（本会话全部）/ 冷（跨会话历史，需显式 expand）。

### 5.5 归档索引

三层，按成本从低到高：

1. **指针自带判别信息**（主力，零额外成本）。指针必须包含来源、位置、一句话内容。
   模型只看指针就能判断要不要取回，大多数情况不需要检索。
2. **`search_archive(query, limit)`** 关键词/全文检索（SQLite FTS5 / BM25 足够）。
   返回指针列表，不返回全文。
3. **向量检索** —— 最后手段，建议先不做。归档内容是代码和日志，关键词匹配往往比语义检索更准。

### 5.6 归档安全

归档层是新的泄露面。工具输出会混入凭据，一旦进归档就同时存在于
上下文、磁盘、索引、undo 日志、导出包。

必须做三件事：

1. **写入时刻脱敏**：模式匹配 `ghp_` / `sk-` / `AKIA` / `BEGIN PRIVATE KEY` /
   `://user:pass@` / JWT 三段式 → 替换占位符
2. **静态加密**，密钥不进归档目录
3. **导出时二次扫描**，默认剔除归档原文，只留指针与描述

脱敏必须在写入时刻做，事后清理一定漏。

### 5.7 token 计量

```text
used = system + tools + memory + worldBook + skills + history
window = 有效窗口（不是宣传窗口）
```

- 按来源分桶计量，便于定位增长源
- 按 provider 区分（图片、工具 schema 计费方式不同）
- `有效窗口 = min(声明窗口, 服务端实际接受上限, 窗口 − 预留输出)`
- 第三方托管商常把同一模型降级（1M → 200K），必须按实际 endpoint 探测

### 5.8 CacheProfile

把易变参数集中到一处：

```text
CacheProfile {
  provider, model
  window_declared, window_effective, max_output
  min_cacheable_tokens
  cache_granularity          // 64 / 128 / block
  breakpoint_max             // 0 = 自动前缀式
  ttl_seconds
  write_multiplier w
  read_multiplier  r
  scope                      // 账号级 / 组织级 / 会话级
  supports_kv_reuse
  measured_at                // 超过 90 天标记"待复核"
  source_url
}
```

### 5.9 运行时健康度指标

前面各章定义了每个模式内部的验收标准，但运行时需要一套**统一的仪表盘**，
用来回答"现在这个会话健康吗"。它跨模式通用，也是决定"是否该切模式"的依据。

| 指标 | 计算方式 | 绿 | 黄 | 红 |
|---|---|---|---|---|
| 上下文增长率 | `Δused / 轮`（10 轮滑动） | < 8k | 8–20k | > 20k |
| 缓存命中率 | `hit / prompt` | > 0.85 | 0.6–0.85 | < 0.6 |
| 退化命中 | 每 10 轮检测到退化的次数 | 0 | 1 | ≥ 2 |
| 语义停滞 | 连续轮次语义相似度 > 阈值的最大长度 | < 3 | 3–5 | > 5 |
| 目标偏移 | 重述目标与原始目标的差异度 | < 0.2 | 0.2–0.4 | > 0.4 |
| 重复读取率 | 同一路径重复读取次数 / 总读取 | < 0.1 | 0.1–0.3 | > 0.3 |
| 工具失败率 | 非零退出 / 总调用 | < 0.1 | 0.1–0.3 | > 0.3 |
| 轨迹长度 | 完成当前子目标的步数 | 接近预期 | 1.5× | > 2× |
| 清理频次 | 清理次数 / 轮 | < 0.1 | 0.1–0.3 | > 0.3 |
| 回灌频次 | fetch 次数 / 轮 | < 0.2 | 0.2–0.5 | > 0.5 |

**红灯对应的动作**：

| 红灯指标 | 含义 | 动作 |
|---|---|---|
| 上下文增长率 + 缓存命中率 | 形态路由失效或前缀被动 | 检查是否有动态内容进了头部 |
| 退化命中 + 语义停滞 | 吸引子已形成 | 走 §3.4.1.2 的三段恢复 |
| 目标偏移 | 任务漂移 | 重述目标，必要时回读原始要求 |
| 重复读取率 | 上下文里的信息没被有效利用 | 检查指针描述是否足够，或归档检索失败 |
| 工具失败率 | 环境问题或方案错误 | 先查环境，再查方案 |
| 轨迹长度 | 效率下降 | 对比历史基线，判断是任务难度还是上下文问题 |
| 清理频次过高 | 要么规则过激，要么任务本身在制造垃圾 | 调阈值；若仍高，说明任务形态不适合当前模式 |
| 回灌频次过高 | 指针信息不足，模型在盲目取回 | 改描述符格式，不要先改阈值 |

**两条使用纪律**：

1. **这些指标不能用来证明"功能有效"**，只能用来发现异常。功能有效性必须靠 §7 的对照实验。
2. **红灯不是"要调参"的信号，是"要换模式"的信号。** 如果模式 2 的上下文增长率持续红灯，
   说明规则覆盖不了这个任务，应该升级到模式 3，而不是把阈值调松。

## 6. 自动压缩触发器

跨模式通用。模式 1 的安全阀也复用它。

### 6.1 触发判据

固定百分比不够用，因为它不知道每轮增长量，也不知道价格比。用实时判据：

```text
R      = (W − used) / avg_per_turn        // 不压缩还能跑几轮
N*     = (w − r)/r × (L − i)/d            // 本次压缩的回本周期（附录 A）
margin = 1.5

if used > 0.85 W                    → 强制压缩（安全阀）
elif R < margin × N*                → 压缩（避免硬失败）
elif 质量指标恶化                    → 压缩（买质量）
else                                → 不压缩
```

`avg_per_turn` 用最近 10 轮滑动平均，设下限 2k 防止除零。

**质量指标**（可观测代理量）：

- 同一文件/同一工具的重复读取次数上升
- 工具调用失败率上升
- 模型引用"上下文里已不存在"的内容（自相矛盾检测）
- 输出里出现"我之前提到过…"但检索不到对应内容

### 6.2 检查点

**只能在原子单元边界检查。** 不能在 token 流中间打断：

- 会得到半截 assistant 消息
- 工具循环里会产生悬空 tool_call
- 多数 provider 直接拒绝

合法检查点：

- 一次"用户输入 → 助手完整回复"结束后
- 一次工具循环收敛后
- 一次工具调用返回后（**且该单元全部 result 到齐**）

### 6.3 压缩会话流程

```text
触发
  → 1. 冻结原上下文（只读快照，记 snapshot_id）
  → 2. 注入"自动压缩助手"临时指令（标记为脚手架）
  → 3. 模型循环调用编辑器工具
        · 每次调用是追加式工具结果 → 缓存友好
        · 有 max_ops 上限 + 超时兜底
  → 4. 覆盖率校验（§3.6）
  → 5. 模型调用 ctx_finish()（幂等）
  → 6. 等模型本轮输出自然结束
  → 7. 生成新会话：新上下文 + 重新注入稳定前缀 + 新 ID 命名空间
  → 8. 切换，清理脚手架消息
  → 9. 记录 trace
```

### 6.4 提交与切换

- **新会话第一条消息的角色**：用 system 或带特殊标记的 user，不能是普通 user
- **必须重新注入** system / memory / world book / skills / tools（稳定前缀不能丢）
- **新会话 = 缓存全冷**，第一轮付全价。无法避免
- **脚手架不进新会话、不进归档**

### 6.5 兜底

- 模型一直不提交 → `max_ops` 上限 + 超时 → 退化为确定性截断（保留最近 N 轮 + 头尾）
- 提交后校验失败 → 回退到快照，记录失败原因
- 压缩过程本身溢出 → 按 `min(主模型窗口, 压缩模型窗口)` 计算预算

## 7. 实施路线

**第 0 步：先证伪，再开发。**

给现成的开源实现打一个 `fetch_archive(ref)` 补丁，跑任务集，看长任务成功率是否提升。
一两天工作量，但它决定后面所有工作是否值得做。

**如果第 0 步无效，正确的做法是停下来，而不是继续做模式 4。**

> **v1.1：第 0 步已执行，结论见附录 E。** 摘要如下：
>
> - `fetch_archive` 的**召回机制有效**，但**纯位置路由会失效**——必须叠加任务锚点（§2.3.0）
> - 加锚点后，掩码臂在 8k/16k/32k 三个规模、两个 provider、多次重复下稳定满分
> - 摘要路线**未被证伪**，v1.0 的负面结论来自未经隔离的观察
> - **立项理由修正**：掩码的成本倒挂 54–56%，收益只能在质量维度，不能在成本维度
>
> 因此第 0 步的结论是：**继续，但调整优先级**——"归档层 + 回灌 + 指针格式"仍值得做，
> 但"摘要"不再是禁区，"纯位置掩码"不再是可选项。

确认有效后：

1. **来源标签 + 原子单元视图 + token 分桶计量**（地基）
2. **归档层 + 回灌 + 指针格式**（模式 2 核心，单独就有价值）
3. **写入时刻路由规则**（extractive 优先，不做摘要）
4. **溢出安全阀**（模式 1 也必须有）
5. **模式 3：打标 + epoch 执行 + 覆盖率校验**
6. **触发器**（§6）
7. **实验框架与任务集**（应与 1–3 并行，不是最后做）
8. **模式 4**（最后做，且默认限时）

**两条路线纪律**：

- 不要重写已经验证过的部分（masking、语义记忆管理），直接用或直接抄
- 资源压在两个未验证的赌注上：打标/执行分离、重排收益

## 附录 A：缓存代价速查

```text
设 L = 前缀总长，i = 变更点，d = 删除量
   w = 写价倍数，r = 读价倍数

一次性代价 ≈ (L − i) × (w − r)
持续节省   ≈ d × r × 剩余轮数
回本周期   N* = (w − r)/r × (L − i)/d

截断式压缩（d = L − i）时：
  N* = (w − r)/r        ← 与规模无关的常数

参数表
  显式断点式：w = 1.25, r = 0.10  →  N* = 11.5 轮
  基准平台  ：w = 1.00, r = 0.04  →  N* = 24   轮

操作代价
  追加              → 0
  尾部窗口内改写    → (窗口长度) × (w − r)
  中段改写          → (L − i) × (w − r)
  开头改写          → L × (w − r)
  恢复原文（追加）  → 0
  恢复原文（插入）  → (L − i) × (w − r)
```

**反直觉结论**：缓存折扣越深，破坏缓存越亏。读价从 10% 降到 4%，回本门槛翻倍。

**第二反直觉结论**：基准平台上输出成本是缓存输入成本的约 90 倍
（89k 输出 × $1.20/M vs 200k 输入 × $0.006/M）。所以上下文管理的立项理由
必须是容量与质量，不能是省钱。

### A.2 回灌成本项（v1.1 新增）

原公式只算了"压缩省下多少"，**漏算了引用式回灌的双份成本**：

```text
指针留在上下文（每轮都付） + 原文被取回（追加，之后每轮也付）
= 同一内容付两次
```

实测（附录 E.2，8k 预算、20k 历史）：

| 臂 | prompt tokens | 相对 full |
|---|---|---|
| full | 38,114 | — |
| mask | 59,622 | **+56%** |
| mask（16k 预算） | 119,448 | **+55%** |
| mask（32k 预算） | 238,362 | **+54%** |

修正后的净收益公式：

```text
净节省 = d × r × 剩余轮数              // 被移出上下文的原文
       − (L − i) × (w − r)             // 一次性缓存代价
       − Σ(回灌量 × 剩余轮数)          // 回灌项（新增）
```

**实践结论**：回灌成本会把掩码模式的收益吃掉一半以上。掩码的立项理由
必须是**质量**（删除干扰项），不能是成本。若要成本中性，回灌后必须在
下一轮把已取回的原文重新归档（避免长期驻留）。

## 附录 B：研究证据

### B.1 压缩会制造错误（支持 extractive 路线）

| 数据 | 来源 |
|---|---|
| 企业 agent 失败中约 **65%** 归因于 context drift / memory loss，非上下文耗尽 | 企业失败分析（口径未公开，仅作参考） |
| 多轮任务成功率：单轮 **58%** → 多轮 **35%** | 多轮任务基准 |
| 加朴素压缩后有改善，但引入新失败模式：到达目标前忘记早期要求 | 同上 |
| 失败模式从"超窗"变成"错窗"，**更难检测，agent 会继续自信地错** | 同上 |
| KV cache 激进压缩使幻觉分数上升最多 **3.36×** | ACL 2026 *Anchoring the Cache* |
| 摘要过程中 **URL / 文件路径被改写**：`swe-agent.com/latest/` → `/agent/latest/` | 软件工程 agent 研究 |
| abstractive 压缩落后 extractive **3–5 分** | arXiv 2407.08892 |
| extractive 压缩**零 token 幻觉**（只用原文 span） | 同上 |

### B.2 摘要让任务变慢

JetBrains 在 SWE-bench Verified（500 实例）的测量：

| 策略 | 成本 | 轨迹长度 |
|---|---|---|
| LLM 摘要 | −50%+ | **+15%（多走步数）** |
| observation masking | −52% | **不延长** |

**这条直接击中"更少耗时"这个目标。** 摘要省 token 但让 agent 多走 15% 步数。

### B.3 全量保留也有代价

Chroma *Context Rot*（18 个前沿模型）：

- 所有模型随输入长度退化，**即使所有 token 都相关**
- 200K 窗口的模型在 50K 时可能已明显退化
- 退化在窗口填满之前就开始，渐进而非断崖
- 反直觉：**结构良好的上下文比随机打乱的更严重降低注意力**
- 机制：lost-in-the-middle + 注意力稀释 + 干扰项干扰

具体的干扰效应：

- **context distraction**：超过约 100K token 后，agent 倾向重复先前动作而非重新推理
- **context confusion**：给量化 Llama 3.1 8B 全部 46 个工具时失败，只给 19 个相关工具时成功
- **context clash**：信息分散在多轮 vs 一次性给出，性能下降 39%（微软/Salesforce）

### B.4 压缩在短任务上净亏

Lindenbauer 等（*The Complexity Trap*, 2025）：

- 短任务上所有压缩策略 token 总量**高于**不压缩（成本无法摊薄）
- 中等任务仍净亏
- 只有长任务才省
- **LLM 摘要即使长任务也可能净亏**
- masking 与摘要在成本与解题率上持平，masking 更便宜
- masking 窗口参数**必须按 scaffold 调**，跨框架不可照搬

### B.5 三条结论

```text
全量保留        → 注意力稀释 → context rot → 准确率下降
abstractive 摘要 → 信息丢失 + 幻觉 → 静默错误 → 轨迹延长
extractive+回灌  → 零幻觉 + 注意力可控 + 精确恢复
```

**只有第三条同时避开两侧。这就是本设计选择 extractive 的依据。**

### B.6 注意力病理分类与对策映射

除了退化循环，长上下文 agent 还有一整套注意力相关的失败模式。
下表把已知的病理、机制、检测信号和对策汇总，并标出对策落在哪个模式。

**生成层**

| 病理 | 机制 | 检测信号 | 对策 | 模式 |
|---|---|---|---|---|
| **退化循环** | 自我强化重复，概率向 1 爬升 | n-gram 重复率、熵骤降 | 清理 + 重启锚点 | 3 / 4 |
| **语义卡死** | 卡在一个想法上（先于文本重复） | 语义相似度、无新实体、无状态变更 | 清空失败路径 | 4 |
| **模式塌缩** | 锁定单一策略（用同一方法解所有问题） | 同一方法重复用于不同问题 | 强制生成替代方案 | 4 |
| **冗长膨胀** | 输出长度失控 | 输出 token / 任务 | 输出控制（不属于上下文管理） | — |

**目标层**

| 病理 | 机制 | 检测信号 | 对策 | 模式 |
|---|---|---|---|---|
| **任务漂移** | 每一步的即时上下文压过原始目标 | 每 N 步让 agent 重述目标，看是否变化 | **目标锚定在头部** + 周期性重述 | 3 / 4 |
| **推理漂移** | 长链中每步轻微偏移，最终完全错误 | 中间结论与前提矛盾 | 周期性回读约束 | 3 |
| **迎合** | RLHF 偏好导致顺从用户 | 用户表示反对后立刻改口 | 独立验证，不依赖模型自评 | — |

**位置层**

| 病理 | 机制 | 检测信号 | 对策 | 模式 |
|---|---|---|---|---|
| **迷失中间** | 中间内容注意力权重最低 | 位置对照测试 | **重排：关键内容放头尾** | 4 |
| **位置偏置** | 注意力位置权重影响判断 | 交换 A/B 顺序看结论是否变 | 重排 + 双序验证 | 4 |
| **近因偏置** | 尾部内容权重过高 | 早期约束被忽略 | 约束重复出现在尾部 | 3 / 4 |

**上下文层**

| 病理 | 机制 | 检测信号 | 对策 | 模式 |
|---|---|---|---|---|
| **上下文污染** | 错误进入上下文后被反复引用 | 引用不存在的内容、自相矛盾 | 清理污染源 + 写入前校验 | 3 / 4 |
| **上下文分心** | 超过一定长度后重复先前动作 | 动作重复率 | 删除无关内容 | 2 / 4 |
| **上下文混淆** | 多余信息影响不该影响的回答 | 工具数量对照实验 | 精简工具与内容 | 2 |
| **上下文冲突** | 不同时点引入矛盾信息 | 前后矛盾检测 | 保留最新 + 显式标注替代关系 | 3 |
| **注意力稀释** | 注意力预算被 token 数量摊薄 | 长度对照测试 | 压缩无关内容 | 2 / 4 |

**三条跨类别的设计结论**

1. **任务漂移与退化循环同源。** 两者都是"最近的上下文压倒了更早的意图"——
   一个是压倒了目标，一个是压倒了多样性。所以同一个机制（重启锚点：
   显式重述当前目标与状态）对两者都有效。这也是为什么清理后必须注入重启锚点。

2. **位置层的病理只能靠模式 4 解决。** 迷失中间、位置偏置、近因偏置都源于
   注意力对位置的固有偏好。压缩（模式 2）和标记（模式 3）都不改变位置，
   只有重排能改变。这是模式 4 唯一无法被其他模式替代的能力。

3. **KV 层驱逐有反效果风险。** LoopGuard 证明基于注意力分数的驱逐会放大循环。
   如果自建推理引擎采用 KV 驱逐，必须引入多样性约束，不能纯按 attention score 排序。

### C.2 模式 3 已有完整实现：Letta / MemGPT

| 层 | 位置 | 操作 |
|---|---|---|
| core memory | 上下文内，可直接改写 | `memory_replace` / `insert` / `rethink` |

### C.3 本设计的真实位置

| 维度 | OpenHands | Letta | 本设计 |
|---|---|---|---|
| 零摘要幻觉 | ✅ | ⚠️ 模型自写记忆会美化 | ✅ |
| 不延长轨迹 | ✅ | ❓ | 待测 |
| 精确恢复 | ❌ | ⚠️ 检索式，非引用 | ✅ 按 ref |
| 粒度 | ⚠️ 事件区间 | ❌ block 2k | ✅ 原子单元 |
| 语义判断 | ⚠️ 只能"请求压缩" | ✅ | ✅ 打标 |
| 可逆 | ⚠️ 有 log 无 undo | ❌ | ✅ |
| 注意力重排 | ❌ | ❌ | ✅ |

**唯一真正的理论改进：把"恢复"从概率变成确定。**

```text
检索式：query → 相似度 → 可能返回片段，可能召回失败
引用式：ref   → 直接寻址 → 必然返回完整原文
```

检索失败不报错，它静默地让模型基于缺失信息推理。引用式把这一步变成确定操作。

**但收益上限 = 检索失败频率 × 失败损失。** 如果 Letta 的 `conversation_search`
在真实任务里召回率接近 100%，这条改进的价值接近零。**必须先测。**

### C.4 唯二未验证的赌注

- **打标与执行分离**：理论上避免"每轮突变"，但无实证
- **灰烬模式的重排**：Context Rot 证明位置影响注意力，但"重排能提升准确率"从未被测量

**其余都是组合已有能力。立项应把资源压在这两个赌注的验证上。**

**判分**：四维正向检查（`is_code` / `port_7411` / `integer_cents` / `log_prefix_ZX`），
满分 4 分。**不做否定匹配**——见 E.4 的教训。

### E.4 方法论教训（重要）

**判分器认词不认语义，会直接毁掉实验。** 这个坑在 v1、v3、v6 三次重演：

1. mask 答案里的"不使用 float"被当成违规
2. `balance_cents=int(...)  # 禁止 float` 被当成"金额用了 float"——否定语境被正则误读
3. `Final[float] = 0.2`（重试延迟常量）被当成金额违规
4. `BalanceCents = NewType("BalanceCents", int)` 这种更规范的写法没被识别

反过来，mask 交的分析报告因为提到 7411 和 `ZX-` 白拿 2 分。
**正则无法区分断言与它的否定**，必须改为正向检查。

### E.5 平台能力实测（供实现参考）

| 发现 | 数值 | 影响 |
|---|---|---|
| 前缀缓存块大小 | 64 token | 对齐粒度 |
| 缓存键跨 provider 共享 | trae 写入 949k，relay-b 命中 99.99%，延迟 90.8s → 9.6s | 多通道可共享前缀 |

| 溢出错误 | 三种失败同为 400 + `upstream_rejected`，message 措辞不一致 | **不能靠错误识别兜底** |
| 思考 token 占比 | completion 的 94–97% | 输出预算必须给足 |
| `max_tokens` 上限 | 可拉满 1048576，模型自然停止 | 关不掉思考时必需 |
