# 只存结束（D252，2026-11-04 定）

> 用户 2026-11-04 定：**只存结束，不存进行时**。
> 无论是正常写完、用户点停止、断流截断、还是上游失败，都算"结束"；
> 结束的那一刻才决定要不要落库。进程被杀 → 这一轮等于没发生过。

## 1. 契约

**库里只有"已经结束的一轮"。** 生成中的正文、思考、工具调用只活在内存里
（native 的 partial 缓冲 + 界面的 `LiveReply`），一个字节都不进库。

这条不是"实现细节"，是**数据层的契约**：

1. 版本表里永远只有能展示的东西——不会再有 `（空消息）`、0 字版本、半截记录。
2. 界面上的"正在写"是纯 UI 状态，不需要在库里造一个空壳去占位。
3. 迁移、备份、导出、搜索都不用处理"半截消息"。

## 2. 四种结束，怎么处理

| 结束方式 | 拿得到信号 | 正文非空 | 正文为空 | 弹不弹 |
|---|---|---|---|---|
| 正常结束（finish=stop） | 是 | 落一版（新版本，旧的留成上一版） | 不落 | 不弹 |
| 用户点停止 | 是 | 落一版，标「被中断」 | 不落 | 不弹 |
| 断流（EOF 无终止信号） | 是 | 落一版，标「没写完」 | 不落 | 不弹 |
| 上游失败（重试耗尽） | 是 | 不落 | 不落 | **弹三选一** |
| 进程被杀 / OOM | **否** | —— | —— | 不弹（下次打开时按"没发生过"处理） |

**为什么只有失败弹**：三选一问的是"这一版要不要留"。正常写完、停止、断流这三种，
答案都是"留"（正文非空）或"没什么可留"（正文为空）——再弹一次只是多一次点击。
失败才是真的需要人决定：留这一版、留上一版、还是都留。

**正文为空时**：三选一里两个"留这一版"灰掉，写「这一版是空的」，默认「保留上一版」。

## 3. 与"允许生成新版本"开关的关系

| 开关 | 正常结束 | 停止 / 断流 | 失败 |
|---|---|---|---|
| 开（默认） | 追加一版，旧版留着 → `<n+1>/<n+1>` | 同左 | 三选一 |
| 关 | 覆盖当前版（D185） | 同左 | 三选一 |

## 4. 版本上限

每消息 **50 版**（`MAX_VERSIONS`，原来是 20）。超了丢**最旧**的一版，不丢当前版。

为什么抬到 50：正常结束默认"留两版"，重试频繁的人会很快撞上 20。撞上之后是静默丢最旧的，
用户会觉得"我明明留了，怎么没了"。50 版 + 界面上写清上限，比 20 版更经得起用。

## 5. 这条契约的代价（明确接受）

1. **进程被杀 = 这一轮没有发生过。** 用户可能已经看到几千字，杀掉之后再打开就没了。
   这是"只存结束"的固有代价，不打算用"边写边落草稿"去补——那会把半截记录重新引回库里。
2. **生成中的内容永远不进上下文。** 半成品不该发给模型，这条本来就是对的。
   副作用：生成中发第二条消息（走队列）时，第二条的上下文里没有第一条的半成品。
   现在队列是"上一条结束才发下一条"，所以没有影响；**以后若改成真并行，这条要重新想**。
