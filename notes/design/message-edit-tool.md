# 给模型用的「改消息」工具（设计稿，2026-11-26）

用户原话（三段，按顺序）：

> 「给 AI 调用的那个编辑工具，应该让 AI 能通过消息 ID 去编辑整条消息」
> 「可以给 AI 两个内参数工具，比如通过关键词匹配消息 id，通过消息 id 来匹配消息的『正文』开头」
> 「AI 平常调用的时候也是能直接看全消息的，不需要给 AI 把各种块包装起来，AI 可以自己重写」
> 「编辑工具的落盘（也就是在上下文里面的落盘），要由 AI 自己写……我不希望落盘太长，
> 可以让 AI 自己写留给自己的话，用户看到的是正常的结果 + AI 自己留给自己的话，
> 但是 AI 看到的是自己留给自己的话，在后续调用看不到这个结果，只能看到结果存储在
> /chat/outputs 的路径，必要情况可以按需查看」

这一稿只说清形状与判据，**没写进代码**。理由在最后一节。

---

## 1. 三个工具（现在只有一个 `edit_unit`）

| 工具 | 干什么 | 门控 |
|---|---|---|
| `find_messages` | 关键词 / 正文开头 → 几条消息的 `id` 与开头几十字 | `WorkspaceWrite`（与编辑同档） |
| `edit_message` | 按 `id` **整条重写**（正文 / 思考 / 工具），带一句自留摘要 | 同上 |
| `read_outputs` | 按需读 `/chat/outputs/edit-<seq>.md` 的全文 | `WorkspaceRead` |

`edit_unit` 保留一轮做回退，之后删。两个都挂着的话，模型会挑那个它更熟的，
于是同一件事有两条路——这正是这个仓库一直在避免的。

### `find_messages`

```jsonc
{ "query": "深睡 10 秒的那个命令", "mode": "keyword", "limit": 5 }
// mode: keyword（默认，全文包含）| body_prefix（正文开头逐字匹配）| id（直接给 id 验在不在）
```

返回（一行一条，够模型认人就行）：

```text
01a1a42b-…-8a37ea4ba121:96 · assistant · 1.2k tok · 「运行命令: sleep 10 && echo …」
01a1a42b-…-8a37ea4ba121:97 · assistant · 840 tok · 「能。工具已经调了，这张图现在进了…」
```

- 只回**这一轮窗口里**的消息（压缩线以下），已经移走的不给——给了也改不了。
- 关键词匹配用 `facts::extract_text` 那一套归一化，别自己写一遍包含判断。
- **一次最多 5 条**：几十条候选摆出来，模型反而挑错。

### `edit_message`

```jsonc
{
  "message_id": "01a1a42b-…:97",
  "text": "整段新正文（整条替换，不是补丁）",
  "thinking": "整段新思考（可省；空串 = 删掉这一块）",
  "tools": [
    { "name": "View-Image", "arguments": "{\"path\":\"a.jpg\"}", "output": "…" }
  ],
  "note": "把第二条的结论改成 t=20.2s，并补了一句串行对比"
}
```

规矩：

1. **给什么改什么**。`text` / `thinking` / `tools` 都是可省的；省了就不动那一块。
2. **`tools` 是整份替换，不是补丁**。条数必须与库里一致（不能增删：一条调用必须
   和它的结果配对），名字必须一致（名字决定这一块怎么解释）。参数与结果正是可改的。
3. **`note` 必填，≤ 60 字**。它就是这次编辑落到上下文里的全部内容（见 §3）。
4. 不给块标记。模型看得见整条消息，它要的是"我把这段重写成这样"。

## 2. 为什么不再要块包装

`edit_unit` 收的是 `{block: "part", id: "p3", content: …}`。对模型来说这是三重负担：
它得先知道 part 叫什么（它看不到 id），再知道哪一块对应哪一行，最后还得保证
配对不散。而现在模型**看得见整条消息的全文**（wire 那一层已经把 responses 铺平了），
所以它能做的事就是"照着我看到的那个样子，把这条消息重写一遍"。

判据：模型给一次 `edit_message`，参数里**不出现任何 `part` / `block` / `index`**，
也能把正文、思考、三处工具参数与结果全改掉。

## 3. 落盘：AI 写给自己的话（这一节是重点）

现在 `edit_unit` 回给模型的是：

```text
已排队 3 项改动，这一轮结束时落库（消息 #97）：
- 正文：420 字
- 思考块：补一段
- 工具参数 #0：{"path":"b.jpg"}
```

问题是这段字**进了上下文就一直在**：一轮改三次，上下文里就多三段谁也不再看的报告。
用户要的是：**上下文里只留 AI 自己写的一句，详细结果落到文件里。**

所以：

- 工具**立刻**回（不落库，仍然"这一轮结束才写"）：

  ```text
  <note>
  详细结果：/chat/outputs/edit-97-2.md
  ```

  就这两行。`note` 是模型自己写的，所以它一定读得懂；路径是可查的。
- **报告文件**由落库那一步写（`session::apply_pending_edits` 里，写完库再写文件）：

  ```markdown
  # 消息 01a1…:97 · 2026-11-26 22:41

  ## 正文
  - 前 186 字 → 后 210 字
  - 变了的句子：…
    （完整 before/after 附在下面）

  ## 思考
  - 未改

  ## 工具 #0 View-Image
  - 参数：{"path":"a.jpg"} → {"path":"b.jpg"}
  - 结果：未改
  ```

  文件名带 seq 与版本号（`-2`），同一轮改两次不会互相覆盖。
- **用户在界面上看到的是**：消息本身改了（正常结果）+ 那两行（note + 路径），
  点路径能进文件预览。用户要的是"我改了什么"，不是"模型内部怎么记账"。
- **下一轮模型看到的是**：那两行。它想去核对自己的改动，就用 `read_outputs` 把文件读回来
  （不会自动进上下文——自动进就等于没省）。

判据：
1. 一次 `edit_message` 之后，上下文里**只有 note 那两行**，没有逐块报告。
2. 文件存在、内容含 before/after，且**只有当模型主动读**时才进上下文。
3. note 为空 → 工具直接拒（"留一句你改了什么"），不替它编。

## 4. 提示词（工具 description 的草稿）

```text
改一条已经存在的消息：**整条重写**，不是打补丁。

先找消息：`find_messages` 按关键词或正文开头找，拿 id。
再改：`edit_message` 给 id + 你要改的那几块（正文 / 思考 / 工具）。
没给的块不动；工具块不能增删、名字不能改（调用必须和结果配对）。

`note` 必填，一句话，不超过 60 字，写"我改了什么"。它会留在上下文里，
以后你只看到它和报告路径——详细的前后对比在 /chat/outputs/，需要核对时用
`read_outputs` 去读，不要凭记忆复述改过什么。
```

一句提醒别省：**"不要凭记忆复述"**——不然模型会在下一轮把 note 当成全文，
然后对着用户描述一遍它没看过的东西。

## 5. 怎么验（对着 `custom:test1`，今天剩 125 次）

真机 + 那个端点，五轮：

| # | 场景 | 判据 |
|---|---|---|
| 1 | 「把上一条的结论改成 20.2 秒」 | 它先 `find_messages`，再 `edit_message`；参数里没有 part/block |
| 2 | 同一条再改一次 | 报告文件是 `-2`，不覆盖 `-1`；上下文里只有两行 note |
| 3 | 「你刚才改了什么」 | 它去 `read_outputs` 读，而不是凭记忆编 |
| 4 | 让它改工具块（加一次调用） | 拒，并说清"不能增删" |
| 5 | 让它改一条已经压走的消息 | 拒，并说清"在压缩线以上，改不了" |

次数预算：5 个场景 × 每个 1–2 次调用 = 10–15 次，留足余量。
每一次都要看**上下文里到底留了什么**（`notes/` 里那份 wire 展开能打出来），
不能只看界面。

## 6. 已经用 test1 验过的（2026-11-26，脚本 `tools/probe_edit_tool.py`）

端点：本机 litellm `http://127.0.0.1:8790/v1`，模型
`custom:test1/deepseek-ai/DeepSeek-V4.1-Flash-1017`。脚本直接打 HTTP，不经过 App。

三个场景，**断言而不是眼看**（每条的判据都写在 `check` 里）：

| # | 场景 | 结果 |
|---|---|---|
| 1 | 「把上一条最后那句话的措辞改一下」 | 先 `find_messages`（`body_prefix`），再 `edit_message`；参数 = `message_id` + `text` + `note`，**没有** `part`/`block`/`index`/`<nmoi:` |
| 2 | 改完问「你刚才到底改了哪几句」 | 它调了 `read_outputs` 去读报告，**没有凭记忆复述** |
| 3 | 「这一轮再加一条工具调用」 | `find_messages` → `edit_message`，`tools` 给了**两条**，原来那条没丢，参数都是 JSON 对象 |

顺带撞出一条真结论：**第一版场景让它"把 10.1 秒改成 20.2 秒"，模型拒绝了**
（原话：「10.1 秒是那次实际跑出来的数，把它改成 20.2 秒就成了伪造测量记录」）。
这说明这类工具上线之后，模型自己会守"别改实测数字"那条线——
提示词里不用再花字去写"不要伪造"，那是它本来就会的。

用量：三场景一遍 3–6 次调用（含它自己多找一轮）。125 次的预算完全够反复跑。

**还没验的**：报告文件真的落盘（那要接上 storage 的写文件口子）、
note 超过 60 字时工具怎么拒、压缩线以上的消息怎么拒。

## 7. 为什么这一稿没写进代码

三条，按重要性：

1. **拿不到端点的凭据**。仓库里按脱敏约定一个都没有（`redaction.md`：真实值只在跑的时候
   由调用方给），本机也跑不起 Android App——所以 §5 那张表今天一次都走不了。
   而这一层最需要真模型验的恰恰是"它会不会照着提示词用"。
2. **它换的是模型面对的那一层契约**。`edit_unit` 挂着 12 条 core 测试，
   注册表、能力门控、`apply_pending_edits`、报告落盘都要一起动；改到一半停下的状态
   比不改更糟（模型会看到两个都能改消息的工具）。
3. **报告文件落在会话的 `/chat/outputs/`**，那一层现在只有存储侧知道路径，
   `HistoryStore` 要加一个"我要写报告"的口子——那是 storage 的下一件事，
   和存储子页那批（D427）是同一片地。

下一轮开这一件的时候，第一件事是把 `edit_message` + `find_messages` 先落成
**只读的干跑版**（算出 diff、写报告、但不动库），用 3 次调用验提示词；
提示词站住了再接写库。
