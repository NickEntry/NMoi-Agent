## 1. 内置世界书只在设置里可见（已落）

`LorebookStore.bookRows` 现在跳过 `builtin`：三个勾选入口（＋ 的世界书面板、助手设置、
角色面板）都不再出现它。它只出现在「设置 → 世界书」那张 `BuiltinCard` 上——那里能看、能改、
**不能关**。

两件事分开：「不显示」是这一条，「仍然注入」是 `filterBy` 里那句无条件的
`+ BUILTIN_ID`。删掉显示不影响生效，删掉生效才会让内置那几条失效。

`activeCount` 跟着回到普通计数：分母是用户真能勾的册数，分子是勾上的那些。
以前那个「内置永远算一册」的补丁不再需要——它本来就是为了修「1/2 里那个 1」。

## 3. 子页手势与状态记忆（横滑）

用户要三样：

1. **左右滑切子页**（横滑翻页，不是"滑一下滚到底"）。
2. **子页各自的滚动位置记在内存**，退出这一页就丢。
3. **子页多于三个时顶栏本身可以横滑**。

判据（三条都能当场看出来）：

- 从「基础设置」横滑到「提示词」，**页面跟着手指走**，松手按位移与速度决定落不落下一页
  （与左滑删除同一条阈值：开 25% / 350，关 15% / 160）。
- 横滑与"上下滚动"不抢：与水平夹角 25 度以内才算横滑，其余交给内容滚动（这条已经在
  `SwipeReveal` 里钉过，直接复用）。
- 切走再切回来，**滚动位置回到原处**；退出这一页再进来，**回到顶部**（记忆不跨进程、不落盘）。
- 顶栏项数超屏时，**顶栏自己可以横滑**，且选中项会被自动带到中间（不然点第四个之后
  它自己躲在屏幕外）。

实现上两件事值得先定：

- **状态怎么存**：`remember` + `SaveableStateHolder` 是"按 key 记住每个子页的滚动状态"的标准做法，
  但它在**进程重建**时会写进 `SavedState`（那是我要的"退出就销毁"的反面）。
  所以用 `remember { mutableStateMapOf<String, Int>() }` 自己记，挂在页面这一层——
  页面一离开组合就没了，正好是"退出销毁"。
- **横滑用什么**：`HorizontalPager`（Compose Foundation 1.9 已稳定）。不用自己算手势——
  自己算的那一套迟早与返回手势、横滑删除、图表横向拖动打架。

**顶栏横滑**用 `LazyRow` + `animateScrollToItem(selected)`：项数少时它不动，
项数多时它滚，不写两套。

## 4. 提示词子页要补的东西

截图里那一页有五块，按**有无必要**排：

### 4.1 可用变量（要做）

它列了一排 `{cur_date}` `{cur_time}` `{cur_datetime}` `{model_id}` `{model_name}` `{locale}`
`{timezone}` `{system_version}` `{device_info}` `{battery_level}` `{nickname}` `{assistant_name}`。

我们的 `PromptVars` 现在只有一个 `<ContextMode>`，而且**只对压缩与摘要两个角色开放**。
扩大到助手这一层要先定一件事：**变量的语法用 `<Name>` 还是 `{name}`**。
现在提示词里用的是 `<ContextMode>`（与用户那套自我认知文本里的 `<var>` 同形），
截图里是 `{cur_date}`。两者混着写，第一个后果是"我写了没生效"——所以：

- **统一成 `<Name>`**（与现有实现、与压缩册、与核心脚手架一致）。不引入第二套语法。
- 变量表按**能填的**列，列了不填就是假开关（`PromptVars.names` 那条注释）。
- 带叹号的那几个（日期/时间/日期时间）在截图里被标了警告——那是"这两个每轮都在变，
  会打掉 Prompt 缓存"的提示。我们照抄这个提示语，因为它是个真问题。

### 4.2 独立对话系统提示 / 独立对话指令注入（要，但排在后面）

它们都是"把这个开关放到会话级"：会话可以有自己的系统提示词、自己选世界书。
我们已经有三层（全局 → 助手 → 角色），再加一层会话会变成四层。
**先把层数定死再开这个开关**，不然"为什么我改了不生效"会变成日常问题。

### 4.3 追加当前时间（要，很小）

在每条用户消息末尾追加发送时刻，位置在请求末尾，不影响 prompt 缓存。
它跟 §7 的 token 测算共用一个事实：**时间戳每轮都变**，所以它必须落在末尾。

### 4.4 聊天内容模板（先不做）

截图里是 `{{ message }}` 加预览。我们每条消息已经是结构化落库的，
"模板"这一层在发出前会再包一层字符串——它解决的是"我想给每条消息加前后缀"，
而这个需求现在可以用系统提示词表达。等真有这个需求再做，现在做等于多一条渲染路径。

### 4.5 预设对话信息（要，语义按用户这次说的定）

**用户这一句把语义定死了**：

> 新话题就会默认挂在会话开头的消息，这个消息**不可被编辑**，**不算作我们正常的处理范围**，
> 某种意义上来说算是**另类的世界书**，只在**会话开头插入**，而且**优先级是最低**。

所以它不是"聊天里的一条消息"，是**注入物**：

| 它是什么 | 它不是什么 |
|---|---|
| 新会话开头插入的一段（用户 / 助手两种角色） | 不是库里的一条消息（不占 `messages` 行、不进版本、不进编辑范围） |
| 每轮请求都会带上（因为它在上下文最前面） | 不是"发一次就完了"的开场白 |
| **优先级最低**：装不下的第一个被挤掉 | 不是世界书（不按关键词触发、不按位置插） |
| 界面上只在助手设置里能改 | 不是聊天页能删的东西 |

三条要写进注释，否则下一轮一定会有人"顺手"把它做成一条真消息：

1. **不落 `messages`**。落进去就会出现在编辑器的段里、被 `apply_turn_edits` 改到、
   被导出带走——三样都不是用户要的。
2. **优先级最低**：预算不够时先丢它，再丢历史尾部。判据是"窗口刚好差一点"时，
   被丢的是预设消息，不是最近那几条对话。
3. **角色只有 user / assistant 两种**（截图也是两个按钮）。`system` 那一格由系统提示词负责，
   在这里再开一个只会让"到底哪段是系统"更糊。

存储：跟助手配置同一份文档（`settings(assistant,<id>)` 的 `preset_messages: [{role, text}]`），
不新开表。理由与 `lorebooks` / `system` 一样：它属于这个助手，不属于某一条会话。

## 5. 上下文管理窗口

替换「＋ → 压缩上下文」那一行：点开是一个 `SheetFrame`（用户给了图），**不是**再弹一层确认。

```
上下文管理
  435.6k            估算
  [分段条：蓝 382.1k / 橙 1.2k / 橙红 17.6k / 黄 2.2k / 灰 3.9k / 绿 18k / 深灰 325 / 棕 10k / 紫 42]

  ● 历史消息   382.1k
  ● 内置工具     1.2k
  ● MCP 工具    17.6k
  ● 技能         2.2k
  ● 系统提示词   3.9k
  ● 世界书        18k
  ● 工作区        325
  ● 附件          10k
  ● 草稿          42

  上下文压缩             ← 手动，只有这五个字
  压缩与清空记录     ›
  图片上下文         ›
  清空上下文     11 条消息

  自动压缩        [ 关 ]
```

**不做的两样**（用户明确）：

- **没有「设置上下文窗口」那一行**：窗口在模型配置里改（`ModelFields` 已经有那一格）。
  同一件事两个入口，迟早给出两个答案。
- **分段条不做点击跳转**：它是"看"，不是"筛选器"。

### 5.1 自动压缩是开关，不是流程

用户这句是重点：

> 自动压缩后面也分离出来开关，压缩是压缩，落盘是落盘，上下文那个档位 F1~F4 管的是"落盘/编辑"这些。

现在 `AppSettings.autoCompress` 已经有（设置 → 上下文页里），但它和"到绝对线自动跑"绑在
`ChatScreen` 的一个 `LaunchedEffect` 里，界面上只在设置页出现。要做的：

1. **这个开关全局共享**：一处改，聊天页那个面板与设置页同时变（同一个 key，不另存一份）。
2. **面板里也摆**（截图里就在面板底部）。从面板关掉，下一次不会自动压；从设置关掉也一样。
3. **压缩 ≠ 落盘**：`F1~F4` 是"原文留多少 / 要不要落盘"，压缩是"把已有上下文换成摘要"。
   两件事的判据不同，UI 上也不能挨着放成一组开关——否则用户会以为关掉 F4 就不压缩了。

### 5.2 手动压缩去条件（原 §7.2）

先在 `CompressionJob::start` 上把"切不出东西就 `NothingToCompress`"这条松开：
手动压缩要能压任意长度（允许把整段都移走、只留摘要，1 轮也能压）。
它与自动压缩走同一条 `CompressRunner.run` → `nmoi_compress_run_json`，不为手动另开一条。

### 5.3 图片上下文：只留一个开关

截图里两个开关（自动管理历史图片 / 允许模型回读历史图片），用户要**只留上面那个**。
我们现在那张 `ContextImagesSheet` 是"这一轮发了哪几张、能移出、能清空"，没有那两个开关。
要加的只有一条：

- **自动管理历史图片**：优先保留用户上传的图，分批收起较早的工具图。
  落 `AppSettings`（全局），设置 → 图片页也摆一个同一个 key。

`允许模型回读` 不做：我们的 `View-Image` 本来就是按需读，关掉它等于把工具废了。

### 5.4 实时上下文预览（后面再做，形状先定）

> 开启后会在标题栏下方贴着一个小窗口，背景最好是透明。

形状：一条**贴在顶栏下面**的细条（高 28–32dp），只写三样——
`435.6k / 1M · 44%`、一段细的分段条、以及"自动压缩：开/关"的小点。
背景用 `surfaceContainerLow.copy(alpha = 0.72f)` + 一条 0.5dp 下边线；
**不用纯透明**：纯透明在浅色主题下会让下面的消息文字透上来，读数变成噪声。
它可点，点开就是 §5 那个面板。

## 6. token 测算：tokenizer.json 路线（这一节是实测）

### 6.1 实测（2026-11-26，本机 PRoot / aarch64，Python `tokenizers` 0.23.3）

取 Qwen2.5 的真实 `tokenizer.json`（**7.03 MB**，151k 词表）：

```text
加载（Tokenizer.from_file）        1290 ms
中文 9,680 字符    → 6,380 token    29.1 ms   （332 k 字符/秒）
混排 15,200 字符   → 6,200 token    36.8 ms   （413 k 字符/秒）
代码 58,920 字符   → 9,720 token    98.7 ms   （597 k 字符/秒）
```

一个 19 万 token 的上下文（30.7 万字符）**全量编码 1249 ms**；只数最后 3 条 **23.1 ms**
（快 54 倍）。

### 6.2 结论：全量每 10 秒不可行，**增量可行**

- 全量 1.2 s / 10 s = 一个核的 **12% 常驻**，手机上是发热与掉帧，不是一个可以接受的背景开销。
- 增量 23 ms / 10 s = **0.2%**，可以忽略。
- 所以路线是 **按消息缓存 token 数 + 只算新增/正在变的那几条**，不是"每 10 秒重算一遍"。

判据（都要能单测）：

1. **缓存键是内容哈希**，不是消息 id：消息被编辑过（`apply_turn_edits`）之后必须重算。
2. **只重算最后一条**（正在流式增长的那条）+ 新到的那些；其余命中缓存。
3. 总账 = Σ 缓存值 + 未命中部分；**不许**"估算总量 - 已缓存"这种减法（差一点就会漂）。
4. 缓存上限按条数（比如 2000）而不是字节：条数是可控的，字节不是。

### 6.3 用户说的"高频暂停恢复"要不要做

他给的方向是"用高频的暂停恢复达到类似限速"。**结论：不作为主力手段**，理由是
拿暂停当节流，实际是"让每次计算都慢一点"，它压不住总开销，只把一次 1.2 s 摊成一分钟的
断续占用；而增量之后单次只有 23 ms，根本不需要节流。

真正要节流的是**这三处**（它们才是一次几十到几百毫秒的那种）：

1. **全量重算**（编辑一条早期消息、切版本、压缩之后）——放到 IO 线程，且**只算一次**
   （用 `Mutex` 或者"正在算就记一个 dirty 标记，算完再补一次"）。
2. **首屏预算**：会话打开时只算最后 N 条 + 已知总量，其余滚动到再算（懒）。
3. **后台预热**：`Tokenizer::from_file` 那 1.3 s 必须发生在**首次需要之前**，
   放 `StartupCheck` 之后的那条预热线程（与 `ModelSnapshot.warm` 同一条），
   且**只在需要时**——用户没开预览、没到绝对线，就不加载。

判据：**主线程上不出现 > 8 ms 的单词**（Android 一帧 16 ms）；用
`Start.mark` 那套计时打点，看"上下文测算"这一项在冷启动里占多少。

### 6.4 与现有 L1（tiktoken）的关系

现在已经有 L0（字符近似）/ L1（tiktoken o200k / cl100k）/ L2（用 `usage` 反向校准）。
实测精度 0.80–1.06（中文高估 24%，方向安全）。

`tokenizer.json` 的好处只有一个：**每个模型用自己的词表**（Qwen 的 151k 与 o200k 不是一套），
把中文那 24% 从"系统性高估"变成"准"。代价是 7 MB 文件 + 1.3 s 加载 + 每个模型一份。

所以路线是**分两步**，不是替换：

1. 先做 §6.2 的增量缓存——它把"多久算一次"变成不是问题，**与用哪套词表无关**。
2. 再决定要不要按模型加载 `tokenizer.json`：只有当**某个模型的误差真影响到压缩判据**时才加。
   在那之前，L1 + L2 已经够用；为 24% 的高估多背 7 MB，在手机上不划算。

## 7. 还有哪些地方适合"节流/增量"

同一种毛病（"每次都要全量算一遍"）在这个仓库还有三处：

| 位置 | 现在的做法 | 该改成 |
|---|---|---|
| 存储页十项大小 | 每次进页面全盘扫（`StorageRepository.scan`） | 增量：按目录 mtime 缓存子树大小；删一个文件只让那一支失效 |
| 会话列表的 `tokens` 汇总 | 每次列表读一遍 `SUM(tokens)` | 已经落库了（`messages.tokens`），够用；但"总 token"这一列要缓存 |
| 搜索/关键词激活世界书 | 每轮全册扫一遍 | 命中缓存（按"册 + 关键词集"做 key） |

三者都是"低频动作，但每次全量"。优先级排在 §9 的顺序后面。

## 8. 判据清单（做完这一批要能逐条对上）

1. 「＋」里那一行叫**上下文压缩**（只有这五个字），点开是 §5 那个面板，没有「设置上下文窗口」。
2. 面板里的**自动压缩**与设置 → 上下文页那个是**同一个开关**：一处改，另一处刷新后一致。
3. 面板里的九项之和 ≈ 顶部那个总数（差值是"未归类"，要写出来，不能吞）。
4. 手动压缩对**一条 1 轮的会话**也能成功（不再 `NothingToCompress`）。
5. 图片上下文只有**一个**开关（自动管理历史图片），设置 → 图片页也有同一个。
6. 助手页横滑能切子页、切回来的滚动位置不丢、退出再进回到顶部。
7. 子页多于三个时顶栏能横滑，选中项自动居中。
8. 预设消息**不在** `messages` 表里（`select count(*) from messages` 对得上）。
9. 窗口刚好差一点时，被丢的是预设消息，不是最近几条对话。
10. token 测算：编辑一条早期消息 → 只有它重算；流式输出中每 10 秒只算最后一条；
    主线程无 > 8 ms 的单点。
