# 超窗时不压缩，先撤回那一条（0.17h 设计稿）

用户 2026-11-15：「如果某次全量读取/调用命令撑爆了上下文的话，我们是不是应该做撤回并把输出
变成相关提醒？而不是按部就班的触发压缩。记得做关键词检测，确保能精准检测到上下文超过限制
的情况且不容易误检测」。

## 1. 为什么是撤回，不是压缩

压缩是**有损且不可逆**的：它把一段历史移出请求、换成一封摘要。而这一次超窗的成因往往只有一条
——某一次 `read_file` / 一条命令吐了 8 MB。按压缩处理，用户付出的代价是"整段对话被摘要"，
问题却只是"这一条太大"。撤回只动那一条，其余原样。

## 2. 三步

1. **判定**（已落地，`crates/core/src/overflow.rs`）：三档 `No / Sure / Maybe`，**只有 `Sure` 动手**。
2. **撤回**：把这一轮里 token 最多的那条工具结果换成 F4 指针 + 一句提醒：
   `[已撤回：这一段 N KB 撑爆了上下文。要看用 read_file 的 offset/limit，或把命令改成 head -n 200]`。
   原文进 `sessions/<id>/archive/`（与 F2–F4 同一套 `archive_put`），所以"撤回"不等于"丢掉"。
3. **重发同一轮**：不重跑工具（重跑可能重复副作用），只把改过的历史再发一次。
   一轮里最多撤回一条、最多重发一次；仍然超窗就交回上层（那时才是压缩/报错的场合）。

## 3. 为什么这一批只落了第 1 步

第 2、3 步要动 `agent.rs` 的请求块：现在 5 处 `map_err` 各成一句，重发需要把整块提成一个
`fn ask(...) -> Result<Answer, AgentError>`，再由外层 `loop` 决定"撤回后再来一次"。
这是热路径，且要同时改 `report` 的落库形状（撤回后的那段才是要落库的那段，铁律②：界面上
看得见的就是库里存的）。按本项目的老规矩（"大改先写稿"），先落判定 + 判据，再动请求块。

## 4. 误检怎么防（这一批的核心）

- 状态码先筛：只有 400 / 413 / 422。401/403（钥匙）、404（模型）、429（限流）、5xx 一律 `No`。
- 只看 `error.message` / `code` / `type`，**不看原始 body**：中转会把请求回显进 body，
  提示词里出现"context length"就成了假阳性。
- 要成对：`context/prompt/input/message` + `too long/exceed/超过` 才算 `Sure`；
  只有 `context` + `limit` 只算 `Maybe`（不动手，只记录）。
- `tokens` 不做主语：`max_tokens: must be >= 1` 这类参数错会被它误伤（测试里红过一次）。
- 实测那两条完全没提上下文的失败（`the param is invalid` / `all models failed`）保留为 `Maybe`。

判据：`overflow` 7 条（明说 / 代码点名 / 一半线索 / 参数错与钥匙错 / 回显 / 实测两条 / 中文），
`runtime` 原有的三条实测用例与"普通 400 不算超窗"保持绿。core **785**。
